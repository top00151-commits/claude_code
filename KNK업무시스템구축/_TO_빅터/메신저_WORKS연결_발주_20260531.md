## 0. 한 줄 요약
복잡한 "비번 위임"(WORKS 자체 로그인 + 비번 검증 API)을 폐기하고, **메신저를 정문**으로 둡니다. 직원은 메신저에 로그인 → 헤더 **"🔗 WORKS 열기"** 버튼 → **이미 만든 SSO 토큰**으로 WORKS 자동 로그인. WORKS는 **자체 로그인 폐지**, **토큰만 받아 입장**.

## 1. 대표님 결정 (2026-05-31)
- 메인 = 메신저. WORKS는 메신저에서 버튼으로 진입.
- WORKS **자체 로그인 화면 폐지** (메신저로만 진입).
- 권한 = **사용 가능/불가 1단계** (메뉴별 세부권한 아님). **메신저 관리자**가 부여.

---

## 2. 진입 흐름 (이미 메신저에 구현됨)
1. 직원이 메신저 로그인 (평소대로)
2. 메신저 헤더 **"🔗 WORKS"** 버튼 클릭 (권한 있는 직원만 노출)
3. 버튼 → 메신저 `GET /msg/sso/login?redirect_uri=<WORKS 랜딩>`
4. 메신저(로그인 상태)가 **즉시 RS256 JWT 발급** → `<WORKS 랜딩>?token=<JWT>` 로 리다이렉트
5. **WORKS 랜딩이 토큰 받아 검증 → WORKS 세션 생성 → WORKS 홈**

- WORKS 랜딩 주소(메신저가 보낼 곳): 기본 **`https://works.knknara.co.kr/sso/land`**
  - 메신저 환경변수 `KNK_WORKS_LANDING_URL` 로 변경 가능. 경로 바꾸려면 알려주세요.

## 3. WORKS(01) 가 할 일
1. **랜딩 엔드포인트** `GET /sso/land?token=<JWT>` 신설
   - 토큰 검증: 메신저 `GET /msg/api/sso/public-key` 의 RS256 공개키로 서명·만료 확인 (기존 SSO 발주 그대로)
   - 검증 실패/만료 → "다시 메신저에서 열어주세요" 안내
2. **권한 게이트**: 토큰 claim `works_access == true` 일 때만 입장. false → "WORKS 사용 권한이 없습니다. 메신저 관리자에게 문의" 안내(입장 거부)
3. **WORKS 자체 로그인 폐지**: 로그인 폼 제거. 미인증 직접접근 시 → "메신저에서 'WORKS 열기'로 들어오세요" 안내 페이지
4. **세션·로그아웃 독립**: WORKS 세션은 WORKS 가 관리. WORKS 로그아웃은 WORKS 세션만 정리(메신저 영향 없음). 재진입은 메신저 버튼으로.
5. (선택) 세션 유지 중 비번 변경 감지가 필요하면 `GET /msg/api/sso/userinfo`(토큰 기반, pwv 포함)로 주기 확인. 단, 세션 짧게 두고 매번 메신저로 재진입하면 불필요.

## 4. 토큰(JWT) claim — WORKS 가 읽을 값
```
sub            : 사번(employee_no, 없으면 username)
uid            : 메신저 내부 user id
pwv            : 비밀번호 버전
works_access   : true/false  ← 이 값 true 여야 입장 (신규)
is_admin       : true/false (메신저 ceo)
name_kr / name_en / name_vi
dept / position / entity / email
iss/aud/iat/exp/jti : 표준
```

## 5. 메신저 쪽 완료 내역 (참고)
- `users.works_access` 컬럼 + 관리자 ⋮메뉴 "WORKS 권한 부여/해제" 토글
- 헤더 "🔗 WORKS" 버튼(권한자만) → `/sso/login?redirect_uri=` SSO 진입
- JWT claim 에 `works_access` 추가
- 배포 완료(healthz 200). 기존 SSO(토큰/공개키/userinfo) 그대로 사용.

## 6. 정리(나중)
- 비번 위임 API 3종(`verify-password`/`admin-reset-password`/`pwv`)·공유키 환경변수는 **불필요**. 지금은 키 미설정으로 403 잠김(무해). 안정화 후 제거 예정.
