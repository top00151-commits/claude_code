## 0. 한 줄 요약

HAIST WORKS 가 **자체 로그인창(사번+비번)을 유지하되**, 입력된 비밀번호를 **메신저에 서버끼리 조용히 물어봐서 검증**한다. WORKS 는 비밀번호를 저장하지 않고, **비밀번호 저장소는 메신저 한 곳**으로 단일화한다. 이를 위해 메신저에 **서버 전용 API 3개**(비번 검증 / 관리자 초기화 / pwv 조회)를 추가 요청한다.

## 1. 배경 — 정책 변경 (대표님 직접 결정, 2026-05-31)

### 1.1 이전(2026-05-31 오전) → 변경 후
| 항목 | 이전 (강제 SSO) | 변경 후 (비번 위임) |
|---|---|---|
| 로그인 진입 | 메신저 SSO 화면으로 강제 redirect | **WORKS 자체 로그인창 유지** (사번+비번) |
| 로그아웃 | 메신저와 묶임(반쪽) | **WORKS 독립** (메신저 로그아웃해도 WORKS 유지, 반대도) |
| 비밀번호 검증 | 메신저가 토큰 발급 | **메신저가 (사번+비번) 맞는지만 확인** |
| 비밀번호 저장 | 양쪽 따로 | **메신저 한 곳만** (WORKS 미저장) |

### 1.2 대표님 요구 (이번 결정의 핵심)
> 1. "로그인, 로그아웃은 별도로 해야할 것 같아. 개정(계정)관리는 같이 하되."
> 2. "비밀번호는 동일하게. (메신저 비밀번호로 WORKS 로그인 가능하게)"
> 3. "임시비번은 무조건 **휴대폰 번호**."
> 4. "한쪽이 초기화 되면 메신저·WORKS **둘 다 초기화**되고, 로그인된 건 **즉시 로그아웃**."

### 1.3 왜 이 방식인가
- 비밀번호 저장소가 **메신저 하나** → "동일 비번"·"한쪽 초기화로 양쪽 끝"이 **자동 충족**.
- 직원은 **쓰던 메신저 비번 그대로** WORKS 로그인 → 별도 세팅 불필요·잠김 위험 0.
- 로그인 화면·세션은 각자라 **로그인/로그아웃 독립** 유지.

## 2. 요청 API (서버 전용 3개)

> **공통 전제**
> - 모두 **서버↔서버(server-to-server)** 호출. 브라우저에 노출 금지.
> - WORKS(NAS 컨테이너) → 메신저 를 **내부 주소**로 호출 (예: `http://localhost:5050/msg/...`). 공인 도메인 NAT loopback 회피.
> - 인증: 공유 비밀키 헤더 **`X-SSO-Service-Key: <secret>`**. 양쪽 OS 환경변수로 주입(코드·git 금지). 키 없으면 **403**.
> - 응답은 JSON. 시간 동기/HTTPS 무관하게 내부망 사용.

### 2.1 ★ 비밀번호 검증 — `POST /msg/api/sso/verify-password`

메신저가 **이미 가진 로그인 인증 로직을 서버용으로 한 겹 여는** 수준입니다.

**요청 (JSON)**
```json
{ "employee_no": "5", "password": "<평문 비밀번호>" }
```

**응답 (HTTP 200, JSON)**
- 검증 성공:
```json
{
  "valid": true,
  "pwv": 3,
  "user": {
    "employee_no": "5",
    "name_kr": "김정락",
    "name_en": "Kim Jeongrak",
    "name_vi": null,
    "dept": "경영",
    "position": "대표이사",
    "entity": "KOR",
    "email": "kjr@knk.co.kr",
    "is_admin": true
  }
}
```
- 검증 실패(비번 틀림/사용자 없음/퇴사): `{ "valid": false }`  ← **정보 유출 방지 위해 사유 미세분, 항상 200**
- 서비스키 누락/불일치: HTTP **403** `{ "error": "forbidden" }`

**보안 요구 (필수)**
- `employee_no` 단위 **무차별 대입 방지**: 분당 N회(예: 5회) 초과 시 일시 잠금/지연.
- 비번 비교는 메신저 기존 해시 검증 그대로(상수시간).
- 시도 로그 기록(성공/실패·요청자IP).

---

### 2.2 ★ 관리자 초기화 — `POST /msg/api/sso/admin-reset-password`

WORKS 관리자 화면의 "비밀번호 초기화" 버튼이 이 API 를 호출합니다. (WORKS 측에서 호출 전에 요청자가 admin/ceo 인지 먼저 확인함)

**요청 (JSON)**
```json
{ "employee_no": "43", "reset_by": "5" }
```
- `reset_by`: 초기화를 누른 관리자 사번 (감사 로그용)

**동작**
1. 해당 직원 비밀번호를 **휴대폰 번호 숫자만**으로 리셋 (§3 규칙)
2. 최초변경 유도 플래그 ON (메신저에 동등 개념 있으면)
3. **`pwv += 1`** (← 세션 무효화 트리거)

**응답 (HTTP 200, JSON)**
```json
{ "ok": true, "new_pwv": 4, "temp_pw_hint": "휴대폰 번호" }
```
- 휴대폰 없음 등 실패: `{ "ok": false, "reason": "no_phone" }`

> **효과**: pwv 증가 → 그 직원의 메신저·WORKS 세션이 다음 pwv 확인 시 **즉시 로그아웃** (대표님 요구 4 충족).

---

### 2.3 pwv 조회 (경량) — `GET /msg/api/sso/pwv?employee_no=5`

WORKS 세션이 살아있는 동안 **주기적으로(5분)** 호출해 비번이 바뀌었는지 감지하는 용도. (토큰 없이 사번만으로 현재 pwv 확인)

**응답 (HTTP 200, JSON)**
```json
{ "employee_no": "5", "pwv": 3 }
```
- 서비스키 보호. 존재하지 않는 사번: `{ "pwv": null }`

> ※ 이미 `GET /api/sso/userinfo` 가 pwv 를 주지만 그건 토큰 기반입니다. 비번 위임 방식은 토큰을 안 들고 있어서, **사번만으로 pwv 조회**가 가능한 경량 엔드포인트가 필요합니다. (userinfo 를 사번 파라미터로도 받게 확장해도 무방)

## 3. 휴대폰 초기비번 규칙 (양쪽 동일 — 필수 합의)

| 법인 | 초기비번 | 예시 |
|---|---|---|
| 본사(KOR) | 휴대폰 **숫자만** (하이픈·공백 제거) | `010-3540-1552` → `01035401552` |
| 베트남(VN) | 동일 (휴대폰 숫자만) ※ 메신저 보유 형식 확인 | — |

- WORKS 직원 import 스크립트(`import_employees_from_excel.py`)가 이미 **`초기비번 = 휴대폰 숫자만`** 으로 동작 → 메신저 초기화도 **반드시 동일 규칙**이어야 "동일 비번" 성립.
- 휴대폰 데이터가 메신저에 없으면 초기화 불가 → `no_phone` 반환.

## 4. WORKS(실무팀1) 측 연동 — 우리가 할 일 (참고용, 메신저 작업 아님)

메신저 API 완료되면 빅터가 WORKS z120 으로 아래를 구현합니다. 메신저 세션은 **API 계약만** 맞춰주시면 됩니다.

1. `POST /login`: 로컬 비번 대신 **2.1 검증 API 호출** → 성공 시 계정정보 upsert + 세션 생성 + pwv 보관
2. 관리자 초기화 메뉴: **2.2 API 호출**
3. `get_user()`: 5분마다 **2.3 pwv 조회** → session pwv 와 다르면 세션 파기(즉시 로그아웃)
4. 관리자 백도어(대표·admin): 메신저 장애 대비 **로컬 비번 유지** (검증 API 실패 시 fallback)
