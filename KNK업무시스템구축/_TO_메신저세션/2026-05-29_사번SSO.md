## 2. 확정된 정책 (대표님 확인 완료)

### 2.1 사번 체계

| 법인 | 형식 | 예시 |
|---|---|---|
| 본사(KOR) | **순수 숫자** (패딩 X) | `1`, `5`, `43`, `300`, `321` |
| 베트남(VN) | `VN` + 3자리 0 패딩 | `VN001`, `VN094`, `VN269` |

> 본사는 패딩 없이 그대로 유지. 베트남은 현행 `VN001` 형식 유지.

### 2.2 로그인 ID = 사번

| 구분 | 신규 로그인 ID | 비고 |
|---|---|---|
| 본사 | 사번 숫자 그대로 (`5`, `43`, ...) | 기존 임의 ID 폐기 |
| VN | 사번 (`VN001`, ...) | 기존 영문이름 폐기 |

### 2.3 초기 비밀번호 (안내 시트 정책 유지)

| 구분 | 초기 비번 |
|---|---|
| 본사 | 휴대폰 숫자만 (예: `010-3540-1552` → `01035401552`) |
| VN | `9999` 일괄 |

→ 첫 로그인 시 강제 비번 변경 (현행 정책 유지)

### 2.4 부서·직급·이름 정책 (현행 유지)
- 부서 코드: 본사 `01_KOR/00_총괄` ~ `01_KOR/21_라이프밸류팀` (14개), VN `02_VN/00_총괄` ~ `02_VN/09_구매팀` (10개)
- 직급: 본사 10개 (대표이사~사원) / VN 7개 (법인장~사원) / 공통 "사원"
- 이름 3종 (VN만): 한국식 한글 / 베트남어 / 영문
- 첫 로그인 강제 비번 변경
- upsert: 재등록 시 자동 갱신, 비번·권한 보존
- 사진 별도 등록 (메신저 안에서 1명씩)

### 2.5 인증 동기화 방식

**방안 C — SSO 토큰 (JWT RS256)** 채택.

- 메신저 = Identity Provider (마스터)
- HAIST WORKS·기타 = Service Provider (메신저 토큰 검증)
- 비번은 **메신저에만 보관**, 다른 시스템은 0 보관 → 비번 유출 사고 시 메신저 1군데만 영향

### 3.4 ★★★ SSO 인증 서버 기능 추가 (메신저 = Identity Provider)

#### 3.4.1 키 쌍 생성 (RS256)

```bash
# 메신저 컨테이너 안
mkdir -p /opt/knk_messenger/keys
openssl genrsa -out /opt/knk_messenger/keys/jwt_rs256_private.pem 2048
openssl rsa -in /opt/knk_messenger/keys/jwt_rs256_private.pem -pubout -out /opt/knk_messenger/keys/jwt_rs256_public.pem
chmod 600 /opt/knk_messenger/keys/jwt_rs256_private.pem
chmod 644 /opt/knk_messenger/keys/jwt_rs256_public.pem
```

- private key: 메신저만 보관 (서명용)
- public key: 모든 Service Provider에 공유 (검증용)

#### 3.4.2 API 엔드포인트

| 엔드포인트 | 메서드 | 용도 | 인증 |
|---|---|---|---|
| `/api/sso/token` | POST | 사번/비번 → JWT 발급 | 없음 |
| `/api/sso/userinfo` | GET | JWT 검증 + 사용자 정보 반환 | Bearer JWT |
| `/api/sso/public-key` | GET | RS256 public key 노출 (JWK 또는 PEM) | 없음 |
| `/api/sso/revoke` | POST | (선택) 토큰 무효화 | Bearer JWT |

**요청·응답 스펙**:

**`POST /api/sso/token`**
```json
요청:
{
  "employee_no": "43",
  "password": "01012345678"
}

응답 (성공, 200):
{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "openid profile employee"
}

응답 (실패, 401):
{
  "error": "invalid_credentials",
  "error_description": "사번 또는 비밀번호 불일치"
}
```

**JWT Payload 표준**:
```json
{
  "iss": "https://haist.knknara.co.kr/msg/",      // 발급자
  "sub": "43",                                     // 사번 (subject)
  "aud": ["haist-works", "knk-internal"],          // 대상 서비스
  "exp": 1748528400,                               // 만료 (1시간 후)
  "iat": 1748524800,                               // 발급 시각
  "jti": "uuid-v4",                                // 토큰 고유 ID
  "name_kr": "김정록",
  "name_en": "Kim Jeong-rock",
  "name_vi": null,
  "dept": "01_KOR/03_품질팀",
  "position": "매니저(팀장)",
  "entity": "KOR",
  "email": "kjr7749@knknara.co.kr",
  "is_admin": false
}
```

**`GET /api/sso/userinfo`**
- 헤더: `Authorization: Bearer <JWT>`
- 응답: JWT payload 의 사용자 정보 부분 (실시간 DB 조회 후 최신 값)

**`GET /api/sso/public-key`**
```
응답 (200):
-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA...
-----END PUBLIC KEY-----
```
(또는 JWK 형식 — Service Provider 가 선호하는 것 제공)

#### 3.4.3 보안 정책

- **토큰 만료**: access_token = 1시간 (3600초)
- **비번 변경 시**: 발급된 모든 토큰 무효화 (revocation list 또는 user `password_version` 증가 + JWT claim에 포함하여 검증 시 매번 확인)
- **HTTPS 필수**: `/api/sso/*` 는 HTTPS 외 거부 (현재 메신저는 이미 HTTPS)
- **CORS**: 사내 도메인(`*.knknara.co.kr`)만 허용
- **Rate limit**: `/api/sso/token` 분당 10회 초과 시 차단 (브루트 포스 방지)
- **로깅**: 모든 인증 시도(성공·실패) 로그 기록 + IP

#### 3.4.4 비번 변경 핸들러 수정

기존 메신저 비번 변경 로직에 추가:
- 비번 변경 성공 시 → `user.password_version` 증가 (또는 redis/memory cache 에 revocation 등록)
- 다음 JWT 발급은 새 `password_version` 으로 발급
- 기존 JWT 는 `userinfo` 호출 시 검증 단에서 거부 → Service Provider 가 재로그인 요청

## 4. 기술 사양 요약

### 4.1 의존성 (메신저 requirements.txt 추가)

```
PyJWT[crypto]>=2.8.0   # JWT 발급·검증 (RS256 지원)

```

### 4.2 JWT 라이브러리 사용 예 (Python)

**발급**:
```python
import jwt
from datetime import datetime, timedelta, timezone

private_key = open('/opt/knk_messenger/keys/jwt_rs256_private.pem').read()

payload = {
    "iss": "https://haist.knknara.co.kr/msg/",
    "sub": user.employee_no,
    "aud": ["haist-works"],
    "exp": datetime.now(timezone.utc) + timedelta(hours=1),
    "iat": datetime.now(timezone.utc),
    "jti": str(uuid.uuid4()),
    "name_kr": user.name_kr,
    "dept": user.dept,
    "position": user.position,
    "entity": user.entity,
    "is_admin": user.is_admin,
    "pwv": user.password_version,  # 비번 변경 추적용
}

token = jwt.encode(payload, private_key, algorithm="RS256")
```

**검증** (Service Provider 측, 참고용):
```python
import jwt
public_key = open('jwt_rs256_public.pem').read()

decoded = jwt.decode(
    token,
    public_key,
    algorithms=["RS256"],
    audience="haist-works",
    issuer="https://haist.knknara.co.kr/msg/"
)
```

### 4.3 DB 스키마 마이그레이션 SQL 초안

```sql
-- 1. 백업
.backup /opt/knk_messenger/data/backup_pre_employee_no_20260529.db

-- 2. 컬럼 추가
ALTER TABLE users ADD COLUMN employee_no TEXT;
ALTER TABLE users ADD COLUMN entity TEXT;
ALTER TABLE users ADD COLUMN password_version INTEGER DEFAULT 1;

-- 3. UNIQUE 제약 (마이그레이션 후 적용)
CREATE UNIQUE INDEX idx_users_employee_no ON users(employee_no);

-- 4. 임시 staging 테이블
CREATE TABLE _staging_employees (
    name_kr TEXT,
    email TEXT,
    phone TEXT,
    employee_no TEXT,
    position TEXT,
    dept TEXT,
    name_en TEXT,
    name_vi TEXT,
    entity TEXT
);
-- → 엑셀 import (Python pandas → sqlite to_sql)

-- 5. 매칭 + 업데이트
UPDATE users SET
    employee_no = s.employee_no,
    entity = s.entity,
    login_id = s.employee_no,   -- ★ login_id 도 사번으로 갱신
    position = COALESCE(s.position, users.position),
    dept = COALESCE(s.dept, users.dept),
    name_en = COALESCE(s.name_en, users.name_en),
    name_vi = COALESCE(s.name_vi, users.name_vi)
FROM _staging_employees s
WHERE users.name_kr = s.name_kr
  AND (users.email = s.email OR users.phone = s.phone);

-- 6. 미매칭 (엑셀에만) → INSERT
INSERT INTO users (name_kr, email, phone, employee_no, entity, login_id, position, dept, name_en, name_vi, password_hash, ...)
SELECT s.name_kr, s.email, s.phone, s.employee_no, s.entity, s.employee_no,
       s.position, s.dept, s.name_en, s.name_vi,
       <초기 비번 해시>
FROM _staging_employees s
WHERE NOT EXISTS (
    SELECT 1 FROM users u
    WHERE u.name_kr = s.name_kr AND (u.email = s.email OR u.phone = s.phone)
);

-- 7. 정리
DROP TABLE _staging_employees;
```

> ★ 비번 해시 알고리즘은 메신저 기존 정책 그대로 사용. 신규 INSERT 의 초기 비번은 본사=휴대폰숫자, VN=`9999`.

## 8. 추가 확정 사항 (대표님 결정 완료 — 2026-05-29 오후)

### 8.1 메신저에만 있는 사용자(엑셀 미등재) → **수동 판단**
- 마이그레이션 스크립트는 미매칭 사용자 목록(이름·기존 ID·마지막 로그인·소속 채널 수)을 별도 출력

- 자동 비활성화 절대 금지 (정상 직원 차단 위험)

### 8.2 테스트 환경 → **실제 서비스에 직접**
- 별도 SSO 테스트 컨테이너 구축 X
- 점심시간(12:00~13:00) 또는 새벽 시간 작업 권장

  1. DB 백업 → 마이그레이션 → 즉시 검증 (대표 사번 `5`로 로그인 시도)
  2. 문제 발견 시 즉시 롤백 (5분 이내)
- 향후 사용자 500명 초과 시 별도 테스트 환경 도입 검토

### 8.3 토큰 무효화 → **방법 A (password_version)**
- `users.password_version INTEGER DEFAULT 1`
- 비번 변경 시 `password_version += 1`
- JWT payload `pwv` claim 에 발급 당시 버전 박음
- 검증 시 매번 DB 의 `password_version`과 JWT 의 `pwv` 비교 → 다르면 거부
- 130~500명 규모 DB 부하 무시 가능
- 1000명 초과 시 revocation list 캐시 방식 도입 검토

### 8.4 로그인 화면 디자인 → **기존 메신저 화면 그대로**
- SSO 전용 새 화면 만들지 않음
- 사용자는 평소 메신저 로그인 화면 그대로 봄
- 백엔드에서 `redirect_uri` 파라미터 있을 시 → 로그인 성공 후 JWT 발급 + redirect
- 직원 경험: "메신저 로그인했더니 HAIST WORKS도 자동으로 들어가졌네" (학습 0)

### 8.5 다국어 → **기존 i18n 그대로 활용**
