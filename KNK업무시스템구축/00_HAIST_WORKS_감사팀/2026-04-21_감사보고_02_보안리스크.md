### SEC-005 [High] Legacy sha256 정적 솔트 fallback 잔존

**실측 근거** (`database.py:88~117`):
```python
def _legacy_pw_hash(pw):
    return hashlib.sha256(("knk-haist-" + pw).encode()).hexdigest()

def verify_pw(pw, stored):
    if stored.startswith("pbkdf2$"):
        ...  # 신규 pbkdf2
    # legacy sha256 fallback
    return stored == _legacy_pw_hash(pw)
```

**위협**:
- 로그인 한번도 안 한 사용자(휴직·퇴사 직전 인계 계정 등)는 여전히 sha256+정적 솔트 형태.
- 백업 DB(SEC-002) 유출 + 정적 솔트 노출 → **레인보우 테이블 즉시 적용 가능**.
- 약한 비밀번호(`knk2026!`, `knk1234` 등)는 사전 공격으로 분 단위 해독.

**시정 지시 (01 메인)**:
1. legacy 해시 사용자 일괄 조회 후 **강제 재설정** (다음 로그인 시 비밀번호 변경 강제) 또는 **관리자 일괄 임의 비밀번호 발급** + 안내.
2. 마이그레이션 완료 후 `_legacy_pw_hash` 함수 자체를 코드에서 제거.
3. 일정 마련: 마이그레이션 데드라인 명시.

### SEC-008 [Medium] CSRF 토큰 부재

**실측 근거**:
- 모든 form POST에서 CSRF 토큰을 검증하지 않음.
- 방어책은 세션 쿠키의 `same_site="lax"` 뿐 — top-level GET 외 cross-site POST는 차단되나, 정교한 우회(예: 같은 도메인 사용자 콘텐츠 영역) 시 부분 노출.

**시정 지시 (01 메인)**:
- `starlette-csrf` 또는 자체 CSRF 미들웨어로 모든 POST/PUT/DELETE 에 토큰 검증.
- 또는 same_site를 `strict`로 격상 가능한지 평가 (외부 링크 → 시스템 진입 UX 영향 확인 후).

### SEC-009 [Medium] `KNK_SECRET_KEY` 미설정 시 fallback

**실측 근거** (`main.py:155`):
```python
_SECRET = os.environ.get("KNK_SECRET_KEY", "knk-haist-2026-phase1-DEV")
if _SECRET.endswith("-DEV"):
    print("[security] ⚠ KNK_SECRET_KEY 환경변수 미설정 ...")
```
- 콘솔 경고만 있을 뿐 **앱은 정상 기동**.
- 운영자가 경고를 못 보면 그대로 세션 위조 가능 (공개된 fallback 키로 쿠키 서명 가능).

**시정 지시 (01 메인)**:
- `KNK_MODE=prod` + fallback 사용 시 **앱 기동 중단** (raise SystemExit). 개발에서만 경고 후 진행.
- 32바이트 이상 임의값을 `secrets.token_urlsafe(32)`로 1회 발급해 운영 환경변수에 영구 등록.

### SEC-012 [Medium] 기본 비밀번호 hardcoded + 복잡도 정책 없음

**시정 지시 (01 메인)**:

### SEC-013 [Medium] `/uploads` 정적 마운트 — 인증 없이 접근

## 9. 00 감사팀 총평

- **인증·세션의 기본 골격은 합리적** — pbkdf2 200k, same_site=lax, RBAC 일관 가드.
- 그러나 **외부 인터넷 노출을 전제로 보면 즉시 차단되어야 할 Critical 2건**(평문 자격증명·백업 DB git tracked)이 발견됨. 이건 운영 시작 여부와 무관하게 오늘 안에 제거 필요.
- **운영 모드 진입 가드(`KNK_MODE=prod`)가 일부만 활성** — fallback에서 앱이 그냥 기동되는 패턴(SEC-009)이나 traceback 노출(SEC-004) 등은 모드별 분기 강화 필요.
- **VPN을 단일 방어선으로 두면 안 됨** — 어플리케이션 자체에 2차 인증·rate limit·HSTS·CSP를 모두 설치한 후 외부 노출 권장.

**다음 감사 우선순위**:
1. SEC-001/002 시정 후 git history clean 검증 (감사팀이 직접 `git log --all -- data/_credentials*` 확인)
2. 외부 노출 직전 보안 헤더·HTTPS·rate limit·SECRET_KEY 시정 확인 후 GO/NO-GO 의견 제시
3. 시정 완료 항목 재감사 (01 메인 PR 단위)
