### 1-3. Email Worker (실제 메일을 WORKS로)
- Worker `knk-mail` (knk-mail.knk-jungrack-kim.workers.dev) 생성.
- 동작: 받은 메일 원문(raw)을 `POST https://works.knknara.co.kr/api/mail/inbound` (헤더 `X-KNK-Mail-Token`) + 안전망으로 gmail에도 forward.
- 변수 3개: WORKS_INBOUND_URL / KNK_MAIL_INBOUND_TOKEN(암호화·비밀) / FORWARD_TO(gmail).
- Email Routing 규칙 test@ 동작을 **'Worker로 전송'** 으로 전환.
- (현재 Worker는 진단 console.log 포함 버전 — 나중에 정리 가능)

### 1-4. 디버깅 2건 (★ 다음 세션 교훈)
1. **Cloudflare Worker 변수는 추가 후 '재배포'해야 적용된다.** 처음엔 변수만 추가 → env undefined → fetch 조용히 실패 → gmail만 도착. Worker 재배포하니 로그 `WORKS_RESULT status=200 ok:true` = 정상.
   - 진단 도구: Worker에 console.log(status/urlSet/tokenSet) + 빅터가 외부에서 /api/mail/inbound 에 틀린 토큰 POST → 401 확인(엔드포인트 정상·토큰 설정됨 입증).
2. **받은 메일이 대표 메일함에 안 보임** — 저장은 성공(ok:true, owner=3)인데 화면엔 없음. 원인: 운영 DB에 동명 계정이 여럿이라 `default_owner`가 시드 'kjr'(id3)로 보냄(대표 실제 로그인 계정과 다름). 시범메일은 본인 id 소유라 보였던 것.
   - **해결(z383)**: `resolve_recipient` 우선순위 = 별칭 > 관리자지정 기본수신자(`mail_default_user_id`) > default_owner. 관리자 **/admin/mail-inbound → '내 메일함으로 받기'** 버튼(설정+별칭+기존 test@ 메일을 본인 메일함으로 이동).
   - 대표가 버튼 클릭 → 받은 메일 3통이 메일함에 나타남(AI 요약 포함) = **받기 파이프라인 완전 가동 확인**.

### 1-5. 받기 토큰·수신자
- 받는 구멍 비밀토큰: WORKS 관리자 `/admin/mail-inbound` 에서 생성 → app_settings `mail_inbound_token`. (전산 불필요)

## 3. 보내기 (SENDING) — 구축·배포 (z384, z385)

### 3-1. 만든 것 (z384 cb7bc54)
- **메일 쓰기**(`/mail/compose`) — 받는사람·참조·제목·내용·첨부(합계 24MB) / **답장**(`?reply=id`, 원문 인용·Re: 제목).
- **발송**(`/mail/send`) — 회사 발송망(SMTP)으로 전송 + 보낸편지함 기록.
- **보낸편지함**(`/mail/sent`) — 받은/보낸 전환, 보낸 메일은 받는사람 표시.
- **보내기 설정**(`/admin/mail-send`) — 발송망(SMTP) 호스트·계정·비번(Fernet 암호화)·보내는 주소 + Cloudflare 연결 안내.
- `mail_send.py`: `send_system`/`_smtp_send`(로그인 계정과 From 분리)/`save·get_send_config`(app_settings: mail_send_host/port/user/pass_enc/mail_from_address).
- `mail_store.py`: `store_outbound`/`list_sent` + 받은편지함 `direction='in'` 분리.
- 메일함 화면에 **✏️ 메일 쓰기** 버튼, 메일보기에 **↩ 답장** 버튼.

### 3-2. 발송망 선택
- 대표 결정: **Cloudflare 보내기**(POC 간편). 우리 코드는 어떤 SMTP든 주소만 넣으면 됨 → 나중에 AWS SES로 호스트만 바꿔도 됨.

### 3-3. 메일 암호화 키 자동생성 (z385 b9a2744, A안)
- 발송 비밀번호 암호화에 KNK_MAIL_KEY 필요한데 NAS에 미설정 → 보내기 설정에 경고.
- **A안(대표 결정)**: `_mail_key()` — env KNK_MAIL_KEY 우선, 없으면 DB 폴더에 `.mail_key` 1회 자동생성(git/DB덤프 미포함, 배포에도 보존). 전산 없이 해결. (운영 본격전환 땐 정식 env 키로 교체 권장)
- 적용 후 경고 사라짐 확인.

## 5. 한도·정책 정리 (오늘 확인)

- **메일 1통 최대 25MiB(≈파일 18MB)** — 이메일 업계 표준(지메일도 25MB). 발신측도 보통 못 넘김. AWS SES면 40MB.
- **큰 파일** = '링크 방식'이 업계 정답. 가비아/네이버/아웃룩 '대용량 첨부'도 사실 **파일서버 업로드 + 다운로드 링크** 방식. → **보내기 단계에 「KNK 대용량 첨부」(NAS 업로드+링크)** 추가 예정(대표 OK). NAS라 사실상 무제한·우리 보안정책.
- **받는 메일 수**: Email Routing 자체 일/월 제한 없음. 실질=Worker 무료 10만건/일.
- **주소 개수**: 개별 규칙 도메인당 200·수신대상 200. 단 **catch-all → Worker** 면 WORKS가 사람 매핑 → 사실상 무제한(전 직원 OK).
- **용량**: Cloudflare는 저장 안 함 → **용량=NAS 디스크**. 1인 쿼터는 원하면 추가.
- **스팸**: Cloudflare 기본 피싱탐지+SPF/DKIM. 본격 필터는 추후(AI 스팸분류 가능).

## 6. 운영 관점 논의 (유지보수·보안·장애)

- **이건 '직접 메일서버 운영'이 아님** — 어려운 인프라(전송·가동·스팸·DDoS)는 Cloudflare/AWS가 관리, 우리는 메일함+AI만 얹음.
- **유지보수**: 추가 부담 낮음(WORKS앱·Worker 40줄·DNS·NAS). 단 자체 조립이라 돌봐줄 사람(빅터+전산) 필요.
- **보안**: 전송=엔터프라이즈급. 데이터=우리 NAS(소유·통제 장점 / 지키는 건 우리 책임, 백업 cron 가동중). DKIM/SPF/DMARC 처리됨.
- **장애 시 대응**: 외부 그룹웨어 같은 SLA·24h 지원은 없음 → 빅터(코드)+전산(NAS) 대응. **이게 자체 전환의 진짜 트레이드오프.** → 정의서의 **1년 단계 전환 + 외부 그룹웨어 병행 + 받기 gmail 안전망**으로 덮음(검증될 때까지 회사 메일 안 끊김).
- **보내기 발송망 안정성**: AWS SES(수년 검증·도달률 최상·월정액0·통당과금)가 Cloudflare 보내기(베타)보다 성숙. 안정성 보면 SES, 간편함 보면 Cloudflare. (코드 수정 없이 호스트만 교체 가능 → 나중에 전환 쉬움)
