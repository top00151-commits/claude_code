> **현장은 기존 관리번호·수주번호로 진행 중인데 시스템에서는 변경**이 되니 안 맞는다."

```

                    현장은 옛 번호로 작업  ≠  시스템만 바뀜
```

**끊어야 할 고리는 "수정 불가" 하나.** 잠금의 대가가 **'삭제·재등록'이라는 훨씬 위험한 우회로**였다.

> "저 아까 추가로 관리번호 직접 입력해서 등록했잖아요. **근데 왜 다 신규라고 나오는거예요?**"

## 1. z1031 — PO유형 수정 잠금 해제

**PO유형은 분류값**(신규/추가/개조/수리/기타)이다. 금액도 번호도 안 건드린다.
감사 무결성 때문에 잠글 항목이 아니었다.

| 층 | 수정 |
|---|---|
| 서버 인라인 편집 | `LOCKED` 에서 제거 → `EDITABLE` 추가 + **값 검증(5종)** |
| 정식 폼 | readonly+hidden → `select` |
| 간편 폼(수정모드) | readonly+hidden → `select` |

**추적성 유지**: `projects_update_logi` 의 `_diff_keys` 에 `po_type` 이 이미 있어 **변경 이력 자동 기록**.

⛔`mgmt_code`·`biz_div`·`project_type` 은 **잠금 유지** — 관리번호 자체를 결정하고 여러 곳이 참조.

### ⚠ 함정 회피
간편폼 수정모드 select 의 id 는 **`qPoTypeEd`**(≠`qPoType`).
`qPoType` 은 신규 등록 흐름의 방아쇠(`qIsFollowup`→`qSyncPoType`/`qBuildUnits`/제출분기)라,
수정모드에서 값이 '추가'면 **기존 호기별 입력 영역이 숨겨지는** 엉뚱한 동작이 난다.

## 2. z1031b — **화면이 그대로 잠겨 있었다** (내 실패)

안지연 프로 재신고: *"프로젝트 수정 가서 잠금 풀고 PO유형에 마우스 대니 🚫 나온다"*

**HTML만 풀고 JS를 못 고쳤다.**

**⭐교훈: 필드 잠금이 HTML·JS·서버 3곳에 흩어져 있다. 하나만 고치면 안 풀린다.**

## 4. z1033 — 수주별 PO유형 (추가발주가 '신규'로 보이던 것)

### 원인
PO유형이 **`projects` 에만** 있었다. 작업일정표는 **수주번호별로 줄을 펼치면서**
PO유형만은 **프로젝트 값 하나를 모든 줄에 복사**했다.

```
projects.po_type = '신규'  (딱 하나)
   ├── M-260305-9  → '신규'
   ├── M-260305-10 → '신규'
   ├── M-260305-11 → '신규'
   └── M-260305-12 → '신규'
```

**안지연 프로가 잘못한 게 아니었다.** 추가발주로 제대로 등록됐고 **표시만 틀렸다.**

> **z981(모델명·장비명)이 완전히 같은 문제를 이미 겪었다** — 같은 해법 적용.

### 수정
| | |
|---|---|
| `orders.po_type` 신설 | NULL=미지정 → 프로젝트 값 상속 (**기존 데이터 무영향**) |
| `add_followup_order` | 정의상 '추가 발주' → 저장(기본 '추가') |
| ⭐호출부 | **폼의 PO유형을 그대로 전달** — 개조·수리를 골랐는데 전부 '추가'가 되면 안 된다 |
| `confirm_order_multi` | 신규 등록 시 프로젝트 유형을 그 수주에 기록 |
| 작업일정표 표시 | 줄마다 SO값 우선·없으면 프로젝트값 |
| ⭐**편집 라우팅** | `/sales/schedule/cell` 에 `so_oid` 전달 → **그 수주에** 저장 |

### ⚠ 표시 대상과 편집 대상은 반드시 같아야 한다
편집 라우팅을 같이 안 고치면 **화면은 SO값을 보여주는데 편집은 프로젝트를 고쳐**
→ **"고쳐도 안 바뀌는"** 상태가 된다. (이번엔 추적기 덕에 미리 잡았다)

안전장치: 값 검증(5종) · **수주가 그 관리번호 소속인지 확인** · 변경 이력 기록.

## 6. 기존 데이터를 자동 보정하지 **않은** 이유

**어느 수주가 '추가'인지 확실히 알 수 없다.**
같은 `confirm_order_multi` 호출에서 **납기·납품처가 달라 SO 가 갈린 경우**도 있는데,
그건 '추가'가 아니라 **한 번의 신규 발주**다. 시간이 지난 뒤에는 둘을 구별할 수 없다.

**추정으로 채우면 틀린 값이 사실처럼 남는다**(대표 방침: 추정 금지).
→ **화면에서 줄마다 고칠 수 있게** 했으니 아는 사람이 정정하는 것이 맞다.

002M2602 는 현재 3줄(M-260305-9·11·12)이 '신규'로 보인다 — **안지연 프로가 직접 '추가'로 바꾸면 된다.**
