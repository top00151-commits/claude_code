## 2. 판정서 지적 5건을 어떻게 고쳤나

### 2.1 ① '확정' 표현 → '임시 저장'

**먼저 사실 정정을 드립니다.** 판정서 §3.1 은 화면 버튼을 `확정`으로 보셨는데,
당시 실제 화면 버튼은 `✅ 보드에 반영` 이었습니다. **`확정` 은 제가 대표께 드린 구두 보고에서
쓴 설명 용어**이고 화면 문구가 아니었습니다. 게이트가 제 보고문을 화면으로 읽으신 것으로 봅니다.

다만 **판정 취지(저장됨 ≠ 구매 사용 가능)는 그대로 유효**하므로, 버튼 개명에 그치지 않고
**상태 고지**로 처리했습니다.

| 층 | 무엇을 넣었나 |
|---|---|
| 업로드 화면 버튼 | `✅ 보드에 반영` → **`💾 보드에 임시 저장`** |
| 업로드 화면 버튼 위 | `이 버튼은 '임시 저장'입니다. … 아직 **Release 전**이라 **구매근거로 쓸 수 없습니다.** **구매팀에는 통보되지 않습니다** …` |
| 업로드 화면 안내문(첫 화면) | `올린 값은 임시 저장됩니다 — Release 전이라 구매근거로 쓸 수 없고, 구매팀에도 통보되지 않습니다` |
| **BOM 보드** 상단 | `📌 임시 저장(업로드 반영) 상태 — 설계팀이 올린 BOM 을 담아 둔 것입니다. Release 전이라 아직 공식 구매근거가 아니며, 이 화면만 보고 발주하지 마세요.` |
| 완료 안내(서버) | `업로드 버전 v1 **반영(임시 저장)** — …` |
| 진행 중 표시 | `BOM 반영 중…` → `BOM 임시 저장 중…` |

⭐ **BOM 보드에도 넣은 이유**: 업로드한 사람만 화면을 보는 게 아닙니다. 구매팀이 보드를
직접 열어 보고 "이게 확정 BOM 이구나" 하고 발주하면 판정서 §3.1 의 위험이 그대로 남습니다.

### 2.2 ② 업로드 시 구매팀 통보 — 서버에서 잠금

**중요한 사실**: 이 통보는 제가 이번에 넣은 게 아니라 **`z984` 대표 지시**

이번 판정이 그 지시를 뒤집는 것이므로 **지우지 않고 잠갔습니다.**

## 3. 저장 **전** — 원본 엑셀 ↔ 읽은 값 대조 (판정서 §6-3)

`POST /bom/upload` 미리보기에서 `verify_source_vs_parsed()` 를 돌려, **반영 버튼을 누르기 전에**
결과를 보여줍니다.

- 대조 칸: `품명 · 품번 · 제조사 · 구매처 · 재질 · 표면처리 · 단위 · 납기 · 비고`
  + `대당수량 · 총수량 · 단가 · 금액 · 사내재고 · 베트남재고(참고) · 발주수량 · 재고금액 · 발주금액`
- 파서가 **일부러** 바꾸는 값은 규칙대로 검산하고, 규칙을 벗어난 것만 불일치로 올립니다.
  - 화살표 `A->B->C` → **마지막 값**
  - 빈 총수량 → 대당 수량
  - 빈 단위 → `EA`
  - **원본이 비어 있을 때만** 계산한 금액
- ⛔ 자동으로 고치지 않습니다. 다르면 **알려주고 사람이 판단**합니다.

## 4. 저장 **후** — 읽은 값 ↔ DB 저장값 대조 (판정서 §6-4)

`POST /bom/upload/apply` 에서 저장 직후 `verify_parsed_vs_saved()` 를 돌립니다.

- ⛔ **대조가 어긋나도 저장을 되돌리지 않습니다** — 알리기만 하고 판단은 사람이 합니다.
- ⚠ `bom_items` 에 **칸이 있는 항목만** 볼 수 있습니다. 재고·발주수량·서비스 의심 표시 등은
  아직 저장되지 않으므로(스키마 확장 미승인) 이 단계의 대조 대상이 아니며,
  그 항목들은 **저장 전 ①(원본↔읽은값)** 에서 확인합니다. 이 한계를 화면에도 적었습니다.

## 5. '전부 일치' 의 한계를 화면에 명시 (판정서 §5)

원본 대조는 파서와 **같은 헤더 매핑 규칙**을 씁니다. 따라서 열 자체를 잘못 알아보면
대조도 같은 방식으로 잘못 읽어 `일치` 라고 말할 수 있습니다. 화면 문구를 이렇게 제한했습니다.

> ✅ 올린 엑셀 원본과 대조 **14줄** — 읽은 값 전부 일치
> 품명·품번·제조사·수량·단위·단가·금액·납기·비고를 한 칸씩 맞춰 봤습니다.
> 단, **시스템이 인식한 열·행을 기준**으로 맞춘 것입니다 — 위 표의 열 이름과 대표 품목이
> 맞는지 눈으로 한 번 봐 주세요. **자동 대조가 설계책임자의 검토를 대신하지 않습니다.**

결과화면에도 같은 취지의 한계 3줄을 넣었습니다.

## 12. 로컬 화면 확인에서 **직접 찾은 결함 1건 — 고쳤습니다**

게이트가 실제 화면 확인을 요구하신 이유가 그대로 증명됐습니다.

### 무엇이 잘못됐나

정상 파일을 올렸는데 결과화면이 뜨고 이렇게 적혀 있었습니다.

```text
⚠ 읽은 값과 저장된 값이 다른 곳이 0건 있습니다 (대조 13줄)
```

**0건인데 '확인이 필요합니다' 화면이 뜬 것**입니다.

### 원인

취소선(삭제) 표기 줄은 **일부러** `status='삭제'` 로 저장하므로 활성 보드에 없는 것이 정상인데,
제 검증 함수가 그것을 **'파일에는 있는데 저장된 곳을 못 찾은 줄'** 로 셌습니다.
같은 파일의 `plan_diff` 는 이미 `삭제 표기 제외` 규칙을 쓰고 있었고, **검증 함수만 빠뜨렸습니다.**

### 고친 곳

- `app/bom.py` `verify_parsed_vs_saved` — 삭제 표기 줄을 대조 대상에서 제외
- `app/templates/bom_upload_result.html` — 머리글을 세 갈래로 갈라 `0건` 헛말이 나올 수 없게

### 시험이 왜 못 잡았나 (같이 고침)

- `J'-1` 이 **HTTP 상태만** 보고 `200`·`303` 둘 다 통과로 뒀습니다.
- `J'-5` 는 주소창이 퍼센트 인코딩된 걸 몰라서, **결과화면 본문에서 우연히 문구를 찾아** 통과했습니다.

→ **목적지와 문구까지** 보게 고쳤습니다.

```text
J'-1a  정상 파일은 헛경고 없이 보드로 간다
J'-1b  정상 파일은 '전부 일치'라고 알린다
```

변별력 확인: 이 한 줄 수정을 되돌리면 `J'-1a · J'-1b · J'-5` 가 **정확히 FAIL** 합니다.

> **배운 것**: 시험이 `200 or 303` 처럼 **여러 결과를 다 통과로 두면 그 시험은 아무것도 지키지 않습니다.**
> 앞으로 라우트 시험은 **목적지와 사용자에게 보이는 문구까지** 못박겠습니다.
