## 1. 기술영업팀장 확정 성공 → 성공 응답 + CONFIRMED (§8-1)

`/units/{id}/confirm` 이 **입력폼을 읽지 않은 채** 확정을 실행하고, 그 뒤 감사 단계에서 폼을 참조했습니다.
확정은 이미 커밋된 뒤라 오류가 나면 **"화면엔 실패, 현장 DB 는 확정"** 이 됩니다.

→ **폼을 확정 전에 읽도록 순서 교정.**

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 화면 응답 | ~~`error=...`~~ 🔴 | **`success=호기 확정됨`** ✅ |
| DB 상태 | `CONFIRMED` | `CONFIRMED` |

## 2. 확정 처리 중 오류 → PROVISIONAL 유지 (§8-2)
호기번호 없는 개발호기를 확정 요청 → **오류 응답 + 상태 `PROVISIONAL` 그대로** ✅
(§8-9'' 에서는 처리 도중 감사 실패를 주입해도 같은 결과임을 확인)

## 3~6. 관리자 우회 사유 없음 → 업무 변경 없음 (§8-3~6)

**6개 쓰기 경로 공통 순서**를 코드로 확립했습니다(게이트 §4 지시 그대로).

```
권한 확인 → 입력폼 읽기 → 관리자 우회 요청자·사유 검증
→ 업무 변경 → 같은 트랜잭션에서 감사 기록 → 성공 응답
```

| 경로 | 사유 없이 요청 | 결과 |
|---|---|---|
| 호기번호 지정·변경 | 거부 ✅ | 번호·이력 불변 (요청자+사유를 넣으면 정상 수행돼 **막힌 이유가 우회검사임**을 확인) |
| 호기 확정 | 거부 ✅ | `PROVISIONAL` 유지 |
| 호기 취소 | 거부 ✅ | 기존 상태 유지 |
| 수주번호 연결 | 거부 ✅ | 링크 수 불변 |
| 후보 일괄반영 | 거부 ✅ | Unit·링크·감사 **모두 불변** |
| 개발호기 생성 | 거부 ✅ | 생성 0 |

> 화면 JavaScript 검사는 **먼저 알려주는 용도**일 뿐이고, 실제 차단은 **서버**가 합니다.
> 화면을 거치지 않고 HTTP 요청을 직접 보내도 막힙니다(테스트가 전부 직접 요청으로 검증).
> 기술영업팀·대표·임원의 **정상 업무에는 비상복구 사유를 요구하지 않습니다**(구분 유지).

## 7. 관리자 후보 일괄반영 사유 없음 → 전부 불변 (§8-7)
Unit 수 · 수주연결 수 · 감사 건수 **세 가지 모두 변화 없음** ✅

## 8. 요청 부서·요청자도 필수 (§8-8 · P1-01)
완료보고 계약은 **요청자 + 사유 둘 다 필수**인데 서버는 사유만 보고 있었습니다 → 계약대로 교정.

| 입력 | 결과 |
|---|---|
| 사유만 | **거부**(업무 변경 전) ✅ |
| 요청자만 | **거부** ✅ |
| 둘 다 | 수행 + 감사에 **요청자·사유 모두 기록** ✅ |

기록 형식: `[관리자 비상복구] <작업> · 요청: <요청 부서·요청자> · 우회 사유: <사유>`

## 9. 감사 실패 주입 → 업무 변경 Rollback (§8-9 · P0-03)

업무 변경 함수가 먼저 자체 트랜잭션으로 커밋되고 감사는 **다른 연결**에서 기록되고 있었습니다.
→ `project_unit.py` 각 함수에 `audit=` 인자를 추가해 **같은 `db_session` 안에서** 기록합니다.

감사 표에 실패 트리거를 심고 6개 경로 전부 시험:

| 경로 | 감사 실패 주입 시 |
|---|---|
| 개발호기 생성 | 생성 **취소** ✅ |
| 호기번호 변경 | 번호·이력 **취소** ✅ |
| 호기 확정 | `PROVISIONAL` 유지 ✅ |
| 수주 연결 | 링크 **취소** ✅ |
| 호기 취소 | 취소 **무효** ✅ |
| 후보 일괄반영 | Unit·링크 **전부 취소** ✅ |
| 주입 해제 후 | 정상 수행 + 감사 1건 ✅ (무조건 막는 게 아님) |
