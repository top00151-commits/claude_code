## 1. 【P0-1】 요청라인 ↔ 발주라인 : 다대다 배분

### 1.1 담아야 하는 KNK 업무 (판정서 §4.1)

```
① 요청 한 줄 → 두 협력사로 분할발주
② 요청 여러 건 → 한 협력사 발주서로 통합
③ 요청의 일부만 먼저 발주, 잔량은 나중에
④ 대체품 선정 → 원요청과 다른 자재를 발주
```

### 1.2 구조

```
material_request_items  (요청라인)
        │ 1
        │
        │ N     ┌──────────────────────────────┐
        └──────►│  purchase_allocations (배분)  │◄──────┐
                │  · allocated_qty  ← 몇 개를   │       │ N
                │  · project_id     ← 관리번호  │       │
                │  · order_id       ← 수주번호  │       │ 1
                │  · substitute_part_id ← 대체품│    po_items (발주라인)
                │  · reason / 처리자 / 시각      │
                └──────────────────────────────┘
```

**한 배분 = "요청라인 X의 수량 N개를 발주라인 Y로 보낸다"** 는 한 건의 업무 사실이다.

| 업무 | 배분으로 어떻게 표현되나 |
|---|---|
| ① 분할발주 | 요청라인 1개 → 배분 2건 → 서로 다른 발주라인 2개 |
| ② 통합발주 | 요청라인 3개 → 배분 3건 → 같은 발주라인 1개 |
| ③ 부분발주 | 요청 100 중 배분 60 → 잔량 40은 배분 없음 |
| ④ 대체품 | 배분에 `substitute_part_id` 기록 → 요청 자재와 발주 자재가 다름을 **사실대로** 남김 |

### 1.3 상태는 사람이 적지 않고 배분으로 계산한다 (판정서 §4.1·D-1)

```
요청라인 발주진행 = Σ allocated_qty / request_item.quantity
    0        → 미발주
    0 < x <1 → 부분발주
    ≥ 1      → 발주완료
```

⭐ **요청상태와 발주진행을 한 칸에 섞지 않는다**(D-1).

| 구분 | 값 | 누가 정하나 |
|---|---|---|
| 요청상태 | 작성 · 제출 · 검토중 · 승인 · 반려 · 취소 | 사람 (승인 행위) |
| 발주진행 | 미발주 · 부분발주 · 발주완료 | **계산값** (배분 합계) |

### 1.4 수량 불변식

| # | 불변식 | 위반 시 |
|---|---|---|
| A-1 | `Σ allocated_qty (요청라인 기준) ≤ request_item.quantity` | 거부 — 요청보다 많이 발주 불가 |
| A-2 | `Σ allocated_qty (발주라인 기준) ≤ po_item.quantity` | 거부 |
| A-3 | 발주라인은 **배분을 최소 1건** 가진다 | 거부 — 근거 없는 발주 금지(D-2) |
| A-4 | `allocated_qty > 0` | 거부 |
| A-5 | 요청 취소·반려 시 이미 배분된 수량이 있으면 | 거부 — 발주를 먼저 취소해야 함 |

## 2. 【P0-2】 관리번호·수주번호 : 어디가 원본인가

### 2.1 계층별 역할 (판정서 §4.2)

| 계층 | 관리번호 | 수주번호 | 성격 |
|---|---|---|---|
| 발주 **헤더** | 대표 표시 | 대표 표시 | **계산값** — 배분이 전부 같으면 그 값, 섞이면 `혼합` |
| 발주 **라인** | 입력 기본값 | 입력 기본값 | 화면 편의. 원본 아님 |
| **배분** | **원본** | **원본** | 원가·추적은 여기서만 |

발주서 목록·상세에서 관리번호가 보이는 것은 **읽기 편하라고** 계산해 보여주는 것이지, 그 값이 원장이 아니다.

### 2.2 필수/선택 규칙 (D-3 확정)

| 구매 성격 | 관리번호 | 수주번호 |
|---|---|---|
| 프로젝트성 구매 | **필수** | 선택 |
| 공용재고·예비품·일반구매 | 없어도 진행 | 없어도 진행 |

⚠ **관리번호 없는 배분을 허용한다.** 이것이 지시서 §2가 말한 "공용구매·예비품·재고보충·개발자재는 특정 호기에 귀속되지 않는다"의 데이터 표현이다.

### 2.3 기존 `po_item_project_links` 와의 관계

이미 있는 이 표(`po_item_id`·`project_id`·`allocated_qty`·`allocation_pct`·0건)는 **발주라인 → 프로젝트** 배분만 담는다. `purchase_allocations` 는 여기에 **요청라인·수주번호·대체품**을 더한 상위 개념이다.

**판단이 필요한 부분**: 두 표를 하나로 합칠지, `po_item_project_links` 를 폐기할지는 구현 착수 시 결정한다. 0건이라 어느 쪽이든 데이터 손실은 없다. V2는 **`purchase_allocations` 하나로 통일**하는 쪽을 제안한다(같은 뜻의 표가 둘이면 어느 것이 원본인지 또 헷갈린다).

## 4. 【P0-4】 재고 최소 상태 (판정서 §4.4)

### 4.1 상태 4종

| 상태 | 뜻 | 생산에 쓸 수 있나 |
|---|---|---|
| `QUARANTINE` 검수대기·격리 | 입고됐으나 검수 전 | ❌ |
| `AVAILABLE` 사용가능 | 검수 합격분 | ✅ |
| `REJECTED` 불합격·처리대기 | 검수 불합격, 처분 미정 | ❌ |
| `DISPOSED` 처분완료 | 반품·폐기·특채 확정 | ❌ (특채는 승인 시 `AVAILABLE` 로 이동) |

### 4.2 표현 방식

`stock_movements` 에 **`stock_state` 칸 추가**(현재 `kind` 는 IN/OUT/ADJUST 3종뿐). 잔량은 `(part_id, stock_state)` 별 집계로 계산한다.

```
입고 등록      → IN,  state=QUARANTINE
검수 합격      → 상태이동 QUARANTINE → AVAILABLE   (수량 보존)
검수 불합격    → 상태이동 QUARANTINE → REJECTED
반품·폐기 확정 → 상태이동 REJECTED  → DISPOSED
특채 승인      → 상태이동 REJECTED  → AVAILABLE   (승인자·사유 필수)
생산출고       → OUT, state=AVAILABLE 에서만
```

⭐ **상태이동은 수량이 사라지지 않는다.** 어디로 갔는지가 항상 원장에 남는다.

⚠ 다단 창고·LOT·FIFO·위치는 **후속**이다(판정서 §4.4). `stock_movements.location` 은 지금도 자유 글자이므로 그대로 둔다.

### 4.3 D-7 확정 반영

검수 불합격의 **기본값은 `REJECTED` 격리·처리대기**다. 자동으로 반품·폐기·특채 처리하지 않는다. 구매·품질 담당자가 명시적으로 결정하고 **사유·승인자·수량**을 남긴다. **특채 승인 전에는 `AVAILABLE` 로 이동하지 않는다.**

## 5. 【P0-5】 BOM 구매근거 : 요청보다 앞에 온다

### 5.1 순서 (판정서 §4.5)

```
① BOM 상태 고정 (구매근거 스냅샷)
        ↓
② 그 근거를 연결한 구매요청
        ↓
③ 견적 · 선정
        ↓
④ 발주 발행 시 근거 재확인 — 차이 있으면 자동 덮어쓰기 ⛔, 담당자 영향판정 후 발행
        ↓
⑤ 이후 BOM 변경 시 영향목록 생성
```

V1이 이것을 마지막(S6)에 둔 것이 잘못이었다. **구매요청을 먼저 만들면 "어느 설계를 근거로 샀나"를 또 잃는다.**

### 5.2 구조

```
bom_purchase_baselines  (구매근거 스냅샷)   ★ 신설
  · project_id · snapshot_no · source_upload_id
  · created_from : REQUEST | PO_ISSUE | MANUAL
  · created_by · created_at · note
        │ 1
        │ N
bom_baseline_items  (그때의 값 그대로)       ★ 신설
  · baseline_id · bom_item_id
  · part_no · part_name · spec · total_qty · unit_price · buy_at …
```

- 구매요청은 `baseline_id` 를 갖는다.
- 발주 발행 시 **연결된 스냅샷 vs 현재 BOM** 차이를 보여준다.
- 차이가 있어도 **자동으로 고치지 않는다.** 담당자가 보고 판정한 뒤 발행한다.

### 5.3 사전구매 (판정서 §4.5)

정식 설계 Release 전에 급히 사야 할 때가 있다. 이때는 요청 유형을 **`사전구매`** 로 구분하고 **사유·승인자·당시 스냅샷**을 남긴다. 스냅샷 없이 진행하는 길은 만들지 않는다.

### 5.4 아직 안 정한 것

**정식 BOM Release 정책과 Revision 명명규칙(Rev A/B/C 인지 숫자인지, 누가 Release 를 선언하는지)은 이 문서에서 닫지 못한다.** 설계 부서의 실제 관행을 확인해야 한다 → §7 미결 항목에 포함.

## 8. A ~ D 업무 묶음 (판정서 §6)

각 묶음은 **사용자가 끝까지 처리할 수 있는 업무 결과**로 검증한다. 코드 단위가 아니다.

### 묶음 A — BOM 구매근거 고정 → 구매요청 → 승인

| | |
|---|---|
| **업무 결과** | 설계자가 올린 BOM에서 구매할 줄을 골라 요청서를 만들고, 구매팀이 검토·승인한다. 그 요청이 **어느 BOM 상태를 근거로 했는지** 언제든 되짚을 수 있다 |
| **구현 전제** | BOM Release/스냅샷 정책 확정(§5.4 미결) |
| **새 표** | `bom_purchase_baselines` · `bom_baseline_items` |
| **칸 추가** | `material_requests`(baseline_id · request_kind · 검토자 · 검토시각 · 승인자 · 승인시각 · 반려사유) |

## 9. 기존 발주 1건 이행 정책 (판정서 §7-11)

### 9.1 그 1건의 실체

```
purchase_orders  id=2 · PO-260716-002 · status='작성중' · order_date=2026-07-16
                 project_id = NULL          ← 관리번호 미연결
po_items         id=2, 3  (2줄)
                 part_id = NULL             ← 자재 미연결
                 quantity = 1.0 / received_qty = 0.0
```

### 9.2 정책

| 무엇을 | 어떻게 |
|---|---|
| 이 1건 | **손대지 않고 그대로 보존한다.** 배분·근거·스냅샷을 소급해 만들지 않는다 |
| 왜 | 관리번호도 자재도 비어 있어 **소급 부여할 근거가 없다.** 없는 사실을 지어내는 것이 된다(지시서 §5 자동 추정 금지) |
| 새 규칙 적용 시점 | **신규 생성분부터.** "배분 없는 발주라인 금지"(A-3) 등 새 검증은 **신규 발주에만** 건다 |
| 화면 표시 | 이 발주는 구 데이터임을 **사실대로 표시**한다(`구매요청 근거 없음 — V1 전 데이터`) |
| 삭제 여부 | 삭제하지 않는다. 대표 판정이 있기 전까지 보존 |

### 9.3 신규 거래

V1 가동 시점부터의 모든 구매는 **근거(구매요청) → 배분 → 발주** 를 거친다. 예외 없음(D-2).
