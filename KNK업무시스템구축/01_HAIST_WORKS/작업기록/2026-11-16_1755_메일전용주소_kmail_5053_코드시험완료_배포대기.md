## 2. 방식 — 「WORKS 프로세스 안에서 5053 도 함께 듣기」

NAS 중계기(DSM)는 그대로 둔다: `kmail → localhost:5053` · `works → localhost:5051`.
옛 메일 앱을 5053 에서 내리고, **WORKS 가 5053 도 듣는다.**

### 검토한 세 길

| 길 | 내용 | 결론 |
|---|---|---|
| ① WORKS 를 하나 더 띄움(5053) | supervisor 프로그램 추가 | ❌ 기동 때 도는 예약 작업 4개(등급 재계산 · 일일 알림 · 명부 동기화 · **메일 자동 수신**)가 **한 벌 더** 돈다 · 배포 때 재시작이 안 따라온다(`auto_deploy.sh` 는 `knk-works` 만 재시작) · 메모리 한 벌 더 |
| ② 5053 → 5051 단순 전달 | 작은 중계 프로그램 | ❌ 포트로 구분이 안 된다 → Host 이름에만 기대야 함(중계기가 이름을 바꿔 보내면 구분 실패) |
| ③ **같은 프로세스에서 포트만 하나 더** | 앱 기동 훅에서 5053 소켓을 열어 같은 앱에 연결 | ✅ **채택** |

③의 장점
- 프로세스·메모리·예약 작업이 **늘지 않는다**
- 배포로 재시작되면 **저절로 같이** 새 코드가 된다(따로 챙길 것 없음)
- 5053 으로 들어온 요청인지 **소켓으로 확실히** 안다(Host 이름에 안 기댄다)
- `KNKHAIST` 컨테이너 설정(supervisor · nginx · 배포 스크립트)을 **하나도 안 건드린다** — `.env` 한 줄만

| `/mail/app?next=/mail/compose` | 이음 로그인 → kmail 로 돌아옴 → **메일 쓰기** |

| 메일 앱 설치 정보(매니페스트) | 범위 = 주소 전체(`/`) · 이미 열린 창은 그 주소로 이동(`navigate-existing`) |

**지금과 같다.** 운영본과 응답 26종을 대조해, 의도한 2곳만 다름을 확인:

2. 메일 매니페스트 `launch_handler` — `focus-existing` → `navigate-existing`

## 5. 안전장치

| | |
|---|---|
| **기본 꺼짐** | 환경변수 `KNK_MAIL_SITE_PORT` 가 없으면 입구를 **열지 않는다** → 배포만으로는 아무 일도 없다 |
| **포트가 막혀 있으면** | 옛 앱이 5053 을 쓰는 동안은 **조용히 기다린다**(30초마다 다시 봄 · 로그는 30분에 한 줄). 풀리면 **재시작 없이** 잡는다 |
| **본체 무영향** | 입구 쪽의 어떤 실패도 5051(업무시스템)에 영향 없음 — 전부 잡아서 로그만 |
| **돌아올 주소는 둘뿐** | 로그인 왕복(SSO)이 돌아올 곳 = `works` · `kmail` — 코드에 박음. 요청이 말하는 주소(Host)로 조립하지 않는다 → 가짜 주소로 로그인 토큰이 새지 않는다 |
| **무한 왕복 방지** | 이름이 `works` 인 요청은 **어느 포트로 왔든** 다시 넘기지 않는다. 훗날 중계 설정이 바뀌어 업무 요청이 메일 입구로 와도 「넘김 → 다시 들어옴 → 넘김…」으로 업무시스템이 멈추는 일이 없다 |
| **로그인 분리** | 로그인 쿠키는 주소별(도메인을 넓히지 않음) → works 와 kmail 의 로그인이 섞이지 않는다 |
