## 1. 배경 — 지금은 MAIL이 WORKS와 "같은 프로그램"

| 구성 | 현황 |
|---|---|
| 메일 핵심 로직 | 이미 별도 파일: `mail_store.py`(1012)·`mail_send.py`(326)·`mail_fetch.py`(262) — **연결(cursor)을 인자로 받는 구조라 별도 DB 재사용 쉬움** ✅ |
| 메일 화면(라우트) | ❗WORKS `main.py`(28,735줄) 안 **12635~13884 (47개, ≈1,270줄 한 덩어리)** |
| DB | WORKS와 **같은 SQLite** 공유 (mail 테이블 + users 참조) |
| 인증 | WORKS 세션 + 메신저 SSO(`sso_client.py`) |
| 결과 | 메일 고치면 `main.py` 변경 → **WORKS 전체가 같이 배포** (대표 지적 정확) |
| 메신저 | 처음부터 **별도 repo·별도 서버** → 따로 동작 |

## 2. 목표 아키텍처 — 메신저처럼 완전 독립

```
[브라우저/PWA]
   └── mail.knknara.co.kr  ── (NAS 리버스프록시) ──▶  KNK Eum MAIL (독립 FastAPI, 자체 포트)
                                                          ├── 자체 DB: mail.db (메일 8종 + settings + users 미러)
                                                          ├── 자체 첨부 저장소: data/mail_uploads/
                                                          └── 메신저 SSO(JWT) 로그인 + 직원명부 동기화
[메신저] haist.knknara.co.kr/msg  ◀── SSO(public-key/userinfo) + GET /api/sso/directory(서비스키)
[WORKS]  works.knknara.co.kr      ── (독립, 메일과 DB·프로세스 무관)
```

- **별도 프로세스**: 자체 uvicorn → 메일만 따로 배포·재시작. WORKS 재시작과 무관.
- **별도 DB(`mail.db`)**: 메일 데이터 완전 분리. 직원명부는 **미러 테이블(users)** 로 보관하고 메신저에서 주기 동기화.
- **별도 주소**: `mail.knknara.co.kr` (정확한 서브도메인은 기존 메일 DNS와 충돌 없게 전산담당자 확정).

## 3. 옮길 메일 테이블 (8종) + 부속

별도 `mail.db`에 신설:
1. `mail_messages` (받은/보낸/임시 본문) — `user_id` FK는 로컬 users 미러 참조
2. `mail_attachments` (첨부, BLOB/경로)
3. `mail_aliases` (수신주소→사용자 매핑)
4. `mail_large_files` (대용량 첨부 다운로드 토큰)
5. `mail_signatures` (서명)
6. `mail_fetch_accounts` (가져오기 계정 — POP3/IMAP, 비번 Fernet)
7. `mail_fetch_seen` (가져오기 중복 방지 UIDL)
8. `mail_rules` (분류 규칙)

부속:
- `settings` (mail_send 설정·fetch 설정 등 get_setting/set_setting용)
- `users` (직원명부 **미러** — 메신저 동기화. employee_no·이름다국어·dept·email·role 등. 메일 소유자/마스킹 권한 판단)

## 4. 외부 의존성 (내가 못 하는 부분 — 정직)

### (A) 메신저 세션/repo — 메일을 SSO 새 소비자로 등록
- 현재 SSO audience = `haist-works`. 메일은 **자체 audience(예: `knk-mail`)** 필요.
- 메신저가 메일용 redirect_uri(`https://mail.knknara.co.kr/sso/callback`)를 allowlist에 등록.
- `GET /api/sso/directory`(직원명부 API) 구현 여부 확인 — `sso_client` 주석상 "메신저 API 완료 전엔 휴면". 미구현이면 임시로 **메신저 DB 직접 동기화**(`sync_employees_from_messenger_db`) 또는 WORKS 경유 폴백.
- 서버↔서버 공유키 `KNK_SSO_SERVICE_KEY` 메일 NAS .env에 공유.

### (B) 전산담당자 — NAS 인프라 (제가 직접 불가)
- 새 서브도메인 DNS (`mail.knknara.co.kr`, **MX 무관 — 웹용 A/CNAME만**)
- SSL 인증서
- 리버스프록시 (`mail.knknara.co.kr` → 메일 프로세스 내부 포트)
- 자동 기동(서비스 등록) + 1분 cron git pull (WORKS와 동일 패턴)
- `.env` (KNK_MAIL_KEY, KNK_SSO_SERVICE_KEY, AI 키 등)

→ **요청서 2종**: 전산담당자용 + 메신저 세션용. (Phase 2에서 작성)
