# 1. B단계가 푸는 문제 — 한 문장

**지금은 "엑셀을 올려 보드에 담아 둔 것"과 "구매팀이 돈을 써도 되는 확정본"이 같은 화면에 있다.**

## 2.1 ⭐ 설계 Release 에 **구매값을 넣지 않는다**

**실물 흐름**: 설계팀 BOM 의 단가·납기 칸은 대개 **비어 있고 구매팀이 나중에 채운다.**
그런데 구매팀이 채운 값을 설계 Release 의 **확정값처럼 보존하면**, 설계가 확정하지 않은 숫자가 설계 확정본에 들어간다.

| | 설계 Release 스냅샷에 | |
|---|---|---|
| 품명 · 품번/모델 · Maker · Specification · 단위 · **대당 설계요구수량** | **넣는다** | 설계가 통제하는 값 |
| 적용범위(§5.2) | **넣는다** | 어디에 쓰는 설계인지 |
| **단가 · 통화** | **넣지 않는다** | 구매값 |
| **구매납기** | **넣지 않는다** | 구매값 |
| 협력사 · 포장단위 · 환산 · 재고배분 · 초과구매 | **넣지 않는다** | 구매값 |
| **VINA 참고재고** | **넣지 않는다** (§11) | 구매검토 전용 |

## 2.2 설계가 특별히 지정한 것은 **설계 요구조건**으로 따로

설계가 *"이 Maker 여야 한다"* · *"이 날짜까지 필요하다"* 를 지정하는 경우가 있다.
이건 구매값이 아니라 **설계 요구조건**이므로 **별도 칸으로 구분해 Release 에 넣는다.**

| 칸 | 뜻 |
|---|---|
| `req_maker_fixed` | 지정 Maker (대체 불가 여부 포함) |
| `req_due_date` | 설계 요구납기 (구매납기와 다름) |
| `req_note` | 그 밖의 설계 요구조건 |

⚠ **구매팀이 채우는 `구매납기` 와 설계의 `요구납기` 는 다른 칸이다.** 같은 칸에 담지 않는다.

# 4. 검증 기록과 Release 차단

## 4.1 항목별 검증 상태

각 불일치 항목은 아래 넷 중 하나를 갖는다.

| 코드 | 사람 이름 | 뜻 |
|---|---|---|
| `OPEN` | **미해결** | 아직 아무도 안 봄 |
| `CONFIRMED_OK` | **확인됨(문제없음)** | 사람이 보고 "이대로 맞다" 고 판단 |
| `FIXED` | **수정됨** | 고쳤다고 표시함 — **이것만으로는 부족** |
| `HOLD` | **보류** | 판단을 미룸 |

## 4.2 ⭐ Release 허용 조건 (B-P0-4)

**허용** — 아래 둘 중 하나

1. 모든 항목이 **`확인됨(문제없음)`**
2. **`수정됨` + 재검증 성공 기록이 있음** (= 새 업로드로 다시 올려 일치 확인)

**차단** — 하나라도 있으면 막는다

- `미해결`
- **`보류`** ← 해결된 상태로 해석하지 못하게 명시
- **파싱 실패**
- **중복시트 미해결**

⛔ **사람이 `수정됨` 을 선택한 사실만으로 `VERIFIED` 가 되지 않는다.**

## 4.3 차단을 어디에 두는가 — 6개 층 전부

| 층 | 무엇 |
|---|---|
| DB | 제약·기본값으로 잘못된 상태 조합을 못 만들게 |
| 서버 함수 | 화면을 거치지 않고 직접 불러도 `PermissionError` |
| 라우트 | 403 / 검증 실패 응답 |
| 화면(HTML) | 버튼을 아예 안 그림 |
| 화면(JS) | 잠금 — **친절함이지 차단이 아님** |
| 안내문 | 왜 안 되는지 사람 말로 |

⛔ **화면에서 버튼만 숨기고 요청이 실행되는 상태는 차단으로 인정하지 않는다.**

## 4.4 검증 무효 (B-P1-1)

검증 완료 뒤 **잘못된 시트 선택·검증 오류**가 발견될 수 있다.

- **원본 업로드를 수정하지 않는다**
- 그 업로드를 `VERIFICATION_VOID` 로 만들어 **Release 근거로 쓰지 못하게** 한다
- **사유 · 처리자 · 일시**를 기록한다
- 데이터를 고치려면 **새 업로드**로 한다
- 이미 그 업로드로 Release 가 발행됐다면 **§8.5** 를 따른다

# 5. Release — 내용범위와 적용범위를 **나눈다**

## 5.1 내용범위 (무엇이 스냅샷에 담기나)

**한 Release 는 선택된 업로드의 활성 BOM 전체 스냅샷을 보존한다.**
품목 일부만 골라 Release 하지 않는다. 담기는 칸은 §2.1 표를 따른다.

## 5.2 ⭐ 적용범위 Effectivity — 허용유형 4종 (B4-1)

**KNK 는 관리번호 1개에 수주번호가 여러 개 붙고, 발주 차수도 나뉜다.**
따라서 *"프로젝트 전체만"* 으로는 실제 업무를 담을 수 없다.

⚠ **V3 에서 `관리번호 전체 / 선택 수주번호 / 선택 호기 / 적용수량` 을 같은 종류 4개처럼 나열한 것은 잘못이었다.**
`적용수량` 만 저장하면 **어느 수주·어느 장비에 적용되는지 알 수 없다.** 아래로 확정한다.

### 5.2.1 허용유형 — 이 넷 외에는 저장할 수 없다

| `scope_type` | 사람 이름 | 적용대상 | 수량 규칙 |
|---|---|---|---|
| **`PROJECT_SNAPSHOT`** | **관리번호 전체 (발행 시점)** | Release 발행 **시점에** 그 관리번호 아래 존재하는 적용대상 전체 | 적용대수 없음 |
| **`SALES_ORDER_SET`** | **선택 수주번호** | 선택한 수주번호 1개 이상 | 선택 수주 **전체수량** 적용 |
| **`UNIT_SET`** | **선택 호기** | 선택한 **확정(CONFIRMED) 호기** 1개 이상 | 적용대수 없음 |
| **`SALES_ORDER_QUANTITY`** | **수주번호 + 적용대수** | 선택 수주번호 + 장비 **적용대수** | **`apply_equipment_qty` 필수 · 사유 필수** |

### 5.2.2 ⭐ `apply_equipment_qty` 는 **장비 적용대수**다 — 부품 수량이 아니다

| | |
|---|---|
| **`apply_equipment_qty`** | 이 Release 를 **장비 몇 대분**에 적용하는가 (예: 5대) |
| **`qty_per_equipment`** | Release 품목의 **대당 설계요구수량** (예: 볼트 8개/대) |
| **부품 필요수량** | **`qty_per_equipment × apply_equipment_qty`** 로 **산정**한다 (예: 40개) |

⛔ **부품 필요수량을 Release 스냅샷에 저장하지 않는다.** 적용대수가 바뀌면 틀린 값이 남는다. **산정식으로만 쓴다.**

### 5.2.3 ⭐ 미래는 자동으로 들어오지 않는다

- **`PROJECT_SNAPSHOT` 은 발행 시점의 스냅샷이다.** 이후에 새로 생기는 수주번호·호기는 **자동 편입하지 않는다**
- 새 수주·새 호기에 적용하려면 **새 Release 를 발행**하거나 **적용범위 확정 절차**를 거친다
- ⚠ 이름이 "전체"라서 미래까지 포함한다고 읽히지 않도록, 화면에는 **`관리번호 전체 (2026-08-05 기준)`** 처럼 **발행 시점을 함께 표시**한다

### 5.2.4 호기는 **확정 호기만**

- `UNIT_SET` 에는 **`unit_state='CONFIRMED'` 인 호기만** 넣을 수 있다
- **개발·미확정(`PROVISIONAL`) 호기는 번호·구성이 계속 바뀌므로** Effectivity 로 쓰지 않는다 (WP-03 확정사항)
- 미확정 단계에서 범위를 좁혀야 하면 **`SALES_ORDER_QUANTITY`(수주번호 + 적용대수)** 를 쓴다
- 취소(`CANCELLED`) 호기도 넣을 수 없다

### 5.2.5 공통 규칙

- `project_id`(관리번호) 는 **모든 유형에서 필수 기준**으로 유지한다
- ⚠ **호기는 선택 적용기준이며 구매업무의 최상위 필수 Key 가 아니다**
- **적용범위 변경은 기존 Release 수정이 아니라 새 Release 로 처리**한다

## 5.3 불변성

**발행된 Release 의 스냅샷은 절대 수정하지 않는다.** 고칠 일이 생기면 새 Release 를 발행한다.

# 6. Revision — 세 가지를 절대 섞지 않는다

| | 무엇 | 누가 매기나 | 예 |
|---|---|---|---|
| **외부 Revision** | 설계 도면·BOM 의 개정 표기 | 설계팀(회사 밖 규칙 포함) | `R1` · `VER.0` · 표기 없음 |
| **내부 Release 회차** | 우리 시스템이 발행한 확정본 순번 | 시스템 | `Rel.1` · `Rel.2` |
| **업로드 버전** | 파일을 몇 번째로 올렸나 | 시스템 | `v1` · `v2` |

## 6.1 ⭐ 외부 Revision 표기가 없는 파일 (B-P0-3)

실물 BOM 에는 `R1` · `VER.0` · **표기 없음**이 섞여 있다.
표기 없는 정상 파일을 영구 차단하면 안 된다.

| 상황 | 처리 |
|---|---|
| **자동 인식 실패** | **Release 차단** |
| 설계책임자가 **`외부 Revision 표기 없음`을 명시 선택 + 사유 기록** | **Release 가능** |
| 파일명에 `R1` 같은 글자가 있음 | **힌트로만 보여준다. Revision 확정값으로 자동 채택하지 않는다** |
| Release 시점 | 설계담당자가 **원문을 확인하거나 직접 입력**한다 |

⛔ 파일명에서 임의 추정하거나 자동 생성하지 않는다.

# 7. 신청·승인 — 세 사람의 역할을 나눈다

## 7.1 ⭐ 올린 사람 · 신청한 사람 · 승인한 사람 (B4-5)

⚠ **V3 의 `설계담당자(업로드한 사람)` 문구는 업로드 대행이 있는 경우 업무를 막는다.** 아래로 확정한다.

| 역할 | 누구 | 규칙 |
|---|---|---|
| **업로더** `uploaded_by` | 파일을 등록한 사람 | 보조·대행 가능 |
| **신청자** `requested_by` | 그 설계를 **책임지고** Release 를 요청할 권한이 있는 설계담당자 | **업로더와 같아도 되고 달라도 된다** |
| **승인자** `approved_by` | 설계책임자 (또는 §7.3 대체 승인자) | ⛔ **신청자와 반드시 다르다** |

## 7.2 두 단계 전이

| 단계 | 누가 | 무엇을 | 전이 |
|---|---|---|---|
| **① Release 신청** | **신청자** | 검증완료 업로드를 지목 + 적용범위 선언 | `(업로드 VERIFIED)` → Release `PENDING` |
| **② 발행** | **승인자** | 스냅샷·적용범위를 보고 발행 | `PENDING` → `RELEASED` |
| **②′ 반려** | **승인자** | 잘못된 신청을 되돌림 | `PENDING` → `REJECTED` (§7.4) |

## 7.3 ⛔ 자가승인 예외는 **열지 않는다**

- **신청자와 승인자는 항상 다른 사람이다**
- 설계담당자가 한 명뿐이면 **대표 또는 지정 임원이 대체 승인자**가 된다
- **대체 승인은 사유와 역할을 기록**한다
- **`SINGLE_APPROVER` 자가승인 예외는 V1 에서 열지 않는다**

## 7.4 ⭐ 반려 (B4-4)

⚠ **V3 에는 신청과 승인만 있고, 설계책임자가 잘못된 신청을 되돌릴 길이 없었다.**

| | 계약 |
|---|---|
| 전이 | **`PENDING` → `REJECTED`** |
| 누가 | 승인자 (신청자는 자기 신청을 반려할 수 없다 — 취소가 필요하면 별건) |
| **사유** | **필수.** 빈 값이면 거부 |
| 기록 | **반려자 · 반려사유 · 반려일시** 를 남긴다. 신청자·신청일시도 그대로 보존 |
| 지위 | ⛔ **반려된 신청은 구매근거가 아니다** |
| 재신청 | **검증완료 업로드를 다시 지목해 새 신청(새 행)으로 만든다.** 반려된 행을 되살리지 않는다 |
| 화면 | 신청자에게 **왜 반려됐는지** 보인다 |

## 7.5 서버에서 막는 것

- ⛔ **신청자 = 승인자면 거부** (화면에서 숨기는 것으로 끝내지 않는다)
- ⛔ `VERIFIED` 가 아닌 업로드는 신청 자체가 안 된다
- ⛔ §4.2 차단 항목이 하나라도 있으면 신청 거부
- ⛔ **같거나 겹치는 적용범위**에 이미 `PENDING` 이 있으면 새 신청 거부 (§8.3.4)
- ⛔ **미확정·취소 호기**를 `UNIT_SET` 에 넣으면 거부 (§5.2.4)
- ⛔ `SALES_ORDER_QUANTITY` 인데 `apply_equipment_qty` 가 없거나 1 미만이면 거부

# 8. Release 상태와 대체 관계

## 8.1 상태 — 다섯 가지

| 코드 | 사람 이름 | 뜻 |
|---|---|---|
| `PENDING` | **발행 대기** | 신청됨. 아직 구매근거 아님 |
| **`REJECTED`** | **반려** | 승인자가 되돌림. 구매근거 아님 (§7.4) |
| `RELEASED` | **발행됨** | ⭐ **이 상태만 구매근거로 쓸 수 있음** |
| `SUPERSEDED` | **대체됨** | **전 범위**가 새 Release 로 덮임. 내용은 불변 보존 |
| `CANCELLED` | **취소** | 잘못 발행했고 **구매근거로 쓰이지 않은** 경우만 |

## 8.2 ⭐⭐ 부분 겹침 — 남은 범위는 계속 유효하다 (B4-2)

⚠ **V3 처럼 새 Release 가 기존 Release 전체를 `SUPERSEDED` 로 바꾸면, 겹치지 않는 수주의 구매근거가 사라진다.**

> **예시** — 관리번호 `001M2607` 전체로 `Rel.1` 을 발행했다. 나중에 수주 `SO-A` 만 설계가 바뀌어 `Rel.2` 를 발행했다.
> `Rel.1` 을 통째로 대체됨으로 만들면 **`SO-B`·`SO-C` 의 발주 근거가 없어진다.**

### 8.2.1 확정 계약

| 상황 | 기존 Release 상태 |
|---|---|
| 기존 Release 의 **전 범위**가 새 Release 로 덮임 | **`SUPERSEDED`** |
| **일부 범위만** 덮임 | **`RELEASED` 유지** — 비중첩 범위에서 계속 유효 |

### 8.2.2 ⭐ `PARTIALLY_SUPERSEDED` 상태코드를 **만들지 않는다** (하나로 확정)

게이트 권고안을 그대로 채택한다.

- **상태 칸에 부분대체 코드를 두지 않는다**
- 부분 대체는 **`bom_release_supersede` 관계에서 계산**한다
- **원 Release 는 잔여범위가 있으면 `RELEASED` 를 유지**한다

> **왜 이렇게 정하나**: 상태코드를 하나 더 만들면 *"부분대체도 구매근거가 되나?"* 를 매번 다시 판단해야 한다.
> `RELEASED` 만 구매근거라는 §8.1 규칙을 그대로 두고, **어느 범위가 죽었는지는 관계표가 답한다.**

### 8.2.3 무엇을 기록하나

`bom_release_supersede` 한 행 = **"새 Release 가 기존 Release 의 이 적용대상을 덮었다"** 한 건.

| 칸 | 뜻 |
|---|---|
| `new_release_id` | 덮은 Release |
| `old_release_id` | 덮인 Release |
| `overlap_effectivity_id` | **실제로 겹친 기존 Effectivity 행** |
| `overlap_kind` | `FULL`(그 행 전부) / `PARTIAL_QTY`(적용대수 일부) |

### 8.2.4 ⭐ "지금 적용되는 Release" 조회 규칙

대상(수주번호 또는 확정 호기) 하나를 놓고 물었을 때:

1. 그 대상을 포함하는 **`RELEASED` Release** 를 모은다
2. 그중 **가장 최근에 발행된 것**이 현재 적용본이다 (`released_at` 기준, 같으면 `release_no` 큰 쪽)
3. `SUPERSEDED` · `PENDING` · `REJECTED` · `CANCELLED` 는 후보에서 뺀다

⚠ **`PROJECT_SNAPSHOT` 과 `SALES_ORDER_SET` 이 같은 수주를 가리키면 둘 다 후보다.** 최신이 이긴다.

### 8.2.5 화면 표시

- 기존 Release 화면에 **`일부 범위 대체`** 를 **상태와 별도로** 표시한다
- **어느 수주·어느 호기가 대체됐는지** 목록으로 보여준다
- **남아 있는 범위**도 함께 보여준다 (이게 아직 유효한 구매근거이기 때문)

## 8.3 겹침 판정 — 유형별 계산 방법

`scope_type` 이 다른 두 Release 도 겹칠 수 있으므로, **적용대상(수주번호·확정호기) 단위로 펼쳐서 비교**한다.

### 8.3.1 펼치기 규칙

| `scope_type` | 펼치면 |
|---|---|
| `PROJECT_SNAPSHOT` | 발행 시점 스냅샷에 담긴 수주번호·확정호기 전부 |
| `SALES_ORDER_SET` | 지정 수주번호들 |
| `UNIT_SET` | 지정 확정호기들 |
| `SALES_ORDER_QUANTITY` | 지정 수주번호 (+ 적용대수) |

### 8.3.2 겹침 판정

- 펼친 **적용대상 집합이 교차하면 겹침**이다
- 교차한 대상마다 `bom_release_supersede` 행을 만든다
- 기존 Release 의 **모든** 적용대상이 교차하면 → `SUPERSEDED`, 아니면 → `RELEASED` 유지

### 8.3.3 적용대수가 있는 경우

- 같은 수주번호에 `SALES_ORDER_QUANTITY` 가 겹치면 **`PARTIAL_QTY`** 로 기록한다
- ⛔ **적용대수 차감·잔여계산을 자동으로 하지 않는다.** 사람이 보고 판단한다
- 화면에는 **"이 수주에 적용대수가 겹치는 Release 가 있습니다"** 로 알린다

### 8.3.4 동시 `PENDING` 차단

- **같거나 겹치는 적용대상**에 이미 `PENDING` 이 있으면 새 신청을 거부한다
- 판정 방법은 §8.3.2 와 같다 (펼쳐서 교차 확인)

## 8.4 취소와 대체의 사용 기준 (B-P1-2)

| 상황 | 처리 |
|---|---|
| **설계 변경** | 새 Release 발행 + 겹치는 기존은 §8.2 규칙대로 |
| **잘못 발행 · 구매근거로 사용되지 않음** | `CANCELLED` |
| **이미 구매요청·발주에 사용됨** | ⛔ **취소로 지우지 않는다.** 새 Release + 영향분석(§10) |
| **신청이 잘못됨 (발행 전)** | `REJECTED` (§7.4) |
| **근거 업로드가 `VERIFICATION_VOID` 로 무효화됨 (§4.4)** | ⭐ 아래 §8.5 |

## 8.5 ⭐ 무효화된 업로드로 이미 Release 가 발행된 경우

**검증 무효(§4.4)는 업로드를 막을 뿐 이미 나간 Release 를 되돌리지 않는다.** 아래로 확정한다.

| 그 Release 가 | 처리 |
|---|---|
| **구매근거로 쓰인 적 없음** | `CANCELLED` + 사유에 **무효 업로드 번호**를 적는다 |
| **이미 구매요청·발주에 쓰임** | ⛔ **취소하지 않는다.** 새 업로드 → 새 Release + **영향분석(§10)** |

- 어느 경우든 **원 Release 스냅샷은 지우지 않는다** (§5.3)
- 화면에 **`근거 업로드가 무효 처리됨`** 을 Release 상태와 **별도로** 표시한다
- ⛔ **무효 처리가 Release 상태를 자동으로 바꾸지 않는다.** 사람이 위 표대로 판단한다

# 9. 구매요청 연결 (B-P0-1)

## 9.1 ⛔ 구매요청 전체에 `release_id NOT NULL` 을 걸지 않는다

그렇게 하면 아래 정상 업무가 **전부 막힌다**.

- 공용재고 보충구매 · 예비품 구매 · 소모품 구매 · 긴급구매 · BOM 외 수동 구매요청

## 9.2 라인 단위로 연결한다

| 구매요청 **라인**의 근거유형 `source_type` | 필수 항목 |
|---|---|
| **`BOM_RELEASE`** | **`bom_release_item_id` 필수** |
| `STOCK_REPLENISH`(공용재고 보충) | `source_reason` 필수 |
| `SPARE`(예비품) | `source_reason` 필수 |
| `CONSUMABLE`(소모품) | `source_reason` 필수 |
| `URGENT`(긴급구매) | `source_reason` 필수 |
| `MANUAL`(수동요청) | `source_reason` 필수 |

**규칙**

- 연결은 **구매요청 문서 머리가 아니라 품목 라인 단위**다
- 한 구매요청서 안에 **근거유형이 섞여도 된다**
- **`RELEASED` 가 아니면 구매요청 금지** 는 **`BOM_RELEASE` 라인에만** 적용된다
- ⛔ `BOM_RELEASE` 라인은 **그 Release 가 `RELEASED` 이고, 대상이 아직 대체되지 않았을 때만** 만들 수 있다 (§8.2.4 조회 규칙)

**UNIQUE — ⚠ 한 칸으로 묶지 않는다 (NULL 함정)**

```sql
-- ⛔ 이렇게 쓰면 안 된다:
--    UNIQUE (release_id, sales_order_id, project_unit_id)
--    SQLite·PostgreSQL 둘 다 UNIQUE 에서 NULL 을 "서로 다른 값"으로 본다.
--    호기 행은 sales_order_id 가 NULL 이므로 같은 호기를 몇 번이든 넣을 수 있다.
CREATE UNIQUE INDEX uq_bre_order ON bom_release_effectivities(release_id, sales_order_id)
    WHERE sales_order_id IS NOT NULL;
CREATE UNIQUE INDEX uq_bre_unit  ON bom_release_effectivities(release_id, project_unit_id)
    WHERE project_unit_id IS NOT NULL;
```

> **부분 고유 인덱스**는 §15.1 에서 확인한 **양쪽 DB 공통 기능**이며, WP-03 `uq_punit_orderlink_active` 에서 이미 쓰고 있다.

**CHECK — 유형별 필수·금지 칸**

`scope_type` 은 머리 표에 있으므로 **행 안에서 판정 가능한 것만 CHECK 로 두고**, 유형별 조합 규칙은 §14.7 대로 **서버 함수에서 강제**한다.

| | 내용 |
|---|---|
| E1 | `sales_order_id IS NOT NULL` **또는** `project_unit_id IS NOT NULL` — 둘 다 NULL 금지 |
| E2 | `sales_order_id` 와 `project_unit_id` 를 **동시에** 채우지 않는다 |
| E3 | `apply_equipment_qty IS NULL` **또는** `apply_equipment_qty >= 1` |
| E4 | `apply_equipment_qty IS NOT NULL` → `apply_reason` NOT NULL AND `<> ''` |
| E5 | `apply_equipment_qty IS NOT NULL` → `project_unit_id IS NULL` (적용대수는 수주 단위에만) |

**서버가 추가로 강제하는 것 (CHECK 로 불가 — §14.7)**

- `scope_type='PROJECT_SNAPSHOT'` → 발행 시점 스냅샷 그대로. 사람이 임의 편집 금지
- `scope_type='SALES_ORDER_SET'` → 모든 행이 `sales_order_id` · `apply_equipment_qty IS NULL`
- `scope_type='UNIT_SET'` → 모든 행이 `project_unit_id` · **`unit_state='CONFIRMED'`**
- `scope_type='SALES_ORDER_QUANTITY'` → 모든 행이 `sales_order_id` + `apply_equipment_qty` NOT NULL
- 지정 수주·호기가 **`bom_releases.project_id` 소속**인지 확인

**삭제정책**: `release_id` → `ON DELETE RESTRICT`. Release 를 지우지 않으므로 실질 삭제 없음.

## 14.7 ⭐ DB CHECK 로 **못 하는 것** — 서버가 강제한다

**CHECK 제약은 같은 행 안의 값만 볼 수 있다.** 다른 표를 조회하는 규칙은 CHECK 로 못 쓴다.

| 규칙 | 왜 CHECK 불가 | 어디서 강제 |
|---|---|---|
| `UNIT_SET` 은 **확정 호기만** | `project_units.unit_state` 는 **다른 표** | 서버 함수 + 라우트 + 화면(선택지에 확정만) |
| 지정 수주·호기가 **그 관리번호 소속**인지 | 다른 표 조회 | 서버 함수 |
| `FIXED` → **재검증 일치**해야 `VERIFIED` | 여러 행 종합 | §4.2 서버 판정 |
| **겹치는 `PENDING` 차단** | 다른 행들과 비교 | §8.3.4 서버 판정 |
| `BOM_RELEASE` 라인은 **`RELEASED` 이고 미대체**일 때만 | 다른 표 조회 | §9.2 서버 판정 |
| 부분 대체 계산 | 여러 표 조인 | §8.3 서버 계산 |

⛔ **"DB 제약이 있으니 됐다" 로 끝내지 않는다.** §4.3 6개 층을 전부 채운다.

# 15. SQLite ↔ PostgreSQL 동일 의미 검토 (게이트 §5-4)

WP-02 에서 **C안(단계적 전체 이관)** 이 승인됐으므로, B단계 스키마는 **두 DB 에서 같은 뜻으로 지켜져야** 한다.

## 15.1 양쪽에서 같은 의미 — **써도 된다**

| 기능 | 확인 |
|---|---|
| `PRIMARY KEY` | 동일 |
| `NOT NULL` | 동일 |
| `UNIQUE` (복합 포함) | 동일 |
| `CHECK` (같은 행 안 값만) | 동일 |
| `FOREIGN KEY … REFERENCES` | 동일 (단 §15.3 주의) |
| **부분 고유 인덱스** `CREATE UNIQUE INDEX … WHERE …` | **양쪽 지원** — WP-03 `uq_punit_orderlink_active` 에서 이미 사용 중 |

## 15.2 한쪽에만 있다 — ⛔ **쓰지 않는다**

| 기능 | 있는 쪽 | 왜 안 쓰나 |
|---|---|---|
| `EXCLUDE USING gist` (범위 배타) | **PostgreSQL 만** | 적용범위 겹침 방지에 딱 맞지만 **SQLite 에 없다** → §8.3 **서버 판정**으로 |
| `DEFERRABLE INITIALLY DEFERRED` | **PostgreSQL 만** | 순환 참조 회피용 — 설계에서 순환을 안 만든다 |
| `ALTER TABLE … ADD CONSTRAINT` | **PostgreSQL 만** | SQLite 는 표 재작성 필요 → **처음 만들 때 제약을 다 넣는다** |
| DB 트리거로 불변성 강제 | 양쪽 있으나 **문법 다름** | §14.8 대로 **서버 함수로** |

## 15.3 ⚠ 의미가 달라 조심할 것

| | SQLite | PostgreSQL | B단계 대응 |
|---|---|---|---|
| **FK 강제** | **연결마다 `PRAGMA foreign_keys=ON`** 필요 (기본 OFF) | 항상 켜짐 | ✅ `get_db()` 가 켠다(실측 `app/database.py:122`). ⚠ **삭제 경로 여러 곳이 명시적으로 OFF 한다** → **FK 만 믿지 말고 서버 검사를 반드시 둔다** |
| **🔴 UNIQUE 안의 NULL** | NULL 끼리 **서로 다르다**고 봄 → 중복 허용 | **동일** (기본 `NULLS DISTINCT`) | ⭐ **두 DB 가 똑같이 뚫린다.** 선택 칸이 섞인 UNIQUE 는 **부분 고유 인덱스로 쪼갠다** (§14.2 실제 적용) |
| **타입 강제** | 안 함 (동적 타입 · `REAL` 칸에 문자열 저장됨) | 거부 | 서버에서 형 변환·검증 후 저장 |
| **불리언** | `INTEGER` 0/1 | `boolean` | 0/1 로 통일 + `CHECK IN (0,1)` |
| **시각** | `TEXT` `datetime('now','localtime')` | `timestamptz` | 기존 WORKS 관행(TEXT)을 유지 · 이관 시 일괄 변환 (WP-02 소관) |
| **자동번호** | `AUTOINCREMENT` | `IDENTITY`/`SERIAL` | 이관 매핑 (WP-02 소관) |
| **문자열 비교** | 기본 BINARY | collation 의존 | 상태코드는 **대문자 고정값**만 써서 영향 없게 |

## 15.4 결론

**B단계 스키마는 §15.1 범위 안에서만 DB 제약을 쓴다.**
겹침 배타·다른 표 참조·여러 행 종합 판정은 **전부 서버 함수**로 두고, DB 는 "같은 행 안에서 판정 가능한 것"만 지킨다.
→ 이렇게 하면 **SQLite 에서도 PostgreSQL 에서도 같은 규칙이 같은 방식으로** 지켜진다.

- **1건이라도 있으면 중단하고 별도 이관 판정을 받는다.** 짐작으로 진행하지 않는다

## 16.3 만약 그때 데이터가 있다면 (판정 기준만 미리 둔다)

- 진행 중 프로젝트의 기존 BOM: **설계책임자 확인 후 초기 Release 발행**
- 종료·과거 프로젝트: **운영 구매근거로 자동 전환하지 않음**
- 기존 구매·발주와 연결된 BOM 발견 시: **별도 영향표 작성**

## 18.4 ⭐ 자체 재검증에서 스스로 찾아 고친 것 (게이트 지적 아님)

B4-6 을 쓰면서 **제가 적은 제약이 실제로 작동하는지** 다시 따져 4건을 고쳤다. **정직하게 남긴다.**

| | 처음 쓴 것 | 무엇이 문제였나 | 어떻게 고쳤나 |
|---|---|---|---|
| 1 | `UNIQUE (release_id, sales_order_id, project_unit_id)` | 🔴 **작동하지 않는다.** 두 DB 모두 UNIQUE 안의 **NULL 을 서로 다른 값**으로 본다 → 호기 행은 `sales_order_id` 가 NULL 이라 **같은 호기를 몇 번이든** 넣을 수 있었다 | **부분 고유 인덱스 2개**로 쪼갬 (§14.2) + §15.3 에 차이 등재 |
| 2 | `UNIQUE (release_id, line_no, part_no)` | 🔴 **정상 데이터를 거부한다.** 실물 BOM 은 같은 품번이 **다른 구분에 여러 줄** 나오고, 시트가 여럿이면 `line_no` 도 겹친다. 스냅샷의 목적은 **원본 보존**인데 원본을 못 담는다 | **`snapshot_seq`** 신설 → `UNIQUE (release_id, snapshot_seq)` (§14.3) |
| 3 | `bom_release_items` · `bom_release_supersede` · `bom_change_impacts` 에 **삭제정책 없음** | 게이트 B4-6 이 요구한 항목인데 3개 표에서 빠져 있었다 | 세 표 모두 `ON DELETE RESTRICT` · 행 삭제 없음 명시 |
| 4 | 검증 무효(§4.4) → *"이미 발행됐으면 §8.4 를 따른다"* | 🔴 **§8.4 표에 그 경우가 없었다.** 가리키는 곳에 답이 없는 참조 | **§8.5 신설** — 구매근거 사용 여부로 두 갈래 · 무효가 상태를 **자동으로 바꾸지 않음** 명시 |

> ⭐ 1·2 는 **"제약을 적었다"와 "제약이 지킨다"가 다르다**는 사례다. B-1 시험(§17.4)에 **NULL 함정**·**스냅샷 중복** 항목을 넣어 실제로 막히는지 확인한다.
