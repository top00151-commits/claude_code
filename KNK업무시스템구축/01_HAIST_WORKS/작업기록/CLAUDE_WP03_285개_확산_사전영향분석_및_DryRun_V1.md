## 7. `project_items` FK 위반 84건 — 원인과 교차 여부

### 7.1 실체

`PRAGMA foreign_key_check` 84건은 **행 84개가 아니라 행 42개**입니다.
`project_items` 에는 FK 가 3개(`orders` · `customers` · `projects`) 있고, **한 행이 그중 2개(`orders`·`projects`)를 동시에 어겨** 84로 세어집니다.

| 항목 | 값 |
|---|---|
| 위반 행 | **42개** (`project_items`) |
| 어긴 FK | `orders(order_id)` · `projects(project_id)` |
| 참조하는 `project_id` | **1538 ~ 1563 (26개)** |
| 그 중 **실제 존재하는 프로젝트** | **0개** — 전부 삭제된 부모 |
| 다른 표의 위반 | **0건** (`project_unit*` 포함) |

**원인**: 프로젝트 26개가 삭제되면서 `project_items` 자식 42행이 남았습니다(FK 가 `NO ACTION` 이고
SQLite 는 `PRAGMA foreign_keys=ON` 인 연결에서만 강제하므로, 과거 삭제 경로가 자식을 정리하지 않으면 이렇게 남습니다).
WP-01 v5 에서 프로젝트 삭제에 전참조 가드를 넣었으므로 **앞으로는 같은 방식으로 늘어나지 않습니다.**

### 7.2 확산 대상과의 교차 — **없습니다**

| 확인 | 결과 |
|---|---|
| 위반 `project_id` ∩ 확산 대상 249개 | **0개** |
| 그 `project_id` 로 만들어진 호기 | **0대** |
| 그 `project_id` 에 딸린 수주·호기 표기 줄 | **0줄** (존재하지 않는 프로젝트이므로) |
| dry-run 으로 781대를 만든 **뒤** FK 위반 | **84건 — 증가 0** |

⭐ **게이트 §9.1 의 "완전히 무관함을 증명하면 별도 정비로 분리할 수 있다" 조건을 충족합니다.**
위반 행이 가리키는 프로젝트는 **하나도 존재하지 않고**, 확산 대상 249개와 **교집합이 공집합**이며,
781대를 만들어도 **위반이 1건도 늘지 않습니다.**

### 7.3 별도 정비 제안 (확산과 분리)

이 42행은 존재하지 않는 프로젝트·수주를 가리키므로 **업무상 조회·집계에 잡히지 않습니다**.
게이트가 제시한 3안 중 **"업무상 무효 데이터로 승인 후 격리"** 를 제안합니다.

- 즉시 삭제는 권하지 않습니다 — 왜 삭제됐는지 이력이 없어 되살릴 근거가 사라집니다.
- 별도 WP 로 ①42행 원문 보존(내보내기) ②무효 표시 ③삭제 여부 대표 판정, 순서로 처리
- **확산의 선행 조건으로 두지 않아도 됩니다**(교차 0 증명 완료)

한 관리번호 안에서 상태가 섞인 곳이 **0개**라, 관리번호 단위로 깨끗하게 묶입니다.

### 각 단계 공통 검증 기준

**실행 전**
1. 운영 DB 백업 + `integrity_check = ok`
2. 대상 관리번호별 **전체 칸 스냅샷**
3. dry-run 재실행 → 건수가 이 문서와 **일치**(다르면 중단)

**실행 후**
4. 대상 호기 수 = 예정 수 · 상태 분포 = 예정 분포
5. **실제 출하일 채워진 호기 0대**
6. 감사기록 수 = 쓰기 수 (1:1)
7. `foreign_key_check` **84건 그대로**(증가 0)
8. **재실행 시 변경 0건**(멱등)
9. 대상 **밖** 데이터 불변 (스냅샷 대조)
10. **화면 실측** — 목록의 신원/진행 칸, 진행 수량, 날짜 미확인 표시

**단계 종료**
11. 결과 보고 제출 → 대표 확인 후 다음 단계
12. 2·3단계 사이에 **기술영업팀 사용자 확인 1회** 추가 권장(대상이 커지기 전에)

### 예상 소요

dry-run 실측 기준 249개 전량 **13초**. 단계별로는 수 초 수준이며, 실제 소요의 대부분은
