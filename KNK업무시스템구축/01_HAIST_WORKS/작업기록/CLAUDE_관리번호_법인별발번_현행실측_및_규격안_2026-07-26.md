## 1. 결론 요약

규정 V1이 요구하는 **베트남 9자리 발번은 현재 구조로 불가능**하며, 그대로 두면 **번호 중복이 발생**한다.
코드 수정 없이 수기로 `V` 번호를 넣으면 순번 계산이 그 번호를 못 읽어 **같은 순번이 두 번 발급**된다.

| 규정 V1 요구 | 현행 | 판정 |
|---|---|---|
| §3 본사 8자리 `[순번3][구분][YYMM]` | ✅ 동일 | 충족 |
| §3 베트남 9자리 `[순번3][V][구분][YYMM]` | ❌ **8자리 고정** · 허용문자 `T·M·L·E·C·R` | **불가** |
| §5-2 시작 법인별 순번 독립 | ❌ 순번 기준 = **업무구분 + 연월**(법인 없음) | **미충족** |
| §5-3 관리번호 ↔ DB 시작법인 일치 검증 | ❌ DB에 시작법인 항목 없음 | **미충족** |
| §5-4 동시 발급 중복 차단 | ⚠ **읽고-쓰기 분리**(MAX 조회 후 INSERT) · DB 유일 제약 없음 | **보강 필요** |
| §5-5 법인 누락 시 본사 자동지정 제거 | — 해당 항목 자체가 없음 | 설계 필요 |
| §5-6 검색·조회·엑셀·API 9자리 지원 | ❌ 8자리 가정 코드 존재 | **미충족** |
| 취소 번호 재사용 금지 | ✅ `retire_mgmt_code` 봉인 | 충족 |

## 2. 현행 발번 실측 (`generate_mgmt_code`)

```
형식   : [일련3][업무구분][YYMM]                       ← 8자리 고정
허용   : T · M · L · E · C · R                          ← V 없음, R 은 규정 표에 없음
순번   : 같은 [업무구분 + 연월] 안에서 MAX + 1          ← 법인이 빠져 있음
스캔   : projects(+ C 는 consumable_orders, R 은 rnd_projects)
판독   : len(code)==8 and code[3]==구분 and code[4:]==연월
검증모드: 'A' + 2자리 + 구분 + 연월 (A01T2606) — 테스트 데이터
```

### 2.1 9자리를 넣으면 왜 깨지나
판독 조건이 **`len(code)==8`** 이고 구분 문자를 **`code[3]`** 한 자리로 읽는다.
`016VC2607`(9자리)은 두 조건 모두 어긋나 **순번 스캔에서 통째로 무시**된다.
→ 다음 발번이 그 번호를 못 보고 **같은 순번을 다시 발급**한다.

### 2.2 실데이터 (개발 사본 69건 · 2026-07-26)
- 규격 일치 **67건** / 불일치 2건(빈 관리번호 1 · `ZZZ2512` 1)
- 업무구분 분포 **T 52 · M 15** · **`V` 접두 0건**(규정 §1 "현재 데이터는 전부 본사"와 일치)

## 3. 규격안

### 3.1 형식
```
본사    : [순번3][업무구분][YYMM]        8자리   016C2607
베트남  : [순번3][V][업무구분][YYMM]     9자리   016VC2607
검증(A) : A[순번2][업무구분][YYMM]       8자리   A01T2606   (본사 · 테스트)
```
판독 정규식(WP-03 에서 이미 사용 중):
```
^(?:A\d{2}|\d{3})(V?)([TMLECR])(\d{4})$
```

### 3.2 순번 기준
> **발생 법인 + 업무구분 + 연월** 별로 각각 `001`부터.

2027년 1월 예시 — 서로 독립:
`001T2701`(본사 검사기) · `001C2701`(본사 소모품) · `001VT2701`(베트남 검사기) · `001VC2701`(베트남 소모품)

### 3.3 DB 시작 법인 (규정 §5-3)
- `projects.start_entity TEXT NOT NULL CHECK (start_entity IN ('KOR','VN'))` 신설(소모품·연구과제 도메인도 동일).
- 발번과 **같은 트랜잭션**에서 기록한다.
- **저장 전 대조**: 관리번호에서 읽은 법인 ≠ `start_entity` → **등록 중단**.
- ⛔ 누락 시 KOR 자동 지정 없음(규정 §5-5·§7).

### 3.4 동시 발급 중복 차단 (규정 §5-4)
현행은 `MAX(순번) 조회` → `INSERT` 가 분리돼 있어 동시 등록 시 같은 번호가 나올 수 있다.

- **DB 유일 제약**을 1순위로: `CREATE UNIQUE INDEX uq_projects_mgmt_code ON projects(mgmt_code) WHERE mgmt_code IS NOT NULL`
  (소모품·연구과제 도메인 포함 — 도메인이 나뉘어 있으므로 **발번대장 표 1개**로 통합 관리하는 방안을 권고)
- 발번+INSERT 를 **한 트랜잭션**으로 묶고, 유일 제약 위반 시 **재시도**(최대 N회).

### 3.5 기존 데이터
규정 §6 그대로 — 기존 번호에 `V` 추가·변환·재발급 **없음**. 전부 `start_entity='KOR'` 로 일괄 기록.

## 4. 영향 범위 (9자리 지원 · 규정 §5-6)

착수 전 전수 조사가 필요한 지점:

| 구분 | 확인 대상 |
|---|---|
| 발번 | `database.generate_mgmt_code` · `project_workflow.generate_mgmt_code`(별도 구현 존재) · 수동발행 검증 `_validate_manual_mgmt_code` · `/api/mgmt-code-check` |
| 판독 | `len(code)==8` · `code[3]` · `code[:3]` 같은 **자릿수 가정 코드 전수** |
| 화면 | 목록·검색·상세·인쇄(QR/발주서/세금계산서)·엑셀 내보내기 열 너비 |
| 연계 | 소모품(`consumable_orders`) · 연구과제(`rnd_projects`) · 메신저 통보 · BOM 업로드 매칭 |
| 권한 | 법인별 조회 범위(규정 §5-7) |

> ⚠ **`R`(연구과제)** 는 코드에 있으나 규정 표에 없다. 규정에 편입할지 확정 필요.
> ⚠ **발번 구현이 두 곳**(`database.py` · `project_workflow.py`)이다. 단일화 여부 확정 필요.

## 5. 단계 제안

1. 영향 범위 전수 조사(자릿수 가정 코드 grep + 화면·엑셀·인쇄)
2. `start_entity` 신설 + 기존 데이터 `KOR` 일괄 기록(순수 추가)
3. 발번 단일화 + 법인별 순번 + DB 유일 제약 + 트랜잭션·재시도
4. 관리번호 ↔ `start_entity` 대조 게이트
5. 9자리 지원 화면·엑셀·인쇄·API
6. 사본 DB 전체 시나리오 검증(규정 §5-10)
7. 게이트 판정 → 대표 승인 → 배포
