# 1. B단계가 푸는 문제 — 한 문장

**지금은 "엑셀을 올려 보드에 담아 둔 것"과 "구매팀이 돈을 써도 되는 확정본"이 같은 화면에 있다.**

# 2. 계층 분리 — 무엇이 어디에 속하는가

| 계층 | 누가 만드는가 | 무엇이 들어가는가 | 확정 방법 |
|---|---|---|---|
| **① 설계 BOM** | 설계팀 | 품명 · 품번/모델 · Maker · Specification · 단위 · **설계요구수량** · 설계 요구조건 | **Release 발행** |
| **② 업로드 검증** | 올린 사람 | 원본↔읽은값 · 읽은값↔저장값 · 중복시트 · 파싱 | 검증 상태 |
| **③ 구매검토** | 구매팀 | 협력사 · **단가 · 통화** · **구매납기** · 포장단위 · 환산 · 본사재고 배분 · 초과구매 · **VINA 참고재고** | 구매요청 |
| **④ 발주·입고·재고** | 구매팀 | 발주 · 입고 · 검수 · 재고원장 | (B단계 범위 밖) |

## 2.1 ⭐ 설계 Release 에 **구매값을 넣지 않는다**

**실물 흐름**: 설계팀 BOM 의 단가·납기 칸은 대개 **비어 있고 구매팀이 나중에 채운다.**
그런데 구매팀이 채운 값을 설계 Release 의 **확정값처럼 보존하면**, 설계가 확정하지 않은 숫자가 설계 확정본에 들어간다.

| | 설계 Release 스냅샷에 | |
|---|---|---|
| 품명 · 품번/모델 · Maker · Specification · 단위 · 설계요구수량 | **넣는다** | 설계가 통제하는 값 |
| 적용범위(§5.2) | **넣는다** | 어디에 쓰는 설계인지 |
| **단가 · 통화** | **넣지 않는다** | 구매값 |
| **구매납기** | **넣지 않는다** | 구매값 |
| 협력사 · 포장단위 · 환산 · 재고배분 · 초과구매 | **넣지 않는다** | 구매값 |
| **VINA 참고재고** | **넣지 않는다** (§11) | 구매검토 전용 |

### 2.2 설계가 특별히 지정한 것은 **설계 요구조건**으로 따로

설계가 *"이 Maker 여야 한다"* · *"이 날짜까지 필요하다"* 를 지정하는 경우가 있다.
이건 구매값이 아니라 **설계 요구조건**이므로 **별도 칸으로 구분해 Release 에 넣는다.**

| 칸 | 뜻 |
|---|---|
| `req_maker_fixed` | 지정 Maker (대체 불가 여부 포함) |
| `req_due_date` | 설계 요구납기 (구매납기와 다름) |
| `req_note` | 그 밖의 설계 요구조건 |

⚠ **구매팀이 채우는 `구매납기` 와 설계의 `요구납기` 는 다른 칸이다.** 같은 칸에 담지 않는다.

# 4. 검증 기록과 Release 차단

## 4.1 항목별 검증 상태

각 불일치 항목은 아래 넷 중 하나를 갖는다.

| 코드 | 사람 이름 | 뜻 |
|---|---|---|
| `OPEN` | **미해결** | 아직 아무도 안 봄 |
| `CONFIRMED_OK` | **확인됨(문제없음)** | 사람이 보고 "이대로 맞다" 고 판단 |
| `FIXED` | **수정됨** | 고쳤다고 표시함 — **이것만으로는 부족** |
| `HOLD` | **보류** | 판단을 미룸 |

## 4.2 ⭐ Release 허용 조건 (B-P0-4)

**허용** — 아래 둘 중 하나

1. 모든 항목이 **`확인됨(문제없음)`**
2. **`수정됨` + 재검증 성공 기록이 있음** (= 새 업로드로 다시 올려 일치 확인)

**차단** — 하나라도 있으면 막는다

- `미해결`
- **`보류`** ← 해결된 상태로 해석하지 못하게 명시
- **파싱 실패**
- **중복시트 미해결**

⛔ **사람이 `수정됨` 을 선택한 사실만으로 `VERIFIED` 가 되지 않는다.**

## 4.3 차단을 어디에 두는가 — 6개 층 전부

| 층 | 무엇 |
|---|---|
| DB | 제약·기본값으로 잘못된 상태 조합을 못 만들게 |
| 서버 함수 | 화면을 거치지 않고 직접 불러도 `PermissionError` |
| 라우트 | 403 / 검증 실패 응답 |
| 화면(HTML) | 버튼을 아예 안 그림 |
| 화면(JS) | 잠금 — **친절함이지 차단이 아님** |
| 안내문 | 왜 안 되는지 사람 말로 |

⛔ **화면에서 버튼만 숨기고 요청이 실행되는 상태는 차단으로 인정하지 않는다.**

## 4.4 검증 무효 (B-P1-1)

검증 완료 뒤 **잘못된 시트 선택·검증 오류**가 발견될 수 있다.

- **원본 업로드를 수정하지 않는다**
- 그 업로드를 `VERIFICATION_VOID` 로 만들어 **Release 근거로 쓰지 못하게** 한다
- **사유 · 처리자 · 일시**를 기록한다
- 데이터를 고치려면 **새 업로드**로 한다
- 이미 그 업로드로 Release 가 발행됐다면 §8.3 을 따른다

# 5. Release — 내용범위와 적용범위를 **나눈다**

## 5.1 내용범위 (무엇이 스냅샷에 담기나)

**한 Release 는 선택된 업로드의 활성 BOM 전체 스냅샷을 보존한다.**
품목 일부만 골라 Release 하지 않는다. 담기는 칸은 §2.1 표를 따른다.

## 5.2 ⭐ 적용범위 Effectivity (어디에 적용되나) — B-P0-2

**KNK 는 관리번호 1개에 수주번호가 여러 개 붙고, 발주 차수도 나뉜다.**
따라서 *"프로젝트 전체만"* 으로는 실제 업무를 담을 수 없다.

**Release 발행 시 적용범위를 반드시 선언한다.**

| 적용범위 | 뜻 |
|---|---|
| **관리번호 전체** | 그 관리번호에 붙은 모든 수주·장비에 적용 |
| **선택 수주번호** | 지정한 수주번호(들)에만 적용 — 한 관리번호에 여러 수주번호 연결 가능 |
| **선택 장비·호기** | 지정한 호기에만 적용 |
| **적용수량** | 몇 대분에 적용되는지 |

**규칙**

- `project_id`(관리번호) 는 **필수 기준**으로 유지한다
- 수주번호는 **선택 연결**이다
- ⚠ **호기는 선택 적용기준이며 구매업무의 최상위 필수 Key 가 아니다**
- **적용범위 변경은 기존 Release 수정이 아니라 새 Release 로 처리**한다

## 5.3 불변성

**발행된 Release 의 스냅샷은 절대 수정하지 않는다.** 고칠 일이 생기면 새 Release 를 발행한다.

# 6. Revision — 세 가지를 절대 섞지 않는다

| | 무엇 | 누가 매기나 | 예 |
|---|---|---|---|
| **외부 Revision** | 설계 도면·BOM 의 개정 표기 | 설계팀(회사 밖 규칙 포함) | `R1` · `VER.0` · 표기 없음 |
| **내부 Release 회차** | 우리 시스템이 발행한 확정본 순번 | 시스템 | `Rel.1` · `Rel.2` |
| **업로드 버전** | 파일을 몇 번째로 올렸나 | 시스템 | `v1` · `v2` |

## 6.1 ⭐ 외부 Revision 표기가 없는 파일 (B-P0-3)

실물 BOM 에는 `R1` · `VER.0` · **표기 없음**이 섞여 있다.
표기 없는 정상 파일을 영구 차단하면 안 된다.

| 상황 | 처리 |
|---|---|
| **자동 인식 실패** | **Release 차단** |
| 설계책임자가 **`외부 Revision 표기 없음`을 명시 선택 + 사유 기록** | **Release 가능** |
| 파일명에 `R1` 같은 글자가 있음 | **힌트로만 보여준다. Revision 확정값으로 자동 채택하지 않는다** |
| Release 시점 | 설계담당자가 **원문을 확인하거나 직접 입력**한다 |

⛔ 파일명에서 임의 추정하거나 자동 생성하지 않는다.

# 7. 승인 분리 (B-P0-5)

## 7.1 두 단계 · 항상 다른 사람

| 단계 | 누가 | 무엇을 | 전이 |
|---|---|---|---|
| **① Release 신청** | **설계담당자** (업로드한 사람) | 검증완료 업로드를 지목 + 적용범위 선언 | `VERIFIED` → `PENDING` |
| **② Release 발행** | **설계책임자** | 스냅샷·적용범위를 보고 발행 | `PENDING` → `RELEASED` |

## 7.2 ⛔ 자가승인 예외는 **열지 않는다**

- **신청자와 승인자는 항상 다른 사람이다**
- 설계담당자가 한 명뿐이면 **대표 또는 지정 임원이 대체 승인자**가 된다
- **대체 승인은 사유와 역할을 기록**한다
- **`SINGLE_APPROVER` 자가승인 예외는 V1 에서 열지 않는다**

> V2 에서 제가 "1인 예외를 열지 말지 대표 결정" 으로 남겨 둔 것은 재판정으로 닫혔다.

## 7.3 서버에서 막는 것

- ⛔ **신청자 = 승인자면 거부** (화면에서 숨기는 것으로 끝내지 않는다)
- ⛔ `VERIFIED` 가 아닌 업로드는 신청 자체가 안 된다
- ⛔ §4.2 차단 항목이 하나라도 있으면 신청 거부
- ⛔ **같은 적용범위**에 이미 `PENDING` 이 있으면 새 신청 거부

# 8. Release 상태와 대체 관계

## 8.1 상태

| 코드 | 사람 이름 | 뜻 |
|---|---|---|
| `PENDING` | **발행 대기** | 신청됨. 아직 구매근거 아님 |
| `RELEASED` | **발행됨** | ⭐ **이 상태만 구매근거로 쓸 수 있음** |
| `SUPERSEDED` | **대체됨** | 겹치는 적용범위의 새 Release 가 나옴. **내용은 불변 보존** |
| `CANCELLED` | **취소** | 잘못 발행했고 **구매근거로 쓰이지 않은** 경우만 |

## 8.2 ⭐ 대체는 **겹치는 적용범위에만** (재판정 §5.2)

**적용범위가 다른 Release 까지 무조건 대체하면 수주번호별·차수별 근거가 무너진다.**

- 새 Release 는 **동일하거나 겹치는 Effectivity** 의 기존 Release 와만 영향관계를 계산한다
- 겹치지 않는 Release 는 **그대로 유효**하다
- 겹침 판정 결과(무엇이 대체됐는지)를 **화면에 표시**한다

## 8.3 취소와 대체의 사용 기준 (B-P1-2)

| 상황 | 처리 |
|---|---|
| **설계 변경** | 새 Release 발행 + 기존은 `SUPERSEDED` |
| **잘못 발행 · 구매근거로 사용되지 않음** | `CANCELLED` |
| **이미 구매요청·발주에 사용됨** | ⛔ **취소로 지우지 않는다.** 새 Release + 영향분석(§10) |

# 9. 구매요청 연결 (B-P0-1)

## 9.1 ⛔ 구매요청 전체에 `release_id NOT NULL` 을 걸지 않는다

그렇게 하면 아래 정상 업무가 **전부 막힌다**.

- 공용재고 보충구매 · 예비품 구매 · 소모품 구매 · 긴급구매 · BOM 외 수동 구매요청

## 9.2 라인 단위로 연결한다

| 구매요청 **라인**의 근거유형 | 필수 항목 |
|---|---|
| **`BOM_RELEASE`** | **`bom_release_item_id` 필수** |
| `STOCK_REPLENISH`(공용재고 보충) | 사유 필수 |
| `SPARE`(예비품) | 사유 필수 |
| `CONSUMABLE`(소모품) | 사유 필수 |
| `URGENT`(긴급구매) | 사유 필수 |
| `MANUAL`(수동요청) | 사유 필수 |

**규칙**

- 연결은 **구매요청 문서 머리가 아니라 품목 라인 단위**다
- 한 구매요청서 안에 **근거유형이 섞여도 된다**
- **`RELEASED` 가 아니면 구매요청 금지** 는 **`BOM_RELEASE` 라인에만** 적용된다

# 11. 베트남 참고재고 (B-P0-7 · 대표 확정 2026-07-28)

## 11.1 설계 Release 에서 **제외**

VINA 참고재고는 **설계가 확정하는 값이 아니다.** Release 스냅샷에 넣지 않는다.

## 11.2 구매검토에서만 — **한 세트로** 저장·표시

| 항목 | 왜 필요한가 |
|---|---|
| **참고수량** | |
| **기준일시** | 오래된 수량이 현재 재고처럼 보이는 것을 막는다 |
| **확인자** | 누가 센 숫자인지 |
| **확인 출처 / 비고** | 어디서 온 숫자인지 |
| **`본사 가용재고·재고원장·자동차감에서 제외` 표시** | 화면에서 오해를 막는다 |

⛔ 위 다섯을 **한 세트로** 저장한다. 숫자만 저장하지 않는다.

## 11.3 쓰지 않는 곳

- 본사 **구매가능수량** 계산
- **재고원장** · **자동차감**

## 11.4 V1 제외

**베트남 재고원장 · 베트남 입출고 · 자동동기화는 V1 범위 밖이다.**

# 14. 기존 데이터 — 이관하지 않는다

## 14.1 근거 — B-0 읽기전용 실측 (2026-07-31 · 게이트 승인)

| 항목 | 결과 |
|---|---|

(이 문장은 재판정 §6.1 지시로 유지한다)

## 14.2 계약

- **과거 BOM 자동이관은 하지 않는다**
- **자동 `Rev.0` 일괄 발행 금지**
- **착수 직전 같은 읽기 전용 실측을 다시 실행**한다 (`_검증/b0_bom_readonly_audit.py`)
- **1건이라도 있으면 중단하고 별도 이관 판정을 받는다.** 짐작으로 진행하지 않는다

## 14.3 만약 그때 데이터가 있다면 (판정 기준만 미리 둔다)

- 진행 중 프로젝트의 기존 BOM: **설계책임자 확인 후 초기 Release 발행**
- 종료·과거 프로젝트: **운영 구매근거로 자동 전환하지 않음**
- 기존 구매·발주와 연결된 BOM 발견 시: **별도 영향표 작성**

# 15. 실행 단계와 시험

## 15.1 실행 전제 (재판정 §6.2)

⭐ **B단계 착수 전 `대상 DB 필수 스키마 점검 통과`를 확인한다.**

(수동 SQL 관리 자체는 **WP-02 소관** — 재판정 §6.2 승인)

## 15.2 단계 분할 — 각 단계마다 게이트 판정

| 단계 | 내용 | 산출물 |
|---|---|---|

| **B-6** | VINA 참고재고 세트(§11) + 알림(§12) | 화면 |

## 15.3 시험 계획 (각 단계 공통)

| 종류 | 내용 |
|---|---|
| 정상 | 검증완료 → 신청 → 발행 → 구매요청까지 한 바퀴 |
| **차단** | §4.2 네 가지 각각 · 신청자=승인자 · `PENDING` 중복 · 비 BOM 라인에 release 요구 안 함 |

| 불변 | 발행된 스냅샷이 어떤 경로로도 안 바뀜 |
| 회귀 | 기존 업로드·보드·파서 그대로 동작 |
| **변별력** | ⭐ 새 시험은 **고치기 전 코드에 먼저 돌려** 실패하는지 확인 |
