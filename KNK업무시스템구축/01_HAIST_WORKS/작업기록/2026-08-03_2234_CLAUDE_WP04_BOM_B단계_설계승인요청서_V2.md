## 1. ⭐ 신설 — Release 적용범위 계약 (V1 §1 앞에 붙는다)

### 1.1 Release 는 **무엇에 대한** 확정인가

V1 은 Release 의 *상태*는 정의했지만 **범위**를 정의하지 않았다. 이건 위험하다 —
"Release 됐다"는 말이 사람마다 다른 뜻이 되면, 구매팀은 있지도 않은 확정을 믿고 발주한다.

**계약(승인 요청):**

| 항목 | 정의 |
|---|---|
| **대상 단위** | **프로젝트(관리번호) 1건의 BOM 전체** — 시트별·유닛별 부분 Release 는 **만들지 않는다** |
| **포함 범위** | 그 시점 활성 품목 **전량**의 스냅샷 (품번·품명·제조사·수량·단가·통화·납기) |
| **제외 범위** | 구매처(KOR/VINA) 지정 · 발주 상태 · 재고 — **구매팀 운영값이지 설계 확정이 아니다** |
| **불변성** | 발행된 Release 의 스냅샷은 **절대 수정하지 않는다.** 고칠 일이 생기면 **새 Release 를 발행**한다 |
| **유효 기간** | 다음 Release 가 발행되면 자동 `SUPERSEDED`. 소급 무효화는 `CANCELLED` 로만 |

### 1.2 왜 "부분 Release" 를 안 만드는가

설계 1대분 BOM 은 유닛(구분)이 16개씩 되지만, **구매는 프로젝트 단위로 움직인다.**
부분 Release 를 허용하면 *"이 유닛은 확정, 저 유닛은 아직"* 이 섞여 **구매팀이 무엇을 사도 되는지 판단할 수 없다.**
필요하면 **자주 발행**하면 된다(Rev.1, Rev.2 …). 범위를 쪼개는 것보다 회차를 늘리는 쪽이 안전하다.

### 1.3 ⚠ 대표 확정이 필요한 지점

**베트남 재고는 참고수량만**이라는 대표 확정(2026-07-28)이 있다.
→ Release 스냅샷에 **VINA 재고를 넣지 않는다**(위 '제외 범위'에 포함). 이 해석이 맞는지 확인 요청.

## 2. ⭐ 신설 — 2단계 승인 (V1 §1.4 를 대체)

### 2.1 한 사람이 신청하고 그 사람이 발행하면 안 된다

V1 은 *"설계책임자가 Release 발행"* 으로 한 단계였다. 그러면 **올린 사람이 스스로 확정**할 수 있다.
BOM 은 곧 돈이므로 **두 사람이 관여**해야 한다.

### 2.2 두 단계

| 단계 | 누가 | 무엇을 | 상태 전이 |
|---|---|---|---|
| **① 발행 신청** | **올린 사람**(설계 담당) | 검증완료 업로드를 지목해 *"이걸로 확정 신청"* | `VERIFIED` → Release `PENDING` |
| **② 발행 승인** | **설계책임자**(신청자와 **다른 사람**) | 스냅샷 내용을 보고 발행 | `PENDING` → `RELEASED` |

**차단 조건 (서버에서 막는다)**

- ⛔ **신청자 = 승인자면 거부** — 화면에서 숨기는 것으로 끝내지 않는다
- ⛔ 검증완료(`VERIFIED`) 가 아닌 업로드는 신청 자체가 안 된다
- ⛔ 미해결 불일치·중복시트 미선택이 하나라도 있으면 신청 거부
- ⛔ 이미 `PENDING` 인 Release 가 있으면 새 신청 거부(하나씩 처리)

### 2.3 예외 — 1인 프로젝트

설계 담당이 1명뿐인 소규모 건에서는 ①②를 같은 사람이 할 수밖에 없다.
→ **대표 승인 시에만** 예외 허용. 그 경우 Release 에 `SINGLE_APPROVER` 표시를 남겨 **나중에 누가 봐도 알 수 있게** 한다.
(⚠ 이 예외를 열지 말지는 **대표 결정 사항**이다. 기본은 닫는 것을 권고한다.)

## 5. ⭐ 신설 — 되돌림 감지: **B단계에서 뺀다** (이미 구현됨)

### 5.1 무엇이었나

대표 리허설(2026-08-03)에서 실제로 일어난 일 — **예전 파일을 올리자 최신 설계변경 4건이 조용히 되돌아갔다.**
화면은 `변경 4` 라고 정직히 보여줬지만 *"이건 되돌리는 겁니다"* 라는 해석은 없었다.

### 5.2 대표 지시로 당일 구현 완료 (z1073f)

- **파일 이름·날짜로 '오래된 파일인가'를 추측하지 않는다.** 사람이 이름을 아무렇게나 붙이기 때문
- 대신 **이력만 본다**: 전에 `A→B` 를 했는데 이번이 `B→A` 면 그건 되돌림이다
- 미리보기에 **🔄 되돌림 N** + 어느 회차의 변경을 되돌리는지 지목 + 경고 문구
- ⛔ **막지 않는다** — 일부러 되돌리는 일도 있으므로 사실만 알리고 판단은 사람이 한다
- 검증 4/4 (특히 **진짜 새 변경에는 0** 이 나오는 변별력 확인) · 재현 키트 `_검증/test_revert.py`

**위치**: 브랜치 `ui/bom-board-align` — 대표 지시로 **A단계 판정 뒤 병합**. 운영 미반영.

### 5.3 B단계에서는 무엇이 남는가

되돌림 **감지**는 끝났다. B단계에서 다룰 것은 **Release 계층에서의 처리**다.

| 항목 | B단계 설계 |
|---|---|
| 발행된 Release 를 되돌리는 업로드 | 신청 단계에서 **경고를 넘어 사유 입력 요구** |
| 되돌림이 포함된 업로드로 Release 신청 | 승인자 화면에 **되돌림 목록을 반드시 표시** |

## 6. ⭐ 신설 — 리허설이 드러낸 것 (B단계 밖으로 넘김)

### 6.1 손으로 돌려야 하는 DB 파일 5개 → **WP-02 소관**

`users.name_vi` · `employee_no` 는 코드가 **34곳 / 32곳**에서 읽는데,
그 칸을 만드는 것은 자동 마이그레이션이 아니라 **`migrations/*.sql` 수동 파일 5개**다.

```
migrations/v5H226z56_자재모듈표준v1.sql
          v5H226z58_VAT_품목강화_v2.sql
          v5H226z109_employee_no.sql      ← 사번·베트남어 이름
          v5H226z110_groupware_rename.sql
          v5H226z115_task_photo.sql
```

**운영은 정상**(2026-05-30 적용됨). 그러나 **새 DB 를 만들면 그 칸이 없어 홈 화면부터 오류**다
(리허설용 임시 DB 에서 실제 재현 — `/home` 500). **빠뜨렸는지 알려주는 장치가 없다.**

→ **WP-02(DB 이관) 점검표에 "수동 SQL 5개 적용 확인" 을 넣어야 한다.** B단계 범위는 아니다.
