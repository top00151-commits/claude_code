# 1. B단계가 푸는 문제 — 한 문장

**설계가 확정한 BOM 과, 구매팀이 돈을 써도 되는 근거를 분리하고, 설계가 바뀌었을 때 각각 몇 개를 사야 하는지 시스템이 답하게 한다.**

> **왜 "몇 개"까지인가**: Release 를 남기는 것만으로는 부족하다.
> 수주 12대 중 5대만 설계가 바뀌면 **옛 BOM 7대분 · 새 BOM 5대분**을 각각 계산해야 한다.
> 그걸 사람이 엑셀로 하면 자재구매센터를 만든 이유가 없어진다.

# 2. 계층 분리

| 계층 | 누가 만드는가 | 무엇이 들어가는가 | 확정 방법 |
|---|---|---|---|
| **① 설계 BOM** | 설계팀 | 품명 · 품번/모델 · Maker · Specification · 단위 · **대당 설계요구수량** · 설계 요구조건 | **Release 발행** |
| **② 업로드 검증** | 올린 사람 | 원본↔읽은값 · 읽은값↔저장값 · 중복시트 · 파싱 | 검증 상태 |
| **③ 구매검토** | 구매팀 | 협력사 · **단가 · 통화** · **구매납기** · 포장단위 · 환산 · 본사재고 배분 · 초과구매 · **VINA 참고재고** | 구매요청 |
| **④ 발주·입고·재고** | 구매팀 | 발주 · 입고 · 검수 · 재고원장 | (연결 기준만 B단계에서 확정) |

## 2.1 ⭐ 설계 Release 에 **구매값을 넣지 않는다**

설계팀 BOM 의 단가·납기 칸은 대개 **비어 있고 구매팀이 나중에 채운다.**
구매팀이 채운 값을 설계 Release 에 보존하면, **설계가 확정하지 않은 숫자가 설계 확정본에 들어간다.**

| | 설계 Release 스냅샷에 | |
|---|---|---|
| 품명 · 품번/모델 · Maker · Specification · 단위 · **대당 설계요구수량** | **넣는다** | 설계가 통제하는 값 |
| 적용범위(§5) | **넣는다** | 어디에 쓰는 설계인지 |
| **단가 · 통화** | **넣지 않는다** | 구매값 |
| **구매납기** | **넣지 않는다** | 구매값 |
| 협력사 · 포장단위 · 환산 · 재고배분 · 초과구매 | **넣지 않는다** | 구매값 |
| **VINA 참고재고** | **넣지 않는다** (§12) | 구매검토 전용 |

## 2.2 설계가 특별히 지정한 것은 **설계 요구조건**으로 따로

| 칸 | 뜻 |
|---|---|
| `req_maker_fixed` | 지정 Maker (대체 불가 여부 포함) |
| `req_due_date` | **설계 요구납기** (구매납기와 다름) |
| `req_note` | 그 밖의 설계 요구조건 |

⚠ **구매팀이 채우는 `구매납기` 와 설계의 `요구납기` 는 다른 칸이다.** 같은 칸에 담지 않는다.

# 4. 검증 기록과 Release 차단

## 4.1 항목별 검증 상태

| 코드 | 사람 이름 | 뜻 |
|---|---|---|
| `OPEN` | **미해결** | 아직 아무도 안 봄 |
| `CONFIRMED_OK` | **확인됨(문제없음)** | 사람이 보고 "이대로 맞다" 고 판단 |
| `FIXED` | **수정됨** | 고쳤다고 표시함 — **이것만으로는 부족** |
| `HOLD` | **보류** | 판단을 미룸 |

## 4.2 Release 허용 조건

**허용** — 아래 둘 중 하나

1. 모든 항목이 **`확인됨(문제없음)`**
2. **`수정됨` + 재검증 성공 기록이 있음** (= 새 업로드로 다시 올려 일치 확인)

**차단** — 하나라도 있으면 막는다

- `미해결` · **`보류`** · **파싱 실패** · **중복시트 미해결**

⛔ **사람이 `수정됨` 을 선택한 사실만으로 `VERIFIED` 가 되지 않는다.**

## 4.3 차단을 어디에 두는가 — 6개 층 전부

| 층 | 무엇 |
|---|---|
| DB | 제약·트리거로 잘못된 상태 조합을 못 만들게 |
| 서버 함수 | 화면을 거치지 않고 직접 불러도 `PermissionError` |
| 라우트 | 403 / 검증 실패 응답 |
| 화면(HTML) | 버튼을 아예 안 그림 |
| 화면(JS) | 잠금 — **친절함이지 차단이 아님** |
| 안내문 | 왜 안 되는지 사람 말로 |

⛔ **화면에서 버튼만 숨기고 요청이 실행되는 상태는 차단으로 인정하지 않는다.**

## 4.4 검증 무효

- **원본 업로드를 수정하지 않는다**
- `VERIFICATION_VOID` 로 만들어 **Release 근거로 쓰지 못하게** 한다
- **사유 · 처리자 · 일시**를 기록한다
- 데이터를 고치려면 **새 업로드**로 한다
- 이미 그 업로드로 Release 가 발행됐다면 **§8.6**

# 5. Release 적용범위 — 장비대수를 **고정**한다

## 5.1 내용범위 (무엇이 스냅샷에 담기나)

**한 Release 는 선택된 업로드의 활성 BOM 전체 스냅샷을 보존한다.** 품목 일부만 골라 Release 하지 않는다.

## 5.2 적용범위 유형 4종

| `scope_type` | 사람 이름 | 적용대상 |
|---|---|---|
| **`PROJECT_SNAPSHOT`** | **관리번호 전체 (발행 시점)** | 발행 시점에 그 관리번호 아래 있는 수주번호 전체 |
| **`SALES_ORDER_SET`** | **선택 수주번호** | 선택한 수주번호 1개 이상 |
| **`UNIT_SET`** | **선택 호기** | 선택한 **확정(CONFIRMED) 호기** 1개 이상 |
| **`SALES_ORDER_QUANTITY`** | **수주번호 + 적용대수** | 선택 수주번호 + 사람이 정한 적용대수 |

### 5.2.1 ⭐ 모든 유형이 **행으로 펼쳐져 저장**된다

⚠ V4 는 `PROJECT_SNAPSHOT` 을 추상으로 뒀다. **V5 에서는 발행 시점에 수주번호별 행으로 펼친다.**
그래야 각 수주의 장비대수를 고정할 수 있다.

| `scope_type` | `bom_release_effectivities` 행 |
|---|---|
| `PROJECT_SNAPSHOT` | 발행 시점 관리번호 아래 **수주번호마다 1행** |
| `SALES_ORDER_SET` | 선택 **수주번호마다 1행** |
| `UNIT_SET` | 선택 **확정 호기마다 1행** |
| `SALES_ORDER_QUANTITY` | 선택 **수주번호마다 1행** (+ 사람이 정한 대수) |

### 5.2.2 ⭐⭐ `equipment_qty_snapshot` — 모든 행이 장비대수를 고정한다

| 유형 | `equipment_qty_snapshot` |
|---|---|
| `PROJECT_SNAPSHOT` | 발행 시점 **각 수주번호의 확정 장비대수**를 복사·고정 |
| `SALES_ORDER_SET` | 선택 수주번호의 **발행 시점 확정 장비대수**를 복사·고정 |
| `UNIT_SET` | 호기 1행당 **`1` 고정** |
| `SALES_ORDER_QUANTITY` | **사람이 확정한 적용대수** · 사유 필수 |

- **`NOT NULL` · `>= 1`**
- **발행 후 절대 수정하지 않는다**

> **왜 고정하나**: 수주 표의 현재 수량을 나중에 다시 읽으면, **수주 수량이 바뀔 때 과거 Release 의
> 필요부품 수량도 소급해서 바뀐다.** Release 불변 원칙과 정면으로 충돌한다.

### 5.2.3 부품 필요수량 = 곱셈으로만

```
부품 필요수량 = qty_per_equipment × 유효 equipment_qty_snapshot
```

- `qty_per_equipment` = Release 품목의 **대당 설계요구수량** (`bom_release_items`)
- `유효 equipment_qty_snapshot` = **잔량**(§8.3) — 대체된 만큼 빠진 값
- ⛔ **부품 필요수량을 스냅샷에 저장하지 않는다.** 잔량이 바뀌면 틀린 값이 남는다

### 5.2.4 미래는 자동으로 들어오지 않는다

- **`PROJECT_SNAPSHOT` 은 발행 시점의 스냅샷이다.** 이후 생기는 수주번호·호기는 **자동 편입하지 않는다**
- 새 수주에 적용하려면 **새 Release 를 발행**한다
- 화면에는 **`관리번호 전체 (2026-08-05 기준)`** 처럼 **발행 시점을 함께 표시**한다

### 5.2.5 호기는 **확정 호기만**

- `UNIT_SET` 에는 **`project_units.unit_state='CONFIRMED'` 인 호기만**
- **개발·미확정(`PROVISIONAL`) 호기는 번호·구성이 계속 바뀌므로** Effectivity 로 쓰지 않는다 (WP-03 확정)
- 취소(`CANCELLED`) 호기도 넣을 수 없다
- 미확정 단계에서 범위를 좁혀야 하면 **`SALES_ORDER_QUANTITY`** 를 쓴다

## 5.3 ⭐⭐ 장비대수를 어디서 읽는가 — 실측으로 확정 (게이트 §2)

### 5.3.1 실측 결과 (2026-08-04 00:0x · 운영 읽기 전용)

| 후보 | 실측 |
|---|---|
| **A안** — `order_items` 중 정식 호기 라벨(z779 `^\d+호기$`) **행 수** | 448개 수주 · **851 행** |
| **B안** — 그 행들의 `qty` 합 | **851** (= A안) |
| **C안** — `project_items` 중 `shipment_form='ASSEMBLY'` 의 `qty` 합 | 467개 수주 |

| 검사 | 결과 |
|---|---|
| 호기 행인데 `qty ≠ 1` | **0 행** |
| 호기 행인데 `qty` 가 정수 아님 | **0 행** |
| 🔴 A안·C안 **값이 다른 수주** | **3 건** |
| 🔴 A안에만 있음 / C안에만 있음 | **45 / 64** |

⭐ **A안 = B안** 은 851행 전수에서 성립한다 (WP-03 z1048 *"호기 대수 = 행 수"* 실증).
🔴 **A안 ≠ C안 이 112건** 있다.

### 5.3.2 ⭐ A안은 **기본 제안값**이다 — 자동 확정값이 아니다 (게이트 §2.1)

**A안(`order_items` 정식 호기 라인 행 수)을 기본 제안값으로 쓴다.**
근거: 851행 전수 `qty=1` · WP-03 호기 규칙과 일치.

⛔ **그러나 자동 확정하지 않는다.**

1. 개발호기와 호기정보는 **변경될 수 있다** (대표 확정 사항)
2. `project_items` 와 **112건이 어긋난다**
3. **호기는 구매업무의 최상위 필수 Key 가 아니다**

### 5.3.3 Release 발행 화면 계약 (게이트 §2.2)

**화면에 아래 6가지를 함께 보인다.**

| | 무엇 |
|---|---|
| 1 | **A안** — 정식 호기 라인 행 수 |
| 2 | **C안** — `project_items` ASSEMBLY `qty` |
| 3 | **두 값의 일치·불일치** |
| 4 | 확정할 **`equipment_qty_snapshot`** |
| 5 | 불일치 시 **확인사유** |
| 6 | **확인자 · 확인일시** |

**처리규칙**

| 상황 | 처리 |
|---|---|
| **A = C** | A값을 **기본 제안**하되 **사람이 확인**한다 |
| **A ≠ C** | **경고**하고 확정대수·**사유를 사람이 입력**한다 |
| **A만 있음** / **C만 있음** | 있는 값을 **참고로 보이되 사유를 남긴다** |
| **둘 다 없음** | 수동 확정대수와 **사유를 필수**로 한다 |
| **발행 후** | `equipment_qty_snapshot` 을 **변경하지 않는다** |

⛔ **시스템이 A·C 중 하나를 임의로 고르지 않는다.** 어느 경우에도 **확인자와 확인일시가 남는다.**

**발행된 Release 의 스냅샷은 절대 수정하지 않는다.** 고칠 일이 생기면 새 Release 를 발행한다. (강제 방법 = §16)

# 6. Revision — 세 가지를 절대 섞지 않는다

| | 무엇 | 누가 매기나 | 예 |
|---|---|---|---|
| **외부 Revision** | 설계 도면·BOM 의 개정 표기 | 설계팀(회사 밖 규칙 포함) | `R1` · `VER.0` · 표기 없음 |
| **내부 Release 회차** | 우리 시스템이 발행한 확정본 순번 | 시스템 | `Rel.1` · `Rel.2` |
| **업로드 버전** | 파일을 몇 번째로 올렸나 | 시스템 | `v1` · `v2` |

## 6.1 외부 Revision 표기가 없는 파일

| 상황 | 처리 |
|---|---|
| **자동 인식 실패** | **Release 차단** |
| 설계책임자가 **`외부 Revision 표기 없음`을 명시 선택 + 사유 기록** | **Release 가능** |
| 파일명에 `R1` 같은 글자가 있음 | **힌트로만 보여준다. 확정값으로 자동 채택하지 않는다** |
| Release 시점 | 설계담당자가 **원문을 확인하거나 직접 입력**한다 |

⛔ 파일명에서 임의 추정하거나 자동 생성하지 않는다.

# 7. 신청·승인·반려

## 7.1 세 역할

| 역할 | 누구 | 규칙 |
|---|---|---|
| **업로더** `uploaded_by` | 파일을 등록한 사람 | 보조·대행 가능 |
| **신청자** `requested_by` | 그 설계를 **책임지고** Release 를 요청할 권한이 있는 설계담당자 | **업로더와 같아도 되고 달라도 된다** |
| **승인자** `approved_by` | 설계책임자 (또는 §7.3 대체 승인자) | ⛔ **신청자와 반드시 다르다** |

## 7.2 전이

| 단계 | 누가 | 무엇을 | 전이 |
|---|---|---|---|
| **① 신청** | 신청자 | 검증완료 업로드 지목 + 적용범위·**확정대수** 선언 | (생성) → `PENDING` |
| **② 발행** | 승인자 | 스냅샷·적용범위·대수를 보고 발행 | `PENDING` → `RELEASED` |
| **②′ 반려** | 승인자 | 잘못된 신청을 되돌림 | `PENDING` → `REJECTED` |

## 7.3 ⛔ 자가승인 예외는 열지 않는다

- **신청자와 승인자는 항상 다른 사람이다**
- 설계담당자가 한 명뿐이면 **대표 또는 지정 임원이 대체 승인자**가 된다
- **대체 승인은 `approver_role` 과 `substitute_reason` 을 필수로 기록**한다
- **`SINGLE_APPROVER` 자가승인 예외는 V1 에서 열지 않는다**

## 7.4 반려

| | 계약 |
|---|---|
| 전이 | **`PENDING` → `REJECTED`** |
| 누가 | 승인자 (신청자는 자기 신청을 반려할 수 없다) |
| **사유** | **필수.** 빈 값이면 거부 |
| 기록 | **반려자 · 반려사유 · 반려일시**. 신청자·신청일시도 보존 |
| 지위 | ⛔ **반려된 신청은 구매근거가 아니다** |
| 재신청 | **새 신청(새 행)** 으로 만든다. 반려된 행을 되살리지 않는다 |
| 화면 | 신청자에게 **왜 반려됐는지** 보인다 |

## 7.5 서버에서 막는 것

- ⛔ **신청자 = 승인자면 거부**
- ⛔ `VERIFIED` 가 아닌 업로드는 신청 자체가 안 된다
- ⛔ §4.2 차단 항목이 하나라도 있으면 신청 거부
- ⛔ **같거나 겹치는 적용대상**에 이미 `PENDING` 이 있으면 새 신청 거부 (§8.5)
- ⛔ **미확정·취소 호기**를 `UNIT_SET` 에 넣으면 거부
- ⛔ `equipment_qty_snapshot` 이 없거나 1 미만이면 거부
- ⛔ **A≠C 인데 확인사유가 없으면 거부** (§5.3.3)
- ⛔ **초과 차감**이면 거부 (§8.3.3)

# 8. Release 상태 · 대체관계 · **잔량 자동계산**

## 8.1 상태

| 코드 | 사람 이름 | 뜻 |
|---|---|---|
| `PENDING` | **발행 대기** | 신청됨. 아직 구매근거 아님 |
| `REJECTED` | **반려** | 승인자가 되돌림. 구매근거 아님 |
| `RELEASED` | **발행됨** | ⭐ **이 상태만 구매근거로 쓸 수 있음** |
| `SUPERSEDED` | **대체됨** | **모든 Effectivity 의 잔량이 0** 이 됨. 내용은 불변 보존 |
| `CANCELLED` | **취소** | 잘못 발행했고 **구매근거로 쓰이지 않은** 경우만 |

## 8.2 ⛔ `PARTIALLY_SUPERSEDED` 상태코드를 만들지 않는다

- 상태 칸에 **부분대체 코드를 두지 않는다**
- 부분 대체는 **`bom_release_supersede` 관계에서 계산**한다
- **잔량이 남으면 `RELEASED` 를 유지**한다

> **왜**: 상태코드를 하나 더 만들면 *"부분대체도 구매근거가 되나?"* 를 매번 다시 판단해야 한다.
> `RELEASED` 만 구매근거라는 규칙을 그대로 두고, **어느 범위가 얼마나 죽었는지는 관계표가 답한다.**

## 8.3 ⭐⭐ 잔량 계산 — **시스템이 한다** (게이트 P0-2)

### 8.3.1 계산식

```
Effectivity 유효 잔량 (remaining_qty)
  = equipment_qty_snapshot
  − Σ (그 Effectivity 를 덮은 관계들의 overlap_equipment_qty)

  단, 합계에 세는 관계는 new_release.status ∈ {RELEASED, SUPERSEDED} 인 것만.
      (REJECTED · CANCELLED 인 Release 가 만든 관계는 세지 않는다 — 차감이 되살아난다)
```

### 8.3.2 12대 → 5대 (게이트가 든 실제 시나리오)

| | |
|---|---|
| `Rel.1` Effectivity E1 | 수주A · `equipment_qty_snapshot = 12` |
| `Rel.2` Effectivity E2 | 수주A · `equipment_qty_snapshot = 5` |
| 관계 1행 | `new=Rel.2 · old=Rel.1 · old_effectivity=E1 · new_effectivity=E2 · overlap_equipment_qty=5 · kind=PARTIAL_QTY` |
| **E1 잔량** | **12 − 5 = 7** |
| **E2 잔량** | **5** |
| `Rel.1` 상태 | 잔량 7 > 0 → **`RELEASED` 유지** |
| 품목별 필요수량 | `Rel.1` = 대당수량 × **7** / `Rel.2` = 대당수량 × **5** |

⛔ **사람이 7을 계산하지 않는다. 시스템이 답한다.**

### 8.3.3 강제규칙

| | 규칙 |
|---|---|
| 1 | **`overlap_equipment_qty` 는 기존 유효 잔량을 초과할 수 없다** |
| 2 | 신규 Release 발행과 잔량차감 관계 생성은 **한 트랜잭션**에서 처리한다 |
| 3 | **잔량이 0 인 Effectivity 만** 전부 대체된 것으로 본다 |
| 4 | **기존 Release 의 모든 Effectivity 잔량이 0 일 때만** `SUPERSEDED` 로 바꾼다 |
| 5 | 일부 잔량이 남으면 `RELEASED` 를 유지하고 **화면에 유효 잔량을 표시**한다 |
| 6 | ⛔ **잔량 계산을 사람이 수기로 판정하게 두지 않는다** |

> ⚠ 규칙 1 은 **다른 행들의 합계**를 봐야 하므로 DB `CHECK` 로 불가하다 → **서버 + 트랜잭션**(§15.8).

### 8.3.4 겹침 판정 — 적용대상 단위로 펼쳐서 비교

모든 유형이 이미 행으로 펼쳐져 있으므로(§5.2.1), **같은 `sales_order_id` 또는 같은 `project_unit_id`** 를 가리키는 행끼리 비교한다.

| 상황 | `overlap_kind` | `overlap_equipment_qty` |
|---|---|---|
| 기존 행의 잔량 **전부**를 덮음 | **`FULL`** | 기존 잔량 전체 |
| 기존 행의 잔량 **일부**만 덮음 | **`PARTIAL_QTY`** | 덮는 만큼 |

### 8.3.5 동시 `PENDING` 차단

- **같거나 겹치는 적용대상**에 이미 `PENDING` 이 있으면 새 신청을 거부한다
- 판정은 §8.3.4 와 같다

## 8.4 ⭐ "지금 적용되는 Release" 조회 — **목록이지 하나가 아니다** (게이트 P0-3)

⚠ V4 는 *"가장 최근 Release 하나가 이긴다"* 라고 했다. **부분수량에서는 틀렸다.**
12대 중 5대만 바뀌면 **`Rel.1` 7대와 `Rel.2` 5대가 동시에 유효**하다.

**조회 결과는 아래를 담은 목록이다.**

| 반환값 | 뜻 |
|---|---|
| **Release** | 적용 중인 확정본 |
| **Effectivity** | 대상 수주·호기 |
| **유효 장비대수** | 대체관계 차감 후 남은 수량 (§8.3.1) |
| **품목별 필요수량** | 대당수량 × 유효 장비대수 |

**규칙**

- 전 범위가 새 Release 로 덮인 대상은 **최신 Release 만** 남는다 (잔량 0 은 목록에서 빠진다)
- 부분수량이면 **구 Release 잔량과 신 Release 수량을 함께** 반환한다
- 구매검토 화면은 **두 Release 별 유효대수와 필요부품 수량을 분리해** 보여 준다
- `PENDING` · `REJECTED` · `CANCELLED` 는 후보에서 뺀다

## 8.5 화면 표시

- 기존 Release 화면에 **`일부 범위 대체`** 를 **상태와 별도로** 표시한다
- **어느 수주·호기가 얼마나 대체됐는지** · **남은 잔량**을 함께 보인다
- 남은 잔량이 **아직 유효한 구매근거**이기 때문이다

## 8.6 취소 · 무효 업로드 처리

| 상황 | 처리 |
|---|---|
| **설계 변경** | 새 Release 발행 + 겹치는 기존은 §8.3 규칙대로 |
| **잘못 발행 · 구매근거로 사용되지 않음** | `CANCELLED` (사유 필수) |
| **이미 구매요청·발주에 사용됨** | ⛔ **취소로 지우지 않는다.** 새 Release + 영향분석(§11) |
| **신청이 잘못됨 (발행 전)** | `REJECTED` |
| **근거 업로드가 `VERIFICATION_VOID` 인데 이미 발행됨** | 아래 |

**무효 업로드로 이미 Release 가 발행된 경우**

| 그 Release 가 | 처리 |
|---|---|
| **구매근거로 쓰인 적 없음** | `CANCELLED` + 사유에 **무효 업로드 번호**를 적는다 |
| **이미 구매요청·발주에 쓰임** | ⛔ **취소하지 않는다.** 새 업로드 → 새 Release + **영향분석(§11)** |

- 어느 경우든 **원 Release 스냅샷은 지우지 않는다**
- 화면에 **`근거 업로드가 무효 처리됨`** 을 상태와 **별도로** 표시한다
- ⛔ **무효 처리가 Release 상태를 자동으로 바꾸지 않는다.** 사람이 위 표대로 판단한다

# 9. 구매요청 ↔ Release 연결 (게이트 P0-4)

## 9.1 ⛔ 구매요청 전체에 `release_id NOT NULL` 을 걸지 않는다

그렇게 하면 아래 정상 업무가 **전부 막힌다**: 공용재고 보충 · 예비품 · 소모품 · 긴급구매 · BOM 외 수동 요청

## 9.2 근거유형은 **라인 단위**

| `material_request_items.source_type` | 필수 |
|---|---|
| **`BOM_RELEASE`** | **§9.3 배분행이 1개 이상** |
| `STOCK_REPLENISH`(공용재고 보충) | `source_reason` 필수 |
| `SPARE`(예비품) | `source_reason` 필수 |
| `CONSUMABLE`(소모품) | `source_reason` 필수 |
| `URGENT`(긴급구매) | `source_reason` 필수 |
| `MANUAL`(수동요청) | `source_reason` 필수 |

- 한 구매요청서 안에 **근거유형이 섞여도 된다**
- **`RELEASED` 가 아니면 구매요청 금지** 는 **`BOM_RELEASE` 라인에만** 적용된다

## 9.3 ⭐ `bom_release_item_id` 하나로는 부족하다 — 배분표를 둔다

⚠ **같은 Release 품목이 여러 수주·호기·적용대수에 걸친다.** 품목 ID 만으로는 **어느 적용범위의 구매인지 알 수 없다.**

```
material_request_item_release_allocations
```

| 칸 | 뜻 |
|---|---|
| `material_request_item_id` | 어느 구매요청 라인인가 |
| `bom_release_item_id` | 어느 Release 품목인가 |
| **`release_effectivity_id`** | **어느 적용범위(수주·호기)의 몫인가** |
| `allocated_equipment_qty` | 그 적용범위에서 **몇 대분**을 사는가 |
| `allocated_part_qty` | 그래서 **부품 몇 개**인가 |
| 작성자 · 작성일시 | |

**규칙**

| | |
|---|---|
| 1 | **`BOM_RELEASE` 라인은 배분행이 1개 이상** 있어야 한다 |
| 2 | **한 구매요청 라인이 여러 Effectivity 의 수량을 묶어** 구매할 수 있다 |
| 3 | 배분된 **장비대수·부품수량은 해당 Effectivity 의 유효 잔량·필요수량을 초과할 수 없다** |
| 4 | 초과구매가 필요하면 **D-11 규칙**대로 — 구매담당자가 **구매팀장에게 보고**, 금액이 크면 **설계담당자에게 대체품 요청**으로 분리 |
| 5 | **비BOM 근거유형은 이 표를 쓰지 않고** `source_reason` 을 쓴다 |

⛔ **`material_request_items.bom_release_item_id` 단일 칸만으로 구현하는 안은 폐기한다.**

# 11. 발주 후 BOM 변경 — 품목·Effectivity 단위 (게이트 P0-5)

## 11.1 계약

| | |
|---|---|
| 1 | **기존 Release · 구매요청 · 발주 근거는 수정·삭제하지 않는다** |
| 2 | 새 Release 발행 시 **기존 구매요청·발주에 영향이 있는지 표시**한다 |
| 3 | **영향 미검토 상태인 변경품목은 추가 구매요청을 차단**한다 |
| 4 | 발주 취소 · 수량변경 · 대체품 전환은 **구매 변경이력으로 보존**한다 |

## 11.2 ⭐ 무엇이 바뀌었는지를 **품목과 적용범위 단위**로 기록한다

⚠ V4 는 새 Release 와 구매요청/발주 라인만 이었다. **어느 BOM 품목이 어느 적용범위에서 바뀌었는지가 없어
"변경품목만 차단" 을 구현할 수 없었다.**

`bom_change_impacts` 가 갖는 관계:

| 칸 | |
|---|---|
| `new_release_id` | 어느 Release 발행이 이 영향을 만들었나 |
| `old_release_item_id` / `new_release_item_id` | **어느 품목이** 바뀌었나 |
| `old_effectivity_id` / `new_effectivity_id` | **어느 적용범위에서** 바뀌었나 |
| `material_request_item_id` (선택) | 영향받는 구매요청 라인 |
| `po_item_id` (선택) | 영향받는 발주 라인 |
| `change_kind` | **추가 / 삭제 / 수량변경 / 사양변경 / Maker변경 / 대체품** |
| `impact_state` · 검토자 · 사유 · 일시 | |

- **품목 추가**는 `old_release_item_id` 가 없고, **품목 삭제**는 `new_release_item_id` 가 없다 — **허용**
- ⛔ **둘 다 NULL 인 행은 금지**

## 11.3 ⭐ `SET NULL` + **상세 스냅샷** (게이트 §3)

`po_items.po_id` 가 **`ON DELETE CASCADE`** 이므로(실측), 발주가 지워지면 발주 라인도 사라진다.
영향기록이 그 라인을 `RESTRICT` 로 붙들면 **발주 삭제 업무 자체가 잠긴다.**

### 11.3.1 계약

| | |
|---|---|
| `po_item_id` | **FK `ON DELETE SET NULL`** |
| `material_request_item_id` | **FK `ON DELETE SET NULL`** |
| 목적 | 참조가 끊겨도 **감사근거가 남게** |

### 11.3.2 필수 스냅샷 — 문서번호·줄번호만으로는 부족하다

**발주 영향**

| 칸 |
|---|
| `po_number_snapshot` |
| `po_line_no_snapshot` |
| `part_no_snapshot` |
| `ordered_qty_snapshot` |
| `po_status_snapshot` |

**구매요청 영향**

| 칸 |
|---|
| `request_no_snapshot` |
| `request_line_no_snapshot` |
| `requested_part_no_snapshot` |
| `requested_qty_snapshot` |
| `request_status_snapshot` |

> ⭐ 이 방식은 **저장소가 이미 쓰는 것**이다 — `po_items` 자신이 `part_no_snapshot`·`part_name_snapshot`·
> `spec_snapshot` 을 갖고, `project_units.seed_order_item_id` 도 이미 `SET NULL` 이다(실측 확인).

### 11.3.3 ⛔ `SET NULL` 은 **삭제 권한을 넓히는 규칙이 아니다**

> 근거: 게이트 판정 2026-08-04 00:10 · 3장 3절

| | |
|---|---|
| 1 | **작성중·미발행 발주만** 기존 WP-01 가드 범위에서 물리삭제 가능 |
| 2 | **발주완료 이후에는 물리삭제 금지** — 취소·변경이력으로 처리 |
| 3 | **입고·검수·세금계산서·변경영향에 사용된 발주는 물리삭제 금지** |
| 4 | `SET NULL` 이 발동해도 **영향기록과 스냅샷은 삭제하지 않는다** |

⛔ **"SET NULL 이니까 지워도 된다" 로 읽으면 안 된다.** 이건 사고가 나도 기록이 남게 하는 **안전장치**다.

### 11.3.4 ⭐ 왜 어떤 표는 `SET NULL` 이고 어떤 표는 `RESTRICT` 인가

같은 `po_items` 를 가리키는데 정책이 다르다. **일부러다. 통일하지 않는다.**

| 표 | 정책 | 그 표가 무엇인가 | 그래서 |
|---|---|---|---|
| **`bom_change_impacts`** (§15.8) | **`SET NULL`** | **기록**(감사) — *"그때 이런 영향이 있었다"* | 발주가 사라져도 **기록은 남아야** 하고, 기록이 **삭제를 막을 이유는 없다**. 스냅샷 5종이 사실을 보존한다 |
| **`po_item_request_allocations`** (§15.7) | **`RESTRICT`** | **업무 연결** — *"이 발주가 이 요청을 쓰고 있다"* | 살아 있는 연결이다. 말없이 끊기면 **요청이 발주된 건지 아닌지 알 수 없어진다** → 막는 게 맞다 |

**판단 기준 한 줄**: **지난 일의 기록이면 `SET NULL` + 스냅샷, 지금 살아 있는 연결이면 `RESTRICT`.**

**UNIQUE — ⚠ 한 칸으로 묶지 않는다 (NULL 함정)**

```sql
-- ⛔ UNIQUE (release_id, sales_order_id, project_unit_id) 는 작동하지 않는다.
--    SQLite·PostgreSQL 둘 다 UNIQUE 안의 NULL 을 "서로 다른 값" 으로 본다.
CREATE UNIQUE INDEX uq_bre_order ON bom_release_effectivities(release_id, sales_order_id)
    WHERE sales_order_id IS NOT NULL;
CREATE UNIQUE INDEX uq_bre_unit  ON bom_release_effectivities(release_id, project_unit_id)
    WHERE project_unit_id IS NOT NULL;
```

**CHECK**

| | 내용 |
|---|---|
| E1 | `sales_order_id IS NOT NULL` **또는** `project_unit_id IS NOT NULL` |
| E2 | 둘을 **동시에** 채우지 않는다 |
| E3 | `equipment_qty_snapshot >= 1` |

| E6 | `project_unit_id IS NOT NULL` → `equipment_qty_snapshot = 1` (호기 1행 = 1대) |

- `scope_type='UNIT_SET'` → 모든 행이 `project_unit_id` · **`unit_state='CONFIRMED'`**
- `scope_type ∈ {PROJECT_SNAPSHOT, SALES_ORDER_SET, SALES_ORDER_QUANTITY}` → 모든 행이 `sales_order_id`
- 지정 수주·호기가 **`bom_releases.project_id` 소속**인지
- `PROJECT_SNAPSHOT` 은 **`scope_asof` 시점 스냅샷 그대로** — 사람이 임의 편집 금지

**삭제정책** — ⛔ 행 삭제 없음. 모든 FK `RESTRICT`.

**삭제정책** — 위 표대로. ⛔ **행 삭제 없음.**

**⛔ UNIQUE 를 두지 않는다 — 일부러다**

`(new_release_id, old_release_item_id, new_release_item_id, po_item_id)` 같은 조합에 UNIQUE 를 걸고 싶어지지만 **걸지 않는다.**

1. 이 칸들은 **대부분 NULL 을 허용**한다. §17.3 대로 **두 DB 모두 UNIQUE 안의 NULL 을 서로 다르게 보므로 실제로 막지 못한다** — 있으나 마나 한 제약이 되어 "막고 있다"는 착각만 준다
2. 같은 품목이 **여러 발주 라인에 영향을 줄 수 있어** 중복처럼 보이는 행이 정상이다
3. 영향 행 생성은 **Release 발행 한 트랜잭션 안에서 시스템이 한 번에** 만든다 (§8.3.3-2). 사람이 손으로 넣는 표가 아니다

→ 중복 방지는 **생성 시점 서버 로직**이 담당한다. 개발자가 임의로 UNIQUE 를 추가하지 않는다.

# 16. 불변성 보호 — **DB 에서도 막는다** (게이트 P0-7)

## 16.1 ⚠ 앞선 판단을 **철회한다**

제가 앞선 설계안에서 *"DB 트리거로 막지 않는다 — SQLite 와 PostgreSQL 의 문법이 달라 이관 시
조용히 빠질 수 있다"* 고 썼다. **잘못이었다.**

> 게이트 판정(2026-08-03 23:45) — *"DB 문법이 다르다는 이유로 보호를 제거하지 않는다.
> 문법은 달라도 **불변이라는 업무 의미**는 같아야 한다."*

**문법이 다른 것은 트리거를 두 벌 쓰면 되는 일이지, 보호를 없앨 이유가 아니다.**
현재 WORKS 에는 **직접 SQL 을 실행하는 경로가 많다.** 코드 검색만으로는 `절대 수정 불가` 를 보장할 수 없다.
→ **양쪽 DB 에 각각 트리거를 두고, 같은 위반 시나리오로 둘 다 시험한다** (§16.3).

## 16.2 보호 대상과 규칙

| 표 | 막는 것 |
|---|---|
| `bom_release_items` | Release 가 `RELEASED`/`SUPERSEDED`/`CANCELLED` 이면 **`UPDATE`·`DELETE` 거부** |
| `bom_releases` | **상태전이용 칸 외** 스냅샷 기준칸(`project_id`·`release_no`·`upload_id`·`scope_type`·`scope_asof`·`external_revision*`·`requested_by`) 변경 **거부** |
| `bom_release_effectivities` | Release 발행 후 **`UPDATE`·`DELETE` 거부** |
| `bom_release_supersede` | **`UPDATE`·`DELETE` 거부** |

## 16.3 구현 방식 — 양쪽 DB 에 **같은 의미**로

| | |
|---|---|
| 1 | **SQLite 용 보호 트리거** (`BEFORE UPDATE` / `BEFORE DELETE` + `RAISE(ABORT, …)`) |
| 2 | **PostgreSQL 용 동등 보호** (트리거 함수 + `RAISE EXCEPTION`, 또는 권한정책) |
| 3 | **두 DB 에서 같은 위반 시나리오가 모두 실패하는 자동시험** |
| 4 | **상태전이 함수는 허용된 칸만** 변경 (트리거가 그 외를 거부) |

## 16.4 서버·화면 층도 그대로 둔다

| 층 | 방법 |
|---|---|
| **서버 함수** | 스냅샷 칸을 바꾸는 **함수를 만들지 않는다**. 있는 것은 삽입·상태전이뿐 |
| **라우트** | 수정 라우트 없음 |
| **화면** | 수정 UI 없음 · *"발행된 확정본은 고칠 수 없습니다. 새 Release 를 발행하세요"* |
| **검사** | 배포 전 검사기가 스냅샷 표에 대한 `UPDATE`/`DELETE` 구문을 훑는다 |

⭐ **DB 트리거가 마지막 방어선이고, 위 네 층은 그 앞에 선다.** 어느 하나로 대신하지 않는다.

# 17. SQLite ↔ PostgreSQL 동일 의미

## 17.1 양쪽에서 같은 의미 — **써도 된다**

| 기능 | 확인 |
|---|---|
| `PRIMARY KEY` · `NOT NULL` · `UNIQUE` | 동일 |
| `CHECK` (같은 행 안 값만) | 동일 |
| `FOREIGN KEY … REFERENCES` + `ON DELETE RESTRICT`/`SET NULL` | 동일 (단 §17.3) |
| **부분 고유 인덱스** `CREATE UNIQUE INDEX … WHERE …` | **양쪽 지원** — WP-03 `uq_punit_orderlink_active` 에서 이미 사용 중 |
| **행 변경 거부 트리거** | 양쪽 지원 (**문법은 다름** → §16.3 대로 각각 작성 + 같은 시나리오로 시험) |

## 17.2 한쪽에만 있다 — ⛔ **쓰지 않는다**

| 기능 | 있는 쪽 | 왜 |
|---|---|---|
| `EXCLUDE USING gist` (범위 배타) | PostgreSQL | SQLite 에 없다 → 겹침·잔량은 **서버 판정**(§8.3) |
| `DEFERRABLE INITIALLY DEFERRED` | PostgreSQL | 설계에서 순환 참조를 만들지 않는다 |
| `ALTER TABLE … ADD CONSTRAINT` | PostgreSQL | SQLite 는 표 재작성 필요 → **처음 만들 때 제약을 다 넣는다** |

## 17.3 ⚠ 의미가 달라 조심할 것

| | SQLite | PostgreSQL | B단계 대응 |
|---|---|---|---|
| **FK 강제** | **연결마다 `PRAGMA foreign_keys=ON`** (기본 OFF) | 항상 | ✅ `get_db()` 가 켠다(`app/database.py:122`). ⚠ **삭제 경로 여러 곳이 명시적으로 OFF 한다** → **FK 만 믿지 말고 서버 검사를 둔다** |
| **🔴 UNIQUE 안의 NULL** | NULL 끼리 서로 다르다고 봄 | **동일**(기본 `NULLS DISTINCT`) | ⭐ **두 DB 가 똑같이 뚫린다** → 부분 고유 인덱스로 분리 (§15.2) |
| **타입 강제** | 안 함(동적 타입) | 거부 | 서버에서 형 검증 후 저장 |
| **불리언** | `INTEGER` 0/1 | `boolean` | 0/1 통일 + `CHECK IN (0,1)` |
| **시각** | `TEXT` `datetime('now','localtime')` | `timestamptz` | 기존 WORKS 관행(TEXT) 유지 · 이관 시 일괄 변환(WP-02) |
| **자동번호** | `AUTOINCREMENT` | `IDENTITY`/`SERIAL` | 이관 매핑(WP-02) |
| **트리거 문법** | `RAISE(ABORT,…)` | 함수 + `RAISE EXCEPTION` | §16.3 — **각각 작성하고 같은 시나리오로 시험** |

## 17.4 결론

**§17.1 범위 안에서만 DB 제약을 쓴다.** 겹침 배타·다른 표 참조·여러 행 합계는 **서버 함수**로,
**불변성은 양쪽 트리거로** 둔다. 그러면 두 DB 에서 같은 규칙이 같은 방식으로 지켜진다.

## 19.3 ⭐ Reference Scenario — 12대 → 5대 (게이트 §10)

```
수주번호 A · 장비 12대
  Rel.1 : 기존 BOM 을 12대에 적용
  Rel.2 : 변경 BOM 을  5대에 적용
```

**기대결과 (전부 시험으로 확인)**

| | 기대 |
|---|---|
| 1 | **`Rel.1` 유효 잔량 = 7대** (시스템이 계산) |
| 2 | **`Rel.2` 유효 수량 = 5대** |
| 3 | 품목별 필요수량이 **7대분과 5대분으로 분리**됨 |
| 4 | `Rel.1` 상태가 **`RELEASED` 유지** (잔량 7 > 0) |
| 5 | 구매요청 라인이 **어느 Effectivity 를 근거로 했는지 추적**됨 |
| 6 | 이미 요청한 수량을 넘겨 다시 요청하면 **차단** 또는 **D-11 예외 흐름** |
| 7 | `Rel.2` 를 5대 더(총 10대) 덮으려 하면 → **잔량 7 초과분 차단** |
| 8 | `Rel.1` 잔량이 0 이 되는 순간에만 **`SUPERSEDED`** 로 바뀜 |

## 19.4 시험 계획

| 종류 | 내용 |
|---|---|
| 정상 | 검증완료 → 신청 → 발행 → 구매요청 → 발주까지 한 바퀴 |
| **차단** | §4.2 네 가지 · 신청자=승인자 · 겹치는 `PENDING` · 미확정 호기 · 대수 누락 · 비BOM 라인에 release 요구 안 함 |
| **반려** | 사유 없으면 거부 · 반려본으로 구매요청 차단 · 재신청은 새 행 |
| **장비대수** | A=C(제안) · **A≠C(경고+사유 필수)** · A만 · C만 · 둘 다 없음(수동+사유) · **사유 없으면 발행 거부** |
| **잔량** | §19.3 8항 전부 · **초과 차감 차단** · 새 Release 가 `REJECTED`/`CANCELLED` 되면 **차감이 되살아나는지** |
| **적용범위** | 유형 4종 · 전 범위 겹침(→`SUPERSEDED`) · **일부 겹침(→`RELEASED` 유지)** · `PROJECT_SNAPSHOT` 발행 후 새 수주 추가 시 **자동 편입 안 됨** |
| **배분** | 요청↔Effectivity · 요청↔발주 · **잔량·필요수량 초과 차단** |
| **변경영향** | 품목·Effectivity 단위 기록 · **`UNREVIEWED` 면 추가 구매요청 차단** |
| **스냅샷 보존** | 발주 라인 삭제 → `po_item_id` NULL 이 되지만 **`po_number_snapshot` 등 5종이 남는지** |
| **불변** | 발행된 스냅샷을 **직접 SQL 로** `UPDATE`/`DELETE` 시도 → **양쪽 DB 에서 모두 거부** |
| **DB 제약** | 각 CHECK 를 **직접 SQL 로** 위반 시도 · **FK OFF 상태에서도 서버가 막는지** |
| **🔴 NULL 함정** | 같은 호기·같은 수주를 한 Release 에 **두 번** 넣어 부분 고유 인덱스가 막는지 |
| **스냅샷 중복** | 같은 품번 다른 구분 두 줄 · 시트 2개에 같은 `line_no` — 둘 다 정상 저장 |
| 회귀 | 기존 업로드·보드·파서 그대로 동작 |
| **변별력** | ⭐ 새 시험은 **고치기 전 코드에 먼저 돌려** 실패하는지 확인 |
