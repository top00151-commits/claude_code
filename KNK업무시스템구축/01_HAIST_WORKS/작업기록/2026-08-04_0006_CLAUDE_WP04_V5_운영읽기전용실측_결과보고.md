# 2. ⭐ 핵심 — 장비대수 원천 (게이트 P0-1 · §9-1 · §9-2)

## 2.1 세 후보 실측

| 후보 | 무엇 | 결과 |
|---|---|---|
| **A안** | `order_items` 중 정식 호기 라벨(z779 `^\d+호기$`) **행 수** | 448개 수주 · **851 행** |

## 2.2 🟢 A안 = B안 — **완전히 같다**

| 검사 | 결과 |
|---|---|
| 호기 행인데 `qty` 가 1 이 아닌 것 | **0 행** |
| 호기 행인데 `qty` 가 정수가 아닌 것 | **0 행** |

⭐ **정식 호기 라인은 예외 없이 `qty=1` 이다.** 즉 **"호기 1대 = 1행"** 이 운영 데이터에서 성립한다.
(WP-03 의 z1048 규약 — *"호기 대수 = 행 수"* — 가 851행 전수에서 확인됐다)

## 2.3 🔴 A안 ≠ C안 — 완전히 같지는 않다

| 항목 | 건수 |
|---|---|
| A안·C안 **둘 다** 값이 있는 수주 | 403 |
| 그중 **값이 같은** 수주 | **400** |
| 🔴 **값이 다른 수주** | **3** |
| A안에만 있음 (C안에 없음) | **45** |
| C안에만 있음 (A안에 없음) | **64** |

⚠ **한쪽에만 있는 109건 + 값이 다른 3건 = 112건**이 두 원천 사이에서 어긋난다.

# 5. 🔴 `po_items` CASCADE 와 변경영향 FK 충돌 — 해결안 (게이트 §6-9)

## 5.1 무엇이 부딪히나

```
po_items.po_id → purchase_orders(id)  ON DELETE CASCADE    ← 발주를 지우면 라인이 딸려 지워진다
bom_change_impacts.po_item_id → po_items(id)  RESTRICT ?   ← 지우지 못하게 막으면?
```

RESTRICT 로 걸면 **영향 검토 기록이 하나라도 있는 발주는 삭제 자체가 실패**한다.
(WP-01 이 이미 발주 삭제를 '작성중' 상태로만 제한했지만, 작성중 발주에도 영향기록이 생길 수 있다)

## 5.2 ⭐ 권고안 — `SET NULL` + 텍스트 스냅샷

| | 계약 |
|---|---|
| `bom_change_impacts.po_item_id` | **`ON DELETE SET NULL`** |
| 함께 저장 | **`po_no_snapshot`** · **`po_line_no_snapshot`** (텍스트) |
| 결과 | 발주가 지워져도 **"어느 발주의 몇 번 줄에 영향이 있었다"는 사실은 남는다** |
| `material_request_item_id` | 같은 방식 (`SET NULL` + `request_no_snapshot` · `line_no_snapshot`) |

**왜 이 방식인가**

1. **저장소가 이미 쓰는 방식이다** — `po_items` 자신이 `part_no_snapshot`·`part_name_snapshot`·
   `spec_snapshot` 을 갖고 있다. 참조가 끊겨도 사실이 남게 하는 같은 생각이다
2. **발주 삭제 업무를 막지 않는다** — RESTRICT 는 구매팀 업무를 잠글 수 있다
3. **영향 기록은 안 지워진다** — 이게 게이트 P0-5 가 원한 것(변경품목 추적)의 핵심

## 5.3 ⛔ 채택하지 않는 안

| 안 | 왜 안 되나 |
|---|---|
| `RESTRICT` | 발주 삭제 업무가 막힌다. 영향기록은 '참고 기록'이지 '삭제 금지 사유'가 아니다 |
| `CASCADE` | 발주를 지우면 **영향 기록까지 사라진다**. 추적 목적과 정반대 |
| FK 없이 정수만 | 오연결을 못 막는다. `material_request_items` 가 이미 그래서 무결성이 없다(§3.1) |
