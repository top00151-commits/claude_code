## 2. 옛 메일 보관함 — 보관만 · 중복 삭제

### ① 결정

WORKS 로 **합치지 않는다**(보관만). 중복은 지운다. ⛔다시 합치기를 권하지 말 것.

### ② 「중복」의 뜻 — 두 가지를 다 셌다

| | 조건 |
|---|---|
| 보관함 **안**의 사본 | 주인 · 방향 · 보낸이 · 받는이 · 참조 · 제목 · 본문 · html **+ 첨부 내용**까지 같음 |
| **WORKS 에도 있는** 메일 | 같은 주인(사번) · 같은 방향 · WORKS 의 중복 기준(보낸이 + 제목 + 본문) · **WORKS 쪽이 휴지통이 아님** · 보관함 쪽 첨부가 그 WORKS 메일에 전부 있고 **파일을 실제로 다시 읽어 지문이 맞음** |

🔴 옛 DB 에는 메일 고유번호(`message_id`) 열이 없다. WORKS 의 🔁 중복정리 기준(보낸이 + 제목 + 본문)만 쓰면
**글은 같고 첨부만 다른 메일이 한 통으로 합쳐져 첨부를 잃는다.** 그래서 첨부를 판정에 넣었다.
(실제 자료에서는 그런 묶음이 0건이었다 — 결과가 아니라 **가능성** 때문에 넣은 장치다)

### ③ 읽기 전용 점검 (대표 실행 21:0x) — `deploy/kmail_old_archive_dupcheck_readonly.ps1`

| | 값 |
|---|---|

| 첨부 | 636개 190.2MB · 내용이 저장돼 있지 않은 기록 5개 · 같은 파일이 여러 번 저장된 것 16.5MB |
| 열 | `message_id` · `dedup_hash` · `sha256` 없음 · 첨부는 DB 안(BLOB) |
| 보관함 안 완전 사본 | 3통(1묶음) · 「글 같고 첨부 다른」 묶음 0 |

### ④ 삭제 (대표 실행 21:16) — `deploy/kmail_old_archive_dedup.ps1 -Apply`

점검보다 **더 엄격한** 조건으로 다시 셌고(휴지통 제외 · 첨부 파일 재확인 · 12자리 지문), 대표가 숫자를 보고 `DELETE` 를 입력했다.

| | 값 |
|---|---|
| 다시 대조 | WORKS 에 온전히 있음 **459통** · 휴지통에만 0 · 첨부 빠짐/파일 없음 0 · WORKS 첨부 파일 **368개 다시 읽어 지문 일치** |
| 남김 | 5통 — 보관함 쪽 첨부 기록에 내용이 없어 견줄 수 없는 메일 |
| 사본 | `/opt/knk_mail/data/mail.db.bak.dedup.20261116_211608` 212.7MB — 메일·첨부가 원본과 전부 같음을 검증 |
| 삭제 | 메일 459 · 첨부 624 (한 트랜잭션) |
| 뒤 확인 | 무결성 ok · 남은 5통은 삭제 전과 동일(본문·첨부 다시 읽음) · 보관함 안 사본 0 |

점검 때의 「456 + 사본 3」과 삭제 때의 「459」는 같은 수다 — 사본 3통도 WORKS 에 있는 메일의 사본이었다.
서로 다른 코드(점검 `dupcheck_b` · 삭제 `dedup_2`)가 같은 수(459 / 5)를 냈다.

### ⑤ 사본 삭제 (대표 실행 21:1x) — `-PurgeBackup`

`RESULT: PURGE OK - 3 backup file(s) removed, 212.8 MB freed.`
(사본 본체 + 그 `-shm` · `-wal` 두 개. 옛 DB 가 WAL 방식이라 사본을 읽어 검증할 때 생긴 딸림 파일이다)

**이제 옛 보관함을 464통 상태로 되돌릴 수 없다.** 그 459통은 WORKS 에 있다.

### ⑥ 지금 옛 보관함

`/opt/knk_mail/data/mail.db` — 5통 · 첨부 12개 · 2.1MB. 옛 앱은 멈춘 채(자동 실행 3줄 주석).

## 4. 🔴 이번에 잡은 결함 둘

### ① 되돌리기가 「최신 사본」을 골랐다 (시험이 잡음 · 대표 실행 전)

삭제를 두 번 실행하면 두 번째에 **이미 줄어든 보관함**의 사본이 또 생기고, 되돌리기가 그것을 골라 **원래 상태로 못 돌아갔다.**
→ 지울 것이 없으면 사본을 만들지 않는다 · 되돌리기는 **메일이 가장 많은 사본**을 고른다.
⭐ 「되돌리기」는 「가장 최근 것으로」가 아니라 「**원래 것으로**」다. 두 번 실행한 뒤의 되돌리기를 시험에 넣을 것.

### ② 확인 글자를 빈칸까지 따졌다 (대표 실행에서 드러남)

대표가 ` PURGE`(앞에 빈칸)를 넣자 「다른 글자」로 보고 멈췄다. 아무것도 바뀌지 않았지만 한 번 더 실행하시게 했다.
→ 앞뒤 빈칸만 떼고 비교(대소문자는 그대로 가림).
⭐ 사람이 치는 확인 글자는 **뜻만 맞으면 통과**시키되(빈칸), 실수로 넘어가는 것(소문자 · 빈 입력)은 막는다. 가짜 입력 시험에 「빈칸 낀 입력」을 넣을 것.
