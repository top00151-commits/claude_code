## 2. 판정서 ① §8 요구 — 구매팀 최종본 파서 시험 결과

**결론: 기존 파서는 구매팀 최종본을 처리하지 못합니다.**

| # | 요구 항목 | 결과 |
|---|---|---|
| ① | 160개 품목 인식 | ✅ **160줄 정확** (헤더 7행 자동탐지 · 관리번호 자동추출) |
| ② | 재고·발주수량·단가·금액·납기 열 매핑 | 🔴 **실패** |
| ③ | `기존→대체`를 한 품번으로 오인하지 않는지 | 🔴 **부분 실패 — 5줄** |
| ④ | 전장·서비스·VINA 행 처리 | ⚠ **부분** |
| ⑤ | 총계행을 품목으로 오인하지 않는지 | ✅ **0줄** |
| ⑥ | 날짜열 미입력과 0값 구분 | ✅ **구분됨** |

### 2-② 🔴 열 매핑 실패 — 구매검토의 핵심 5열이 사라진다

`bom.detect_header()` 가 실제로 만든 매핑입니다.

```
열11  사내 재고                  →  (버림)
열12  베트남 재고                 →  (버림)
열13  발주 수량                  →  (버림)     ← 구매검토의 핵심 3열
열14  UNIT PRICE 단가            →  unit_price      ✅
열15  재고 금액                  →  amount     ← 🔴 잘못 매핑
열16  발주 금액                  →  (버림)
열17  AMOINT 합계 (진짜 합계)     →  (버림)
열18  DELIVERY 납기              →  delivery_text   ✅
```

**원인**: `_HEADER_ALIASES` 의 `amount` 별칭에 `"금액"` 이 있고, 왼쪽부터 스캔하다 **처음 걸리는 열(재고 금액)** 을 잡은 뒤 `used` 에 넣어 이후 금액 열을 전부 무시합니다.

**두 번째 결함** — 금액을 원본에서 안 읽고 **계산해 채웁니다**.

```python
# app/bom.py:254-255
if it["amount"] == 0 and it["unit_price"]:
    it["amount"] = round((it["total_qty"] or it["unit_count"] or 0) * it["unit_price"], 2)
```

그 결과:

```
파서가 내놓은 합계 : 103,266,661.32원
엑셀 원본 합계     : 103,521,961.32원
                     ─────────────────
차이               :     255,300원
```

⚠ **왜 설계팀 파일에서는 안 드러났나**: 설계팀 파일은 단가·금액이 전부 비어 있어(`unit_price=0`) 계산 분기도 타지 않았습니다. **그래서 제가 "완벽히 읽는다"고 착각했습니다.**

### 2-③ 🔴 대체품 화살표 — 78줄은 성공, 5줄 실패

엑셀 원문에 `->` 표기: **코드명 77줄 · 제조사 34줄 · 제품명 1줄**

✅ **잘 되는 부분**: 파서에 `_split_arrow()` 와 `excel_changes` 가 이미 있어 **78줄에서 old/new 를 분리 보존**합니다.

```
'GPA 0803->KQ2Z08-03NS'  →  part_no='KQ2Z08-03NS'
                            excel_changes=[{field:'part_no', old:'GPA 0803', new:'KQ2Z08-03NS'}]
```

🔴 **실패하는 5줄** — 원인은 **화살표가 두 번** 있는 것입니다.

```
'MFMCA0030RJD->ELM-PWR3M0-A1->E-CASP3M-N'
'MFECA0030TJD->ELM-ENC3M0-A1->E-CAS2E3M-N'
'MSMF042L1S1->ELM1H-0400MA60F->E-MASH1-0604'
'MBDLT25SF->EL7-RS400P->E-DFAS04P'
'견적서 참조->1M (PANASONIC A6)->1.5M (PANASONIC A6)'
```

`_split_arrow` 가 `maxsplit=1` 이라 **첫 화살표만 자르고 뒤쪽 화살표가 새 품번 안에 그대로 남습니다.**

→ 즉 **단종 → 대체 → 재대체처럼 2회 이상 바뀐 품목을 처리하지 못합니다.** 실제 구매에서 흔한 일입니다.

### 2-④ ⚠ 전장·서비스·VINA 행

| 구분 | 실측 |
|---|---|
| 전장 부품 | **21줄** — `CATEGORY = "전장 부품"` 으로 구분됨 ✅ |
| 서비스성 | **2줄** — `해외 출장비 (VINA)` · `프로그램 개발비` |

⚠ 서비스성 2줄의 **단위가 `EA`** 입니다. 자재가 아닌데 자재와 같은 모양으로 들어옵니다. 재고·입고·검수 흐름에 그대로 태우면 안 됩니다.

### 2-⑥ ✅ 날짜열 미입력 vs 0 — 구분됩니다

```
납기      : 글자 160줄 ("1 WEEK" 등)
```

## 3. 보정된 수량·단위 계약 (판정서 ① §4 접수)

V3 계약 1(`Σ배분 ≤ 요청수량`)·계약 2(`단위 같을 때만`)로는 **실제 구매가 막힙니다.**

```
설계 요구  GPA 0803          12 EA
구매 실제  → KQ2Z08-03NS     포장 10 EA · 구매 20 EA
```

- 설계 12를 20으로 덮어쓰면 **장비 필요수량 12가 사라집니다**
- `배분 ≤ 요청수량`만 강제하면 **20개 구매가 거부됩니다**

### 3.1 수량을 아홉 개로 분리한다

| 값 | 의미 | 원본 |
|---|---|---|
| `required_qty_base` | 설계가 요구한 기준단위 총수량 | 설계팀 |
| `stock_allocated_kor` | **본사** 가용재고 배분 | 구매·자재팀 |
| `stock_ref_vn` | **베트남 참고수량** (운영재고 아님·§4) | 참고 |
| `demand_to_purchase_base` | 재고배분 후 구매로 충족할 기준단위 수량 | 계산 |
| `purchase_qty` | 협력사에 실제 주문할 **구매단위** 수량 | 구매팀 |
| `purchase_unit` | EA·BOX·M·SET | 구매팀 |
| `conversion_to_base` | 구매단위 1개 = 기준단위 몇 개 | 구매팀 입력·승인 |
| `ordered_qty_base` | `purchase_qty × conversion_to_base` | 계산 |
| `surplus_qty_base` | 포장·최소주문으로 남는 **초과구매** | 계산 |

### 3.2 불변식 (V3 계약 1·2를 대체)

```
설계요구량 = 재고배분량 + 구매로 충족할 요구량
발주 기준단위 수량 = 구매요구 충족량 + 승인된 초과구매·재고보충량
```

| # | 규칙 |
|---|---|
| Q-1 | 구매요구 충족량은 설계요구 잔량을 **초과할 수 없다** |
| Q-2 | 실제 발주량은 포장·최소주문·길이환산 때문에 **요구 잔량보다 클 수 있다** |
| Q-3 | ⛔ 초과분을 **설계요구에 억지로 배분하지 않는다** |
| Q-4 | 초과분은 `재고보충` 근거 **또는** 초과구매 사유·승인자를 가진다 |
| Q-5 | 단위가 같으면 환산계수 **1** |
| Q-6 | 단위가 다르면 구매팀이 환산계수를 입력하고 **서버가 검증** |
| Q-7 | 환산계수가 없으면 **다른 단위 발주를 발행하지 못한다** |
| Q-8 | ⛔ 시스템이 포장수량·환산계수를 **임의 추정하지 않는다** |
| Q-9 | ⛔ 발주수량과 배분수량을 **서로 다른 단위로 직접 비교하지 않는다** |

## 4. 베트남 재고 = 참고수량만 (판정서 ② 접수)

**본사 V1의 가용재고·재고원장·자동 구매량 계산에서 베트남 재고를 제외합니다.**

| 허용 | 금지 |
|---|---|
| 구매검토 화면에 **`베트남 재고 참고수량`** 표시 | 본사 가용재고에 **합산** |
| 기준일·확인자·출처문서·비고 보존 | 본사 재고원장에 **입고 처리** |
| 구매담당자가 발주량 판단 시 **참고** | 본사 프로젝트에 **자동 예약** |
| | 본사 구매 필요량에서 **자동 차감** |
| | ⛔ `vn_stock_qty` 같은 **법인 전용 고정 칼럼 생성** |

### 4.1 구조에 남길 최소 확장 기준

- 창고에 **소유·운영 법인 식별자**
- 구매주문·입고·재고이동·출고에 **거래 법인 식별자**
- **V1 기본값·허용값은 `KOR` 하나로 제한**
- 품목 Master는 공통 가능, **단가·협력사·재고·발주·입고는 법인별 분리**
- 법인 간 이동을 **일반 창고 간 이동으로 처리하지 않는다**

⛔ 해석 금지: `KOR + VN = 전체 가용재고` 계산 · 창고 코드로 소유권 추정 · 관리번호 `V` 유무로 재고 법인 확정.

⭐ **이 결정으로 WP-04 본사 개발을 멈추지 않습니다.** 베트남 화면·구매·입고·재고는 이번 범위에 **추가하지 않습니다.**

## 5. 묶음 A 범위 (재정의)

### 5.1 업무 결과

```
설계팀이 BOM을 Release
  → 구매팀이 구매검토 (재고배분·구매수량·환산·대체품·단가·납기)
    → 구매요청 생성 → 검토 → 승인/반려
      → 어느 Release를 근거로 했는지 언제든 되짚어진다
```

### 5.2 파서 보수 — 묶음 A의 첫 관문

| # | 고칠 것 |
|---|---|
| P-1 | `사내재고`·`발주수량` 열 매핑 신설 (베트남재고는 **참고칸**으로 분리) |
| P-2 | 금액 열 **3종 구분** — `재고금액`·`발주금액`·`합계` 를 각각 다른 필드로 |
| P-3 | ⛔ **원본 금액이 있으면 계산하지 않는다.** 계산은 원본이 **비어 있을 때만**, 그리고 **계산값임을 표시** |
| P-4 | `_split_arrow` **다단 화살표** 지원 (`A->B->C` = 변경 이력 2단) |
| P-5 | 서비스성 항목(출장비·개발비) **구분 표시** — 재고·검수 흐름에 태우지 않음 |
| P-6 | 두 파일 **양쪽 회귀 시험** (설계팀 132줄 · 구매팀 160줄) |

### 5.3 설계품목별 구매처리 상태 (판정서 ① §5.3)

설계 BOM 품목은 반드시 하나의 처리를 갖는다.

```
구매대상 · 재고사용 · 사급품 · 자체제작 · 대체품구매 · 보류 · 불필요·취소
```

⛔ **설계에만 있고 구매팀 문서에서 사라진 항목(5줄)을 상태·사유 없이 누락시키지 않는다.**

### 5.4 구매팀 추가품목 (33줄)

다음 근거 중 하나를 가져야 한다: 다른 설계영역 Release 품목 / 설계변경 추가품 / 설치·출장·프로그램 등 비BOM 요청 / 구매 포장·부속품 / 구매팀 제안 후 **설계승인**을 받은 대체·추가품.

⚠ 장비 기능·사양에 영향을 주는 추가품·대체품은 **해당 설계책임자 승인**이 필요하다.

## 6. Revision과 시간 (판정서 ① §6)

```
구매팀 최종본 파일명 : 20260722
```

업로드마다 따로 저장: 원본 파일명 · 작성부서 · **원본문서 작성일** · **시스템 접수일시** · 외부 Revision 원문 · 내부 Release 순번 · **어느 Release를 근거로 한 구매검토인지**.
