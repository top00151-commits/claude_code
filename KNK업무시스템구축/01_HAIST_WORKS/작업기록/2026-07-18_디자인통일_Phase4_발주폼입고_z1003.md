# 디자인 통일 Phase 4 ③ — 발주 작성 폼·입고 처리 knk 전환 (z1003)

- **일자**: 2026-07-18
- **대상**: `po_form.html`(577줄·발주 작성/수정)·`po_receive.html`(496줄·입고 처리 GR).
  이번 Phase 4 구간 중 **가장 크고 스크립트 의존이 강한 두 화면**.

## 1. 전환 원칙 — "셸만 knk, 위젯은 유지+브리지"

두 화면 모두 라인 표가 **JS의 생명선**이라, z999 구매사 카드와 같은 판단으로 라인 표·상호작용
위젯은 통째 유지하고 **머리글·입력 필드·제출 바·버튼만** knk로 전환.

| 전환(knk) | 유지(업무 특화·색만 Sage 브리지) |
|---|---|
| 머리글 → knk-page-head | 4단계 스텝퍼(step/step-num) |
| 입력 필드 → knk-field(공통 규격·Sage 포커스 `#3E6F89`) | **발주 라인 표**(lines/line-input) |
| 하단 액션 → knk-submit-bar(sticky) | 합계(VAT 3모드 subLabel/vatLabel) |
| 버튼 → knk-btn(+Tabler) | 사이드(요약/작성 가이드/도움말) |
| :root → pq→knk 브리지 | **입고 KPI 4칸**(발주량/기입고/금일입고/잔량) |
| | **입고 라인 표**+입고율 바·QR 스캐너·발주정보 카드 |

## 2. ⭐JS를 건드리지 않은 이유와 증명

- `po_form`: `recalcLine`·`recalcTotals`·**`addLine`(innerHTML 템플릿)**·`onPartNameInput`·`delLine`이
  `.lines-row`·`.line-input.qty/.price/.amount`·`.line-part-id`·`.line-name`·`.line-num`에 의존.
- `po_receive`: `recalc`·`qfillAll`·**QR 스캐너**(`highlightPartLine`·`processPayload`)가
  `.line-input.rcv`·`.line-row`·`.part-cell .code`·`[data-rest-cell]`·`#kpiRecv`/`#kpiRest`에 의존.
  특히 KPI는 JS가 `innerHTML = fmt + '<span class="u">개</span>'`로 **다시 씀** → KPI를 knk-kpi-strip으로
  바꾸면 `.u`가 깨짐 → **입고 KPI는 유지가 정답**(색 의미 3종도 knk 무대응이라 유지 근거 2중).
- **증명**: 검증에서 `line-input line-name/qty/price/amount` 각 **3회**(HTML 2 + addLine 템플릿 1) →
  addLine의 이너HTML 템플릿까지 원형 보존됨을 수치로 확인. JS 문자열 0줄 수정.

  라벨의 `.req`/`.info`(모노·우측정렬) 부가 스타일은 `.knk-field > label` 페이지 규칙으로 이식.

## 7. 🔧 z1003b — 입고 페이지 잠복 버그 수정 (렌더 오류 실측 → 근본 원인 규명)

- **증상**: 모든 발주의 `/po/{id}/receive`가 "페이지 오류"(PO-1·PO-4 실측).
- **내 변경 무관 확인**: `git diff`로 z1003이 바꾼 데이터식은 `{{ po.items|length }}`(위치 이동, 내용 동일)뿐 —
  오류를 낸 `{% set total_order = po.items|sum(attribute='qty') %}`·`{% for it in po.items %}`는 **미변경**.
  → z1003 이전부터의 문제로 확정.
- **근본 원인(로컬 렌더로 재현)**: 라우트가 `po=dict(header)`(plain dict)를 넘기는데 템플릿이 **`po.items`(점 접근)**
  → Jinja가 dict의 **`.items()` 메서드**로 해석 → `{% for %}` 순회 시 `'builtin_function_or_method' object is
  not iterable` TypeError. **입고 가능 상태(발주완료/부분입고) 발주가 아직 없어** 버튼이 안 떠 아무도 안 밟은 잠복 버그.
  (발주 상세는 `attribute='quantity'`+다른 접근이라 무사했음 — z1002에서 정상 렌더 확인된 이유.)
- **수정**: `po.items` → **`po['items']`**(대괄호 첨자=dict 값 강제) 5곳. 타 템플릿엔 이 패턴 없음(grep 0).
- **배포**: `4a16c50d` → LIVE `ac9ecf4`. **결과: dict.items 오류는 사라졌으나 더 깊은 2겹째 버그 노출**(§8).

## 8. 🔧 z1003c — 입고 품목 필드명 오류 (2겹째 잠복 버그·대표 승인 후 수정)

- **증상**: z1003b 후 재실측 시 새 오류 — `UndefinedError: 'dict object' has no attribute 'qty'`
  (`{% set total_order = po['items']|sum(attribute='qty') %}` 119줄). **서버 전체 트레이스백 확보**로 근본 규명.
- **원인**: `po_items` 실제 저장 컬럼 = **`quantity`·`part_name_snapshot`·`part_no_snapshot`**
  (`database.py po_create`가 `it.get("quantity")`로 저장·정상 렌더되는 **발주 상세가 쓰는 바로 그 이름들**).
  입고 템플릿만 `qty`·`part_name`·`part_code`로 **틀리게** 읽고 있었음 — 처음부터.
- **왜 여태 미발견**: '입고 처리' 버튼은 발주가 **발주완료/부분입고**일 때만 노출 → 전 발주가 '작성중'이라
  이 화면에 진입 자체가 0회. **입고(GR) 기능이 만든 이래 한 번도 동작한 적 없는 잠복 상태.**
- **수정(대표 "지금 고치기" 승인)**: 6곳 — `sum(attribute='qty')`→`quantity`·`it.qty`→`it.quantity`(3곳)·
  `part_name`→`part_name_snapshot` 우선·`part_no_snapshot` 우선(모두 하위호환 default 체인). **저장(POST)·po_receive() 불변.**
- **검증**: 실스키마(quantity/snapshot) 목데이터 **로컬 렌더** — 품목명·품번·발주량(10/20)·**합계(30)**·
  잔량(7/20)·data-order·QR·KPI 색의미 전부 정상 출력·옛 클래스 잔재 0. Jinja·esprima·div 균형 통과.
- **배포**: `88b2ee14` → LIVE 재실측 예정.

## 9. ⭐교훈

1. **dict를 템플릿에 넘길 때 `obj.items`/`.keys`/`.values` 점 접근 금지**(Jinja가 dict 메서드로 잡음) → `obj['items']`.
2. **상태 조건으로 진입이 막힌 화면은 "렌더된 적 없음"=버그 미발견** → 재설계 시 조건을 우회해 **실제 렌더까지** 확인.
3. **자매 화면(발주 상세)이 정상이면 그 필드명이 정답** — 대조가 근본 원인 규명의 지름길.
