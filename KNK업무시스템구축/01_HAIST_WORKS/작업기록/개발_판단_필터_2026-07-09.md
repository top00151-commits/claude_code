## 0. 최상위 원칙 (대표 원문)

> **"정말 우리가 이걸 만들면서 일을 하기 위해 또 일을 만드는 잘못된 판단을 하면 안 돼. 우리는 실무자들이 일을 효율적으로 완료하고, 일을 지연 또는 놓치지 않게 하기 위해서 만드는 거야."**
>
> — 대표 김정락, 2026-07-09

**이 문장이 다른 모든 문서·설계·로드맵보다 우선한다.**

---

## 1. 판단 필터 5조 (Yes/No)

신규 화면·기능 제안 전에 반드시 5개 모두 답해야 한다.

| # | 질문 | 통과 조건 |
|---|---|---|
| ① | **실무자의 하루가 짧아지는가?** | 절약 시간을 숫자로 답할 수 있어야 (예: "발주 1건당 3분 → 30초") |
| ② | **실무자가 놓치던 걸 자동으로 잡아주는가?** | 사람이 챙기던 일을 시스템이 대신 (예: 안전재고 도달 자동 알림) |
| ③ | **실무자의 반복 작업이 없어지는가?** | 매일 하던 클릭·복사·붙여넣기 감소 (예: 지난 발주 자동 복사) |
| ④ | **실무자에게 새 입력을 요구하지 않는가?** | ⚠ 요구하면 **부담 증가** → 만들지 말 것 |
| ⑤ | **이걸 안 만들면 실무자가 정말 힘든가?** | 아니면 **필요 없음** → 만들지 말 것 |

**5개 중 하나라도 위반 → 재설계 또는 폐기.**

---

## 2. 화이트리스트 (만들어야 할 것)

이 유형의 기능은 필터 통과 가능성이 높다.

| ✅ 유형 | 실무자 이득 | 예시 |
|---|---|---|
| **자동 알림** | 놓치던 것 잡음 · 새 일 X | 안전재고 도달 시 담당자 자동 알림 |
| **자동 채우기** | 반복 입력 감소 | 발주서에 지난 값 자동 · 요청서에 즐겨찾기 |
| **한 화면 처리** | 여러 화면 왕복 X | 견적 요청부터 발주까지 한 화면 |
| **오류 방지 검증** | 사고 방지 | 잘못된 입력 즉시 차단 (예: 이원화 판정) |
| **검색·필터** | 찾는 시간 단축 | 자재 검색·유사자재 추천 |
| **자동 계산·판단 지원** | 시간·판단 부담 감소 | 공급사 자동 비교표 · 저렴/빠른 자동 표시 |

---

## 3. 블랙리스트 (만들지 말 것)

이 유형은 **원칙 위반**. 어떤 이유로도 만들지 않는다.

| ❌ 유형 | 왜 금지 |
|---|---|
| **관리자만 보는 KPI 대시보드** | 실무자에게 도움 X · 감시 압박 O |
| **미완 리스트 (이원화 미완 등)** | 압박만 · 실제 해결 X |
| **수동 상태 관리 화면** | 새로운 입력 부담 (자동 변경만 허용) |
| **보고서 위한 보고서** | 실무자 시간 소모 |
| **좋아 보이지만 안 쓰는 화면** | 이미 라우트 33개+ · 오히려 정리 대상 |
| **주간·월간 리포트 자동 발송** | 열어보지 않으면 무의미 |
| **모든 것을 다 보여주는 종합 뷰** | 인지 부하 · 결국 아무도 안 봄 |

⚠ 대표·관리자 관점의 지표가 필요하면 → **실무자 화면에 노출 X**, 별도 관리자 페이지에만.

## 4. 신규 개발 제안 양식 (필수)

앞으로 어떤 개발이든 시작 전 이 양식을 대표에게 전달한다.

```markdown
## 제안: [기능 이름]

### 판단 필터 5조 통과 여부
| # | 질문 | 답 (Y/N) | 근거 |
|---|---|---|---|
| ① | 실무자 하루가 짧아지는가? | Y | 예: 발주 3분 → 30초, 하루 10건 = 25분 절약 |
| ② | 놓치던 걸 자동으로 잡는가? | Y/N | 예: 자동/해당없음 |
| ③ | 반복 작업이 없어지는가? | Y/N | 예: 클릭 5회 → 1회 |
| ④ | 실무자에게 새 입력 요구 X? | Y | 반드시 Y |
| ⑤ | 안 만들면 실무자가 힘든가? | Y/N | 예: 매일 발생하는 통증 |

**5개 모두 Y가 아니면 제안 자체 재검토.**

### 실무자 검증
- [ ] 이 기능이 도움될 담당자: __________
- [ ] 프로토타입 검증 방법: __________
- [ ] 배포 후 실사용률 측정 방법: __________

### 개발 범위
- 파일: __________
- 예상 시간: __________
- 리스크: __________
```

## 5. 실무자 검증 룰 (배포 전 필수)

### 배포 전
1. **실무자에게 프로토타입 보여줌** → "이게 도움됩니까?" 확인
2. 답이 "그냥 그래요" · "잘 모르겠어요" → **재설계**
3. 답이 "이거 있으면 매일 N분 아껴요" · "이거 없이는 놓쳐요" → **배포**

### 배포 후 (1주일)
1. **실사용률 확인** — 로그·기록으로 검증
2. 아무도 안 쓰면 → **회수 및 폐기**
3. 잘 쓰면 → **개선점 청취**

**개발자가 좋은 아이디어라고 생각한 게 실무자에겐 새 일인 경우가 대부분이다. 검증 없이 배포 금지.**

## 6. 이 문서 위반 시 대응

| 위반 사례 | 대응 |
|---|---|
| 필터 5조 명시 없이 개발 시작 | **즉시 중단** · 필터 통과 후 재시작 |
| 실무자 검증 없이 배포 | **롤백** · 사후 검증 후 재배포 |
| 블랙리스트 유형 개발 발견 | **즉시 폐기** · 대표 보고 |
| "그래도 좋은 아이디어" 라는 주장 | **원칙 우선** — 아이디어 우선 X |

## 8. 앞으로 원칙 요약 (한 페이지)

1. **실무자가 지금 하는 일을 더 쉽게·빠르게** 만든다.
2. **실무자가 놓치던 일**을 시스템이 대신 챙긴다.
3. **실무자에게 새로운 일을 시키지 않는다.** (새 입력·상태관리·리포트 작성 X)
4. **관리자·대표 지표**는 실무자 화면에 안 넣는다.
5. **아이디어보다 원칙**이 우선. 필터 통과 안 하면 폐기.
