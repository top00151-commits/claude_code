# 자재구매센터 · 역할별 "완벽 처리" 설계 v1

> **작성**: 2026-07-06 · 빅터(05 자재구매) / **트리거**: 대표 지시 *"역할을 봤을 때 좀 더 완벽하게 일을 처리할 수 있는 방법이 있어야 해"*
> **위치**: `01_HAIST_WORKS/작업기록/`
> **지위**: 자재구매센터 개발·운영의 **최상위 기준서**. 이 문서와 어긋난 세부 기능은 즉시 재검토·수정.

---

## 0. 배경 · 왜 이 문서인가

- 자재구매센터는 이미 라우트 약 110개·템플릿 52개·DB 테이블 17개로 **기능 자체는 완성 단계**.
- 하지만 화면·기능이 낱개로 흩어져 있어 **각 팀이 "내가 지금 뭘 해야 하는지" 를 한눈에 못 봄** → 놓치는 일 · 병목 · 중복 작업 발생.
- **해결**: 업무 범위·흐름을 문서로 확정하고, 앞으로 모든 개발이 이 문서를 기준으로 정렬되도록.

## 1. "완벽 처리" 5축 정의

| 축 | 뜻 | 시스템 요구 |
|---|---|---|
| ① **놓치지 않음** | 해야 할 일이 모두 눈에 보임 | 역할별 작업 큐(Task Inbox) |
| ② **실수 없음** | 데이터·순서 오류 원천 차단 | 상태 모델 + 자동 검증 |
| ③ **인수인계 명확** | 다음 담당자가 바로 이어받음 | 라이프사이클 상태 + 담당자 지정 |
| ④ **이력 추적** | 언제 누가 뭘 했는지 | 자재/요청/PO별 타임라인 |
| ⑤ **병목 발견** | 늦어지는 곳 즉시 파악 | KPI 대시보드 + escalation |

앞으로 어떤 기능을 만들든 이 5축 중 하나라도 **후퇴**하면 재설계.

| 역할 | 주 업무 | 시스템 영역 (기존 라우트 그룹) |

| 입고 검수 | 전체 | **자재팀** |
| 자재 요청 | 요청자·구매팀·자재팀 | 요청자(수정)·구매팀(검토) |

## 3. 2흐름 (구매 진행 방식)

### 🔵 흐름 1 · 선행 구매 (Proactive Sourcing)
구매팀이 **필요 전에 미리** 최적 공급 조건을 확보하는 활동.

```
1. 자재 발굴
   (신규 부품·대체품 조사)
   ↓
2. 여러 공급사 견적 수집
   ↓
3. 이원화 등록
   (같은 자재코드에 vendor1/2/3 슬롯)
   ↓
4. 단가 등록·승인
   (승인권자: 리더+)
   ↓
5. 발주 가능 상태로 대기
   (실제 발주는 요청 발생 시)
```

**KPI**: 이원화율(전체 자재 중 vendor2+ 있는 비율), 최적 공급사 발굴 소요일

### 🟢 흐름 2 · 요청 구매 (Reactive Procurement)
관련부서 요청에 대응하는 활동.

```
1. [관련부서]
   BOM에서 필요 자재 파악
   ↓
2. [관련부서]
   자재요청서 작성
   (이미 등록 = 수량·납기, 신규 = 스펙·용도)
   ↓
3. [구매팀]
   신규검토
   ├── 유사 자재 있음 → 매칭 (신규 등록 안 함)
   └── 신규 등록 필요 → parts 등록 → 이원화(§1)
   ↓
4. [구매팀]
   PO 발주
   ↓
5. [자재팀]
   입고·검수(QC)
   ↓
6. [자재팀]
   출고 (관련부서로)
   ↓
7. [관련부서]
   수령·사용
```

**KPI**: 요청→발주 리드타임, 요청→입고 리드타임, 신규검토 24h 초과 건수

## 4. 자재 라이프사이클 상태 모델

각 자재는 하나의 **상태**를 가지며 담당 팀·다음 액션·미완 사유가 명확.

| 상태 | 뜻 | 담당 | 다음 액션 |
|---|---|---|---|
| 🟡 **발굴 대기** | 신규 검토 요청은 왔지만 아직 마스터 등록 X | 구매팀 | 등록 or 유사매칭 |
| 🟡 **이원화 필요** | 마스터 등록됐지만 공급사 1개만 | 구매팀 | 견적 수집→vendor2 추가 |
| 🟢 **이원화 완료** | 공급사 2+ 등록 | — | 대기 |
| 🟡 **단가 승인 대기** | 단가 등록됐지만 미승인 | 리더+ | 승인 or 반려 |
| 🟢 **발주 가능** | 자재·단가·공급사 모두 완비 | — | 요청 발생 시 발주 |
| 🔵 **발주 진행 중** | PO 있음 · 입고 전 | 구매팀 | 납기 관리 |
| 🔵 **입고 대기** | PO 발주 완료 · 검수 전 | 자재팀 | 입고 검수 |
| 🟢 **재고 정상** | 재고 있음 · 안전재고 이상 | — | 모니터링 |
| 🟠 **재고 알림** | 안전재고 미달 | 구매팀 | 재발주 |
| ⚪ **단종** | 사용 중단 | — | 아카이브 |

⚠ 상태 전환 로직은 **자동**이어야 (수동 조작 금지). 예: PO 승인 → 자동 "발주 진행 중", 입고 완료 → 자동 "재고 정상".

## 5. 역할별 "완벽 처리" 필수 요소

### 🛒 구매팀 홈 (신규)
매일 아침 이 화면 하나만 보면 오늘 할 일이 모두 정렬됨.

| 위젯 | 내용 |
|---|---|
| **작업 큐 (Task Inbox)** | 이원화 미완 N건 · 신규검토 대기 N건 (24h 초과 빨강) · 재고 알림 → 발주 필요 N건 · 단가 승인 대기 N건 · 예상 납기 오늘·내일 PO N건 |
| **이원화 KPI 카드** | 전체 자재 중 vendor2+ 비율 % · 지난주 대비 증감 |
| **신규자재 발굴 지원** | 자재요청서에서 아직 마스터 미등록 항목 리스트 → 클릭 하나로 등록 화면 |
| **공급사 견적 비교표** | 같은 자재코드의 여러 공급사 견적을 한 표에 (가격·리드타임·품질 점수) |

### 📦 자재팀 홈 (신규)
| 위젯 | 내용 |
|---|---|
| **입고 예정 · 검수 대기** | 시간순 큐 |
| **출고 요청 대기** | 승인 필요 순 |
| **실사 진행 상황** | 실사 캠페인·완료율·차이 발견 |
| **안전재고 알림** | 도달 자재 → 자동으로 구매팀에 재발주 요청 발행 |
| **부적합 처리 큐** | 반품·특별수용·폐기 미결 |

### 📋 관련부서 홈 (신규)
| 위젯 | 내용 |
|---|---|
| **내 요청 진행 바** | 요청→검토→발주→입고 상태를 한 줄로 |
| **자주 쓴 자재** | 반복 요청 즐겨찾기·복제 |
| **새 요청 작성 (원터치)** | BOM에서 클릭 하나로 · 신규자재 요청 시 유사 자재 자동 추천 (이미 등록된 것 재요청 방지) |
| **내 부서 통계** | 이번 달 요청 N건 · 평균 리드타임 |

## 6. 시스템 관점 5가지 핵심 방법론

### ① 상태 모델 컬럼 신설
`parts.lifecycle_status` (§4 상태) 컬럼 + 자동 갱신 트리거.

### ② 작업 큐 (Task Inbox)
각 팀 홈에 상태별 "내 큐" 표시. 화면 이름: `/logistics/inbox/purchasing`, `/inbox/warehouse`, `/inbox/requester`.

### ③ 자재 타임라인 뷰
자재 상세 페이지에 라이프사이클 진행 바(§4 상태). 각 단계 담당자·일자·소요 시간.

### ④ 자동화 워크플로우
- 상태 변경 시 다음 담당자 자동 알림 (Eum 봇)
- 24h/72h 미처리 → 상급자 escalation
- 안전재고 도달 → 구매+자재 동시 알림

### ⑤ KPI 대시보드 (대표 전용)
`/logistics/kpi` 신규.
- 이달 처리량 · 평균 리드타임 · 이원화율 · 재고 회전율
- 트렌드 그래프 → 병목 발견

## 8. 구현 우선순위 로드맵

각 단계는 대표 승인 후 개별 개발·배포. 완료마다 이 문서 갱신.

| 단계 | 내용 | 예상 규모 | 효과 |
|---|---|---|---|
| **P1** | ① 라이프사이클 상태 컬럼 + 자동 갱신 | 중 (2~3일) | 모든 후속 기능의 기반 |
| **P2** | ② 구매팀 홈 (작업 큐) | 중 | 대표 지시한 "완벽 처리" 즉시 체감 |
| **P3** | ② 자재팀 홈 · 관련부서 홈 | 중 | 3역할 완비 |
| **P4** | 이원화 미완 리스트 + 견적 비교표 | 소 (반나절) | 구매팀 즉시 활용 |
| **P5** | ③ 자재 타임라인 뷰 (상세 페이지) | 소 | 이력 추적 |
| **P6** | ④ 자동화 워크플로우 (알림·escalation) | 중 | 병목 자동 감지 |
| **P7** | ⑤ KPI 대시보드 (대표 전용) | 중 | 경영 관점 |

**P1 → P2 → P3** 이 순서로 가면 대표는 P2 배포 시점부터 "완벽 처리" 체감 시작.

## 9. KPI 정의 (측정 지표)

| KPI | 계산 | 목표 |
|---|---|---|
| **이원화율** | vendor2+ 있는 자재 / 전체 자재 | 향후 결정 |
| **신규검토 리드타임** | 요청 → 검토 완료 평균 시간 | ≤ 24h |
| **요청→발주 리드타임** | 자재요청 → PO 발행 평균 시간 | ≤ 3일 |
| **요청→입고 리드타임** | 자재요청 → 입고 완료 평균 시간 | 자재 종류별 |
| **안전재고 도달률** | 최근 30일 안전재고 미달 발생 자재 수 | 감소 추세 |
| **재고 회전율** | 출고량 / 평균 재고량 | 자재 종류별 |
| **24h 초과 미처리 큐** | 각 팀별 24h 이상 미처리 항목 수 | 0 근접 |

## 10. 앞으로 개발 원칙 (필독)

1. **새 기능은 "5축 중 어느 걸 강화하는가" 명시 후 진행.**
2. **자재구매센터 관련 코드 손댈 때 라이프사이클 상태 컬럼과의 정합성 유지.**
3. **알림·escalation은 자동, 수동 트리거 없음.** (사람이 챙기게 하면 놓침 = 완벽 실패)
4. **화면 신설 시 반드시 3역할 중 어느 팀 소유인지 명시** (권한 게이트 명확).
5. **라이프사이클 상태 전환은 트리거로 자동**, UI에서 수동 상태 변경 금지.
