# 메일 중복정리 자동화 + DB 압축 (대표 지시 2026-06-21)

> 대표 질문: "같은 메일(메일고유코드)이 여러 개 들어오면 지금은 개수가 표시되는데 — 표현만 되는 거냐, 동일 메일은 하나만 받는 거냐? 용량을 줄여야 해서 같은 메일은 하나만 받게 해 용량을 최대한 줄이고 싶다."
> 대표 선택(AskUserQuestion): **"과거 중복정리 자동화 + DB 압축"**(옵션 A).

## 사실 확인(코드 직접 검증)
- **신규 중복은 이미 1통만 저장됨**(표현만 X). `store_inbound`이 `dedup_hash`(Message-ID 우선 / 없으면 보낸이+제목+본문 완전일치)로 판별 → 이미 있으면 **새로 저장 안 하고**(early return) 기존 1통의 `dup_count`만 +1. 첨부도 1벌만.
- **3개 수신 경로 모두 dedup 통과**: 하이웍스 가져오기(`/admin/mail-fetch/run`)·외부 인바운드(Worker)·자동 가져오기 스케줄러 — 전부 `message_id` 전달.
- 첨부는 DB(`mail_attachments.data` BLOB)에 저장("POC 단계") = 용량 주범.
- 빠져 있던 것: ① 과거(도입 전) 중복 자동정리 없음(수동 🔁 버튼만·휴지통행) ② VACUUM 수동 버튼만.

## 구현 (mono `<커밋>`)
### 1) `app/mail_store.py` — `dedup_inbox(c, user_id, hard=False)`
- `hard=False`(기본): 기존대로 **휴지통 소프트삭제**(복구 가능) — 사람이 누르는 수동 🔁 정리용.
- `hard=True`: 중복 사본을 **첨부(BLOB)까지 영구삭제**, 원본 1통·읽음·별표·`dup_count`는 100% 보존 → **정보손실 0**. 휴지통에 안 쌓여 **용량이 실제로 줄어듦**. 신규를 아예 안 쌓는 `store_inbound`과 같은 원리.

### 2) `app/main.py` — 자동 가져오기 스케줄러 연결
- `_mailfetch_run_owner`: 새 메일 적재 후 `dedup_inbox(c, owner_id, hard=True)` 자동 호출(과거 잔존 중복 정리·보통 도입 직후 1회만 큼). 영구삭제 누계를 전역 `_mail_dedup_removed_since_vacuum`에 적산.
- `_maybe_vacuum_mail_db()`: **하루 1회·새벽 2~7시(KST)·직전에 지운 중복이 있을 때만** VACUUM(autocommit 별도 연결)으로 DB 파일 물리 축소. 업무시간 락 회피. 즉시 압축은 기존 수동 버튼 `/admin/mail-purge/vacuum`.
- `_mail_fetch_tick` 매 사이클 끝에 `_maybe_vacuum_mail_db()` 호출.

## 검증
- `_검증/mail_dedup_hard_test.py` **22/22 PASS**: 영구삭제(첨부 포함)·원본/읽음/별표/`dup_count` 보존·휴지통 모드·답장 불가침(본문 다르면 안 묶임)·사용자 격리·NULL 백필·`_dedup_hash` 규칙.

## 안전 원칙
- 자동=영구삭제지만 **진짜 같은 메일(Message-ID 또는 완전일치)만** + **원본 1통 무조건 보존** → 잃는 정보 0([[feedback_data_connectivity]]).
- 수동 🔁 버튼은 보수적으로 휴지통(복구 가능) 유지.
- VACUUM은 새벽·하루1회·삭제분 있을 때만(과부하 방지).
