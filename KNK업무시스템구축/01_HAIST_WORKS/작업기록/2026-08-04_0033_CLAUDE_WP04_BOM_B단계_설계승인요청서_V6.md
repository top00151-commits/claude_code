# 1. B단계가 푸는 문제 — 한 문장

**설계가 확정한 BOM 과 구매팀이 돈을 써도 되는 근거를 분리하고, 설계가 바뀌었을 때 각각 몇 개를 사야 하는지 시스템이 답하게 한다.**

> Release 를 남기는 것만으로는 부족하다. 수주 12대 중 5대만 설계가 바뀌면
> **옛 BOM 7대분 · 새 BOM 5대분**을 각각 계산해야 한다. 사람이 엑셀로 하면 만든 이유가 없다.

# 4. 검증 기록과 Release 차단

## 4.1 항목별 검증 상태

| 코드 | 사람 이름 | 뜻 |
|---|---|---|
| `OPEN` | **미해결** | 아직 아무도 안 봄 |
| `CONFIRMED_OK` | **확인됨(문제없음)** | 사람이 보고 "이대로 맞다" 고 판단 |
| `FIXED` | **수정됨** | 고쳤다고 표시함 — **이것만으로는 부족** |
| `HOLD` | **보류** | 판단을 미룸 |

## 4.2 Release 허용 조건

**허용** — ① 모든 항목이 `확인됨` 이거나 ② `수정됨` + **재검증 성공 기록**

**차단** — `미해결` · **`보류`** · **파싱 실패** · **중복시트 미해결** 중 하나라도 있으면

⛔ **사람이 `수정됨` 을 선택한 사실만으로 `VERIFIED` 가 되지 않는다.**

## 4.3 차단을 어디에 두는가 — 6개 층 전부

| 층 | 무엇 |
|---|---|
| DB | 제약·트리거로 잘못된 상태 조합을 못 만들게 |
| 서버 함수 | 화면을 거치지 않고 직접 불러도 `PermissionError` |
| 라우트 | 403 / 검증 실패 응답 |
| 화면(HTML) | 버튼을 아예 안 그림 |
| 화면(JS) | 잠금 — **친절함이지 차단이 아님** |
| 안내문 | 왜 안 되는지 사람 말로 |

⛔ **화면에서 버튼만 숨기고 요청이 실행되는 상태는 차단으로 인정하지 않는다.**

## 4.4 검증 무효

- **원본 업로드를 수정하지 않는다** · `VERIFICATION_VOID` 로 만들어 **Release 근거 불가**
- **사유 · 처리자 · 일시** 기록 · 데이터를 고치려면 **새 업로드**
- 이미 그 업로드로 Release 가 발행됐다면 **§8.7**

# 5. Release 적용범위 — 장비대수를 **고정**한다

## 5.1 내용범위

**한 Release 는 선택된 업로드의 활성 BOM 전체 스냅샷을 보존한다.** 품목 일부만 골라 Release 하지 않는다.

## 5.2 적용범위 유형 4종

| `scope_type` | 사람 이름 | 적용대상 |
|---|---|---|
| **`PROJECT_SNAPSHOT`** | **관리번호 전체 (발행 시점)** | 발행 시점 그 관리번호 아래 수주번호 전체 |
| **`SALES_ORDER_SET`** | **선택 수주번호** | 선택한 수주번호 1개 이상 |
| **`UNIT_SET`** | **선택 호기** | 선택한 **확정(CONFIRMED) 호기** 1개 이상 |
| **`SALES_ORDER_QUANTITY`** | **수주번호 + 적용대수** | 선택 수주번호 + 사람이 정한 적용대수 |

### 5.2.1 모든 유형이 **행으로 펼쳐져 저장**된다

| `scope_type` | `bom_release_effectivities` 행 |
|---|---|
| `PROJECT_SNAPSHOT` | 발행 시점 관리번호 아래 **수주번호마다 1행** |
| `SALES_ORDER_SET` | 선택 **수주번호마다 1행** |
| `UNIT_SET` | 선택 **확정 호기마다 1행** |
| `SALES_ORDER_QUANTITY` | 선택 **수주번호마다 1행** |

### 5.2.2 ⭐⭐ 모든 행이 **`sales_order_id` 를 반드시 가진다**

⚠ **이것이 V5 에서 가장 크게 고친 곳이다.**

**왜 필요한가** — KNK 실제 업무는 이렇게 흐른다.

```
① 개발 초기      : SALES_ORDER_QUANTITY 로 수주A 12대 확정
② 이후          : 호기가 확정됨
③ 그중 5호기만  : UNIT_SET 으로 설계 변경
```

V5 처럼 **수주 행은 `sales_order_id` 만, 호기 행은 `project_unit_id` 만** 가지면
**같은 수주의 같은 장비인데도 "안 겹친다" 고 판정**된다. → **12대가 그대로 남고 5대가 새로 생겨 17대분을 산다.**

**확정 계약**

| | |
|---|---|
| 1 | **모든 Effectivity 행은 소속 `sales_order_id` 를 반드시 가진다** (`NOT NULL`) |
| 2 | `UNIT_SET` 행은 **`sales_order_id` 와 `project_unit_id` 를 함께** 가진다 |
| 3 | `project_unit_id` 가 있으면 **그 호기의 실제 소속 수주번호와 `sales_order_id` 가 일치**해야 한다 |
| 4 | `UNIT_SET` 행은 **`equipment_qty_snapshot = 1`** |
| 5 | 수주수량 범위와 호기 범위가 겹치면 — **호기 1행이 같은 수주의 수량 잔량 1대를 소비**한다 |
| 6 | 호기에서 수주수량 범위로 **되돌아가는** 변경은 대상이 모호하므로 — **어느 기존 유효 구간을 대체하는지 발행자가 명시적으로 선택**한다 |

⛔ **"`sales_order_id` 와 `project_unit_id` 를 동시에 채우지 않는다" 는 규칙은 폐기한다.**

### 5.2.2.1 ⭐ "호기의 소속 수주" 는 **하나가 아니다** — 판정 규칙

⚠ WP-03 실측: **한 호기가 여러 수주에 활성 연결될 수 있다.**
같은 호기가 최초·추가·변경 발주에 모두 나오는 것은 **KNK 정상 업무**다 (WP-03 F-02).

| 저장소 사실 (`project_unit_order_links`) | |
|---|---|
| `uq_punit_orderlink_active` = `(project_unit_id, order_id, relation_type) WHERE active=1` | **한 호기 : 여러 수주 활성 연결 가능** |
| `uq_punit_orderlink_origin` = `(project_unit_id) WHERE active=1 AND relation_type='ORIGIN'` | **활성 `ORIGIN` 은 호기당 정확히 1개** |

**확정 계약**

| | |
|---|---|
| 1 | `sales_order_id` 는 그 호기의 **활성 연결(`active=1`) 의 `order_id` 중 하나**여야 한다 |
| 2 | **기본 제안값은 활성 `ORIGIN` 의 수주** (호기당 정확히 1개이므로 모호하지 않다) |
| 3 | 활성 연결이 여럿이면 **발행자가 어느 수주 몫인지 명시 선택**한다 |
| 4 | ⛔ **활성 연결에 없는 수주를 넣으면 거부** |
| 5 | ⛔ **활성 연결이 하나도 없는 호기는 `UNIT_SET` 에 넣을 수 없다** |

### 5.2.2.2 ⚠ 수주가 없으면 Release 를 발행할 수 없다

모든 Effectivity 행이 `sales_order_id` 를 가져야 하므로 — **수주번호가 하나도 없는 관리번호는 Release 발행 대상이 아니다.**

| | |
|---|---|
| 왜 그런가 | Release 는 **구매근거**다. 돈을 쓰는 근거이므로 **어느 수주 몫인지** 반드시 있어야 한다 |
| 선행 설계는? | 업로드·검증까지는 된다. **`DRAFT`(임시 저장) 상태로 보드에 담긴다** |
| 화면 | 수주가 없으면 **발행 버튼을 그리지 않고**, *"수주번호가 등록되어야 확정본을 발행할 수 있습니다"* 로 안내한다 |
| 서버 | 신청 자체를 거부한다 |

### 5.2.3 ⭐ `equipment_qty_snapshot` — 모든 행이 장비대수를 고정한다

| 유형 | `equipment_qty_snapshot` |
|---|---|
| `PROJECT_SNAPSHOT` | 발행 시점 **각 수주번호의 확정 장비대수** 복사·고정 |
| `SALES_ORDER_SET` | 선택 수주번호의 **발행 시점 확정 장비대수** 복사·고정 |
| `UNIT_SET` | **`1` 고정** (호기 1행 = 1대) |
| `SALES_ORDER_QUANTITY` | **사람이 확정한 적용대수** · 사유 필수 |

- **`NOT NULL` · `>= 1`** · **발행 후 절대 수정하지 않는다**

> **왜 고정하나**: 수주 표의 현재 수량을 나중에 읽으면 **수주 수량이 바뀔 때 과거 Release 의
> 필요부품 수량도 소급해서 바뀐다.** Release 불변 원칙과 정면 충돌한다.

### 5.2.4 부품 필요수량 = 곱셈으로만

```
부품 필요수량 = qty_per_equipment × 유효 equipment_qty_snapshot(= 잔량)
```

⛔ **부품 필요수량을 스냅샷에 저장하지 않는다.** 잔량이 바뀌면 틀린 값이 남는다.

### 5.2.5 미래는 자동으로 들어오지 않는다

- **`PROJECT_SNAPSHOT` 은 발행 시점 스냅샷이다.** 이후 생기는 수주번호·호기는 **자동 편입하지 않는다**
- 새 수주에 적용하려면 **새 Release 를 발행**한다
- 화면에는 **`관리번호 전체 (2026-08-05 기준)`** 처럼 **발행 시점을 함께 표시**한다

### 5.2.6 호기는 **확정 호기만**

- **`project_units.unit_state='CONFIRMED'` 인 호기만**
- **개발·미확정(`PROVISIONAL`)** 은 번호·구성이 계속 바뀌므로 쓰지 않는다 (WP-03 확정)
- 취소(`CANCELLED`) 호기도 안 된다
- 미확정 단계에서 범위를 좁혀야 하면 **`SALES_ORDER_QUANTITY`** 를 쓴다

🔴 **A안 ≠ C안 이 112건.** ⭐ **12~23대 수주가 실재 5건** — 부분수량 변경은 반드시 설계해야 한다.

### 5.3.2 A안은 **기본 제안값**이다 — 자동 확정값이 아니다

**A안을 기본 제안값으로 쓴다.** 근거: 851행 전수 `qty=1` · WP-03 호기 규칙 일치.

⛔ **그러나 자동 확정하지 않는다.**

1. 개발호기와 호기정보는 **변경될 수 있다** (대표 확정)
2. `project_items` 와 **112건이 어긋난다**
3. **호기는 구매업무의 최상위 필수 Key 가 아니다**

### 5.3.3 Release 발행 화면 계약

**화면에 아래 6가지를 함께 보인다.**

| | 무엇 |
|---|---|
| 1 | **A안** — 정식 호기 라인 행 수 |
| 2 | **C안** — `project_items` ASSEMBLY `qty` |
| 3 | **두 값의 일치·불일치** |
| 4 | 확정할 **`equipment_qty_snapshot`** |
| 5 | 불일치 시 **확인사유** |
| 6 | **확인자 · 확인일시** |

| 상황 | 처리 |
|---|---|
| **A = C** | A값을 **기본 제안**하되 **사람이 확인**한다 |
| **A ≠ C** | **경고**하고 확정대수·**사유를 사람이 입력**한다 |
| **A만 있음** / **C만 있음** | 있는 값을 **참고로 보이되 사유를 남긴다** |
| **둘 다 없음** | **`MANUAL` 만 허용** · 수동 확정대수와 **사유 필수** |
| **발행 후** | `equipment_qty_snapshot` 을 **변경하지 않는다** |

⛔ **시스템이 A·C 중 하나를 임의로 고르지 않는다.** 어느 경우에도 **확인자와 확인일시가 남는다.**

### 5.3.4 ⭐ 출처와 확정값이 어긋나면 저장되지 않는다

⚠ 화면 규칙만으로는 **직접 SQL·배치가 어긋난 값을 넣는 것**을 못 막는다. 아래를 **강제**한다.

| `qty_source` | 강제 |
|---|---|
| **`ORDER_ITEMS_HOGI`** | `qty_a_value` **NOT NULL** AND **`equipment_qty_snapshot = qty_a_value`** |
| **`PROJECT_ITEMS_ASSEMBLY`** | `qty_c_value` **NOT NULL** AND **`equipment_qty_snapshot = qty_c_value`** |
| **`MANUAL`** | `qty_confirm_reason` **필수** |

| 상황 | 강제 |
|---|---|
| **A만 있음** 또는 **C만 있음** | `qty_confirm_reason` **필수** |
| **A·C 둘 다 있고 불일치** | `qty_confirm_reason` **필수** |
| **A·C 둘 다 없음** | **`qty_source='MANUAL'` 만 허용** + `qty_confirm_reason` **필수** |

→ 같은 행 안에서 판정되는 것은 **DB CHECK**(§15.2 E4~E9), 다른 표를 봐야 하는 것은 **서버 + 자동시험**.

## 5.4 불변성

**발행된 Release 의 스냅샷은 절대 수정하지 않는다.** (강제 방법 = §16)

# 7. 신청·승인·반려

## 7.1 세 역할

| 역할 | 누구 | 규칙 |
|---|---|---|
| **업로더** `uploaded_by` | 파일을 등록한 사람 | 보조·대행 가능 |
| **신청자** `requested_by` | 그 설계를 **책임지고** Release 를 요청할 권한이 있는 설계담당자 | **업로더와 같아도 되고 달라도 된다** |
| **승인자** `approved_by` | 설계책임자 (또는 §7.3 대체 승인자) | ⛔ **신청자와 반드시 다르다** |

## 7.2 전이

| 단계 | 누가 | 무엇을 | 전이 |
|---|---|---|---|
| **① 신청** | 신청자 | 검증완료 업로드 지목 + 적용범위·**확정대수** 선언 | (생성) → `PENDING` |
| **② 발행** | 승인자 | 스냅샷·적용범위·대수·**대체관계**를 보고 발행 | `PENDING` → `RELEASED` |
| **②′ 반려** | 승인자 | 잘못된 신청을 되돌림 | `PENDING` → `REJECTED` |

## 7.3 ⛔ 자가승인 예외는 열지 않는다

- **신청자와 승인자는 항상 다른 사람이다**
- 설계담당자가 한 명뿐이면 **대표 또는 지정 임원이 대체 승인자**
- **대체 승인은 `approver_role` 과 `substitute_reason` 을 필수로 기록**
- **`SINGLE_APPROVER` 자가승인 예외는 V1 에서 열지 않는다**

## 7.4 반려

| | 계약 |
|---|---|
| 전이 | **`PENDING` → `REJECTED`** |
| 누가 | 승인자 (신청자는 자기 신청을 반려할 수 없다) |
| **사유** | **필수.** 빈 값이면 거부 |
| 기록 | **반려자 · 반려사유 · 반려일시** · 신청자·신청일시도 보존 |
| 지위 | ⛔ **반려된 신청은 구매근거가 아니다** |
| 재신청 | **새 신청(새 행)**. 반려된 행을 되살리지 않는다 |
| 화면 | 신청자에게 **왜 반려됐는지** 보인다 |

## 7.5 ⭐ Release 발행은 **하나의 원자적 처리**다

아래 **전체가 한 트랜잭션**이다.

| | 단계 |
|---|---|
| 1 | Release 스냅샷 생성 (`bom_release_items`) |
| 2 | Effectivity 생성 (`bom_release_effectivities`) |
| 3 | **대체관계 및 잔량 검증·생성** (`bom_release_supersede`) |
| 4 | **변경영향행 생성** (`bom_change_impacts`) |
| 5 | 승인자·발행시각 기록 |
| 6 | **`PENDING` → `RELEASED` 상태전이** |

- **하나라도 실패하면 전부 되돌린다**
- ⛔ **`RELEASED` 인데 대체관계나 영향행이 일부만 존재하는 상태를 허용하지 않는다**
- 기존 Release 의 `SUPERSEDED` 전이(§8.4.3-4)도 같은 트랜잭션 안에서 일어난다

## 7.6 서버에서 막는 것

- ⛔ **신청자 = 승인자면 거부**
- ⛔ `VERIFIED` 가 아닌 업로드는 신청 자체가 안 된다
- ⛔ §4.2 차단 항목이 하나라도 있으면 신청 거부
- ⛔ **같거나 겹치는 적용대상**에 이미 `PENDING` 이 있으면 새 신청 거부 (§8.6)
- ⛔ **미확정·취소 호기**를 `UNIT_SET` 에 넣으면 거부
- ⛔ **호기의 소속 수주와 `sales_order_id` 가 다르면** 거부 (§5.2.2-3)
- ⛔ `equipment_qty_snapshot` 이 없거나 1 미만이면 거부
- ⛔ **출처와 확정값이 어긋나거나 필요한 사유가 없으면** 거부 (§5.3.4)
- ⛔ **초과 차감**이면 거부 (§8.4.3)
- ⛔ **조상 구간 재차감·순환관계**면 거부 (§8.3)

# 8. Release 상태 · 대체관계 · **잔량 자동계산**

## 8.1 상태

| 코드 | 사람 이름 | 뜻 |
|---|---|---|
| `PENDING` | **발행 대기** | 신청됨. 아직 구매근거 아님 |
| `REJECTED` | **반려** | 승인자가 되돌림. 구매근거 아님 |
| `RELEASED` | **발행됨** | ⭐ **이 상태만 구매근거로 쓸 수 있음** |
| `SUPERSEDED` | **대체됨** | **모든 Effectivity 잔량이 0**. 내용은 불변 보존 |
| `CANCELLED` | **취소** | 잘못 발행했고 **구매근거로 쓰이지 않은** 경우만 |

## 8.2 ⛔ `PARTIALLY_SUPERSEDED` 상태코드를 만들지 않는다

- 부분 대체는 **`bom_release_supersede` 관계에서 계산**한다
- **잔량이 남으면 `RELEASED` 를 유지**한다

> **왜**: 상태코드를 하나 더 만들면 *"부분대체도 구매근거가 되나?"* 를 매번 다시 판단해야 한다.
> `RELEASED` 만 구매근거라는 규칙을 그대로 두고, **어느 범위가 얼마나 죽었는지는 관계표가 답한다.**

## 8.3 ⭐⭐ 연속 변경 — **조상을 두 번 차감하지 않는다**

⚠ **이것이 V5 에서 두 번째로 크게 고친 곳이다.**

**무엇이 문제였나**

```
Rel.1 = 수주A 12대
Rel.2 = 그중 5대 변경
Rel.3 = Rel.2 의 5대를 다시 변경
```

`Rel.3` 이 `Rel.2` 뿐 아니라 **조상인 `Rel.1` 에도 관계를 만들면 `Rel.1` 이 한 번 더 차감**된다.
→ 실제로는 7대가 남아야 하는데 2대만 남는다. **수량이 이중으로 사라진다.**

### 8.3.1 확정 계약

| | |
|---|---|
| 1 | 신규 Release 는 **발행 직전 현재 유효한 잔량 구간만** 대체할 수 있다 |
| 2 | **이미 후속 Release 로 소비된 조상 구간을 다시 직접 차감하지 않는다** |
| 3 | 신규 Effectivity 하나가 **여러 기존 유효 구간을 대체할 수는 있지만**, **같은 장비 범위·수량을 두 번 소비할 수 없다** |
| 4 | **`old_release_id` 는 `new_release_id` 보다 먼저 발행된 Release** 여야 한다 |
| 5 | **자기참조와 순환관계는 금지**한다 |
| 6 | 기존 유효 구간 선택 · 잔량검사 · 관계 생성 · 상태전이는 **한 트랜잭션** (§7.5) |

### 8.3.2 소비 순서

신규 Effectivity 가 여러 유효 구간을 덮을 때는 **최신 구간부터 소비**한다.
(가장 최근 설계가 가장 먼저 교체되는 것이 업무 상식이고, 조상이 남아 있는 한 그 근거로 이미 산 물건이 있을 수 있기 때문)

**예시** — `Rel.1` 12대 → `Rel.2` 5대 → `Rel.3` 8대

| 순서 | 소비 | 결과 |
|---|---|---|
| ① | `Rel.2` 잔량 **5** 전부 | `Rel.2` 잔량 **0** |
| ② | 남은 3을 `Rel.1` 잔량 7 에서 | `Rel.1` 잔량 **4** |
| 합 | `Rel.3` = 8 | `Rel.1` 4 + `Rel.3` 8 = 12 ✅ |

⭐ **어느 경우에도 `Σ 유효 잔량 = 원래 장비대수` 가 유지된다.** 이것이 이중 차감 여부를 판정하는 불변식이다.

## 8.4 잔량 계산

### 8.4.1 계산식

```
Effectivity 유효 잔량 (remaining_qty)
  = equipment_qty_snapshot
  − Σ (그 Effectivity 를 덮은 관계들의 overlap_equipment_qty)

  단, 합계에 세는 관계는 new_release.status ∈ {RELEASED, SUPERSEDED} 인 것만.
      (REJECTED · CANCELLED 인 Release 가 만든 관계는 세지 않는다 — 차감이 되살아난다)
```

### 8.4.2 12대 → 5대

| | |
|---|---|
| `Rel.1` E1 | 수주A · `equipment_qty_snapshot = 12` |
| `Rel.2` E2 | 수주A · `equipment_qty_snapshot = 5` |
| 관계 1행 | `new=Rel.2 · old=Rel.1 · old_effectivity=E1 · new_effectivity=E2 · overlap=5 · kind=PARTIAL_QTY` |
| **E1 잔량** | **12 − 5 = 7** |
| `Rel.1` 상태 | 잔량 7 > 0 → **`RELEASED` 유지** |
| 품목별 필요수량 | `Rel.1` = 대당수량 × **7** / `Rel.2` = 대당수량 × **5** |

⛔ **사람이 7을 계산하지 않는다. 시스템이 답한다.**

### 8.4.3 강제규칙

| | 규칙 |
|---|---|
| 1 | **`overlap_equipment_qty` 는 기존 유효 잔량을 초과할 수 없다** |
| 2 | 발행과 잔량차감 관계 생성은 **한 트랜잭션** (§7.5) |
| 3 | **잔량이 0 인 Effectivity 만** 전부 대체된 것으로 본다 |
| 4 | **기존 Release 의 모든 Effectivity 잔량이 0 일 때만** `SUPERSEDED` |
| 5 | 일부 잔량이 남으면 `RELEASED` 유지 + **화면에 유효 잔량 표시** |
| 6 | ⛔ **잔량 계산을 사람이 수기로 판정하게 두지 않는다** |

> ⚠ 규칙 1 은 **다른 행들의 합계**를 봐야 하므로 DB `CHECK` 로 불가 → **서버 + 트랜잭션**(§15.12).

## 8.5 ⭐ 겹침 판정 — **수주번호를 공통 축으로**

모든 Effectivity 행이 `sales_order_id` 를 가지므로(§5.2.2), **같은 수주번호를 공통 축으로 비교**한다.

| 기존 행 | 신규 행 | 판정 |
|---|---|---|
| 수주 범위 (`project_unit_id` 없음) | 수주 범위 | 같은 수주면 겹침 · 수량만큼 소비 |
| 수주 범위 | **호기 행** | ⭐ **같은 수주면 겹침** — **호기 1행이 수량 잔량 1대를 소비** |
| **호기 행** | 같은 호기 행 | 겹침 · `FULL`(1대) |
| **호기 행** | 수주 범위 | ⭐ **대상이 모호** → **발행자가 어느 구간을 대체하는지 명시 선택** (§5.2.2-6) |
| 다른 수주 | — | **겹치지 않음** |

| `overlap_kind` | 언제 |
|---|---|
| **`FULL`** | 기존 행의 잔량 **전부**를 덮음 |
| **`PARTIAL_QTY`** | 기존 행의 잔량 **일부**만 덮음 |

## 8.6 동시 `PENDING` 차단

- **같거나 겹치는 적용대상**에 이미 `PENDING` 이 있으면 새 신청을 거부한다
- 판정은 §8.5 와 같다

## 8.7 "지금 적용되는 Release" 조회 — **목록이지 하나가 아니다**

⚠ *"가장 최근 Release 하나가 이긴다"* 는 **부분수량에서 틀렸다.**
12대 중 5대만 바뀌면 **`Rel.1` 7대와 `Rel.2` 5대가 동시에 유효**하다.

**조회 결과는 아래를 담은 목록이다.**

| 반환값 | 뜻 |
|---|---|
| **Release** | 적용 중인 확정본 |
| **Effectivity** | 대상 수주·호기 |
| **유효 장비대수** | 대체관계 차감 후 남은 수량 (§8.4.1) |
| **품목별 필요수량** | 대당수량 × 유효 장비대수 |

- **유효 잔량 0 은 목록에서 제외**한다
- 부분수량이면 **구 Release 잔량과 신 Release 수량을 함께** 반환한다
- 구매검토 화면은 **Release 별로 분리해** 보여 준다
- `PENDING` · `REJECTED` · `CANCELLED` 는 후보에서 뺀다

## 8.8 화면 표시

- 기존 Release 화면에 **`일부 범위 대체`** 를 **상태와 별도로** 표시
- **어느 수주·호기가 얼마나 대체됐는지** · **남은 잔량**을 함께 보인다

## 8.9 취소 · 무효 업로드 처리

| 상황 | 처리 |
|---|---|
| **설계 변경** | 새 Release 발행 + 겹치는 기존은 §8.3~8.5 규칙대로 |
| **잘못 발행 · 구매근거 미사용** | `CANCELLED` (사유 필수) |
| **이미 구매요청·발주에 사용됨** | ⛔ **취소로 지우지 않는다.** 새 Release + 영향분석(§11) |
| **신청이 잘못됨 (발행 전)** | `REJECTED` |

**무효 업로드로 이미 Release 가 발행된 경우**

| 그 Release 가 | 처리 |
|---|---|
| **구매근거로 쓰인 적 없음** | `CANCELLED` + 사유에 **무효 업로드 번호** |
| **이미 구매요청·발주에 쓰임** | ⛔ **취소하지 않는다.** 새 업로드 → 새 Release + **영향분석(§11)** |

- 원 Release 스냅샷은 **지우지 않는다**
- 화면에 **`근거 업로드가 무효 처리됨`** 을 상태와 **별도로** 표시
- ⛔ **무효 처리가 Release 상태를 자동으로 바꾸지 않는다**

# 9. 구매요청 ↔ Release 연결

## 9.1 ⛔ 구매요청 전체에 `release_id NOT NULL` 을 걸지 않는다

공용재고 보충 · 예비품 · 소모품 · 긴급구매 · BOM 외 수동 요청이 **전부 막힌다**.

## 9.2 근거유형은 **라인 단위**

| `material_request_items.source_type` | 필수 |
|---|---|
| **`BOM_RELEASE`** | **§9.3 배분행이 1개 이상** |
| `STOCK_REPLENISH` · `SPARE` · `CONSUMABLE` · `URGENT` · `MANUAL` | `source_reason` 필수 |

- 한 구매요청서 안에 **근거유형이 섞여도 된다**
- **`RELEASED` 가 아니면 구매요청 금지** 는 **`BOM_RELEASE` 라인에만**

## 9.3 ⭐ 배분표 — **수량 단위는 `부품 개수` 하나로**

⚠ **이것이 V5 에서 세 번째로 크게 고친 곳이다.**

**무엇이 문제였나** — V5 는 `allocated_equipment_qty`(몇 대분)와 `allocated_part_qty`(부품 몇 개)를 **둘 다 저장·검사**했다.

- 장비 1대당 부품 3개인데 조달 사정으로 **5개만 먼저 요청**하면 — **"몇 대분" 을 정수로 쓸 수 없다**
- 장비대수 합계를 Effectivity 전체에서 검사하면 — **서로 다른 BOM 품목이 각각 같은 12대에 필요한 정상 배분**을 중복으로 오인한다

### 9.3.1 확정 계약

```
material_request_item_release_allocations
```

| 칸 | 뜻 |
|---|---|
| `material_request_item_id` | 어느 구매요청 라인인가 |
| `bom_release_item_id` | 어느 Release 품목인가 |
| **`release_effectivity_id`** | **어느 적용범위(수주·호기)의 몫인가** |
| **`allocated_part_qty`** | ⭐ **부품 몇 개인가 — 무결성 계산의 유일한 기준** |
| 작성자 · 작성일시 | |

⛔ **`allocated_equipment_qty` 를 저장하지 않는다.** 차단 기준에서도 뺀다.
필요하면 화면에서 **`allocated_part_qty ÷ qty_per_equipment`** 로 **참고 표시**만 한다.

### 9.3.2 ⭐ 초과 판정은 **품목 × 적용범위 별로**

```
그 (품목, Effectivity) 의 구매가능 필요수량
  = qty_per_equipment × Effectivity 유효 잔량
    − 이미 유효한 구매요청에 배분된 부품수량
```

| | 규칙 |
|---|---|
| 1 | **`BOM_RELEASE` 라인은 배분행이 1개 이상** |
| 2 | **한 구매요청 라인이 여러 Effectivity 의 수량을 묶어** 구매할 수 있다 |
| 3 | 초과 여부는 반드시 **`(bom_release_item_id, release_effectivity_id)` 별로** 계산한다 |
| 4 | **취소된 구매요청 배분은 유효 합계에서 제외**한다 |
| 5 | ⛔ **제출·승인된 구매요청을 수정해 과거 합계를 바꾸지 않는다** |
| 6 | 초과가 필요하면 **§9.4 초과구매 계약**을 따른다 |
| 7 | **비BOM 근거유형은 이 표를 쓰지 않고** `source_reason` 을 쓴다 |

> ⭐ **서로 다른 BOM 품목이 같은 Effectivity 의 12대에 각각 배분되는 것은 정상**이다.
> 부품 A 12개 · 부품 B 24개가 같은 12대분이어도 **품목이 다르므로 서로 초과가 아니다.**

## 9.4 ⭐ 초과구매 (D-11) — 업무규칙에 **저장계약**을 붙인다

**확정된 KNK 업무규칙**

| | |
|---|---|
| 판단·진행자 | **구매담당자** |
| 절차 | 구매담당자가 **구매팀장에게 구두보고 후 진행** |
| 금액이 클 때 | **설계담당자에게 대체품을 요청**할 수 있다 |
| 대체품 기술승인자 | **설계담당자** (D-12) |

⚠ **구매팀장이 시스템 승인 버튼을 누른다는 뜻이 아니다.**
현행 업무 그대로 **구두보고 사실을 구매담당자가 기록**하는 계약이다.

### 9.4.1 저장계약 — 아래 의미를 반드시 보존한다

| 항목 | 계약 |
|---|---|
| **BOM 기준 필요수량** | Release 배분 합계 |
| **실제 요청수량** | 구매요청 수량 |
| **초과구매수량** | `실제 요청수량 − BOM 기준 필요수량` · **0 미만 불가** |
| **초과구매 사유** | 초과 시 **필수** |
| **처리 구매담당자** | **필수** |
| **구매팀장 보고대상** | 초과 시 **필수** |
| **구두보고 일시** | 초과 시 **필수** |
| **대체품 요청 여부** | 기록 |
| **대체품 승인자** | 요청이 **실제 대체품 적용으로 이어질 때 설계담당자 필수** |

### 9.4.2 수량식 — 맞지 않으면 제출을 막는다

```
구매요청 실제수량 = Σ BOM 배분수량 + 승인된 초과구매수량
```

⛔ **이 식이 맞지 않으면 제출을 차단한다.** 초과구매가 정상 필요수량처럼 섞이지 않게 한다.

# 11. 발주 후 BOM 변경 — 품목·Effectivity 단위

## 11.1 계약

| | |
|---|---|
| 1 | **기존 Release · 구매요청 · 발주 근거는 수정·삭제하지 않는다** |
| 2 | 새 Release 발행 시 **기존 구매요청·발주에 영향이 있는지 표시** |
| 3 | **영향 미검토 상태인 변경품목은 추가 구매요청을 차단** |
| 4 | 발주 취소 · 수량변경 · 대체품 전환은 **구매 변경이력으로 보존** |

## 11.2 무엇이 바뀌었는지를 **품목과 적용범위 단위**로

| 칸 | |
|---|---|
| `new_release_id` | 어느 Release 발행이 이 영향을 만들었나 |
| `old_release_item_id` / `new_release_item_id` | **어느 품목이** 바뀌었나 |
| `old_effectivity_id` / `new_effectivity_id` | **어느 적용범위에서** 바뀌었나 |
| `material_request_item_id` (선택) | 영향받는 구매요청 라인 |
| `po_item_id` (선택) | 영향받는 발주 라인 |
| `change_kind` | **추가 / 삭제 / 수량변경 / 사양변경 / Maker변경 / 대체품** |
| `impact_state` · 검토자 · 사유 · 일시 | |

- **품목 추가**는 `old_release_item_id` 가 없고, **품목 삭제**는 `new_release_item_id` 가 없다 — **허용**
- ⛔ **둘 다 NULL 인 행은 금지**

## 11.3 `SET NULL` + **상세 스냅샷**

`po_items.po_id` 가 **`ON DELETE CASCADE`** 이므로(실측), 발주가 지워지면 발주 라인도 사라진다.
영향기록이 그 라인을 `RESTRICT` 로 붙들면 **발주 삭제 업무 자체가 잠긴다.**

### 11.3.1 계약

| | |
|---|---|
| `po_item_id` | **FK `ON DELETE SET NULL`** |
| `material_request_item_id` | **FK `ON DELETE SET NULL`** |
| 목적 | 참조가 끊겨도 **감사근거가 남게** |

### 11.3.2 필수 스냅샷 — 문서번호·줄번호만으로는 부족하다

| 발주 영향 | 구매요청 영향 |
|---|---|
| `po_number_snapshot` | `request_no_snapshot` |
| `po_line_no_snapshot` | `request_line_no_snapshot` |
| `part_no_snapshot` | `requested_part_no_snapshot` |
| `ordered_qty_snapshot` | `requested_qty_snapshot` |
| `po_status_snapshot` | `request_status_snapshot` |

> ⭐ **저장소가 이미 쓰는 방식**이다 — `po_items` 자신이 `part_no_snapshot`·`part_name_snapshot`·
> `spec_snapshot` 을 갖고, `project_units.seed_order_item_id` 도 이미 `SET NULL` 이다(실측 확인).

### 11.3.3 ⛔ `SET NULL` 은 **삭제 권한을 넓히는 규칙이 아니다**

| | |
|---|---|
| 1 | **작성중·미발행 발주만** 기존 WP-01 가드 범위에서 물리삭제 가능 |
| 2 | **발주완료 이후에는 물리삭제 금지** — 취소·변경이력으로 처리 |
| 3 | **입고·검수·세금계산서·변경영향에 사용된 발주는 물리삭제 금지** |
| 4 | `SET NULL` 이 발동해도 **영향기록과 스냅샷은 삭제하지 않는다** |

⛔ **"SET NULL 이니까 지워도 된다" 로 읽으면 안 된다.** 사고가 나도 기록이 남게 하는 **안전장치**다.

### 11.3.4 왜 어떤 표는 `SET NULL` 이고 어떤 표는 `RESTRICT` 인가

같은 `po_items` 를 가리키는데 정책이 다르다. **일부러다. 통일하지 않는다.**

| 표 | 정책 | 그 표가 무엇인가 | 그래서 |
|---|---|---|---|
| **`bom_change_impacts`** | **`SET NULL`** | **기록**(감사) — *"그때 이런 영향이 있었다"* | 발주가 사라져도 **기록은 남아야** 하고, 기록이 **삭제를 막을 이유는 없다**. 스냅샷 5종이 사실을 보존 |
| **`po_item_request_allocations`** | **`RESTRICT`** | **업무 연결** — *"이 발주가 이 요청을 쓰고 있다"* | 살아 있는 연결이다. 말없이 끊기면 **요청이 발주된 건지 알 수 없어진다** |

**판단 기준 한 줄**: **지난 일의 기록이면 `SET NULL` + 스냅샷, 지금 살아 있는 연결이면 `RESTRICT`.**

| **(생성)** | `UNREVIEWED` | 시스템 | **Release 발행 트랜잭션 안에서만** (§7.5-4) |
| `UNREVIEWED` | `REVIEWED` | 사람 | **검토자·사유 필수** |
| `REVIEWED` | `RESOLVED` | 사람 | 조치 완료 기록 |
| `RESOLVED` | **(없음)** | — | ⛔ 되돌리지 않는다 |
| 어느 상태든 → **행 삭제** | **(없음)** | — | ⛔ **DB 가 막는다** (§16.2) |

⛔ **`UNREVIEWED` 인 품목은 추가 구매요청을 차단**한다 (§11.1-3).
⛔ **상태전이에서 바꿀 수 있는 칸은 `impact_state` · `reviewed_by` · `review_reason` · `reviewed_at` 넷뿐이다** (§16.2).

⛔ **표에 없는 전이는 서버가 거부한다.**

**UNIQUE — ⚠ 한 칸으로 묶지 않는다 (NULL 함정)**

```sql
-- ⛔ UNIQUE (release_id, sales_order_id, project_unit_id) 는 작동하지 않는다.
--    SQLite·PostgreSQL 둘 다 UNIQUE 안의 NULL 을 "서로 다른 값" 으로 본다.
-- 수주 범위 행 — 한 Release 에 수주당 1개
CREATE UNIQUE INDEX uq_bre_order ON bom_release_effectivities(release_id, sales_order_id)
    WHERE project_unit_id IS NULL;
-- 호기 행 — 한 Release 에 호기당 1개
CREATE UNIQUE INDEX uq_bre_unit  ON bom_release_effectivities(release_id, project_unit_id)
    WHERE project_unit_id IS NOT NULL;
```

**CHECK**

| | 내용 |
|---|---|
| **E1** | ⭐ `sales_order_id` 는 **`NOT NULL`** (모든 행이 수주를 가진다 — §5.2.2) |
| **E2** | ⭐ `project_unit_id IS NOT NULL` → `sales_order_id IS NOT NULL` (E1 로 자동 충족. **소속 일치는 서버**) |
| E3 | `equipment_qty_snapshot >= 1` |
| **E4** | `project_unit_id IS NOT NULL` → **`equipment_qty_snapshot = 1`** |
| **E5** | `qty_source='ORDER_ITEMS_HOGI'` → `qty_a_value` NOT NULL AND **`equipment_qty_snapshot = qty_a_value`** |
| **E6** | `qty_source='PROJECT_ITEMS_ASSEMBLY'` → `qty_c_value` NOT NULL AND **`equipment_qty_snapshot = qty_c_value`** |
| **E7** | `qty_source='MANUAL'` → `qty_confirm_reason` NOT NULL AND `<> ''` |
| **E8** | `qty_a_value IS NULL` AND `qty_c_value IS NULL` → **`qty_source='MANUAL'`** |
| **E9** | (`qty_a_value IS NULL`) <> (`qty_c_value IS NULL`) **또는** (둘 다 있고 `qty_a_value <> qty_c_value`) → `qty_confirm_reason` NOT NULL AND `<> ''` |

**서버가 추가로 강제 (CHECK 불가 — §15.12)**

- ⭐ **`sales_order_id` 가 그 호기의 `project_unit_order_links` 활성(`active=1`) 연결에 있는지** (§5.2.2.1) ← **다른 표 조회**
- ⛔ **활성 연결이 하나도 없는 호기**는 `UNIT_SET` 불가
- ⛔ **수주번호가 하나도 없는 관리번호**는 Release 신청 자체 거부 (§5.2.2.2)
- `scope_type='UNIT_SET'` → 모든 행에 `project_unit_id` · **`unit_state='CONFIRMED'`**
- `scope_type ≠ 'UNIT_SET'` → 모든 행에 `project_unit_id IS NULL`
- 지정 수주·호기가 **`bom_releases.project_id` 소속**인지
- `PROJECT_SNAPSHOT` 은 **`scope_asof` 시점 스냅샷 그대로** — 임의 편집 금지

**삭제정책** — ⛔ 행 삭제 없음. 모든 FK `RESTRICT`.

| | 내용 |
|---|---|

| I3 | `po_item_id IS NOT NULL` → `po_number_snapshot` · `po_line_no_snapshot` · `ordered_qty_snapshot` NOT NULL |
| I4 | `material_request_item_id IS NOT NULL` → `request_no_snapshot` · `request_line_no_snapshot` · `requested_qty_snapshot` NOT NULL |

| I6 | `change_kind='REMOVED'` → `new_release_item_id IS NULL` |

**삭제정책** — ⛔ **물리삭제를 DB 가 막는다** (§16.2).

**⛔ UNIQUE 를 두지 않는다 — 일부러다**

1. 이 칸들은 **대부분 NULL 을 허용**한다. §17.3 대로 **두 DB 모두 UNIQUE 안의 NULL 을 서로 다르게 보므로 실제로 막지 못한다** — 있으나 마나 한 제약이 되어 "막고 있다"는 착각만 준다
2. 같은 품목이 **여러 발주 라인에 영향**을 줄 수 있어 중복처럼 보이는 행이 정상이다
3. 영향 행 생성은 **Release 발행 한 트랜잭션 안에서 시스템이** 만든다 (§7.5-4). 사람이 손으로 넣는 표가 아니다

→ 중복 방지는 **생성 시점 서버 로직**이 담당한다. 개발자가 임의로 UNIQUE 를 추가하지 않는다.

| 구매검토 | VINA 참고재고 5종 세트(§12.1) |

**`material_request_items` CHECK** — R1 `source_type <> 'BOM_RELEASE'` → `source_reason` NOT NULL AND `<> ''`
R2 ⚠ *"`BOM_RELEASE` 면 배분행 ≥ 1"* 은 **다른 표**를 봐야 하므로 CHECK 불가 → **서버 + 트리거**

## 15.11 `material_request_items.request_id` FK 보강

**운영 0건인 지금이 무결성을 보강할 가장 안전한 시점이다.**

| | 계약 |
|---|---|
| 추가 | **`request_id` FK → `material_requests(id)`** |
| 삭제정책 | **`ON DELETE RESTRICT`** |
| 업무 규칙 | **제출·승인 이후 물리삭제 금지** — 취소 상태로 처리 |
| 신규 배분표 | 실제 `material_request_items(id)` 를 FK 로 참조 |
| 나머지 FK 부재 | `part_id` · `registered_part_id` · `quote_supplier_id` 등은 **별도 기술부채 목록** (범위 아님) |
| 실행 시점 | ⛔ **표 재작성은 V6 승인 후 B-1 리허설에서만** |

⚠ SQLite 는 `ALTER TABLE` 로 FK 를 추가할 수 없어 **표 재작성**이 필요하다.
**WP-03 에서 겪은 `PRAGMA legacy_alter_table` 함정**(RENAME 이 다른 표의 FK 이름까지 바꿈)을 B-1 리허설에서 반드시 재현·확인한다.

## 15.12 DB CHECK 로 **못 하는 것** — 서버가 강제한다

**CHECK 는 같은 행 안의 값만 볼 수 있다.**

| 규칙 | 왜 CHECK 불가 | 어디서 |
|---|---|---|
| **호기 소속 수주 = `sales_order_id`** | `project_units` 조회 | 서버 + 라우트 + 화면 |
| `UNIT_SET` 은 **확정 호기만** | `unit_state` 는 다른 표 | 서버 + 화면(선택지 제한) |
| 지정 수주·호기가 **그 관리번호 소속**인지 | 다른 표 | 서버 |
| `FIXED` → 재검증 일치해야 `VERIFIED` | 여러 행 종합 | §4.2 서버 |
| **겹치는 `PENDING` 차단** | 다른 행 비교 | §8.6 서버 |
| **`overlap` ≤ 유효 잔량** | 다른 행 **합계** | §8.4.3 서버 + 트랜잭션 |
| **조상 재차감·순환 금지 · 발행순서** | 관계 그래프 | §8.3 서버 |
| **배분 합계 ≤ 구매가능 필요수량** | 다른 표 합계 | §9.3.2 서버 |
| **`requested_qty = Σ배분 + 초과`** | 다른 표 합계 | §9.4.2 서버 |
| `BOM_RELEASE` 라인은 배분행 ≥ 1 | 다른 표 | 서버 + 트리거 |
| 잔량·부분대체 계산 | 여러 표 조인 | §8.4 서버 |

⛔ **"DB 제약이 있으니 됐다" 로 끝내지 않는다.** §4.3 6개 층을 전부 채운다.

# 16. 불변성 보호 — **DB 에서도 막는다**

## 16.1 왜 DB 까지 가는가

**문법이 다른 것은 트리거를 두 벌 쓰면 되는 일이지, 보호를 없앨 이유가 아니다.**

> 게이트 판정(2026-08-03 23:45) — *"DB 문법이 다르다는 이유로 보호를 제거하지 않는다.
> 문법은 달라도 **불변이라는 업무 의미**는 같아야 한다."*

현재 WORKS 에는 **직접 SQL 을 실행하는 경로가 많다.** 코드 검색만으로는 `절대 수정 불가` 를 보장할 수 없다.

## 16.2 보호 대상과 규칙

| 표 | 막는 것 |
|---|---|
| `bom_release_items` | Release 가 `RELEASED`/`SUPERSEDED`/`CANCELLED` 이면 **`UPDATE`·`DELETE` 거부** |
| `bom_releases` | **상태전이용 칸 외** 스냅샷 기준칸(`project_id`·`release_no`·`upload_id`·`scope_type`·`scope_asof`·`external_revision*`·`requested_by`) 변경 **거부** |
| `bom_release_effectivities` | Release 발행 후 **`UPDATE`·`DELETE` 거부** |
| `bom_release_supersede` | **`UPDATE`·`DELETE` 거부** |
| **`bom_change_impacts`** | ⭐ 아래 §16.3 |

## 16.3 ⭐ 변경영향 감사행도 보호한다

**이 표는 KNK 변경 중심 ERP 에서 다음을 증명하는 감사기록**이다 — *어떤 설계변경이 있었나 · 어떤 구매요청·발주가 영향받았나 · 누가 검토하고 어떻게 처리했나.*

| | 규칙 |
|---|---|
| 1 | ⛔ **물리삭제를 DB 에서 금지**한다 |
| 2 | **생성근거 칸은 생성 후 수정 금지** — `new_release_id` · `old/new_release_item_id` · `old/new_effectivity_id` · `change_kind` · **구매요청·발주 스냅샷 전부** |
| 3 | **바꿀 수 있는 칸은 넷뿐** — `impact_state` · `reviewed_by` · `review_reason` · `reviewed_at` |
| 4 | `po_item_id` · `material_request_item_id` 의 **`SET NULL` 은 FK 동작에 의한 경우만** 허용 |
| 5 | **직접 SQL 로 스냅샷을 NULL·다른 값으로 바꾸는 시험**과 **행 삭제 시험**을 **SQLite·PostgreSQL 양쪽에서** 수행한다 |

## 16.4 구현 방식 — 양쪽 DB 에 **같은 의미**로

| | |
|---|---|
| 1 | **SQLite 용 보호 트리거** (`BEFORE UPDATE` / `BEFORE DELETE` + `RAISE(ABORT, …)`) |
| 2 | **PostgreSQL 용 동등 보호** (트리거 함수 + `RAISE EXCEPTION`, 또는 권한정책) |
| 3 | **두 DB 에서 같은 위반 시나리오가 모두 실패하는 자동시험** |
| 4 | **상태전이 함수는 허용된 칸만** 변경 |

## 16.5 서버·화면 층도 그대로 둔다

| 층 | 방법 |
|---|---|
| **서버 함수** | 스냅샷 칸을 바꾸는 **함수를 만들지 않는다**. 있는 것은 삽입·상태전이뿐 |
| **라우트** | 수정 라우트 없음 |
| **화면** | 수정 UI 없음 · *"발행된 확정본은 고칠 수 없습니다. 새 Release 를 발행하세요"* |
| **검사** | 배포 전 검사기가 보호 대상 표에 대한 `UPDATE`/`DELETE` 구문을 훑는다 |

⭐ **DB 트리거가 마지막 방어선이고, 위 네 층은 그 앞에 선다.** 어느 하나로 대신하지 않는다.

# 17. SQLite ↔ PostgreSQL 동일 의미

## 17.1 양쪽에서 같은 의미 — **써도 된다**

| 기능 | 확인 |
|---|---|
| `PRIMARY KEY` · `NOT NULL` · `UNIQUE` | 동일 |
| `CHECK` (같은 행 안 값만) | 동일 |
| `FOREIGN KEY … REFERENCES` + `ON DELETE RESTRICT`/`SET NULL` | 동일 (단 §17.3) |
| **부분 고유 인덱스** `CREATE UNIQUE INDEX … WHERE …` | **양쪽 지원** — WP-03 `uq_punit_orderlink_active` 에서 이미 사용 중 |
| **행 변경 거부 트리거** | 양쪽 지원 (**문법은 다름** → §16.4 대로 각각 작성 + 같은 시나리오로 시험) |

## 17.2 한쪽에만 있다 — ⛔ **쓰지 않는다**

| 기능 | 있는 쪽 | 왜 |
|---|---|---|
| `EXCLUDE USING gist` (범위 배타) | PostgreSQL | SQLite 에 없다 → 겹침·잔량은 **서버 판정**(§8) |
| `DEFERRABLE INITIALLY DEFERRED` | PostgreSQL | 설계에서 순환 참조를 만들지 않는다 |
| `ALTER TABLE … ADD CONSTRAINT` | PostgreSQL | SQLite 는 표 재작성 필요 → **처음 만들 때 제약을 다 넣는다** |

## 17.3 ⚠ 의미가 달라 조심할 것

| | SQLite | PostgreSQL | B단계 대응 |
|---|---|---|---|
| **FK 강제** | **연결마다 `PRAGMA foreign_keys=ON`** (기본 OFF) | 항상 | ✅ `get_db()` 가 켠다(`app/database.py:122`). ⚠ **삭제 경로 여러 곳이 명시적으로 OFF 한다** → **FK 만 믿지 말고 서버 검사를 둔다** |
| **🔴 UNIQUE 안의 NULL** | NULL 끼리 서로 다르다고 봄 | **동일**(기본 `NULLS DISTINCT`) | ⭐ **두 DB 가 똑같이 뚫린다** → 부분 고유 인덱스로 분리 (§15.2) |
| **타입 강제** | 안 함(동적 타입) | 거부 | 서버에서 형 검증 후 저장 |
| **불리언** | `INTEGER` 0/1 | `boolean` | 0/1 통일 + `CHECK IN (0,1)` |
| **시각** | `TEXT` `datetime('now','localtime')` | `timestamptz` | 기존 WORKS 관행(TEXT) 유지 · 이관 시 일괄 변환(WP-02) |
| **자동번호** | `AUTOINCREMENT` | `IDENTITY`/`SERIAL` | 이관 매핑(WP-02) |
| **트리거 문법** | `RAISE(ABORT,…)` | 함수 + `RAISE EXCEPTION` | §16.4 — **각각 작성하고 같은 시나리오로 시험** |

## 17.4 결론

**§17.1 범위 안에서만 DB 제약을 쓴다.** 겹침 배타·다른 표 참조·여러 행 합계는 **서버 함수**로,
**불변성은 양쪽 트리거로** 둔다.

| | 기대 |

| 2 | **`Rel.2` 유효 수량 = 5대** |

### 19.3.2 ⭐ 연속 변경 — 조상 이중 차감 방지

| 시나리오 | 기대결과 |
|---|---|
| `Rel.1` 12 → `Rel.2` 5 → **`Rel.3` 5 가 `Rel.2` 를 다시 변경** | **`Rel.1` 잔량 7 · `Rel.2` 잔량 0 · `Rel.3` 잔량 5** |

| **순환관계 생성 시도** | **서버가 거부** |
| 어느 경우든 | **`Σ 유효 잔량 = 12` 유지** (§8.3.2 불변식) |

### 19.3.3 ⭐ 교차 범위 — 수주수량 ↔ 호기

| 시나리오 | 기대결과 |
|---|---|
| 수주 12대 범위 중 **확정호기 5대를 `UNIT_SET` 으로 변경** | **구 범위 잔량 7** |

| **소속 수주가 바뀐 값으로 직접 저장 시도** | **거부** |

### 19.3.4 ⭐ 구매요청 배분 · 초과구매

| 시나리오 | 기대결과 |
|---|---|
| 같은 Effectivity 의 **서로 다른 BOM 품목**이 각각 12대분 배분 | **정상** (품목이 다르면 서로 초과가 아니다) |

| 대당 3개 품목을 **5개와 4개로 나눠 요청** | **부품수량 기준으로 정상 추적** |
| `requested_qty ≠ Σ배분 + 초과구매` | **제출 차단** |
| 초과구매인데 **사유·보고대상·구두보고일시 없음** | **저장 거부** |

## 19.4 시험 계획

| 종류 | 내용 |
|---|---|
| 정상 | 검증완료 → 신청 → 발행 → 구매요청 → 발주까지 한 바퀴 |
| **차단** | §4.2 네 가지 · 신청자=승인자 · 겹치는 `PENDING` · 미확정 호기 · 대수 누락 · 비BOM 라인에 release 요구 안 함 |
| **반려** | 사유 없으면 거부 · 반려본으로 구매요청 차단 · 재신청은 새 행 |
| **장비대수** | A=C · **A≠C(경고+사유 필수)** · A만 · C만 · 둘 다 없음(`MANUAL`만) · **출처와 확정값 불일치 저장 거부**(E5~E9) |
| **잔량** | §19.3.1 8항 · **§19.3.2 연속변경 4항** · 새 Release 가 `REJECTED`/`CANCELLED` 되면 **차감이 되살아나는지** |
| **교차범위** | **§19.3.3 4항** |
| **배분·초과구매** | **§19.3.4 6항** |
| **적용범위** | 유형 4종 · 전 범위 겹침(→`SUPERSEDED`) · **일부 겹침(→`RELEASED` 유지)** · `PROJECT_SNAPSHOT` 발행 후 새 수주 **자동 편입 안 됨** |
| **트랜잭션 원자성** | **§7.5 6단계 중 하나를 실패시켜 전부 되돌아가는지** · `RELEASED` 인데 관계·영향행이 일부만 있는 상태가 안 생기는지 |
| **변경영향** | 품목·Effectivity 단위 기록 · **`UNREVIEWED` 면 추가 구매요청 차단** |
| **감사행 불변** | ⭐ **직접 SQL 로 `bom_change_impacts` 스냅샷 변경·행 삭제 시도 → 양쪽 DB 에서 거부** · 허용 4칸만 변경 가능 |
| **스냅샷 보존** | 발주 라인 삭제 → `po_item_id` NULL 이 되지만 **스냅샷 5종이 남는지** |
| **불변** | 발행된 스냅샷을 **직접 SQL 로** `UPDATE`/`DELETE` → **양쪽 DB 에서 거부** |
| **DB 제약** | 각 CHECK 를 **직접 SQL 로** 위반 시도 · **FK OFF 상태에서도 서버가 막는지** |
| **🔴 NULL 함정** | 같은 호기·같은 수주를 한 Release 에 **두 번** 넣어 부분 고유 인덱스가 막는지 |
| **스냅샷 중복** | 같은 품번 다른 구분 두 줄 · 시트 2개에 같은 `line_no` — 둘 다 정상 저장 |
| 회귀 | 기존 업로드·보드·파서 그대로 동작 |
| **변별력** | ⭐ 새 시험은 **고치기 전 코드에 먼저 돌려** 실패하는지 확인 |
