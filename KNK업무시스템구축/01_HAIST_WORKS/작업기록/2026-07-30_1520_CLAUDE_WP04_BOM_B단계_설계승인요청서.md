## 0. 왜 B단계가 필요한가 — 한 문장

A단계에서 **"올린 엑셀과 읽은 값이 같은지"** 는 볼 수 있게 됐지만,
**"누가 언제 확인했고, 이 BOM 으로 구매해도 되는지"** 를 시스템이 아직 모릅니다.

| A단계가 만든 것 | B단계가 있어야 하는 것 |
|---|---|
| 대조 결과를 **그 자리에서 보여준다** | 대조 결과를 **남긴다** (확인자·확인일시·해결상태) |
| 저장됨 | 저장됨과 **구매 사용 가능**을 구분한다 |
| `업로드 버전 v2` (파일 회차) | 외부 `Revision R1` 과 내부 `Release Rev.1` 을 따로 안다 |
| 구매팀 통보를 **잠갔다** | 통보를 **Release·구매요청 시점**으로 옮겨 되살린다 |

## 1. 상태와 전이 (판정서 §7.1)

### 1.1 무엇에 붙는 상태인가 — 먼저 확실히

혼동을 막기 위해 **상태를 두 층으로 완전히 분리**합니다.

| 층 | 대상 | 상태 |
|---|---|---|
| **업로드 상태** | 업로드 1건 (`bom_uploads` 1행 = 엑셀 파일 1개) | 초안 / 검증실패 / 검증완료 |
| **Release 상태** | Release 1건 (`bom_releases` 1행) | 대기 / 발행됨 / 대체됨 / 취소 |

⭐ **업로드 ≠ Release.** 여러 번 올려도 Release 는 사람이 발행할 때만 생깁니다.

### 1.2 업로드 상태

| 코드 | 사람 이름 | 뜻 |
|---|---|---|
| `DRAFT` | **임시 저장** | 올려서 보드에 담겼음. 구매근거 아님 (= 지금 A단계의 상태) |
| `VERIFICATION_FAILED` | **검증 불일치** | 미해결 불일치·중복시트·파싱실패 중 하나 이상 있음 |
| `VERIFIED` | **검증 완료** | 전부 일치이거나, 불일치를 사람이 전부 확인·처리함 |

### 1.3 Release 상태

| 코드 | 사람 이름 | 뜻 |
|---|---|---|
| `PENDING` | **Release 대기** | 검증완료 업로드를 근거로 Release 발행을 신청함 |
| `RELEASED` | **발행됨** | ⭐ **이 상태의 BOM 만 구매근거로 쓸 수 있음** |
| `SUPERSEDED` | **대체됨** | 새 Release 가 나와 밀려남 (내용은 **불변 보존**) |
| `CANCELLED` | **취소** | 발행 전 취소 또는 발행 후 무효화 |

### 1.4 전이·권한·차단조건

```text
[업로드]
  엑셀 업로드 ──> DRAFT
  DRAFT ──(대조 결과 불일치 있음)──> VERIFICATION_FAILED
  DRAFT ──(대조 전부 일치)────────> VERIFIED
  VERIFICATION_FAILED ──(불일치 전건을 사람이 확인·처리)──> VERIFIED
  ⛔ VERIFIED 에서 되돌아가지 않는다 (재업로드는 새 업로드 1건)

[Release]
  VERIFIED 업로드 ──(설계책임자 발행 신청)──> PENDING
  PENDING ──(설계책임자 발행)─────────────> RELEASED
  PENDING ──(취소)───────────────────────> CANCELLED
  RELEASED ──(새 Release 발행)───────────> SUPERSEDED
  RELEASED ──(대표 승인 + 사유)──────────> CANCELLED
  ⛔ RELEASED · SUPERSEDED 의 내용은 **수정 불가** (불변)
```

| 전이 | 누가 | 차단조건 |
|---|---|---|
| 업로드 → `DRAFT` | 설계·전장·SW팀 (현행 업로드 권한 그대로) | 없음 |
| `VERIFICATION_FAILED` → `VERIFIED` | **설계책임자** | 미해결 불일치가 1건이라도 남으면 차단 |
| `VERIFIED` → `PENDING` | **설계책임자** | 업로드가 `VERIFIED` 아니면 차단 |
| `PENDING` → `RELEASED` | **설계책임자** | §2 Release 차단기준 전부 통과해야 함 |
| `RELEASED` → `CANCELLED` | **대표** + 사유 필수 | 이 Release 를 근거로 한 구매요청이 있으면 차단 |
| 구매요청 제출 | 구매팀 | ⛔ **근거 Release 가 `RELEASED` 아니면 차단** |

> 명칭은 대표께서 바꾸라 하시면 바꿉니다. 다만 **`저장됨` 과 `구매 사용 가능` 은 반드시 분리**합니다
> (판정서 §3.3).

## 2. Release 차단기준 (판정서 §3.3·§4 B단계·§6)

Release 발행을 다음 중 **하나라도** 해당하면 막습니다.

| # | 차단조건 | 왜 |
|---|---|---|
| 1 | **미해결 불일치** 1건 이상 | 값이 틀린 채 구매가 시작되면 되돌리기 어렵다 |
| 2 | **중복 후보 시트 미해결** | 수량이 두 배로 발주된다 |
| 3 | **파싱 실패 행** 존재 | 못 읽은 줄이 구매 대상에서 통째로 빠진다 |
| 4 | **Revision 근거 불명확** | 어느 개정본을 근거로 산 것인지 나중에 증명할 수 없다 |

그리고 **가장 중요한 한 줄**:

> ⛔ **`RELEASED` 가 아닌 BOM 으로는 구매요청을 낼 수 없다.**

### 2.1 차단을 어디에 두는가 — 6개 층 전부

한 곳만 막고 끝내지 않습니다(대표규정 `한 곳만 고치고 완료 금지`).

| 층 | 조치 |
|---|---|
| DB | `bom_releases.state` + 구매요청의 `release_id` 필수(NOT NULL) |
| 서버 | Release 발행 함수 · 구매요청 제출 함수 양쪽에서 검사 |
| 화면(HTML) | 조건 미충족이면 발행·제출 버튼 **잠금** |
| 화면(JS) | 잠금 유지 + 왜 잠겼는지 표시 |
| 안내문 | `미해결 불일치 3건 때문에 Release 할 수 없습니다` 처럼 **막힌 이유를 사람 말로** |
| 진입경로 | BOM 보드·업로드 결과화면·구매요청 화면 모두 같은 문구 |

## 4. Revision (판정서 §7.3)

### 4.1 두 개를 절대 섞지 않습니다

| | 누가 매기나 | 예 | 어디 저장 |
|---|---|---|---|
| **외부 Revision** | **설계팀** (엑셀 자체) | `R1` · `VER.0` · 없음 | `bom_releases.ext_revision_raw` — **원문 그대로** |
| **내부 Release 순번** | **우리 시스템** | `Rev.0` · `Rev.1` | `bom_releases.release_no` |
| **업로드 버전** | 시스템 (파일 회차) | `v1` · `v2` | `bom_uploads.version_no` (기존) |

⛔ **외부 Revision 을 해석·정규화하지 않습니다.** 설계팀이 `R1` 이라 썼으면 `R1` 로 저장합니다.
읽을 수 없으면 `NULL` + `근거 불명확` 으로 두고, 그 상태로는 **Release 를 막습니다**(§2-4).

### 4.2 `bom_releases` (신규)

| 칸 | 뜻 |
|---|---|
`id` | 일련번호
`project_id` | 프로젝트
`release_no` | **내부 Release 순번** (프로젝트별 1,2,3…)
`based_upload_id` | ⭐ **어느 업로드를 근거로 발행했는지** (판정서 §7.3)
`ext_revision_raw` | 외부 Revision **원문** (`R1` · `VER.0` · `NULL`)
`ext_revision_source` | 어디서 읽었는지: `파일명` / `개정이력시트` / `제목행` / `없음`
`revision_history_raw` | 엑셀 **개정이력 시트 원문**(있으면 텍스트로 통째 보관)
`state` | §1.3 Release 상태
`released_by` · `released_at` | 발행자 · 발행일시
`superseded_by` | 어느 Release 로 대체됐는지
`cancel_reason` | 취소 사유 (취소 시 필수)

### 4.3 이전 Release 불변 원칙

- `RELEASED` · `SUPERSEDED` Release 의 **품목 내용은 수정 불가**입니다.
- 그러려면 Release 시점의 품목을 **스냅샷**으로 떠야 합니다 → `bom_release_items`(신규).
  - `bom_items` 는 계속 바뀌지만, **"그때 그 Release 로 산 것"** 은 영구히 남습니다.
  - ⭐ 구매요청·발주는 **스냅샷**을 근거로 겁니다. 나중에 설계가 바뀌어도 과거 발주 근거가 흔들리지 않습니다.

## 5. 데이터 계층 분리 (판정서 §7.4)

**⭐ 판정서 지시대로, 설계 BOM 원본과 구매검토 결과를 같은 `bom_items` 에 뒤섞지 않습니다.**

| 데이터 | 저장 계층 | 표 |
|---|---|---|
| 설계 요구품 · 설계수량 · Maker · 모델 | **설계 BOM** | `bom_items` (기존 · 칸 추가 최소화) |
| Release 시점 스냅샷 | **Release** | `bom_release_items` (신규) |
| 원본 시트·행 · 신규·삭제 · 서비스 의심 | **업로드·검증** | `bom_item_sources` (신규) |
| 대조 결과 · 확인자 · 해결상태 | **업로드·검증** | `bom_upload_verifications` (신규) |
| 본사 재고배분 · 구매수량 · 구매단위 · 환산계수 · 초과구매 | **구매검토** | `bom_purchase_review` (신규) |
| 베트남 재고 | **외부 참고정보** | `bom_purchase_review.stock_ref_vn` — ⭐ **참고수량만**, 가용재고·원장·자동 구매량 계산에서 제외 |
| 발주 · 입고 · 검수 · 재고 | **구매 거래** | 기존 구매 모듈 (WP-05 이후) |

> ⭐ **파서가 읽는 새 필드가 있다고 해서 모두 `bom_items` 칼럼으로 추가하지 않습니다**
> (판정서 §7.4 마지막 문단).
> 현재 A단계에서 파서가 읽고 있으나 **저장하지 않는** 값들(`source_stock_allocated_kor` ·
> `stock_ref_vn` · `source_purchase_qty` · `stock_amount` · `order_amount`)은
> **구매검토 계층**으로 갑니다. 설계 BOM 에 넣지 않습니다.

## 6. 알림 시점 (판정서 §7.5)

A단계에서 **잠가 둔** 통보를 여기서 제자리에 놓습니다.

| 시점 | 누구에게 | 무엇을 |
|---|---|---|
| **업로드(임시 저장)** | **설계담당자**(올린 사람 + 설계책임자) | `확인이 필요합니다` — 대조 결과 요약 |
| **검증 불일치** | 설계담당자 | `불일치 N건 — 확인 필요` · ⛔ **구매팀 통보 금지** |
| **Release 발행** | **구매팀** | `구매요청을 낼 수 있는 상태가 됐습니다` |
| **구매요청 제출** | **구매팀** | `구매 업무 시작` (기존 z984 통보의 진짜 자리) |
| **Release 취소** | 구매팀 + 설계담당자 | `근거가 취소됐습니다 — 진행 중 발주 재검토` |

| 원칙 | |
|---|---|
| ⛔ 검증 실패 상태에서 | **어떤 구매업무 통보도 발송 금지** |
| ⛔ 단순 업로드·임시저장에서 | **구매팀 통보 금지** |
| 단가·금액 | 통보 본문에 넣지 않음 (`can_money` 게이트 · 누출 주의) |
| 잠금 해제 | `KNK_ENABLE_BOM_UPLOAD_NOTIFY` 를 지우고, Release·구매요청 시점 통보로 **교체** |

## 7. 기존 데이터 · 복구 · 이관 (판정서 §7.6)

### 7.1 ⚠ 먼저 실측이 필요합니다 — 숫자를 짐작하지 않겠습니다

제가 과거에 *"칸이 있다"* 를 *"쓰고 있다"* 로 잘못 보고드린 일이 있었습니다
(`po_entity` 86% 빈칸 · 부분입고 예정일 입력 0건). 같은 잘못을 반복하지 않겠습니다.

**승인 후 첫 작업 = 읽기 전용 실측.** 아래를 **채워진 줄 수까지** 세어 보고드린 뒤 이관안을 확정합니다.

| 실측 항목 |
|---|
| `bom_uploads` 운영 행 수 · 프로젝트 수 · 최근 업로드 일시 |
| `bom_items` 활성/삭제 행 수 |
| 외부 Revision 을 파일명·제목에서 읽어낼 수 있는 비율 |
| 개정이력 시트를 가진 파일 비율 |
| 같은 파일을 두 번 올린 사례 수 |

### 7.2 이관 방침 (승인 요청)

현재 활성 BOM 을 **암묵적으로 Release 로 간주하지 않겠습니다.** 두 안을 올립니다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A안 (권고)** | 기존 활성 BOM 을 `DRAFT` 로 두고, 설계책임자가 프로젝트별로 **초기 Release 를 1회 명시 발행** | 누가 언제 책임지고 확정했는지 남는다 | 설계팀이 프로젝트마다 한 번 눌러야 한다 |
| B안 | 마이그레이션이 `Rev.0` 을 자동 발행 | 손이 안 간다 | ⛔ **아무도 확인하지 않은 것이 공식 구매근거가 된다** |

→ **A안을 권고**합니다. B안은 판정서 §3.3 취지(저장됨 ≠ 구매 사용 가능)를 정면으로 어깁니다.

### 7.3 실패 시 복구

| 단계 | 조치 |
|---|---|
| 마이그레이션 전 | 운영 DB **백업** + 정상 열림 확인 (WP-01 과 같은 절차) |
| 리허설 | **운영 사본**에서 마이그레이션 → 필수데이터 전·후 대조 |
| 범위 제한 복구 스크립트 | 신규 표만 되돌리는 스크립트를 **미리 작성해 저장소에 보존** |
| 되돌림 원칙 | 신규 표 `DROP` 만으로 원상 복귀 가능하게 설계 (기존 표는 **칸 추가만**, 기존 칸 변형·삭제 없음) |

### 7.4 기존 화면·파서 회귀

| 확인 대상 |
|---|
`/bom/upload` 미리보기·반영 (A단계 기능이 그대로 동작하는지)
`/projects/{id}/bom` 보드 (그룹·필터·상세이력·수정·구매처 일괄·엑셀 내보내기)
`/bom/uploads/{id}/report` 업로드 변경 보고
BOM 전체 삭제 (`bom_purge`) — 신규 표까지 함께 지워지는지 (`purge 목록`에 추가 필수)
자재구매센터 다른 화면 (BOM 을 참조하는 곳 전수 `grep`)

## 8. 실행 단계 분할 — 각 단계마다 게이트 판정

한 번에 다 만들지 않습니다. **단계마다 판정을 받고 다음으로 갑니다.**

| 단계 | 내용 | 산출물 | 코드·DB |
|---|---|---|---|
| **B-0** | 읽기 전용 실측 (§7.1) | 실측 보고 | ⛔ 무접촉 |
| **B-1** | 스키마 마이그레이션 + 복구 스크립트 + 사본 리허설 | 완료보고 + 전·후 대조표 | DB 신규 표 · 기존 표 칸 추가 |
| **B-2** | 검증 기록 저장 + 불일치 확인·해결 화면 | 완료보고 + 캡처 | 코드 |
| **B-3** | Revision 저장 + Release 발행 + 스냅샷 + §2 차단 6층 | 완료보고 + 차단 시험표 | 코드 |
| **B-4** | 알림 재배치 (§6) + `KNK_ENABLE_BOM_UPLOAD_NOTIFY` 해제 | 완료보고 + 발송 실측 | 코드 |
| **B-5** | 기존 데이터 이관(A안) + 기존 화면·파서 회귀 | 완료보고 | 데이터 |
| **B-6** | main 병합 · 운영 배포 | 배포 확인 | **대표 승인 필수** |

⛔ 각 단계는 **앞 단계 판정 통과 후** 착수합니다.
⛔ **B-6 이전에는 main 병합·운영 배포를 하지 않습니다.**

## 9. 시험 계획

| 종류 | 내용 |
|---|---|
| **비식별 자동시험** | 상태 전이 매트릭스 전수 · Release 차단 4조건 각각 · 권한별 허용/차단 · 불변 원칙(발행된 Release 수정 시도) |
| **라우트 시험** | Release 안 된 BOM 으로 구매요청 시도 → **차단** · 알림이 **올바른 시점에만** 발송 |
| **발송 0건 시험** | 검증 실패 상태에서 구매팀 통보 **0건** (A단계 `J'-2/J'-3` 과 같은 방식) |
| **변별력 확인** | ⭐ 새 시험을 **고치기 전 코드에 먼저 돌려** FAIL 하는지 확인 (A단계에서 이 절차가 실제로 결함을 잡았습니다) |
| **회귀** | WP-01 · WP-03 · A단계 시험 전부 |
| **화면 확인** | 단계마다 로컬 캡처 (⛔ 운영 DB·실발송 금지 — A단계와 같은 조건) |

## 10. ⛔ 승인 전까지 하지 않는 것

| 항목 | 상태 |
|---|---|
| DB 스키마 변경 (`CREATE` · `ALTER` · 마이그레이션 파일) | ⛔ 하지 않음 |
| 코드 변경 | ⛔ 하지 않음 |
| Release · 구매근거 · 구매요청 구현 | ⛔ 하지 않음 |
| `KNK_ENABLE_BOM_UPLOAD_NOTIFY` 잠금 해제 | ⛔ 하지 않음 (계속 잠김) |
| main 병합 · 운영 배포 | ⛔ 하지 않음 |
| 운영 데이터 생성·수정 | ⛔ 하지 않음 |

## 11. 승인 요청 사항

| # | 요청 |
|---|---|
| 1 | **§1 상태·전이 체계** 승인 (업로드 상태 3종 · Release 상태 4종 · 전이 권한) |

| 3 | **§3~§5 신규 표 5개 + 기존 표 칸 추가** 승인 (`bom_releases` · `bom_release_items` · `bom_upload_verifications` · `bom_item_sources` · `bom_purchase_review`) |
| 4 | **§6 알림 시점 재배치** 승인 |
| 5 | **§7.2 이관 A안**(초기 Release 명시 발행) 채택 여부 결정 |
| 6 | **§8 단계 분할**(B-0~B-6, 단계별 게이트) 승인 |
| 7 | **B-0 읽기 전용 실측** 착수 승인 (이것만 승인하시면 나머지는 실측 후 다시 올립니다) |

> 7번만 먼저 승인하시는 것도 가능합니다. 실측 없이 스키마를 확정하면
> 제가 과거에 반복했던 *"칸이 있다 = 쓰고 있다"* 잘못을 또 저지를 수 있습니다.
> **B-0 먼저**를 권고드립니다.
