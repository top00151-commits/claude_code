## 2. 조사에서 밝혀진 사실 (이게 이 문서의 핵심 자산)

### 2-1. 수주번호(SO)가 갈리는 기준 — 코드에 박힌 KNK 표준

`app/project_workflow.py` `confirm_order_multi` 주석:

> SO 번호는 **호기/수량 구분이 아니라 진행 단위 구분용**.
> 동일 관리번호라도 (납기 또는 납품지가 다르면) SO 분리.
> 반대로 동일 납기 + 동일 납품지면 호기 N개라도 SO 1개.

**실제 그룹화 키 = (납기, 납품처, 통화) 3개.** PO는 없다.
`po_number` 파라미터는 *"고객 PO 번호 (전체 공통)"* — **수주 1건에 PO 1개**를 전제로 설계돼 있다.

→ M-260305-1은 7대 모두 발주일 2026-03-05 · 납기 2026-07-28 · 납품처 없음 · KRW라 **완전히 같은 그룹** → 수주번호 1개.

### 2-2. ⭐ 추가발주는 PO와 무관하게 **항상** 새 수주번호가 나온다 (철회의 결정적 근거)

`add_followup_order` 는 재사용 로직이 **없고** 무조건 `generate_so_no()` 를 호출한다.

**실측** (인메모리 DB로 실제 함수 호출):
```
1차 추가발주(6대) → M-260305-1
2차 추가발주(1대) → M-260305-2      ← PO를 안 적어도 갈림
```

즉 **"나중에 추가 발주가 나온 경우"는 PO 없이도 이미 수주번호가 갈린다.**
PO를 입력해야 갈리는 경우는 **"처음부터 여러 대를 한 번에 등록하는데 PO가 섞인 경우"** 하나뿐이다.

| 상황 | 수주번호 갈림 | PO 필요? |
|---|---|---|
| 나중에 추가 발주 (추가발주로 등록) | ✅ 자동 | **불필요** |
| 처음부터 여러 대인데 PO 섞임 (한 번에 등록) | ❌ PO 없으면 안 갈림 | 필요 |
| 어느 수주번호가 어느 PO 건인지 대조 | — | 필요(추적용) |

**대표 판단**: 실무에서 PO가 늦게/따로 나오는 건은 어차피 추가발주로 등록하므로 이미 갈린다.
→ 나누기 위해 PO를 입력할 이유가 없다. **입력 부담만 남는다.** → 철회.

### 2-3. PO를 넣을 정식 칸이 사실상 없었다 (철회 후에도 그대로)

| | 상태 |
|---|---|
| DB 칸 | ✅ `orders.customer_po` 존재 |
| 입력 가능한 곳 | **제작요청서 편집 화면 1곳뿐** (`prod_request_edit.html`) |
| 신규 등록 폼 | ❌ hidden (사람이 못 넣음·수정 시 기존값 보존용) |
| 일괄등록 엑셀 양식 | ❌ 칸 없음 |
| 작업일정표 | ❌ 열 없음 |
| 수주 내역(프로젝트 상세) | ❌ 표시 없음 |
| 호기별 PO | ❌ 칸 자체가 없음 |

→ 그래서 **비고(`order_items.line_note`)에 손으로 적는 것이 현행 방식**이고, 대표가 그대로 가기로 확정.
작업일정표를 보면 그 칸에 `PO#4505977712` 와 `가성불량 개선건`·`메인핀블럭` 같은 메모가 뒤섞여 있다.

### 2-4. ⚠️ 추가발주는 PO를 넘겨줘도 **저장하지 않는다** (미해결·현행 유지)

`add_followup_order(po_number=...)` 는 파라미터를 **받기만 하고 쓰지 않는다.**
`INSERT INTO orders(...)` 컬럼 목록에 `customer_po` 가 없다.

호출부(`app/main.py` 27276·27522)는 `po_number=form.get("customer_po","")` 로 **제대로 넘기고 있다.**
받는 쪽이 버린다.

**실측**:
```
1차 추가발주(PO#4505977712) → M-260305-1  customer_po = (비어있음)
2차 추가발주(PO#4505977715) → M-260305-2  customer_po = (비어있음)
```

> 지금은 PO를 비고로 관리하므로 당장 문제는 없다. 다만 **제작요청서에서 PO를 적어도 추가발주 SO엔 안 남는다**는 사실은 알고 있어야 한다.

### 2-5. ⚠️ 엑셀 `PO번호` 열이 **우리 수주번호**로 읽힌다 (미해결·의도적으로 원복)

`app/main.py` `_parse_packing_list_xlsx`:
```python
("order_no", ["수주번호", "수주No", "ORDERNO", "SO번호", "PO번호", "PONO"])
                                                  ↑            ↑
```
PACKING LIST 엑셀에 **`PO번호` 열을 만들어 고객 PO를 적어 올리면 우리 수주번호 자리에 들어간다.**

z1027에서 한 번 뺐다가 **철회 때 원상 복구했다.** 이유:
- 이 별칭이 왜 들어갔는지 이력이 없다. **기존 PACKING LIST 파일이 자기네 수주번호 열을 'PO번호'로 부르고 있을 가능성**을 배제할 수 없다.
- 그렇다면 별칭을 빼는 순간 **잘 되던 업로드가 조용히 깨진다.**
- 실파일 확인 없이 건드리는 건 위험 → 원복하고 여기 기록.

**확인 방법**: 구매팀·기술영업팀이 실제로 쓰는 PACKING LIST 엑셀에서 `PO번호` 열이
① 고객 PO를 적는 칸인지 ② 우리 수주번호를 적는 칸인지 확인.
①이면 별칭에서 빼야 하고, ②면 그대로 두는 게 맞다.

## 3. 만들었다가 되돌린 것 (`a2da2077` → `c0a57585`)

| # | 만든 내용 | 상태 |
|---|---|---|
| 1 | `order_items.po_no` 컬럼 신설 | 되돌림 |
| 2 | 그룹화 키에 PO 추가 `(납기·납품처·통화·PO)` | 되돌림 |
| 3 | 기존 SO 재사용 조건에 `customer_po` 일치 요구 | 되돌림 |
| 4 | `orders.customer_po` = 그룹 PO 기록 | 되돌림 |
| 5 | 등록폼 '고객 발주(PO)번호' + 호기별 `unit_po[]` | 되돌림 |
| 6 | 수주 내역 '고객 PO' 열(편집 가능) | 되돌림 |
| 7 | 작업일정표 '고객 PO번호' 열(기본 꺼짐) | 되돌림 |
| 8 | 엑셀 `PO번호` 오인식 차단 | 되돌림(2-5 참조) |

### ⭐ 다시 만든다면 반드시 기억할 것 — 3번을 빼먹으면 2번이 무의미하다
그룹화 키만 고치면 **한 번의 호출 안에서만** 갈린다.
나중에 들어오는 추가 발주는 `기존 SO 재사용` 쿼리를 타는데, 그 조건에 PO가 없으면
**PO가 달라도 기존 수주번호에 그대로 붙는다.** 두 곳을 **반드시 같이** 고쳐야 한다.

### 그 밖에 걸렸던 함정들
- 등록폼 `ed` 모드에 hidden `customer_po` 가 있다. 본문에 정식 칸을 추가하면 **같은 `name` 이 2개**가 되어 값이 2개 전송된다 → hidden 제거 필요.
- 공통 PO → 호기별 PO는 **빈칸에만** 내려채워야 한다. 대별로 다르게 적은 값을 덮으면 기능 자체가 무의미(PO가 섞인 게 목적).
- 수량을 바꾸면 호기 줄이 다시 그려진다 → **이미 입력한 PO 보존** 필요(`pP` 배열).
- 작업일정표에 이미 **`PO유형`**(신규/추가/개조/수리) 열이 있다. **완전히 다른 값**이므로 이름을 반드시 구분(`고객 PO번호`).
- 작업일정표 컬럼은 계정별 저장이라 **기본 꺼짐**을 위해 `COL_HIDE_DEFAULT` 같은 장치가 따로 필요하다(없으면 기본 켜짐).

### 검증까지 통과했던 항목 (되살릴 때 그대로 재사용 가능)
| 사례 | 결과 |
|---|---|
| 7대 중 1대만 PO 다름 | 수주번호 2개(1대/6대)로 분리 ✅ |
| PO 전부 빈칸 7대 | 1개 (기존과 동일) ✅ |

## 4. LIVE에 남은 잔여물

**`order_items.po_no` 컬럼이 LIVE DB에 남아 있다.**
- z1027 배포 시 마이그레이션으로 생성됨. 철회로 **읽고 쓰는 코드는 0**.
- 값은 전부 NULL(테스트로 넣었던 1건도 빈칸으로 복구 완료).
- SQLite는 컬럼 삭제가 위험(테이블 재생성 필요)해서 **그대로 둔다. 무해하다.**
- 되살릴 땐 이 컬럼을 그대로 재사용하면 된다.

## 6. 나중에 다시 검토할 거리 (지금은 안 함)

## 7. 안지연 프로께 전달할 내용

> 확인해 보니 **추가 발주로 등록하시면 PO번호를 적지 않아도 수주번호가 자동으로 갈립니다.**
> 같은 날이어도 `M-260305-1`, `M-260305-2` 처럼 차수가 올라갑니다.
> 그래서 PO번호 입력칸은 넣지 않기로 했고, **PO는 지금처럼 기타(비고) 칸에 적어 관리**합니다.
> 한 번에 여러 대를 등록하시는데 PO가 섞여 있으면, **PO별로 나눠서 등록**해 주시면 수주번호가 분리됩니다.
