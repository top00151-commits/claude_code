| 999M2601 구매품 LIST_**20260119** | 없음 | `20260119` |

**같은 회사 안에서 `R1` · `VER.0` · 표기 없음이 섞여 있다.** 날짜 형식도 넷이다.

→ **파일명에서 Revision을 자동으로 뽑아내면 안 된다.** Release 할 때 **사람이 입력**받고, 그 값을 `drawing_rev`(외부 도면 원본 표기)에 그대로 보존한다. 시스템 내부 Rev는 별도로 `Rev.0/1/2` 숫자로 매긴다.

⭐ 이것이 V3 §1.2와 보충계약의 **"외부 도면의 문자 Revision은 도면 자체의 원래 값으로 별도 보존"** 이 실제로 필요하다는 실증이다.

## B-5. 🔴 BOM과 수주내역이 서로 다르다 — 구매 근거는 BOM이어야 한다

같은 프로젝트(001M2607)의 두 목록을 대조했다.

```
설계팀 BOM (R1) : 132줄 · 4,944개
WORKS 수주내역   : 141줄 · 5,126개

양쪽 다 있음      :  49종
수주내역에만 있음 :  88종
BOM에만 있음      :  70종
```

**겹치는 것이 절반도 안 된다.**

⚠ **정직하게 말씀드립니다.** 이 수치는 품번·품명을 기계적으로 맞춘 결과이므로, **실제로는 같은 물건인데 표기가 달라 안 붙은 것이 상당수 포함**돼 있습니다. 예:

| 수주내역 | 설계팀 BOM |
|---|---|
| `SENSOR` / `BS5-Y1M` ×108 | `센서` / `BS5-Y1M DC5-24V` ×48 |
| `LM GUIDE` / `PNH15SSS-1060` ×24 | `LM GUIDE` / `PNH15S2SS-1660`, `PNH15SSS-280`, `PNH15SSS-580` |

즉 **"설계가 그만큼 바뀌었다"는 뜻이 아닙니다.** 표기 차이와 설계 개정이 섞여 있고, 지금은 **어느 쪽이 구매 근거인지 시스템이 답하지 못합니다.**

**이 상태가 묶음 A의 존재 이유입니다.**

| | |
|---|---|
| 수주내역(`order_items`) | **매출·납품** 기준 — 고객과의 계약 |
| 설계팀 BOM | **구매** 기준 — 무엇을 사야 하나 |

둘은 목적이 다른 목록이므로 **일치할 이유가 없고, 일치시키려 해서도 안 됩니다.** V3 계약 3대로 **구매요청은 BOM 근거(`baseline_item_id`)를 가리키고**, 수주번호는 선택 입력으로 둡니다.
