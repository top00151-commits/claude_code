### 1.2 BOM Release 확정

| 영역 | Release 책임 | 인원 |
|---|---|---|
| 기계 BOM | 설계팀 책임자 | 11 |
| 전장 BOM | 전장설계팀 책임자 | **1** |
| SW 구매품 | 소프트웨어팀 책임자 | 10 |

- 영역별로 **독립 Release·독립 Revision**
- 시스템 내부 Revision 표기 = **숫자** `Rev.0 · Rev.1 · Rev.2 …`
- 외부 도면의 문자 Revision(A/B/C)은 **도면 원래 값 그대로 별도 보존**
- 구매요청은 **Release된 영역별 BOM 근거**를 사용
- 프로젝트 전체 구매현황에서는 영역별 Release를 **통합 조회**

### 1.3 대표께서 「다음에 지정」하신 2건 — 영향 범위를 정직하게

대표 지시: **"품질팀, 전장설계팀 대행자는 다음에 지정할게. 있는 인원대로 진행해."**

| 미지정 | 묶음 A 영향 | 나중에 문제되는 시점 |
|---|---|---|
| **품질팀 인원(2명)** | **없음** — 묶음 A에는 검수가 들어가지 않습니다(요청 작성·검토·승인까지) | **묶음 C**(부분입고→검수). 입고량이 늘면 검수에서 밀립니다 |
| **전장설계 대행자** | **있음** — 전장설계 책임자가 1명이라, 그분이 부재하면 **전장 BOM Release가 멈추고** 전장 자재 구매요청을 만들 수 없습니다 | 묶음 A 운영 중 즉시 |

## 2. 묶음 A 범위 — 이것만 합니다

### 2.1 업무 결과 (완료 판정 기준)

```
설계자가 BOM을 올려 Release
   → 구매할 줄을 골라 구매요청 생성
      → 구매팀이 검토 → 승인 또는 반려
         → 그 요청이 "어느 BOM 상태를 근거로 했는지" 언제든 되짚어진다
```

화면 개수나 표 개수가 아니라 **위 한 줄이 끝까지 돌아가는가**로 판정합니다.

### 2.2 만들 것

| 구분 | 내용 |
|---|---|
| **새 표 2개** | `bom_purchase_baselines`(구매근거 스냅샷) · `bom_baseline_items`(그때 값 그대로) |
| **칸 추가** | `bom_uploads`: `release_area`(기계/전장/SW) · `release_rev_no`(숫자) · `released_by` · `released_at` · `drawing_rev`(외부 도면 문자 Rev 원본)<br>`material_requests`: `request_kind`(NORMAL/EMERGENCY/DIRECT/STOCK_REPLENISHMENT) · `baseline_id`(화면 기본값) · `reviewed_by/at` · `approved_by/at` · `rejected_reason`<br>`material_request_items`: `basis_type`(BOM/NON_BOM) · `baseline_item_id` · `basis_reason` |
| **화면** | BOM 보드에 **Release** 버튼 + **구매요청 담기** · 구매요청 상세에 **검토·승인·반려** |
| **모듈** | `main.py`(41.9k행)에 얹지 않고 **새 모듈로 분리** |

### 2.3 하지 않을 것

견적 · 발주 · 배분 · 입고 · 검수 · 재고 · 출고(묶음 B~D) · 관련 없는 UI · 타 센터 · 과거 호기 확산.

## 4. 시범 검증 (001M2607)

```
① 001M2607 의 기계 BOM 엑셀을 /bom/upload 로 올린다
② 설계팀 책임자가 기계 영역 Rev.0 으로 Release
③ 구매근거 스냅샷 생성 확인
④ 상위 20~30줄을 골라 구매요청 생성
     — 이미 자재에 등록된 줄(110/141)과 미등록 줄(31)이 섞이게 고른다
⑤ 구매팀이 검토 → 일부 승인 · 일부 반려
⑥ BOM 2판을 올려 바꾼 뒤, ④의 요청이 여전히 Rev.0 근거로 보이는지 확인
```

⚠ **실제 납기(2026-09-07)를 늦추지 않습니다.** 구매 실무는 기존 방식대로 가고, 시스템은 **병행 기록**으로 시작합니다.

## 7. 중단 조건

하나라도 발생하면 **즉시 중단하고 보고**합니다.

1. 스냅샷 없이 구매요청이 만들어지는 경로가 **1개라도** 발견
2. `basis_type` 이 BOM/NON_BOM 외의 값을 갖게 되는 경로 발견
3. Release 없이 구매근거가 생성되는 경로 발견
4. 업무 변경만 되고 감사가 안 남는 경우
5. 기존 기능(자재·협력사·프로젝트·수주) 회귀 실패
6. 마이그레이션이 기존 칸을 변경·삭제하는 것이 발견
7. 시범 프로젝트의 **실제 납기 업무에 지장**이 생김
