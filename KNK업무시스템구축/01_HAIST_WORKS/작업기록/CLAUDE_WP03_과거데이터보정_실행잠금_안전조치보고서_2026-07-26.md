## 1. 지시받은 것과 한 일

대표 지시(잠금 처리 2항)의 허용 범위는 넷뿐이었다. 넷 다 했고, 그 밖은 하지 않았다.

| # | 허용된 범위 | 한 일 | 증빙 |
|---|---|---|---|
| ① | status-sync 실행 차단 | 4겹으로 막음 | §M-1~M-4 |
| ② | 실행 차단 안내문 표시 | 화면 4곳(위 배너·안내문·실행 자리·진입 버튼) | §M-8~M-13 |
| ③ | 기존 데이터 변경 없음 확인 | 운영 실측 + 시험 | §2·§M-5~M-7 |
| ④ | 후보 반영 정상 동작 회귀검증 | 6개 조건 전부 | §M-14~M-19 |

### 금지 사항 — 하지 않았음

| 금지된 것 | 확인 |
|---|---|
| DB 구조 변경 | 마이그레이션 **0건**. 표·칸 추가·변경·삭제 없음 |
| 과거 데이터 수정 | 운영 DB **쓰기 0건**. 이 작업 중 운영 접속은 읽기전용 조회 1회뿐 |
| 권한체계 전면 개편 | 권한 함수·역할·팀 매핑 **무변경**. 잠금은 권한과 **별개 층**(권한이 있어도 잠금이 우선) |
| 관련 없는 UI 수정 | 손댄 화면 2개(보정 화면·호기 목록의 그 버튼 한 줄)뿐. 색·배치·다른 기능 무변경 |

## 2. 실행 전 사실 확인 — 운영 데이터

지시서 §4.3이 요구한 "S1 또는 다른 확산이 실행되었다면 사실대로 보고" 에 대한 확인이다. 운영 DB를 **읽기 전용**으로 열어 확인했다.

```
project_units 총계    : 23
호기가 있는 관리번호   : 1개  (project_id 821 = 005T2601)
신원상태             : CONFIRMED 23
진행상태             : SHIPPED 23
감사기록             : 2건 (2026-07-26 13:28:55 / 13:31:10 · status_backfill)
보정이력             : 23건
```

**확산은 실행되지 않았다.** 248개 프로젝트·781대는 하나도 만들어지지 않았고, 승인받은 시범 프로젝트 23대만 존재한다. 이 상태를 WP-03 최종 보존 기준으로 삼는다.

## 3. 어떻게 막았나 — 4겹

한 겹만 막으면 다른 경로로 새는 것이 이 프로젝트에서 반복된 사고였다(WP-01 F-01: 홈 링크만 지우고 사이드바 메뉴가 남아 재현). 그래서 **깊은 곳부터** 막았다.

| 겹 | 위치 | 막는 것 |
|---|---|---|
| 1 | `project_unit.py` `status_backfill_apply()` | 화면을 거치지 않고 **함수를 직접 불러도** `PermissionError` |
| 2 | `main.py` POST `/project/{id}/units/status-sync/apply` | **403** — 승인권자·대표여도 잠금이 우선 |
| 3 | `project_unit_status_sync.html` | 실행 폼(`syncForm`) **자체를 그리지 않음** |
| 4 | `project_units.html` 진입 버튼 | `🔄 작업일정표 상태 맞추기` → `🔒 작업일정표 상태 대조 (보기만)` |

### 잠금 방식 — 새 체계를 만들지 않았다

WP-01에서 대표 승인으로 만든 잠금 체계(`WP01_LOCK_SWITCHES` / `wp01_unlocked`)에 스위치 하나를 더했다.

```
KNK_ENABLE_UNIT_STATUS_SYNC     # 과거 데이터 보정
```

이렇게 한 이유:

- 운영 NAS에는 이 환경변수가 **없다** → 항상 잠김. 실수로 열릴 여지가 없다.
- 배포 전 검사기 `deploy/check_wp01_locks.py` 가 **자동으로 함께 점검**한다(따로 관리할 것이 늘지 않음).
- 다시 열려면 대표 승인 + 환경변수 설정이 **둘 다** 필요하다.

검사기 실행 결과: **7개 전부 잠김**(기존 6 + 새 1).

## 4. 잠그지 않은 것 — 수주내역 후보 반영

대표 지시 1항대로 **잠그지 않았다.** 이 기능은 기술영업팀이 신규 프로젝트의 호기를 등록하는 정상 업무 경로다.

유지하라고 하신 6개 조건을 시험으로 확인했다.

| 조건 | 확인 방법 | 결과 |
|---|---|---|
| 관리번호 한 건씩 사용자가 직접 처리 | 여러 관리번호를 한 번에 받는 경로 탐색 | 없음(404) |
| 기술영업팀 또는 승인된 권한만 | 설계팀 계정으로 시도 | 차단 |
| 개발·미확정 상태 허용 | 반영 후 신원 상태 확인 | 전부 PROVISIONAL |
| 대량 프로젝트 일괄처리 금지 | 위 첫 항목과 동일 | 경로 없음 |
| 과거 프로젝트 자동확정 금지 | 반영 후 CONFIRMED 개수 | 0건 |
| 작업자·시각·변경이력 기록 | 감사기록·호기번호 이력 증가 | 각각 증가 확인 |

## 5. 검증

### 5.1 새 시험을 고치기 전 코드에 먼저 돌렸다

이 프로젝트의 규칙대로, 시험이 실제로 변별력이 있는지부터 확인했다. 앱 코드를 잠금 이전으로 되돌리고 새 시험 21항을 돌렸다.

**결과: 13건 FAIL.** 그중 가장 중요한 것:

```
FAIL §M-5  ('PROVISIONAL', 'IN_PROGRESS') → ('CONFIRMED', 'SHIPPED')
FAIL §M-3  status=303          (403이 아니라 그대로 실행됨)
```

즉 **고치기 전에는 요청하면 실제로 보정이 실행됐다.** 잠금이 빈 껍데기가 아니라는 증거다.

PASS로 남은 8건(§M-0·12·14~19)은 회귀 시험이라 양쪽 모두 통과해야 정상인 항목이다.

### 5.2 고친 뒤

| 검사 | 결과 |
|---|---|
| WP-03 호기 (§M 21항 신설 포함) | **300 / 300** |
| WP-01 회귀 | **98 / 98** |
| `deploy/check_standards.py` | 전부 통과 |
| `deploy/check_wp01_locks.py` | 7개 전부 잠김 |

### 5.3 잠금과 기존 시험의 관계 — 정직히

지시서 §4.3이 "이미 구현·배포된 WP-03 기능은 삭제하거나 되돌리지 않는다"고 했으므로, 보정 **로직**(멱등·예외 보존·감사·단일 트랜잭션)을 검증하던 기존 시험 10곳은 **그대로 살려 두었다**. 시험 환경에서만 스위치를 켜서 돌린다.

**잠금 자체는 §M에서 스위치를 도로 끄고**, 운영과 똑같은 상태로 검증한다. 기능은 보존하되 운영에서는 못 쓰게 하는 것이 지시의 뜻이라 이렇게 나눴다.

## 6. 화면에서 달라지는 것

기술영업팀이 보게 될 변화다.

**호기 목록에서** — 버튼 글이 바뀐다.

```
전: 🔄 작업일정표 상태 맞추기
후: 🔒 작업일정표 상태 대조 (보기만)
```

**그 화면에 들어가면** — 위에 빨간 안내가 뜨고, 아래 실행 버튼이 있던 자리에는 이렇게 적힌다.

> 🔒 **보정 실행이 잠겨 있습니다.** 여기 있던 '위 표대로 보정' 버튼은 지금 없습니다.
> 대표 승인 없이는 실행되지 않으며, 혹시 예전 화면이 열려 있어 눌러 보시더라도 **서버가 거부합니다.**

**대조표와 이력은 그대로 보인다.** 무엇이 어긋나 있는지 확인하는 것까지 막을 이유는 없다.

안내 문구는 `project_unit.py` 한 곳에서만 정의해서, 화면과 서버가 서로 다른 말을 할 수 없게 했다.
