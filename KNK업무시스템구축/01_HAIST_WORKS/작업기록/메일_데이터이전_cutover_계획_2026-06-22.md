# 메일 데이터 이전(cutover) 계획 (대표 지시 2026-06-22)

> 대표 지시: "데이터도 옮겼어야지." — 컨테이너 분리(6/18) 때 메일 '앱'만 독립 컨테이너로 갔고
> '데이터'는 WORKS 통합 DB에 남아 kmail이 빈 깡통(메일0·사용자0). **WORKS DB의 메일 데이터를
> kmail DB(`data/mail.db`)로 안전 이전 + 수신 일원화 + 정식 전환.**
>
> **절대원칙**: 메일은 ①올바른 주인에게(오배치 0) ②유실 0 ③분기(중복수신) 0. 실패 시 즉시 롤백(WORKS 원본 보존). [[feedback_data_connectivity]]

## 1. 현황 (점검 완료 2026-06-22)
- **kmail DB**(`/opt/knk_mail/data/mail.db`): mail_messages **0**·users **0**·attachments 0 (빈 골격 106KB·6/14).
- **WORKS DB**: 메일 실데이터 보유(works.knknara.co.kr/mail 정상 작동이 증거). 정확 건수·용량은 §2-1에서 확인.
- **스키마 비교**: mail_messages(22컬럼)·attachments·aliases·signatures·rules·fetch_accounts **거의 동일**(kmail이 WORKS 메일 모듈 포팅).
  - 차이① WORKS `mail_messages`에 lazy ALTER 컬럼(`dedup_hash`·`dup_count`·`is_blocked`·`risk_level`·`risk_note`) 추가됨 — kmail엔 없음(이전 시 kmail에 컬럼 추가 또는 무시·재계산).
  - 차이② `users` id 체계 다름(각자 AUTOINCREMENT) → **매핑 키 = `login_id`(사번)/`email`**. WORKS=login_id(UNIQUE), kmail=employee_no(UNIQUE)·login_id(=사번).

## 2. 단계별 계획

### 2-1. 규모·매핑 가능성 조사 (읽기전용·SSH·대표 비번) ← 다음 실행
- WORKS DB: `mail_messages` direction별 건수·고유 user_id 수·`attachments` 건수·**첨부 BLOB 총용량(GB)**·`users`(login_id·email·name) 목록.
- **매핑 검증**: WORKS `users.login_id` 가 메신저 SSO 사번(employee_no)과 같은 체계인지(1:1 가능?). email 보조키.
- 산출물: 이전 규모·예상 소요·매핑표 초안·위험 목록.

### 2-2. kmail 사용자 채우기 (메일 주인 준비)
- 메일마다 붙는 user_id 가 가리킬 사용자를 kmail에 먼저 생성(현재 0명).
- **권장 A**: WORKS `users` → kmail `users` 복사(employee_no=login_id·email·name·name_en/vi·role·entity·lang·rank). 사번 UNIQUE.
- 대안 B: 메신저 SSO 직원명부 동기화(kmail 기능·task#22) — 단 공유키(`KNK_SSO_SERVICE_KEY`) 필요·블로커 가능.

### 2-3. user_id 매핑표 작성 (가장 위험·핵심)
- WORKS `user.id` → kmail `user.id` 1:1 매핑. **키 = `login_id`(사번) 정확 일치**, email 보조 검증.
- **불일치·중복·누락 = 미매핑 → 수동 검토**(추측 매핑 절대 금지). 미매핑 user의 메일은 이전 보류.

### 2-4. 메일 데이터 복사 (user_id 재매핑·WORKS 원본 보존)
- `mail_messages`: WORKS→kmail. user_id=매핑값. kmail id 재생성 + **WORKS_id→kmail_id 매핑 보관**(첨부 연결용).
- `mail_attachments`: mail_id=새 매핑·data(BLOB) 복사. (용량 크면 배치·작은 트랜잭션·busy_timeout)
- `mail_aliases`·`signatures`·`rules`·`fetch_accounts`: user_id 재매핑 복사.
- WORKS 추가 컬럼(dedup_hash 등): kmail에 컬럼 추가 후 복사 or 생략(kmail서 중복정리 재계산).
- ⛔ WORKS 원본은 **삭제 아님·읽기만**(롤백 대비).

### 2-5. 검증
- 건수 일치(WORKS vs kmail, **user별**). 표본 메일 주인 정확(login_id 대조). 첨부 개수·용량 일치.
- 대표+표본 계정 kmail 로그인 → 받은편지함 메일 보임·첨부 열림·읽음/별표 보존.

### 2-6. 수신 일원화 (분기 방지)
- WORKS 자동수신(mail_fetch 스케줄러·계정) **비활성** + kmail 자동수신 계정 설정·활성(WORKS서 옮긴 계정).
- **동결 시점** 정하고, 그 이후 WORKS에 들어온 메일은 증분 1회 복사 후 전환.

### 2-7. 정식 전환 (DNS·라우팅)
- kmail.knknara.co.kr 정식. WORKS `/mail`은 kmail 안내(리다이렉트) 또는 읽기전용 보존. 메신저 메일버튼·WORKS 링크 kmail로.

### 2-8. 롤백
- 각 단계 WORKS 원본 보존. 문제 시 WORKS 수신 재활성·kmail 중단·DNS 원복.

## 4. 검증환경 우선 (실데이터 건드리기 전)
- WORKS DB 복사본 → kmail 복사본으로 **전체 리허설**(매핑·복사·검증) 후 실데이터 적용.
