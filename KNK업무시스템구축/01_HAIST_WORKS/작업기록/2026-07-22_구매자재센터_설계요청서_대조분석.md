## 0. 세 줄 요약

1. 요청서는 *"구매·자재센터를 **구축하고 있다**"* 를 전제로 하지만, 실제로는 **자재·구매 화면 경로가 이미 122개** 있고 요청서가 구상한 **13개 메뉴 중 11개가 이미 존재**한다.
2. **진짜 문제는 기능 부재가 아니라 "만들었는데 데이터가 안 돈다"** 이다 — 자재 마스터 3,194건을 빼면 **BOM·입고·재고이동이 LIVE 0건**이다.
3. 요청서 **§9 '구매 의사결정 화면'에 필요한 정보의 약 절반은 저장할 칸(DB 컬럼) 자체가 없다.** 화면 문제가 아니라 **테이블 설계 문제**다.

## 3. 【사실】 ⭐ 핵심 발견 — 화면은 있는데 **데이터가 안 돈다**

LIVE 실측:

```
자재(부품) 마스터   3,194 건   ← 유일하게 살아 있음
BOM 보드                0 건
입고 내역               0 건
수불부(재고 이동)        0 건
발주 목록            거의 0 건
```

즉 **설계 → BOM → 구매검토 → 발주 → 입고 → 재고 → 출고** 사슬에서
**첫 칸(자재 마스터)만 채워져 있고 나머지가 비어 있다.**

**이것이 시사하는 바**
- 화면 부족이 아니라 **업무가 시스템으로 들어오지 않고 있다**.
- 원인 후보(미검증): 초기 데이터 적재 부담 · 기존 엑셀 방식과 병행 · 진입 동선 · 입력 항목 과다 · 담당자 교육 · 앞단(BOM)이 안 채워져 뒷단이 시작 불가.
- **앞단이 비면 뒷단은 구조적으로 0이 된다** — BOM 0건이면 구매검토·발주·입고·재고가 순서대로 0이 될 수밖에 없다. 사슬의 **첫 막힌 지점은 BOM** 이다.

> **예약·가용재고, 발주잔량, 대체품, 단종, 최근·최저·평균 구매가** 등 **절반 가까이가 저장할 곳이 없다.**

### 특히 §4.9 발주 상태 14종은 현재 성립 불가

그런데 **발주에 승인자·승인상태 칸이 없다.** 승인 개념 자체가 없으므로 `승인대기`·`승인완료` 는 지금 구조에서 만들 수 없다.

## 5. 【사실】 기존 **확정 규정과 충돌**하는 2가지

### ① 용어 — "부품" vs **"자재"**
- **확정 규정**: 공식 용어는 **'자재'** (기술 식별자만 '부품 코드' 예외). 디자인 통일 Phase 0 에서 대표 확정.
- **요청서**: 전편에 **"부품 마스터"·"부품"** 사용 (§4.3·§6.1·§7·§11.2).
- **현재 화면**: 사이드바가 `🔩 부품 마스터` — **이미 규정과 어긋나 있다.**
- ⚠ 이 요청서를 기준으로 명세서를 쓰면 **어긋난 용어가 문서로 고착된다.**

### ② 수출관리의 소속
- **요청서 §4.14**: 수출관리를 **구매·자재센터** 메뉴로 둔다.
- **현재**: `/export` 는 **매출영업센터** 소속이며 이미 크게 구현됨 — 통관 입력, Invoice, Packing List, B/L, FTA 원산지증명, HS 사전, 출고 QR 등 **30여 경로**.
- ⚠ 옮기면 **기존 영업 동선이 끊긴다.** 자재 관점의 '수출 대기' 화면을 **새로 만드는 것**과, 기존 수출 모듈을 **이관하는 것**은 전혀 다른 작업이다. 요청서는 이를 구분하지 않았다.

## 7. 【사실】 요청서에서 **잘 짚은 것** (그대로 지킬 것)

- **§5.5 / §6.3 원본 미덮어쓰기** — "최초 발주정보를 덮어쓰면 안 되며 모든 변경을 이력으로". KNK 실무(발주 후 설계변경 빈번)를 정확히 반영.
- **§6.1 프로젝트 축 + 부품 축 동시** — 한쪽만으로는 실무가 안 돈다는 지적이 맞다.
- **§6.2 변경관리 중심** — 설계 변경 시 *미발주/발주완료/취소가능/입고완료/출고완료* 영향범위를 자동 표시하자는 것. **이것이 KNK 구매 ERP 의 진짜 차별점**이 맞다.
- **§6.4 상태값 전사 공통 코드** — 현재는 화면마다 상태값이 제각각이라 **지금 정리하지 않으면 뒤로 갈수록 비싸진다.**
- **§10 "지금은 분석만, 바로 개발 금지"** — 순서가 옳다.
- **§5.1 관리번호 ↔ 수주번호 구분** — 실제 구현과 일치한다(같은 관리번호 안에서 발주 시점이 다르면 수주번호가 갈린다).

## 8. 【제안】 다음 우선순위

> 아래는 **확인된 사실이 아니라 제 판단**이다.

### 1순위 — **BOM 이 왜 0건인지** 먼저 밝힌다
사슬의 첫 칸이 막혀 있어 뒷단 전체가 0이다. 명세서를 아무리 잘 써도 **안 쓰이는 이유를 모르면 같은 일이 반복된다.**
할 일: 구매팀·설계팀에게 *지금 BOM 을 무엇으로 관리하는지 · 왜 시스템에 안 넣는지* 직접 확인 → 그 답을 설계 입력으로 삼는다.

### 2순위 — **테이블 설계** (화면보다 먼저)
§4 에서 확인한 **없는 칸**들을 먼저 잡는다. 순서:
1. `parts` 확장 — 대체품 · 단종 · 표준/최근/최저/평균 단가
2. **재고 수량 분해** — 총재고 / 가용 / 예약 / 불량 / 프로젝트 귀속
3. **BOM 버전** — 요청서 §6.3 '원본 유지'의 전제
4. **발주 승인** — 승인자·승인상태·결재선(금액 기준은 대표 확정 필요)

### 3순위 — **BOM 구매검토 화면** (요청서 §4.6·§9)
요청서의 핵심이자 실제로 없는 화면. **단, 2순위 테이블이 먼저다** — 지금 만들면 보여줄 데이터가 없다.

### 4순위 — 상태값 전사 공통 코드 정리 (§6.4)

### 보류 권장
- **수출관리 이관** — 이미 도는 모듈을 옮기는 건 이득 대비 위험이 크다. 필요하면 *자재 관점의 '수출 대기' 화면만* 새로 만든다.
- **전수 기능명세서(§2)** — 지금 쓰면 "안 쓰이는 화면 122개의 명세서"가 된다. 1순위 결과를 반영한 뒤 쓰는 편이 값이 크다.

## 9. 【확인 필요】 대표 결정 대기 항목

1. **용어** — '자재' 로 통일할 것인가(기존 확정 규정 유지) vs 요청서대로 '부품'?
   → 유지 시 현재 메뉴 `🔩 부품 마스터` 도 함께 고쳐야 한다.
2. **수출관리** — 매출영업센터 유지 vs 구매·자재센터 이관?
3. **발주 결재선** — 금액 얼마부터 누가 승인하는가? (이게 정해져야 §4.9 상태 14종 설계 가능)
