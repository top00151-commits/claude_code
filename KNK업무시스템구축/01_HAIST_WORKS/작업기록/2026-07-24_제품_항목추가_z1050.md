## 1. 조사 결과 — 안지연 프로 말이 정확했다

### 1-1. "1 수주번호 = 1 품목" 이 실제로 코드에 있다
```python
def add_followup_order(...):
    """추가 발주 — 동일 관리번호로 신규 SO만 발행 (KNK 표준)."""
```
| 형태 | 한 수주번호 안 |
|---|---|
| 🏭 완제품(ASSEMBLY) | 호기 N줄 — `1호기·2호기…` **같은 품목의 여러 대**(`expand_units=True`) |
| 📦 제품(SEMI) | **1줄**(`expand_units=False`) |
| 🧰 상품(PARTS) | **1줄**(qty=N) |
| 소모품(C) | **라인 여러 개** ← 안지연이 *"소모품처럼"* 이라 한 것 |

실데이터: 완제품 수주 70건 중 27건이 여러 줄인데 **전부 `N호기`이고 `spec` 은 비어 있다**(= 같은 품목).

### 1-2. 🔴 "추가 품목" 기능은 만들어 놓고 **길이 끊겨 있었다**
`project_form.html:1274` 에 `📦 추가 품목` 반복 UI 가 있다(z209 · 2026-06-04 대표 지시).
그런데 **그 화면이 열리지 않는다**:
```python
# z319 (대표 지시): NEW_EQUIP 단건 등록은 간편 폼으로 통일 → 리다이렉트.
#   상세 폼(project_form.html)은 코드 보존, 라우팅만 변경.
if _t == "NEW_EQUIP": return RedirectResponse("/projects/quick?...")
if _t == "OTHER":     return RedirectResponse("/projects/quick?biz_div=E")
# CONSUMABLE 만 정식 폼 유지
```
**실측**: `/projects/new` = 유형 선택 화면 · 실제 등록은 전부 `/projects/quick`(간편 폼).
간편 폼에는 추가 품목 UI 가 **아예 없다**. → 대표가 보신 화면이 맞다.

### 1-3. 게다가 그 기능은 **품목마다 수주번호를 따로 발행**한다
```python
_r = _pwf.add_followup_order(...)      # 추가 품목 1개당 SO 1개
```
안내문에도 *"(추가 품목은 등록 시 **수주번호로도 함께 발행**됩니다)"*.
→ 소켓·PCB 가 **각각 다른 수주번호**가 된다. 견적서 한 장과 어긋난다.

## 2. ⭐ 좋은 소식 — 스키마를 안 바꿔도 된다

`order_items` 에 이미 다 있다.
```
order_items: unit_label(품목명 자리), spec(규격), qty, unit_price, amount,
             line_note, unit_status, statement_date, tax_invoice_date,
             arrival_status, ship_to, due_date, currency …
```
**출하·세금계산서·상태가 이미 '줄 단위'로 돌아간다.** 한 수주 아래에 서로 다른 품목 줄이 와도 그 부분은 그대로 동작한다.
그리고 `add_followup_order` 는 이미 **order 1건 + order_items N줄**을 만든다 — 그 N줄이 '같은 품목'이라는 전제만 깨면 된다.

## 4. 설계

### 4-1. 서버 — `add_followup_order(items=[...])` 파라미터 추가
```python
items = [{"name": "소켓", "spec": "THES123-SK", "qty": 2, "price": 150000},
         {"name": "소켓PCB", "spec": "THES123-PCB", "qty": 3, "price": 80000}]
```
- `items` 가 오면 **`expand_units` 무시** → 그 줄들을 `order_items` 에 그대로 INSERT
  - `unit_label` = 품명 · `spec` = 규격 · `qty` · `unit_price` · `amount = qty × price`
- SO 총액 = `Σ(qty × price)`
- **미전달 시 기존 동작 그대로** (백워드 호환 — 완제품 호기·부품 1줄 경로 불변)
- 상한: 항목 **50개**(그 이상은 소모품/상품 경로가 맞다)

### 4-2. 화면 — 간편 폼(`project_quick_form.html`)
- 형태가 **제품(SEMI)** 일 때만 `📋 항목` 반복 블록 표시(hidden `#qFormType` 값으로 토글)
- 칸: `No · 품명 · 규격(모델) · 수량 · 단가 · 금액(자동) · 삭제`
- 위쪽 **수량·단가·금액 3칸은 항목 합계로 자동 채움**(읽기 전용) — 두 곳에 따로 적어 어긋나는 사고 방지
- 항목이 0개면 기존 동작 그대로(지금처럼 1품목)

### 4-3. 저장 라우트
`/projects/quick` POST 에서 `it_name[]·it_spec[]·it_qty[]·it_price[]` 를 받아 `items` 로 전달.

### 4-4. ⛔ 안 건드리는 것
- 완제품 호기 로직 · 상품(PARTS) · 소모품 — **전부 현행 유지**
- `orders` / `order_items` 스키마
- 출하·세금계산서·작업일정표 — 이미 줄 단위라 그대로 동작해야 한다(**검증 대상**)

## 5. 🔴 실측에서 잡은 것 2개 — 안 잡았으면 등록 자체가 안 됐다

### 5-1. 항목만 적으면 '단가 필수'에 막혔다
`unit_price_required` 검증이 **항목 파싱보다 앞**에 있었다. 항목을 적고 위 단가를 비우면
저장이 튕긴다. → 파싱을 **검증 앞으로** 옮기고 **항목 합계로 검증**(호기별 단가와 같은 원리).
```python
if _z1050_items:
    if _z1050_total <= 0: return _err_redirect("unit_price_required")
elif _multi_v: ...
```

### 5-2. `confirm_order_multi(units=[])` 가 수주를 아예 안 만들었다
빈 SO 는 `so_type=='PARTS_EXPORT'` 또는 소모품일 때만 허용이었다 → 제품은 **"호기 정보가 없습니다"** 로 실패.
프로젝트만 생기고 **수주번호가 0개**였다(실측으로 발견).
→ `allow_empty=` 파라미터 신설. ⚠`shipment_form=='SEMI'` 만 보고 열지 않았다 —
다른 경로가 실수로 빈 SO 를 만들 수 있어 **호출자 명시**로 한정(PARTS 가 so_type 명시로 여는 것과 같은 방식).
