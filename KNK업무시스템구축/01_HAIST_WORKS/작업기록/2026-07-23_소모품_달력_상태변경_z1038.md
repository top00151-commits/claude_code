## 1. 원인 — 버그가 아니라 **의도적으로 숨긴 것**. 그런데 그 이유가 지금은 안 맞다.

`schedule_board.html` 의 `openMemo()`:
```js
const isProj = (tr.dataset.kind === 'project');
if (sec) sec.style.display = isProj ? '' : 'none';   // 소모품이면 상태 칸 숨김
```
서버도 같이 막고 있었다 — `kind != "project"` 면 **400 거부**.

z711 당시 주석: *"소모품 행은 **호기 개념이 없어** 이 경로 미지원(소모품 상세에서 변경)"*

**호기가 없다는 건 맞다.** 프로젝트는 상태를 **호기(`order_items.unit_status`)** 에 저장한다.
**그러나 소모품은 자기 줄에 같은 4가지 상태를 이미 갖고 있었다:**

```
consumable_orders.status
  CONFIRMED = 진행중     SHIPPED = 출하
  CANCELLED = 취소       HOLD    = 보류
```

소모품 **상세 화면에서는 이미 이 4개를 바꿀 수 있었다.**
즉 *"상태 개념이 없다"* 가 아니라 **"저장 위치가 호기가 아니라 소모품 자기 줄"** 일 뿐이었다.

### ⚠ 그리고 달력은 그 상태를 **이미 그리고 있었다**
`schedule_board.html` 납기 칸 렌더링은 `r.status == '출하'` 면 **"출하"**, 아니면 **"납품"** 을 찍는다.
소모품 행도 `_co_map` 으로 상태가 들어오므로 **출하/납품 글자가 이미 상태를 반영**하고 있었다.

> **보여주면서 고칠 자리는 안 주는 상태** — z1034(수주별 PO유형)와 **같은 유형의 문제**다.
> 규정 §4-14 *"보여주는 곳엔 고치는 자리도"* 위반.

## 2. 고친 것

| 층 | 내용 |
|---|---|
| **① DB** | `consumable_orders.status_date` 신설 — 프로젝트 호기(`order_items.status_date`)와 **짝**. NULL=미지정(**기존 데이터 무영향**) |
| **② 서버** | `/sales/schedule/row-status` 가 `kind='consumable'` 수용. 한국어 상태 ↔ 코드 매핑, 대상 존재 확인, 변경 이력 기록 |
| **② 서버(보드)** | 작업일정표 **두 곳**의 소모품 행 생성기에 `status_date` 실어 보냄(달력 표식용) |
| **③ 화면 HTML** | 안내문에 `id="memoStatHint"` 부여(행 종류별 문구 교체용) |
| **④ 화면 JS** | 팝업 노출 조건 완화 + ⚠**`setRowStatus` 의 클라 차단도 함께 해제** |
| **⑤ 안내문** | 소모품엔 '호기'가 없으므로 그 말을 쓰지 않는다 → *"이 **소모품 발주**에 위 날짜로 적용합니다"* |

### ⚠ z1031 과 같은 함정을 피했다
`openMemo()` 만 고치면 **팝업은 열리는데 저장이 막힌다** — `setRowStatus()` 안에 별도 차단이 있었다.
**한 개념이 여러 층에 흩어져 있다**는 원칙대로 ④층을 같이 확인해서 잡았다. cf [[feedback_trace_all_layers]]

### 대표 확정
> "**프로젝트와 똑같이 기록**" — 발생일을 소모품에도 남긴다(추적 가능).

## 3. ⚠ 검증 중 **내 버그 1건**을 자체 발견

첫 통합시험에서 상태는 4/4 저장됐는데 **변경 이력이 0건**이었다.

원인: `_co_mod` 는 **모듈 전역이 아니라** 다른 함수 안의 **지역 import** 였다.
→ 내 코드에서 `NameError` → 내가 쓴 `except Exception: pass` 가 **조용히 삼킴** → 이력만 안 남았다.

```python
# 고치기 전 — 실패해도 아무도 모른다
except Exception:
    pass

# 고친 뒤 — 지역 import + 실패를 로그에 남긴다
try:
    from . import consumables as _co_mod2
    _co_mod2.co_log_change(...)
except Exception as _e_log:
    log.warning("소모품 상태 변경 이력 기록 실패 co_id=%s: %s", _cid, _e_log)
```

> **`except: pass` 금지 원칙**([[feedback_data_connectivity]])을 내가 어겼다가 검증에서 잡았다.
> 검증을 '상태가 바뀌었나'로만 끝냈으면 **이력 없이 배포**됐을 것이다.

## 6. z1039 — 소모품 **상세**에도 발생일 (대표 "진행해")

z1038 은 달력만 고쳤다. 상세의 상태 드롭다운엔 발생일 칸이 없어
**같은 값을 두 화면이 다르게 다루는** 상태였다(상세에서 바꾸면 발생일이 안 들어감).

| | |
|---|---|
| 서버 | `_ORDER_FIELD_LABELS` 에 `status_date` 추가 → **기존 `.ef` 자동저장·이력 경로에 그대로 탑승**(새 엔드포인트 불필요) |
| 화면 | 상태 드롭다운 옆에 `상태 발생일 (출하·보류·취소한 날)` 날짜칸 |
| 연동 | **달력과 같은 규칙** — 진행중으로 되돌리면 발생일 해제 / 출하·보류·취소인데 비었으면 그 칸을 짚어줌(강제 아님) |

⛔**오늘 날짜 자동 채움은 하지 않는다** — 며칠 전 출하를 오늘로 적으면 틀린 값이 사실처럼 남는다(추정 금지).
언제 그렇게 됐는지는 사람만 안다.

### ⚠ z1039b — 넣었는데 **쓸 수 없는 크기**였다 (LIVE 실측으로 잡음)

배포 후 LIVE 화면을 **실제로 재보니** 라벨만 보이고 **날짜칸이 14px** 로 눌려 있었다.

```css
.h-cell .lbl { flex-shrink: 0; white-space: nowrap; }   /* 라벨은 안 줄어든다 */
```
한 칸이 154px 인데 라벨이 길어 **입력칸이 남은 폭만** 가졌다(발주일은 라벨 3글자라 100px 확보).
→ 그 칸만 **2칸 차지**(`grid-column: span 2`) + `max-width:130px`.

**LIVE 재측정: 130px (발주일 100px 보다 넉넉) · 화면에 보임 ✅**

> ⭐교훈: **HTML 에 넣었다 ≠ 사용자가 쓸 수 있다.** 칸을 새로 넣었으면
> **실제로 보이는지·쓸 수 있는 크기인지**까지 재봐야 한다.
