## 계약 1. 발주 발행 시 수량 등식

| 시점 | 등식 |
|---|---|
| 발주 **작성중** | `Σ 배분수량 ≤ 발주라인 수량` (허용) |
| 발주 **발행** | `Σ 배분수량 = 발주라인 수량` **필수** |
| 발행 후 **변경(새 Rev)** | 같은 등식 **재검증** |
| 요청라인 기준 | `Σ 배분수량 ≤ 요청라인 수량` (항상) |

- 배분 없는 잔량이 **0.0001이라도 있으면 발행 거부**한다.
- 판정은 발행 버튼이 아니라 **서버**가 한다. 화면은 미리 알려줄 뿐이다.

> V2 A-2가 `≤` 하나뿐이라 **근거 없는 수량이 섞인 채 발행**될 수 있었다. 작성중과 발행을 나눈다.

## 계약 2. 단위 — 자동 환산하지 않는다

**권장안 채택: 요청·배분·발주의 단위가 같을 때만 배분을 허용한다.**

| | |
|---|---|
| 단위 같음 | 배분 허용 |
| 단위 다름 | **배분 거부** + "단위가 다릅니다(요청 EA / 발주 BOX). 같은 단위로 맞춰 주세요" 안내 |
| 자동 환산 | **구현하지 않는다.** `1 BOX = 1 EA` 같은 임의 취급 ⛔ |
| 환산이 필요해지면 | 승인된 환산계수와 기준단위 수량을 **별도 저장**하는 별건으로 올린다(V1 범위 밖) |

⚠ 이 제약은 **불변식 A-1·A-2가 거짓을 승인하지 않게** 하기 위한 것이다. 단위를 무시하고 숫자만 더하면 "요청 100 EA에 발주 100 BOX"가 통과한다.

## 계약 3. BOM 구매근거는 요청 **라인**에 붙는다

요청서 한 장에 **BOM 줄 · BOM에 없는 긴급품 · 공용재고 · 다른 수주 귀속품**이 섞일 수 있다. 헤더 하나로는 못 가리킨다.

```
material_request_items (요청라인)          ← 구매근거 원본은 여기
  · basis_type   : BOM | 긴급 | 공용재고 | 예비품 | 재고보충 | 기타
  · baseline_item_id  (basis_type=BOM 일 때 · 불변 참조)
  · basis_reason      (BOM 아닐 때 필수)
        │
        ▼
purchase_allocations (배분)   ← 요청라인의 구매근거를 **그대로 이어받음**
```

| | |
|---|---|
| 원본 | `material_request_items` 의 `basis_type` + `baseline_item_id` |
| 요청 헤더의 baseline | **화면 기본값으로만** 사용. 추적 원본 아님 |
| BOM 아닌 품목 | `basis_type` + `basis_reason` **필수** |
| 발주 배분 | 요청라인의 근거를 승계. 배분이 근거를 새로 만들지 않음 |

## 계약 4. 대체품 — 자재 ID를 두 벌 두지 않는다

**권장안 채택: `purchase_allocations.substitute_part_id` 를 만들지 않는다.**

| 값 | 원본 |
|---|---|
| 요청한 자재 | `material_request_items.part_id` |
| **실제 발주한 자재** | `po_items.part_id` |
| 대체품 여부 | **두 값이 다르면 시스템이 대체품으로 판정**(저장하지 않고 계산) |

배분에는 **판단 근거만** 남긴다.

```
purchase_allocations
  · substitute_reason    대체 사유
  · substitute_requested_by / approved_by / approved_at
```

> V2는 `substitute_part_id` 를 따로 두려 했다. 그러면 `po_items.part_id` 와 어긋났을 때 **어느 것이 진짜 발주품인지 모호**해진다. 같은 사실을 두 곳에 적지 않는다.

## 계약 5. 재고 상태이동 = 복식 원장

**권장안 채택: 같은 `transaction_group` 으로 묶인 두 행.**

```
QUARANTINE   -10   ┐ 같은 거래그룹 · 같은 원천문서 · 같은 처리자
AVAILABLE    +10   ┘ 두 행 합계 = 0 · 한 행만 저장되면 전체 롤백
```

`stock_movements` 에 추가할 칸: `stock_state` · `transaction_group` · `source_doc_type` · `source_doc_id`

⛔ 상태이동을 **`IN` 한 행으로 기록하지 않는다.** 그러면 어디서 빠져 어디로 갔는지 사라진다.

### 상태별 불변식

| # | 불변식 |
|---|---|
| S-1 | 모든 상태 잔량 **≥ 0** |
| S-2 | 입고 → `QUARANTINE` 증가 |
| S-3 | 합격 → `QUARANTINE` 감소 = `AVAILABLE` 증가 (**동일 수량**) |
| S-4 | 불합격 → `QUARANTINE` 감소 = `REJECTED` 증가 (**동일 수량**) |
| S-5 | 특채 → `REJECTED` 감소 = `AVAILABLE` 증가 (승인자·사유 필수) |
| S-6 | 반품·폐기 → `REJECTED` 감소 후 **재고 외 처분상태**로 이동 |
| S-7 | `parts.stock_qty` = **`AVAILABLE` 잔량만** |
| S-8 | 거래그룹 내 수량 합계 = 0 (상태이동인 경우) |

## 계약 6. 기존 재고 직접쓰기 경로 — 전수 조사 결과

판정서 §3.6 지시대로 **먼저 찾았다.** 데이터가 0이라고 생략하지 않았다.

### 6.1 `parts.stock_qty` 를 쓰는 곳 = **4곳** (전수)

| # | 위치 | 함수 | 지금 하는 일 | 새 체계에서 |
|---|---|---|---|---|
| W-1 | `database.py:5849` | `parts_merge_one()` | 자재 중복 병합 — `ADJUST` 원장 1행을 남기고 **동시에** `stock_qty +=` | 원장행에 `stock_state='AVAILABLE'` 부여 + **직접 `+=` 폐지** → 원장 재계산으로 통일 |
| W-2 | `database.py:5965` | `parts_unmerge()` | 병합 취소 — `stock_qty -=` | W-1과 같음 |
| W-3 | `database.py:8731` | `_recalc_part_stock()` | 원장 **전체 합계**로 덮어씀. 호출처는 `stock_movement_create_tx()` **한 곳** | **`AVAILABLE` 만 합산**하도록 수정 |
| W-4 | `main.py:32593` | `parts_detail_page()` | 🔴 **자재 상세 화면을 여는 것만으로** 원장 전체 합계로 덮어씀(자가치유) | **가장 위험** — 아래 §6.2 |

### 6.2 🔴 W-4 — 상태 도입 시 규정을 정면으로 깬다

```python
# main.py:32586  (GET /parts/{pid} 진입 시)
_sm_total = SELECT SUM(quantity) FROM stock_movements WHERE part_id=?   ← 상태 구분 없음
if abs(_sm_total - _cur_qty) > 0.0001:
    UPDATE parts SET stock_qty = _sm_total
```

재고 상태를 도입하면 `stock_movements` 에 `QUARANTINE` 행도 쌓인다. 이 자가치유는 **상태를 구분하지 않고 전부 합산**하므로 —

> **검수하지 않은 격리 재고가, 자재 상세 화면을 열기만 해도 가용재고가 된다.**

이는 판정서 §2-6 「입고만으로 가용재고가 증가하지 않는다」를 정면으로 위반한다. 지금은 원장이 0건이라 드러나지 않을 뿐이다.

### 6.3 묶음 C 착수 시 처리 계약

| 경로 | 처리 |
|---|---|
| W-3 `_recalc_part_stock` | **계속 사용** — 단, `AVAILABLE` 만 합산하도록 수정 |
| W-4 자가치유 | **상태 인식으로 수정.** 수정이 늦어지면 **잠근다**(`WP01_LOCK_SWITCHES` 등록) |
| W-1·W-2 병합/병합취소 | 직접 `±` **폐지** → 원장 기록 후 `_recalc_part_stock` 호출로 통일 |
| 새 경로 | 재고를 바꾸는 모든 신규 경로는 **원장을 통해서만** |

**중단 조건**

- 원장(`AVAILABLE` 합계)과 캐시(`parts.stock_qty`)가 어긋나면 **즉시 중단**
- 화면에서 `stock_qty` 를 사람이 고칠 수 있는 자리가 **1곳이라도** 발견되면 중단
- 위 4곳 외에 `stock_qty` 를 쓰는 경로가 새로 발견되면 중단

**착수 전 재확인**: 묶음 C 시작 시 `parts.stock_qty` 쓰기 경로를 **다시 전수 검색**한다(이 문서 작성 이후 추가됐을 수 있으므로).

## 계약 9. Revision 별 배분 스냅샷

발주가 바뀌면 수량·단가·납기뿐 아니라 **배분관계도 그 차수 기준으로 보존**한다.

| # | 규칙 |
|---|---|
| R-1 | 각 Revision에 **발주라인 + 배분 스냅샷**을 함께 보존 |
| R-2 | Rev.1 생성 후 **Rev.0의 발주라인·배분 수정 금지** |
| R-3 | 변경 전후 차이와 **변경 사유** 표시 |
| R-4 | 부분입고가 시작된 발주는 **입고수량 미만으로 수량 감소 금지** |
| R-5 | 취소된 발주도 **기존 배분과 구매근거를 보존** |
| R-6 | 각 Revision에서 계약 1의 등식(`Σ배분 = 발주수량`) **재검증** |

## 계약 10. 복구 — "코드 롤백만으로 원복"은 사실이 아니다

**V2 §11의 그 문장을 철회한다.** 새 코드가 새 표에 거래를 기록한 뒤 구버전으로 돌아가면 이런 일이 생긴다.

- 새 거래가 구버전 화면에 **안 보임**
- 구버전 코드가 **신규 불변식을 우회**
- 새 표와 기존 집계값 **불일치**
- 스키마와 데이터는 DB에 **그대로 남음**

### 각 묶음의 복구 계획에 반드시 포함할 7항

| # | 항목 |
|---|---|
| 1 | 배포 직전 **전체 DB 백업 + `integrity_check`** |
| 2 | 스키마 마이그레이션 **적용·검증 기록** |
| 3 | 새 코드 배포 후 **생성된 거래 수와 ID 범위** 기록 |
| 4 | 코드 롤백 시 **신규 거래 생성을 즉시 잠그는 절차** |
| 5 | 신규 거래 **0건일 때**의 단순 롤백 절차 |
| 6 | 신규 거래가 **있을 때**의 데이터 보존·복구 또는 호환 배포 절차 |
| 7 | **「단순 코드 롤백만으로 안전하다」고 표현하지 않는다** |
