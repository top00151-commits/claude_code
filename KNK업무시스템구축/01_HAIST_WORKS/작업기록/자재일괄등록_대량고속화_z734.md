# 자재 일괄등록 대량(3000+) 고속화 — z734 (2026-06-30 · 대표 지시)

## 배경
대표가 "자재 일괄등록에 자재코드가 3000개가 넘는데 한 번에 올리기 너무 많냐?" 질문.
코드 점검 결과: **행 수 제한(cap)은 없어 잘리진 않지만**, 행마다 무거운 작업 3가지가 돌아 3000행이면 수십 초~분 걸리고 게이트웨이 타임아웃으로 실패할 위험.

## 진단 (병목 = 행마다 반복)
`/parts/import`(z58) → `database.py: parts_bulk_import_excel()` (미리보기 dry_run + 등록 apply 둘 다 호출).
행마다:
1. **유사 자재 검사**(`parts_find_similar`) — `SELECT … WHERE part_name LIKE '%…%'`(선행 와일드카드라 **인덱스 못 탐 → 자재 테이블 전체 스캔**) + 최대 200건 파이썬 퍼지 점수. **O(N행 × M기존자재)**.
2. **DB 중복조회** — 행마다 `SELECT … WHERE part_no=?`(인덱스라 개별은 빠르나 3000회 연결).
3. **개별 INSERT + 커밋** — `parts_create()`를 행마다 호출(자체 db_session·커밋·PRAGMA). 3000 커밋(fsync) = 느림.
+ 미리보기→등록 사이 파일을 base64로 hidden 필드 왕복(3000행이면 ~수백KB·OK) · 유사검사는 미리보기·등록에서 **두 번** 돔.

**임시 DB 실측(기존 자재 500·로컬 SSD)**: 1500행 미리보기 **6.77초** / 등록 **15.45초**. → 3000행+운영(자재 수천·NAS)이면 30~60초+.

## 수정 (database.py)
1. **`_parts_build_cols_values(data, existing_cols, now)` 공용 빌드 헬퍼 신설** — INSERT용 (cols, values) 빌드(정규화 purchase_prices→std_price·vendor 미러 포함). `parts_create`의 base_cols/ext_pairs를 **복제**(대량 1트랜잭션용). ⚠컬럼 추가 시 둘 다 갱신.
2. **등록을 '한 트랜잭션 일괄 INSERT'** — `if not dry_run:` 블록을 `with db_session() as c:` 하나로 묶어 PRAGMA 1회·헬퍼로 빌드·`c.execute(INSERT)` 반복·**커밋 1회**. 행별 오류는 try/except로 격리(SQLite는 문장단위 롤백이라 나머지 진행). `parts_create` 호출 제거(중복·유사검사는 미리보기 루프에서 이미 끝남).
3. **대량(>800행)이면 유사검사 생략** — 데이터행 먼저 `list()`로 수집→건수(`_nonempty_cnt`) 파악→`_do_similar=(not force_similar) and cnt<=800`. 생략 시 `similar_skipped=True` 반환→`parts_import.html`에 안내(정확 코드중복은 항상 검사).
4. **기존 part_no 1회 메모리 맵** — 루프 전 `SELECT part_no,id,part_name FROM parts` 1회→`_existing_pno{part_no:(id,name)}`. 행마다 DB 중복조회 제거.
- **`parts_create`(단건 등록)은 무변경** — 무위험.
