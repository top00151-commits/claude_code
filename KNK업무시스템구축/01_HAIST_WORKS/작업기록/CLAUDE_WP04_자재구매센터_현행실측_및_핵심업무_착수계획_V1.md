| 무엇을 | 어떻게 |

## 1. 현재 구현 현황

### 1.1 대표께서 요구하신 5단계 구분

지시서대로, **데이터가 0건이라는 사실만으로 미구현이라 판정하지 않았다.**

| 구분 | 뜻 | 해당 |
|---|---|---|
| ① 실제 사용 가능 | 화면·코드·DB 있고 운영에서 돌고 있음 | 자재 기준정보 · 협력사 · 관리번호/수주 · BOM 업로드 |
| ② 기능은 있으나 운영 데이터 없음 | 만들어졌고 저장도 되는데 아직 안 씀 | 구매요청 · 검수 · 재고 원장 · 단가 이력 · 생산 작업지시 |
| ③ 일부만 구현 — 업무가 중단됨 | 앞이나 뒤가 없어서 흐름이 끊김 | 입고(잠김) · 견적 비교 · 검수→재고 · 발주 상태 |
| ④ 화면만 있고 저장·전이·연결 없음 | 눌러도 다음이 없음 | BOM 발주상태 칸 · 발주 취소 · 반품 후속 |
| ⑤ 실제로 구현되지 않음 | 표도 코드도 없음 | **BOM Revision** · 구매요청 승인/변경/취소 · 구매요청→발주 · 발주 변경이력 · 생산투입 대상 기록 · 창고·위치 |

**발주 — 1건뿐이고, 그 1건도 비어 있다**

```

                       project_id = None   ← 관리번호 미연결

                       received_qty = 0
```

**재고**

```

```

→ 재고는 **아직 아무것도 없다.** 기준값과 원장이 어긋난 것이 아니라 **둘 다 0**이다.

> ⭐ 이 상태의 뜻: 자재·구매센터는 **기준정보(자재·협력사)만 갖춰졌고, 거래는 아직 한 건도 돌지 않았다.**
> 바꿔 말하면 **되돌릴 거래 데이터가 없어 지금이 구조를 바로잡기 가장 싼 시점**이다.

## 3. 흐름이 끊기는 지점 — 근거와 함께

> 대표 지시대로 **끊기는 지점을 먼저** 적는다. 우선순위는 "이게 없으면 업무가 실제로 멈추는가"로 매겼다.

### 3.1 🔴 구매요청 → 발주 : 연결 자체가 없다

구매요청을 제출하면 **거기서 끝난다.**

- `material_requests` 에 발주를 가리키는 칸이 없고, `purchase_orders` 에 구매요청을 가리키는 칸도 없다.
- 코드 전체에서 `material_request` 와 발주를 함께 다루는 곳이 **0곳**이다.
- 구매요청 상태를 바꾸는 코드가 없어, 제출된 요청은 영원히 `'제출'` 이다.

**업무상 뜻**: 현업이 요청서를 올려도 구매팀은 그것을 **눈으로 보고 발주 화면에 다시 손으로 입력**해야 한다. 요청과 발주가 이어지지 않으니 "내 요청이 어떻게 됐나"를 시스템이 답하지 못한다.

### 3.2 🔴 BOM → 구매 : 가는 길이 없다

BOM 보드(`/projects/{id}/bom`)에서 나가는 링크는 `/bom/upload` 와 `/logistics` 둘뿐이다. **BOM 줄을 골라 구매요청을 만들거나 발주로 넘기는 경로가 없다.**

또 `bom_items.order_status`(미발주/발주/부분입고/입고) 칸은 스키마 주석에 이렇게 적혀 있다.

> `-- 미발주/발주/부분입고/입고 (1차 수동 표시·2차 PO 연동)`

즉 **사람이 손으로 적는 칸**이고, 이 칸을 발주 실적으로 채우는 코드는 없다(전 파일 검색: 읽기만 6곳, 쓰기 0곳).

### 3.3 🔴 협력사 견적 비교가 구조적으로 불가능

견적은 `material_request_items` 한 줄에 **한 협력사만** 들어간다.

```
quote_supplier_id, quoted_price, quoted_lead_days
```

`main.py:10300` 이 이 세 칸을 **UPDATE** 한다. 두 번째 협력사 견적을 넣으면 **첫 번째가 지워진다.**

- 견적 표(quotes/rfq)가 **아예 없다.**
- 이 경로는 `/materials/new-review`(아직 등록 안 된 **신규 자재**)에만 있다. **기존 자재의 견적 비교 경로는 없다.**

**업무상 뜻**: "A사 100원 / B사 95원 / C사 98원 중 B사 선정" 이라는 구매의 기본 행위를 시스템이 담지 못한다. 선정 근거도 남지 않는다.

### 3.4 🔴 발주 변경·취소 이력이 없다

`purchase_orders` 칸: `po_number, project_id, supplier_id, order_date, expected_date, currency, exchange_rate, total_amount, status, shipping_terms, payment_terms, po_type, created_by, note, created_at, updated_at`

- **Revision(차수) 칸 없음** → 발주 후 수량·단가·납기를 바꾸면 **원래 값이 사라진다.**
- 취소는 `status='취소'` 글자뿐 → **누가 왜 언제 취소했는지 안 남는다.**
- `/po/{id}/edit` 이 헤더·라인을 그대로 덮어쓴다(`database.py:8302·8506`). 라인 삭제는 `received_qty>0` 일 때만 막는다.

### 3.5 🟠 발주 → 입고 : 잠겨 있다 (WP-01, 의도된 상태)

두 입고 경로가 모두 운영 잠금이다.

| 경로 | 잠금 스위치 | 잠근 이유(코드 주석) |
|---|---|---|
| `/po/{id}/receive` | `KNK_ENABLE_PO_RECEIVE` | 입고문서·검수·격리재고가 없어 **검수 전 자재가 곧바로 가용재고**가 됨 |
| `/stock/receipts` | `KNK_ENABLE_STOCK_RECEIPT_POST` | 골격 · PO 수량 미연동 |

로직 자체는 갖춰져 있다 — 라인별 수량 누적, 단일 트랜잭션, 발주 상태 자동 전이(부분입고/입고완료). **정식 입고 엔진이 준비되면 열 수 있는 상태**다.

또 `receipts` 표는 **헤더뿐이고 라인 표가 없다**(`po_id, received_at, total_qty, qc_inspection_id, status`). 부분입고를 문서 단위로 남기려면 라인이 필요하다.

### 3.6 🟠 검수 기록이 무엇을 검수한 것인지 불분명

`main.py:34222` 가 검수를 저장할 때 **같은 값을 두 칸에 넣는다.**

```python
INSERT INTO qc_inspections (po_item_id, receipt_id, ...) VALUES (?,?,...)
                            (po_item_id, po_item_id, ...)   ← 같은 값
```

코드 주석도 이렇게 인정하고 있다.

> `# po_item_id 가 receipts.id 로 들어올 수 있으므로 둘다 시도 (UI 단순화)`

이어서 `UPDATE receipts SET qc_inspection_id=?, status=? WHERE id=?` 를 **같은 값으로** 실행한다. 발주 라인 번호와 입고 문서 번호가 우연히 겹치면 **엉뚱한 입고 문서가 검수 완료로 바뀐다.**

지금은 양쪽 다 0건이라 사고가 나지 않았을 뿐이다.

### 3.7 🔴 검수 → 재고 : 합격 수량이 재고로 가지 않는다

검수를 저장해도 `stock_movements` 도, `parts.stock_qty` 도 건드리지 않는다(`main.py:34222~34238` 전체). 검수는 **기록만 하는 화면**이다.

`qc_disposition` 의 `RETURN`(반품)도 마찬가지다 — 반품 결정만 적히고, 반품 수량이 재고나 발주에서 빠지지 않는다.

`po_items` 에 **`accepted_qty`(검수 합격 수량) 칸이 없다.** 그래서 "발주 100 중 입고 100, 합격 95, 반품 5" 를 표현할 수 없다.

### 3.8 🔴 생산투입 : 어디에 썼는지 기록할 칸이 없다

`issues_out` 칸: `part_id, requester_id, approver_id, requested_at, issued_at, qty, purpose, status`

- **`project_id` 없음 · 수주번호 없음 · 호기 없음.**
- 대상은 `purpose` 자유 입력 글자뿐이다.

**업무상 뜻**: 자재를 꺼내 써도 **어느 관리번호 장비에 들어갔는지 시스템이 모른다.** 프로젝트 원가·잔여 자재·As-Built 추적이 전부 불가능하다. 지시서 §10의 "프로젝트 종료 시 미결 구매·미입고·잔여재고 확인"이 지금 구조로는 답이 안 나온다.

### 3.9 🟠 발주가 수주번호를 가리키지 못한다

`purchase_orders` 에는 `project_id`(관리번호) 하나만 있고 **`order_id`(수주번호) 칸이 없다.** 발주 화면(`po_form.html`)에도 수주번호 입력이 없다.

이게 왜 문제인지는 §4에서 숫자로 보인다.

## 4. 관리번호 1개에 수주번호 여러 개 — 현재 구조의 처리 방식

### 4.1 이건 예외가 아니라 절반에 가깝다

운영 데이터 실측:

| 관리번호에 붙은 수주 개수 | 관리번호 수 |
|---:|---:|
| 1개 | 160 |
| 2개 | 61 |
| 3개 | 13 |
| 4개 | 18 |
| 5~9개 | 23 |
| 10~15개 | 11 |

**수주가 있는 관리번호 286개 중 126개(44%)가 수주번호를 2개 이상 갖는다. 최대 15개.**

### 4.2 현재 처리 방식

| 계층 | 수주번호를 다루나 |
|---|---|
| `orders` (수주) | ✅ `project_id` 로 관리번호에 붙는다. 여러 개 정상 |
| `order_items` (수주 품목) | ✅ 수주에 붙는다 |
| `project_units` (호기) | ✅ WP-03에서 **수주 다중 연결** 구현(ORIGIN/ADDITIONAL/CHANGE) |
| **`material_requests` (구매요청)** | ❌ `project_id` 만. 수주번호 칸 없음 |
| **`purchase_orders` (발주)** | ❌ `project_id` 만. 수주번호 칸 없음 |
| **`stock_movements` (재고 원장)** | ❌ `project_id` 만 |
| **`issues_out` (출고)** | ❌ 프로젝트조차 없음 |

`po_item_project_links` 표는 **발주 라인 1줄을 여러 프로젝트에 배분**하는 구조(`allocated_qty`, `allocation_pct`)로 이미 있다(0건). 하지만 이것도 **프로젝트 단위**이지 수주번호 단위가 아니다.

### 4.3 뜻

관리번호 하나에 계약이 여러 건인데(최대 15건), 구매·입고·재고는 **전부 관리번호 한 덩어리로만** 본다. 그래서 "이 자재는 3차 발주분 계약에 쓴 것"을 구분할 수 없고, 수주별 원가·잔여를 낼 수 없다.

⚠ 다만 **모든 구매가 수주번호를 가져야 한다는 뜻은 아니다.** 지시서 §2가 말한 공용구매·예비품·재고보충·개발자재는 특정 수주에 귀속되지 않는다. 그래서 **수주번호는 '있으면 기록, 없어도 진행 가능'** 이어야 한다. 이 판단은 §9에서 대표께 여쭙는다.

## 5. BOM Revision과 설계변경이 발주·입고·재고에 미치는 영향

### 5.1 지금은 Revision 개념이 없다

| 찾은 것 | 실체 |
|---|---|
| `bom_uploads.version_no` | **파일 업로드 회차** — 같은 프로젝트에 몇 번째로 올렸나 |
| `bom_items.first_upload_id / last_upload_id` | 그 줄이 처음·마지막으로 보인 업로드 |
| `bom_item_history` | 줄 단위 변경 이력(추가·변경·삭제) |

저장소 전체에서 `revision` · `baseline` · `effectivity` 를 검색한 결과, **BOM과 관련된 것은 하나도 없었다**(걸린 것은 인덱스 이름 `newrev`, 메신저 수정발행 알림, `order_status_history` 로 전부 무관).

즉 **"Rev A로 샀는데 Rev B로 바뀌었다"를 시스템이 표현할 수 없다.** 업로드 회차는 "언제 파일을 올렸나"이지 "설계가 몇 번 바뀌었나"가 아니다.

### 5.2 이게 발주·입고·재고에 미치는 영향

| 상황 | 지금 무슨 일이 나나 |
|---|---|
| 발주 후 BOM이 바뀜 | BOM 보드가 `🔴 발주 후 변경` 경고를 띄운다(`bom.py:348·361·487`). **경고까지가 끝** — 발주를 자동으로 손대지 않는다 |
| 그 경고의 근거 | `bom_items.order_status` 가 발주 상태로 보이는데, 이 칸은 **사람이 손으로 적는 값**이다(§3.2). 아무도 안 적으면 경고가 안 뜬다 |
| 어느 Rev로 발주했나 | **답할 수 없다.** `po_items` 에 `bom_item_id` 도 Revision 도 없다 |
| 입고한 자재가 어느 Rev용인가 | 답할 수 없다 |
| 재고에 남은 자재가 구 Rev 전용인가 | 답할 수 없다 |

**정리**: 변경 감지(diff·이력)는 **이미 잘 만들어져 있다.** 없는 것은 **"구매가 어느 설계 상태를 근거로 이뤄졌는가"를 붙들어 두는 기준점(Baseline)** 이다. 그것이 없으면 설계변경의 구매 영향을 기계적으로 계산할 수 없다.

## 부록 A. 이 문서가 정정하는 과거 기술

정직을 위해 적습니다. WP-00 실측에서 제가 결함으로 보고했던 것 중 하나는 **지금 기준으로 유효하지 않습니다.**

| 과거 기술 | 지금 실측 |
|---|---|
| "`/materials/requests/{rid}` 라우트가 백슬래시 경로로 등록되어 상세가 404일 것" | **정상입니다** — `main.py:10197` 에 `@app.get("/materials/requests/{rid:int}")` 로 올바르게 등록돼 있습니다 |
