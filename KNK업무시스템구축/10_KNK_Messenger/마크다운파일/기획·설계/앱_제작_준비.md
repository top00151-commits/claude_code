# KNK 메신저 앱(App) 제작 준비 정리

**문서 작성**: 2026-05-29
**대상**: KNK 메신저를 Android·iOS 앱으로 출시하기 위한 검토·결정 사항 종합
**현 상태**: 검토 완료, 발주·착수 대기

---

## 1. 왜 앱으로 만드나

### 목적
메신저의 **안정성 + 기능 향상**, 특히 **알림 신뢰성** 확보.

### 핵심 인식
> **알림 신뢰성 = 메신저의 90%**
> 메시지 1초 내 도달 · 잠금화면/앱 닫혀도 푸시 · 탭하면 그 방으로 이동 · 알림 사고 0건

현재 PWA(Web Push) 는 이 부분에서 한계가 있어 앱(네이티브 푸시)으로 보완 필요.

---

## 2. 검토한 3가지 방법

| 안 | 방식 | 결론 |
|---|---|---|
| **A. Capacitor 래퍼** | 현재 웹 코드를 네이티브 쉘로 감쌈 | ⭐ **채택** |
| B. PWA 강화 | 지금 그대로 + Service Worker·푸시 강화 | ❌ 메신저로 부족 |
| C. React Native/Flutter 재작성 | UI 전체 재개발 | ❌ KNK 규모에 과투자 |

### B안 탈락 이유 — 메신저 본질에서 결정적 약점
- iOS 16.4+ 만 Web Push 작동 (구형 iPhone 못 받음)
- iOS PWA "홈화면 추가" 안 한 직원은 알림 0
- Android 일부 제조사(샤오미·화웨이·오포) 가 백그라운드 앱 종료
- 예상 사고: 긴급 메시지 놓침 **연 5~10건** → 사내 메신저로 치명적

### C안 탈락 이유 — 130명 규모에 과투자
- 개발 3~6개월 풀타임 + 빅터 학습 곡선 1개월
- 6개월간 만든 웹 코드 100% 폐기
- 웹 + 앱 두 코드베이스 유지 (1인 개발 2배 부담)

### A안 채택 이유 — 유일한 현실적 정답
| 핵심 요구 | A안 결과 |
|---|---|
| FCM/APNs 진짜 푸시 | ✅ OS 시스템 푸시 — Web Push 한계 완전 해결 |
| 코드 재사용 | ✅ 6개월간 만든 웹 코드 약 95% 그대로 |
| 카메라·파일 네이티브 API | ✅ 플러그인 |
| 앱 아이콘·스플래시 | ✅ "앱처럼" 인식 |
| Play Store / App Store 등록 | ✅ |
| 1인(빅터) 개발 | ✅ Capacitor 학습 곡선 짧음, 6~8주 |
| 장기 유지보수 | ✅ 웹 코드 수정 = 앱 자동 반영 |
| 안 맞으면 롤백 | ✅ PWA 로 쉽게 복귀 |

> Capacitor 는 "껍데기", 내용물(메신저)은 지금 NAS 서버 코드 그대로 사용.
> 카톡·라인이 PWA 가 아닌 이유 = 푸시 신뢰성. A안이 이를 확보.

## 3. 메신저 운영과 앱 제작 — 동시 진행 가능 (확인 완료)

### 구조 — 서버는 하나, 화면은 셋
```
        [앱 출시 후]
  웹브라우저 ──┐
  PWA ────────┼──→ 똑같은 NAS 서버 (app.py 그대로)
  앱(껍데기) ──┘
```

### 메신저 수정 시 반영
| 사용자 | 반영 |
|---|---|
| 웹 브라우저 | 새로고침 → 즉시 ✅ |
| PWA | 새로고침 → 즉시 ✅ |
| **앱** | **새로고침 → 즉시 ✅ (재빌드 불필요)** |

- 99% 의 일상 수정(기능·UI·테마·번역·DB)은 **서버 배포(sync_to_synology.ps1)만** 하면 앱에도 자동 반영
- 앱 재빌드가 필요한 경우는 드뭄: 앱 아이콘·이름·푸시 설정·네이티브 기능 변경 시만

### 폴더 분리 — 서로 안 섞임
```
10_KNK_Messenger/          ← 메신저 (지금 코드, 계속 수정)
10_KNK_Messenger_App/      ← 앱 껍데기 (새 폴더, 별도)
```
- 앱 작업은 별도 폴더 → 기존 메신저 코드(app.py 등) 거의 안 건드림
- 메신저 코드 건드리는 유일한 경우 = **FCM 푸시 통합** (기존 Web Push 는 그대로 두고 나란히 추가)

### 진행 리듬 — 방식 A 채택 (메신저 우선, 앱은 짬짬이)
- **메신저 수정 지시 = 항상 1순위** (지금처럼 즉시 처리·배포·보고)
- 앱 작업은 지시 없는 시간에 빅터가 배경 작업으로 진행
- 작업이 왔다갔다 해도 빅터가 Task 목록으로 분리 관리 → 헷갈림 없음

## 4. iOS 빌드 — Mac 필요

### 왜 Mac 이 필요한가
- Apple 규정: iOS 앱은 **Xcode** 로만 빌드 가능, Xcode 는 **macOS 에서만** 작동
- Windows/Linux 에서는 iOS 빌드·서명·App Store 업로드 불가
- Android 는 Windows/Mac/Linux 어디서나 빌드 가능 (제약 없음)

### KNK 결정: iPhone 사용자 약 50% → **iOS 도 필수**

### Mac 구매 추천: Mac mini M4 기본형
| 항목 | 내용 |
|---|---|
| 모델 | **Mac mini M4** (2024.11 출시) |
| 사양 | M4 칩 / 메모리 16GB(기본) / SSD 256GB |
| 가격 | **약 89만원** (Apple 공식) |
| 추가 | 키보드·마우스·모니터는 기존 사내 부품 재활용 (셋업 1회만) |

### 왜 Mac mini 인가
- 가장 저렴한 Mac (MacBook Air 130만원보다 쌈)
- 헤드리스(모니터 없이) 운영 가능 → NAS 옆에 두고 사용
- 빅터 원격(SSH·화면공유) 접근 → 사내 PC 에서 작업
- 6~10년 사용 가능 (M4 신형)

### 피해야 할 선택
- ❌ Intel Mac (구형): iOS 18+ 빌드 지원 미흡
- ❌ 중고 M1/M2: 보증 끝, 장기 지원 위험
- △ Codemagic 클라우드(월 $30 ≈ 연 50만원): 3년이면 Mac mini 보다 비쌈 + 빌드 느림

### KNK 가 Mac 으로 할 일 (거의 없음)
1. 박스 받기 → 전원 + 랜선 연결 → 1회 셋업(모니터 임시 연결) → "켜놨어" 알리기
2. 이후 빅터가 원격으로 모두 처리 (NAS 와 동일하게 "조용히 일하는 박스")
3. 일상 조작: 사실상 없음 (월 1회 재부팅 정도, 안 해도 됨)

   - KNK 법인 명의 (사내 자산) / 김정락 대표 개인 명의

## 8. /compact 안전성 (확인 완료)

- 빅터 작업물은 대화가 아닌 **파일·git 커밋(161개+)·NAS 배포본·메모리**에 저장됨
- compact 는 대화를 요약할 뿐, **실제 작업물은 1도 안 사라짐**
- 작업 중간에 compact 해도 안전 (git·파일로 복원)
- **가장 좋은 타이밍**: 수정 → 배포 → 커밋 완료 직후
