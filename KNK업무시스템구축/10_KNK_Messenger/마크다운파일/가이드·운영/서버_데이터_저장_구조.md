## 0. 한 줄 요약

메신저의 모든 데이터는 **회사 시놀로지 NAS 한 대 안**에 저장된다. 형태는 두 가지뿐이다.

1. **글·구조 데이터** → SQLite 데이터베이스 파일 **1개** (`data/messenger.db`)
2. **첨부 실파일** (사진·문서·프로필) → **`data/uploads/` 폴더**의 원본 파일

외부 클라우드/외부 DB는 쓰지 않는다. 단, **AI 번역·요약 기능을 사용할 때만** 해당 문장이 외부 AI(OpenAI)로 전송된다(§8).

## 1. 시스템 구성 (런타임 스택)

```
[사용자 브라우저/PWA]
        │  HTTPS (haist.knknara.co.kr)
        ▼
   nginx  (knk-nginx)         ← 리버스 프록시 / TLS 종단
        │  내부 프록시
        ▼
   gunicorn (run_gunicorn.sh) ← WSGI, eventlet 워커 (WebSocket=Socket.IO)
        │
        ▼
   Flask 앱 (app.py)          ← 업무 로직
        │  파일 I/O
        ▼
   SQLite (messenger.db, WAL) +  uploads/ 폴더
```

- 프로세스 관리: **supervisord** (`knk-messenger`, `knk-nginx`, `cron`)
- 실행 위치(컨테이너 내부): **`/opt/knk_messenger/`**
- 앱 서버: Flask + Flask-SocketIO(실시간 메시지), 동기 저장소는 SQLite

## 2. 저장 위치 (경로 맵)

`app.py` 상단 정의:

```python
APP_DIR    = (앱 루트)                      # 운영: /opt/knk_messenger
DB_PATH    = APP_DIR/data/messenger.db
UPLOAD_DIR = APP_DIR/data/uploads
```

| 경로 | 내용 |
|---|---|
| `/opt/knk_messenger/data/messenger.db` | **메인 데이터베이스** (모든 글·구조 데이터) |
| `/opt/knk_messenger/data/messenger.db-wal` | WAL 저널(쓰기 임시) — DB와 **한 세트** |
| `/opt/knk_messenger/data/messenger.db-shm` | WAL 공유메모리 인덱스 — DB와 한 세트 |
| `/opt/knk_messenger/data/uploads/` | 채팅 첨부 원본 파일 |
| `/opt/knk_messenger/data/uploads/avatars/` | 사용자 프로필 사진 |
| `/opt/knk_messenger/data/uploads/room_avatars/` | 방·채널 사진 |
| `/opt/knk_messenger/data/vapid_private.pem` | 웹푸시 서명키(비밀) |
| `/opt/knk_messenger/backups/` | 자동 백업 산출물(§10) |

> **중요**: WAL 모드라 `.db` 단독 복사는 최신 쓰기를 놓칠 수 있다. 파일 단위로 백업할 땐 `.db` + `.db-wal` + `.db-shm`를 **함께** 복사하거나, §10의 온라인 백업(`backup.py`)을 사용한다.

## 3. 데이터베이스 개요

- **엔진**: SQLite 3 (서버리스 임베디드 — 별도 DB 서버 프로세스 없음)
- **파일**: 단일 파일 `messenger.db`
- **연결**: 요청마다 연결 생성/종료 (`get_db()`, Flask `g` 캐시)
- **무결성/동시성 설정** (`app.py` 연결 시 PRAGMA):

| PRAGMA | 값 | 의미 |
|---|---|---|
| `foreign_keys` | `ON` | 외래키 강제 → `ON DELETE CASCADE` 실제 작동 |
| `journal_mode` | `WAL` | 읽기·쓰기 동시 가능, 쓰기 락 범위 축소 |
| `synchronous` | `NORMAL` | WAL과 함께 안전/성능 균형 |
| `busy_timeout` | `20000` (20초) | 락 대기 — 동시 쓰기 충돌 완화 |
| `cache_size` | `-65536` (64MB) | 페이지 캐시 |

- **DB 구조 변경 방식**: 코드가 시작될 때 `CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ADD COLUMN`(컬럼 존재 검사 후)로 **자동 마이그레이션**. 1회성 데이터 변환은 `app_migrations` 테이블로 중복 실행을 막는다.

## 6. 첨부파일 저장 (uploads)

- 채팅 사진/문서, 프로필·방 사진은 **DB가 아니라 `data/uploads/` 폴더에 원본 파일로** 저장된다.
- DB(`messages.file_path` 등)에는 **파일 경로·이름·크기·MIME만** 기록 → 화면에서 그 경로로 내려받는다.
- 하위 폴더: `avatars/`(프로필), `room_avatars/`(방 사진), 그 외 첨부.
- 업로드 파일명은 안전 처리(`secure_filename`) 후 저장.
- **DB와 uploads는 한 세트** — 한쪽만 복원하면 "메시지는 있는데 파일이 없음"(또는 그 반대)이 발생하므로 백업·복원은 **항상 같이**.

## 7. 보안

| 항목 | 방식 |
|---|---|
| 비밀번호 | **해시 저장**(`werkzeug` `generate_password_hash` / `check_password_hash`). 원문·복호화 불가. DB 유출돼도 비번 원문은 못 얻음 |
| 전송 구간 | **HTTPS**(nginx TLS 종단) |
| 로그인 | 세션 기반 + 동시로그인 제한(PC1·모바일1, `active_sessions`) |
| 권한 | 역할(role) + 방 역할(host/pm) + 게스트 격리(고객사는 제한 기능) — 서버에서 가드 |
| 동의 이력 | `consent_agreements`에 버전·시각·IP·UA 기록(감사 추적) |
| 비밀키 파일 | 웹푸시 서명키 `vapid_private.pem` 등은 `data/`에 보관, **GitHub 제외**(§12) |

## 8. 외부로 나가는 데이터 (중요)

평상시 대화·파일은 **100% 회사 NAS 안**에만 있다. 외부로 나가는 경우는 다음뿐이다.

| 기능 | 전송처 | 보내는 것 |
|---|---|---|
| **AI 번역** | OpenAI API | 번역할 **그 메시지 문장** |
| **AI 요약** | OpenAI API | 요약 대상 **메시지들의 본문** |
| **푸시 알림** | 브라우저 푸시 서비스(FCM 등) | 알림 제목·미리보기(가리기 옵션 가능) |

- 번역/요약 결과는 `message_translations` / `ai_summaries`에 캐시 → 같은 내용 재요청 시 외부 호출 없이 재사용(비용·노출 최소화).
- AI 공급자 키는 서버 환경변수(`OPENAI_API_KEY`)로만 보관, 코드/깃에 없음.
- ⚠️ 민감 정보는 번역·요약 버튼을 누르면 외부 AI로 갈 수 있음을 운영 정책으로 인지(필요 시 관리자에서 AI 기능 권한 제한 가능).

## 9. 보존·삭제 정책

- **메시지 삭제 = 소프트 삭제**: 완전 제거가 아니라 `kind='deleted'`(또는 "삭제된 메시지" 표시)로 남음 → "업무 누락 0" 추적 목적.
- **공지 삭제**: `active=0` (화면에서만 제거, 데이터 보존).
- **스레드/방 보관**: `rooms.retention_days`, `messages.archive_extended_until`, `thread_hidden`으로 보관·숨김 제어.
- **방 삭제 시**: 외래키 `ON DELETE CASCADE`로 그 방의 메시지·멤버·요청 등 연쇄 정리(첨부 실파일은 별도).
- **게스트 초대**: `revoked_at`로 회수(레코드는 보존).

## 10. 백업 (`backup.py`)

자동 백업 스크립트가 다음을 수행하도록 작성되어 있다.

```
호출 주기   : 매일 새벽 3시 (스케줄러)
보관 위치   : /opt/knk_messenger/backups/
보관 기간   : 14일 (초과분 자동 삭제)
산출물      :
  · messenger_YYYY-MM-DD_HHMM.db    ← SQLite 온라인 백업(.backup API, WAL 안전, 락 없음)
  · uploads_YYYY-MM-DD_HHMM.zip     ← 첨부 폴더 통째 압축
```

- **온라인 백업 API**(`sqlite3 .backup()`)를 쓰므로 서비스 중단 없이, WAL을 포함해 일관된 스냅샷을 뜬다(단순 파일 복사보다 안전).
- `backups/`는 **GitHub·배포 양쪽에서 제외**(§11·§12).

### ⚠️ 점검·보강 필요 (전산 담당)
1. **자동 실행 확인**: 위 "매일 3시"가 NAS에서 실제로 동작 중인지(스케줄러/cron 등록 여부) 확인. (스크립트는 준비됨)
2. **NAS 밖 이중화**: `backups/`가 **같은 NAS 안**에만 있으면 장비 고장 시 원본·백업 동시 손실. 외장/타 장치/원격으로 **3-2-1 백업**(사본 3, 매체 2, 오프사이트 1) 권장.
3. **복원 리허설**: 분기 1회 정도 `messenger_*.db` + `uploads_*.zip`로 실제 복원이 되는지 테스트.

## 11. 배포와 데이터 안전

새 기능 배포(`deploy/sync_to_synology.ps1`)는 **데이터를 건드리지 않는다**.

- 배포 패키지에 포함되는 것: `app.py`, `wsgi.py`, `templates/`, `static/`, `deploy/`, `requirements.txt`, 보조 스크립트(`backup.py` 등) — **코드만**.
- **제외(서버 데이터 보존)**: `data/`(DB·uploads), `backups/`, `.venv/`, `__pycache__/`.
- 절차: 코드 패킹 → NAS 업로드·추출 → `supervisorctl restart knk-messenger` → `/healthz` 200 확인.
- 결론: **업데이트를 해도 `data/`는 그대로** → 대화·파일·계정이 유지된다.

---

## 12. GitHub 분리 (`.gitignore`)

GitHub(코드 백업)에는 **프로그램 소스만** 올라가고 **실데이터는 절대 올라가지 않는다**.

GitHub에서 제외되는 것:
- `data/` (DB·uploads), `backups/`
- `*.pem`(비밀키), `.env`(환경변수/키), `secret.key`, `keys/`
- 직원 명단 엑셀(`KNK_직원등록.xlsx` — 개인정보), SSO 정찰 덤프 등

> 따라서 **GitHub는 "코드" 백업이지 "데이터" 백업이 아니다.** 대화·파일의 백업은 §10에 의존한다.

## 13. 운영 점검 체크리스트

- [ ] `backup.py` 자동 실행(매일 3시)이 NAS에 등록·동작 중인가
- [ ] `backups/`가 NAS 밖(외장/원격)으로도 복제되는가 (오프사이트 1부)
- [ ] 분기 1회 복원 리허설 (DB + uploads 동시 복원)
- [ ] `data/messenger.db` + `.db-wal` + `.db-shm` 를 한 세트로 다루는가(파일 단위 백업 시)
- [ ] `vapid_private.pem` 등 비밀키 별도 안전 보관(분실 시 푸시 재설정 필요)
- [ ] 디스크 여유 모니터링(첨부 누적 + `.wal` 증가)
- [ ] AI 기능(번역·요약) 외부 전송 정책 — 민감정보 취급 기준 공유
