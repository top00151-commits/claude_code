## 7. HTTPS 강제전환 — 메신저 ⭐

### 발단
동의서 "전송 구간 암호화 적용" 문구를 100% 사실로 만들려면 항상 https 여야 하는데, `http://` 로 들어오면 평문으로 열리는 구멍이 있었음.

### 이전 진단(오판) → 재진단(정정)
- **이전(다른 세션)**: 컨테이너 nginx / 앱 redirect 시도 → "효과 없음. DSM 리버스 프록시가 원래 scheme(X-Forwarded-Proto)을 컨테이너로 안 넘겨준다" 결론 → 전산담당(최보현 상무)에게 DSM 설정 요청서 작성.
- **이번 재진단(실측)**: 앱에 임시 진단 라우트(`/_diag_scheme`) 붙여 http·https 각각 호출 →
  - `http://` → `X-Forwarded-Proto: http`
  - `https://` → `X-Forwarded-Proto: https`
  - **DSM 은 원래 scheme 을 정확히 전달하고 있었음**(ProxyFix 로 `request.scheme` 도 정확). → **이전 진단이 틀렸음.**

### 해결 (앱 레벨, 시놀로지 무수정)
- `app.py` 에 `@app.before_request _force_https`:
  ```python
  if request.headers.get("X-Forwarded-Proto","").lower()=="http" and request.path!="/healthz":
      return redirect(request.url.replace("http://","https://",1), code=301)
  ```
- **안전장치**: https 는 헤더가 `https` 라 전환 안 됨(무한루프 없음) / 헤더 없는 내부접속·docker healthcheck 은 전환 안 됨 / `/healthz` 명시 제외.
- 배포: `deploy/sync_to_synology.ps1` (NAS `o.knknara.co.kr:31201`, supervisorctl restart knk-messenger).
- **검증(curl)**: `http://…/msg/login`→**301 https**, `https://…/msg/login`→**200**, `http://…/healthz`→**200**, 임시진단 제거 확인.
- 커밋 `dcba6f4`. (임시 진단 라우트는 추가→확인→제거, 커밋엔 미포함)

## 8. HTTPS 강제전환 — WORKS ⭐

### 핵심 차이
- WORKS 는 메신저(Flask)와 달리 **FastAPI / uvicorn**, `works.knknara.co.kr → :8081`, **별도 저장소**(`github.com/top00151-commits/knk-haist-works`), **직원 130명 핵심 플랫폼**.
- 효과는 동일(http→https 301)하되 **코드 방식이 다름**(Flask `before_request` 대신 FastAPI 미들웨어).

### 적용
- `app/main.py` (SessionMiddleware 다음) 에 미들웨어 추가:
  ```python
  @app.middleware("http")
  async def _force_https(request, call_next):
      if request.headers.get("x-forwarded-proto","").lower()=="http":
          return RedirectResponse(str(request.url).replace("http://","https://",1), status_code=301)
      return await call_next(request)
  ```
- 안전: 메신저에서 https→`https` 확인된 동일 DSM 이라 루프 없음 / 헤더 없으면(내부) 전환 안 함 → 최악의 경우에도 "현상 유지", 잠김 없음.

### 배포 — git 자동배포 (SSH 불필요)
- WORKS 의 정식 배포 스크립트(`deploy/sync_to_synology.ps1`)는 **사무실 LAN IP(192.168.1.10)** 대상이라 외부에서 못 돌림.
- 그런데 WORKS 는 메신저와 **같은 NAS 컨테이너**(`/opt/knk_haist`, supervisor `knk-works`)에서 돌고, **`deploy/auto_deploy.sh` 가 cron 1분 주기로 `git pull` → 변경 시 `supervisorctl restart knk-works`** 하는 **git 자동배포** 구조.
- → **GitHub push 만으로 자동 반영.** (프로덕션 SSH 직접 접속은 안전장치가 차단 — 자동배포가 정답)
- 커밋 `25d207c` (WORKS repo, main).

- `https://works.../login` → **200** (로그인 화면 정상)
