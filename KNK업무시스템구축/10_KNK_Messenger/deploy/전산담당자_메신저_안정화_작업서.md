> **목적:** 사내 메신저가 어떤 경우에도 멈추지 않도록, 장애 발생 시 **사람 개입 없이 약 2분 이내 자동 복구**되는 안전망을 NAS(Synology DSM)에 설정한다.
>
> | 항목 | 내용 |
> |---|---|
> | 작성일 | 2026-05-25 |
> | 대상 | ㈜케이엔케이 전산 담당자 |

## 📌 한눈에 보기 — 전산 담당자가 할 일 (쉬운 설명)

> 어려운 용어 없이 핵심만. 자세한 단계·화면 위치·스크립트 전문은 아래 **6 · 7 · 8절**에 있습니다.

**왜 하나요?**
메신저를 켜놓고 관리해 주는 "관리 프로그램"이 한 번 꺼졌는데, **아무도 다시 켜주지 못해** 메신저 전체가 멈췄습니다(전 직원 접속 불가). → 그래서 **"자동으로 감시하고, 죽으면 다시 켜주는 장치"**를 NAS에 심는 작업입니다.

### 할 일은 딱 3가지

**1️⃣ 컨테이너 "자동 재시작" 켜기  — 약 2분**
- **무엇:** NAS가 재부팅되거나 메신저가 통째로 꺼지면 **저절로 다시 켜지게** 하는 스위치 켜기
- **어디서:** DSM → **Container Manager** → **컨테이너** → 메신저 선택 → **설정** → **"자동 재시작 사용"** 체크 → 저장
- **완료 확인:** 옵션이 켜져 있고 상태가 "실행 중"

**2️⃣ 자동 감시·복구 장치(워치독) 등록  — 약 10분  ★ 가장 중요**
- **무엇:** **1분마다 메신저 생존을 자동 점검** → 죽어 있으면 **자동으로 살리고** 담당자에게 **알림**. 새벽·주말에 사람이 없어도 **약 2분 안에 무인 자동 복구**
- **어디서:** DSM → **제어판** → **작업 스케줄러** → **생성** → **예약된 작업** → **사용자 정의 스크립트**
- **설정 3가지:** ① 이름 `KNK메신저 워치독`·사용자 **root**  ② **1분마다 반복**  ③ 스크립트 칸에 **7절 코드를 그대로 복사·붙여넣기**
- **완료 확인:** 만든 작업을 한 번 "실행" → 메신저가 정상이면 끝 (정상일 땐 아무 일도 안 일어남)

**3️⃣ 진짜 되는지 테스트  — 약 10분**
- **무엇:** **업무시간 외**에 일부러 메신저를 잠깐 멈춰보고 → 2~3분 안에 저절로 복구되는지 확인
- **도움:** 이 테스트는 **개발 담당(빅터)이 원격으로 함께** 진행 가능 — 1·2 완료 후 연락 주세요

### 준비물 / 안심해도 되는 점
- **준비물:** ① NAS 관리화면(DSM) **관리자 로그인 권한** ② 본 작업서 ③ (3번 테스트 때) 컨테이너 SSH 접속 정보 — **5절**에 있음
- **안심:** **대화·파일·데이터는 전혀 건드리지 않습니다**(감시·재시작만). 평상시엔 아무 변화 없습니다.

| 순서 | 할 일 | 소요 | 중요도 |
|---|---|---|---|
| 1 | 컨테이너 자동 재시작 켜기 | 2분 | 보조 |
| 2 | 워치독 등록 | 10분 | ★ 필수(핵심) |
| 3 | 복구 테스트 (빅터 협조) | 10분 | 권장 |

## 1. 배경 — 발생한 장애

- **증상:** 2026-05-25 새벽, 사내 메신저(`https://haist.knknara.co.kr/msg/`) 전체가 **HTTP 502 (전 직원 접속 불가)** 상태가 됨.
- **영향:** 전 직원 메신저 사용 중단.
- **임시 복구:** 컨테이너 내부의 `supervisord`(프로세스 관리 데몬)를 수동으로 재기동하여 복구 완료. 현재 정상 운영 중.
- **문제점:** 이번엔 수동 복구가 가능했으나, **담당자가 부재한 시간(야간·주말)에 재발하면 장시간 다운**될 위험이 있음 → 본 작업서로 **무인 자동복구 체계**를 구축한다.

---

## 2. 원인 분석 (확정)

### 2-1. 진짜 원인 — 컨테이너 구조의 단일 취약점
- 메신저 운영 컨테이너의 **최상위 프로세스(PID 1)가 `supervisord`가 아니라 `bash`** 이다.
- 이 구조에서는 `supervisord`(웹앱 gunicorn·nginx·cron을 관리)가 죽으면 **아무도 그것을 되살리지 못한다.**
  - `bash`(PID 1)는 계속 살아있으므로 **Docker는 컨테이너를 "정상 실행 중"으로 인식** → 자동재시작도 발동 안 함.
  - `supervisord`가 없으니 죽은 웹앱(gunicorn)을 **재시작해 주는 주체가 사라짐** → 영구 502.
- **증거:**
  - `supervisord` 로그가 정상 운영 중 **갑자기 끊기고**(정상 종료 기록 없음), 수동 복구 시점에야 새로 시작됨 → 비정상 사망.
  - 장애 시각 무렵 **호스트 재부팅/컨테이너 재시작** 정황(호스트 가동시간이 짧았음). 재시작 후 `supervisord`가 제대로 안 올라온 것으로 추정.

### 2-2. 보조 취약점
- supervisor 설정에서 **nginx가 `autostart=false`** 로 되어 있어, `supervisord` 복구 시 nginx를 별도로 수동 시작해야 했음. → **이미 `autostart=true`로 수정 완료** (아래 4절 참고).

### 2-3. 원인이 아닌 것 (조사로 배제)
| 의심 항목 | 조사 결과 | 판정 |
|---|---|---|
| 메모리 부족 / OOM | 32GB 중 1.8GB만 사용, OOM 흔적 0, failcnt 0 | ❌ 아님 |
| 디스크 부족 | 사용률 14% · 42% (여유 충분) | ❌ 아님 |
| 애플리케이션 코드 | gunicorn 자체는 정상 기동, 코드 무관 | ❌ 아님 |

## 3. 목표

1. **무중단:** 평상시 끊김·지연 없음.
2. **무인 자동복구:** 장애가 나도 **사람 개입 없이 약 2분 이내** 자동 복구.
3. **즉시 인지:** 장애·복구 발생 시 관리자에게 알림.

## 6. 작업 A — 컨테이너 자동재시작 정책 (필수)

**목적:** NAS 재부팅·컨테이너 비정상 종료 시 컨테이너가 자동으로 다시 켜지도록 한다.

### 단계
1. DSM 로그인 → **Container Manager** 실행 (주 메뉴 ⊞ → Container Manager. 구형은 "Docker").
2. 왼쪽 **컨테이너** 탭 클릭.
3. 메신저 컨테이너 선택 → **세부정보** 또는 **설정**(⋯/톱니) 진입.
4. **"자동 재시작 사용(Enable auto-restart)"** 옵션을 **켠다(체크)** → 저장.
   - (CLI 가능 시 동일 효과: `docker update --restart unless-stopped <컨테이너이름>`)

### 확인
- 설정 후 컨테이너 상태가 **실행 중(Running)** 유지되는지 확인.

> ⚠️ 단, 이 항목만으로는 부족하다. 컨테이너는 살아 있는데 **내부 supervisord만 죽는** 이번 같은 경우는 자동재시작이 발동하지 않는다. 그래서 **작업 B(외부 워치독)가 핵심**이다.

## 7. 작업 B — 외부 워치독 (★ 핵심 ★)

**목적:** 1분마다 메신저 상태를 점검하여, 다운 시 **컨테이너 밖에서** 자동 복구한다. 컨테이너 내부가 어떻게 망가지든(=supervisord 사망 포함) 무조건 동작하는 최종 안전망.

**동작 순서:**
1. 1분마다 `/healthz` 점검 → 정상이면 종료.
2. **2회 연속 실패** 시에만 복구 시작 (일시적 깜빡임 무시).
3. 1차 복구: `supervisord` 재기동 + 앱 시작 (가벼움, 수초).
4. 2차 복구: 그래도 안 되면 **컨테이너 재시작**.
5. 복구/실패 시 **관리자에게 DSM 알림**.

### 단계
1. DSM → **제어판 → 작업 스케줄러(Task Scheduler)**.
2. **생성 → 예약된 작업 → 사용자 정의 스크립트** 클릭.
3. **[일반] 탭**
   - 작업 이름: `KNK메신저 워치독`
   - 사용자: **`root`** (반드시 root)
   - "활성화" 체크
4. **[일정] 탭**
   - 실행 빈도: **매일**
   - 시간 → **"반복 간격"** 을 **1분**(또는 선택 가능한 가장 짧은 간격, 예: 1분/3분/5분)으로 설정.
   - 첫 실행 시간 `00:00`, 마지막 실행 시간 `23:59`.
   - (DSM 버전에 따라 "반복: 분 단위" 옵션 위치가 다를 수 있음. 가장 짧은 주기로.)
5. **[작업 설정] 탭 → "사용자 정의 스크립트"** 입력란에 **아래 스크립트를 그대로 붙여넣기:**

```sh
#!/bin/sh
# KNK 메신저 외부 워치독 — 1분마다 healthz 점검 → 다운 시 자동복구
C=$(docker ps --format '{{.Names}}' | grep -i messenger | head -1)
[ -z "$C" ] && C=knk-messenger
S=/tmp/knk_wd_fail
L=/var/log/knk_watchdog.log
H="curl -fsS --max-time 8 http://127.0.0.1:5050/healthz"

# 1) 정상 점검
if docker exec "$C" sh -c "$H" >/dev/null 2>&1; then
  rm -f "$S"; exit 0
fi

# 2) 연속 실패 카운트 (일시적 실패 무시, 2회 연속이어야 복구)
N=0; [ -f "$S" ] && N=$(cat "$S")
N=$((N+1)); echo "$N" > "$S"
echo "$(date) healthz FAIL $N" >> "$L"
[ "$N" -lt 2 ] && exit 0

# 3) 1차 복구 — supervisord 재기동 + 앱 시작
docker exec "$C" sh -c 'pgrep -f supervisord >/dev/null 2>&1 || supervisord -c /etc/supervisor/supervisord.conf; sleep 5; supervisorctl start knk-messenger knk-nginx' >> "$L" 2>&1
sleep 5
if docker exec "$C" sh -c "$H" >/dev/null 2>&1; then
  echo "$(date) RECOVERED via supervisord" >> "$L"; rm -f "$S"
  synodsmnotify @administrators "KNK메신저 자동복구" "메신저 일시 다운 → supervisord 재기동으로 자동복구 완료."
  exit 0
fi

# 4) 2차 복구 — 컨테이너 재시작
docker restart "$C" >> "$L" 2>&1
sleep 20
if docker exec "$C" sh -c "$H" >/dev/null 2>&1; then
  echo "$(date) RECOVERED via restart" >> "$L"; rm -f "$S"
  synodsmnotify @administrators "KNK메신저 자동복구" "메신저 컨테이너 재시작으로 자동복구 완료."
else
  echo "$(date) RECOVERY FAILED" >> "$L"
  synodsmnotify @administrators "[긴급] KNK메신저 복구 실패" "자동복구 실패. 즉시 수동 점검 필요."
fi
exit 0
```

6. **확인** 클릭 → (NAS 비밀번호 입력 요구 시 입력).
7. 작업 목록에서 방금 만든 작업을 **선택 → "실행"** 으로 1회 수동 테스트.

### 스크립트 동작 메모 (담당자 참고)
- `C=...grep -i messenger` : 컨테이너 이름 자동 탐색. 이름에 "messenger"가 없으면 스크립트 2번째 줄 `C=knk-messenger` 의 값을 실제 이름으로 수정.
- `docker` 경로 문제 시: `docker` → `/usr/local/bin/docker` 로 바꿔 기입(전체 치환).
- `synodsmnotify` : DSM 알림 발송 명령. 알림이 안 오면 **제어판 → 알림** 에서 이메일/푸시 수신 설정 확인.

## 8. 작업 C — 검증 (필수)

설정이 실제로 동작하는지 반드시 확인한다.

### 8-1. 평상시(정상) 확인
- 워치독 1회 수동 실행 후, 로그 파일에 **실패 기록이 없으면 정상**:
  - SSH(NAS 호스트) 또는 DSM File Station 으로 `/var/log/knk_watchdog.log` 확인 → 비어있거나 과거 기록만 있으면 OK.
- 브라우저에서 `https://haist.knknara.co.kr/msg/` 접속 정상 확인.

### 8-2. 의도적 장애 복구 테스트 (강력 권장)
> ⚠️ 이 테스트는 메신저를 잠깐 다운시키므로 **업무 시간 외**에 수행 권장.

1. SSH로 컨테이너 접속: `ssh -p 31201 root@(NAS주소)`
2. 앱을 의도적으로 죽인다(테스트):
   `supervisorctl stop knk-messenger`
   (또는 supervisord 자체 종료로 더 강한 테스트: `kill -9 $(cat /var/run/supervisord.pid)` )
3. 브라우저에서 502 다운 확인.
4. **최대 2~3분 대기** → 워치독이 자동 복구하는지 관찰.
5. `https://haist.knknara.co.kr/msg/` 정상 복귀 + 관리자 알림 수신 확인.
6. `/var/log/knk_watchdog.log` 에 `RECOVERED...` 기록 확인.

> 이 테스트는 개발 측(빅터)에 요청하면 원격으로 함께 진행·확인할 수 있다.

## 9. 운영 / 모니터링

- **로그:** `/var/log/knk_watchdog.log` (복구 이력). 정상 시 거의 비어 있음.
- **알림:** 다운/복구/복구실패 시 DSM 관리자 알림 수신.
- **정기 점검(권장):** 월 1회, 위 로그와 컨테이너 상태(Container Manager), 디스크 여유 확인.

## 10. 롤백 / 주의사항

- 워치독을 중지하려면: 작업 스케줄러에서 `KNK메신저 워치독` 작업 **비활성화** 또는 삭제.
- 스크립트 수정 시 **컨테이너 이름·docker 경로**만 환경에 맞게. 나머지 로직은 변경 금지.
- 작업 A의 자동재시작은 끄지 말 것(끄면 재부팅 시 메신저가 안 올라옴).
- **DB·데이터는 본 작업과 무관**(읽기/재시작만 함). 데이터 손상 위험 없음.

## 11. (선택) 중장기 근본 개선 제안

현재 컨테이너는 **PID 1이 bash인 수동 구성**이라 구조적으로 취약하다. 여유가 될 때 아래를 검토하면 더 견고해진다. (별도 프로젝트 · 개발 측과 협의)

1. 컨테이너를 **`supervisord`가 PID 1**이 되도록(또는 정식 init 사용) 재구성 → supervisord가 죽으면 컨테이너가 죽고 Docker가 자동 재시작.
2. 표준 `Dockerfile`/`docker-compose.yml`로 **재현 가능한 이미지화** (현재 저장소 파일은 운영 컨테이너와 불일치 상태).
3. DSM 알림에 **모바일 푸시(Synology 앱)** 연동으로 야간 즉시 인지.
